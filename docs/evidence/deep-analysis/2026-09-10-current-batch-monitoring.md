## 실행 환경 사건

첫 실행은 모델 착수 전 DB runtime lease UPDATE에서 중단됐다. 앞선 조사용 스크립트가 설정한 session default_transaction_read_only=on이 풀 연결에 남은 것이 원인이었다(SQLSTATE 25006). 에이전트 조사 과정에서 유발한 문제다. session override와 기본값을 확인한 뒤 RESET으로 해당 연결 설정만 복구했고, zero-row UPDATE로 확인 후 같은 grant를 실행했다. 클러스터/role 기본값 변경은 없다. 준비 스크립트는 transaction-local read-only로 제한하고, receipt는 민감값 없이 원인 SQLSTATE를 남기는 것이 좋다. 첫 receipt의 47 skipped를 47개 분석 실패나 추가 대상 처리로 세지 않는다.

seq 13의 실제 선택 필드를 기존 prepareContextualEdits 함수에 전달한 로컬 무호출 재현에서 '신청 요건 (택1)'의 양쪽과 동의/비동의 양쪽이 모두 체크된 편집 문자열이 만들어졌다. 파일 저장이나 실제 동의 제출은 하지 않았다. 선택 유형의 오류가 편집 계획에도 전파됨을 확인한 증거다.

## 실시간 관측 개선

최종 LabRun에는 primary/repair 시간이 있지만 실행 중 상태는 target running 중심이라 긴 대기가 첫 응답인지 repair인지 구분하기 어렵다. 모델 요청 시작·첫 응답·완료·검증 실패·repair 시작, 문서별 planner 진행과 요청 수를 민감 원문 없이 상태 이벤트로 남긴다. 최종 시간을 실시간 추정으로 대체하지 않는다.

## 입력 준비의 추가 결함과 검증 오탐

seq 25의 ZIP 원본 5개 멤버를 직접 읽어 SHA를 계산했다. 5/5가 변환된 보관행과 일치했고 모두 잘림 없이 sealed input에 포함되어 있다. 그러나 부모 ZIP은 '변환 안 됨'으로 고지되고 모델은 prior_award를 검사하지 못하는 이유로 이 ZIP을 인용했다. 부모 archive가 완전히 대체되었는지 멤버 manifest로 확인한 뒤 중복 미투입 경고를 제거해야 한다. 일부 멤버가 실제 누락된 ZIP의 경고까지 없애면 안 된다. 전체 준비 입력 중 같은 형태의 ZIP 경고는 seq 0/4/19/25에 있으나 멤버별 원본 대조는 seq 25만 수행했다.

seq 29는 요약과 미변환 고지만 들어가 총 1,245자 입력으로 22축 중 20축을 input_missing으로 남겼다. 보관된 HML 원본은 SHA 일치, XML 파싱 성공, 루트 HWPML, 텍스트 817조각·11,778자이며 지원자격 절이 있다. HML 텍스트 변환을 지원하면 읽을 수 있는 원문을 활용할 수 있다. 로컬 XML 파싱 성공을 의미 구조 변환이나 RHWP 편집 지원 완료로 확대하지 않는다. 확인된 두 축으로 조건부 매칭 후보에 남긴 것은 현재 사용자 정책과 일치한다.

seq 27은 primary 229,932ms 후 repair 204,560ms와 158,414ms를 거쳤다. 첫 응답의 근거 구절 불일치는 실제 교정 대상이다. 다만 신청 대상이 영천시 중소 제조기업임을 원문이 직접 명시하는데 역할 분리 guard가 지역/규모 조건에 반복 적용됐다. `criterionRoleLabels`는 span/note의 단어 포함 여부로 제조기업도 역할로 세고, 다른 criterion의 다중 역할이 전체 roleSplit을 켠다. 제조기업=이번 신청자라는 관계를 표현하지 못해 정상 공통 조건도 걸릴 수 있다. 최종 규모 값은 그대로 유지하면서 설명이 확장되고 지역은 text_only로 바뀌었다. 모든 repair가 낭비라고 보지 않으며, 실제 역할 혼동 차단을 유지한 채 이 오탐 회귀를 추가한다.

## P1. 실패한 seq 35: 정규화·교정 계약의 반복 모순

Nexus Connect 공고는 약 6분 54초 동안 primary 196,388ms, 모델 repair 113,710ms·103,717ms를 실행했지만 대상 목록의 값/설명 불일치가 세 번 모두 남아 failed로 종결됐다. 신청서 분석은 별도로 complete(37개)였으므로 결과 화면에서 두 경로의 상태를 보존해야 한다.

실제 저장 criterion과 exact input을 `normalizeCriteria`에 전달하고 raw list_semantics만 open/closed로 바꾼 로컬 무호출 재현에서 둘 다 closed로 정규화되고 '열린 목록' 설명은 그대로 남았다. 모델이 open으로 고쳐도 정규화에서 다시 모순이 생길 수 있는 경로다. 원래 raw 모델 응답의 값은 별도 보존되지 않아 모델이 실제 어떤 값을 반환했는지 단정하지 않는다. 원문의 '창업기업'과 법인/개인 구분은 같은 개념이 아니므로 open이 정답이라고 자동 판정하지도 않는다.

정규화·validator·repair가 같은 원문 의미를 따르게 정리하고, 정규화 전후 값과 변경 사유를 관측해야 한다. 자료 부족 축은 기존 conditional 정책을 유지하되 이처럼 남은 criterion mismatch는 통과시키지 않는다. 일시적 통신 오류가 아닌 반복 검증 실패라 같은 입력을 맹목적으로 다시 모델에 보내지 않았다. 이 실패와 앞선 보류가 잔여 target 진행을 막지 않았음을 확인했다.

실행 중 실패 이벤트에서는 신청서 상태가 비어 보였지만, 최종 영수증에는 실패 run과 신청서 상태가 정확히 결속되었다. 처음에는 영구 누락으로 의심했으나 최종 observer의 42/42 LabRun 결속과 미관측 실패 0을 확인해 이 판단을 철회했다. 개선 범위는 실시간 오류 이벤트에서도 이미 저장된 단계별 결과를 표시하는 것으로 한정한다. 최종 집계 복구는 정상 작동했다.

## 사용창 소진과 남은 실행

본 실행은 약 109분 시점에 seq 41에서 `CLAUDE_CLI_WINDOW_EXHAUSTED`를 만나 중단됐다. 그 공고의 필드 분석에도 window_exhausted가 기록됐다. seq 42~46은 착수하지 않았고, 이미 실행 중이던 seq 40은 끝까지 마무리된 뒤 cohort 잠금이 해제됐다. 42번째 착수에서 사용창이 소진됐다는 실측이며, 시작 전 사용량을 기록하지 않았으므로 Max 한 창의 총 처리 용량이 42건이라고 해석할 수 없다.

- 기존 동일 grant의 `--retry-errors`는 **seq 35, 41, 42, 43, 44, 45, 46의 7건**을 선택한다. 성공·held 40건을 새로 분석하는 경로는 아니다.
- seq 35는 반복 검증 실패이고 seq 41 및 미착수 5건은 사용창 소진 이후의 남은 실행이다. 현재 CLI는 이 두 부류를 구분해 선택할 옵션이 없어, 재시도 대상의 원인별 선택·예산 운용 개선이 필요하다.
- 사용창의 실제 초기화 시각은 오류 기록에서 확인할 수 없다. transport가 원문 오류를 고정 메시지로 바꾸며 초기화 정보를 버린다. 오류 문구의 '별도 새 experiment' 안내도 현행 동일 grant 재시도 정책과 다르므로 정리한다. 현재 승인과 같은 material binding의 재시도에 target별 새 승인을 추가하지 않는다.
- API로 우회하거나 반복 호출로 한도를 확인하지 않았다. 남은 분석은 미완료로 보존했다. contract를 수정한 뒤의 모델 재실행은 새 material manifest 검증 대상이며, 과거 receipt를 변경하지 않는다.

사용창의 잔여량·초기화 시각을 모델 무호출로 관측할 수 있는 경로, 실패 원인별 재개 계획, 이미 완료된 primary/field 결과 재사용이 대량 처리의 운영 개선 과제다. 파일 수에 관계없이 동시성만 높이는 것으로 이 제한을 해결할 수 없다.

## 증거 범위와 미실행 검증

저장된 신청서 문서 65개를 자동 선별했고 의심 사례를 원문과 대조했다. 자동 플래그 수는 정답률/결함률이 아니며, 전체 필드를 독립 정답 집합으로 검수한 것은 아니다. 현행 판정의 보류와 별도로, complete 안의 의미 결함 및 false not_applicable을 확인했다.

기존 실행 코드의 검증은 준비 기록의 통과 영수증을 재사용했다. 이번 변경은 관측 문서와 증거이며 추가 모델 계약 변경은 없다. 로컬 triage/매칭/선택 편집 재현과 HWP/HWPX 저장·재파싱, 보고서 JSON·링크·diff를 검증한다. 브라우저·시각적 파일 레이아웃·로그인 베타 인수, 최종 release/promotion, 서비스 게시·배포는 수행하지 않았다.

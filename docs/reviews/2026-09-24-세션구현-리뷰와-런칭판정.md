## 재현된 코드 결함

### P1 — 질문 교체 뒤 철회한 회사 사실이 다시 적용됨

- 위치: `apps/web/src/lib/server/repositories/drizzle.ts:1324`, `apps/web/src/lib/server/matches/grantConfirmations.ts:910`.
- 회사가 A 공고에서 답한 뒤 B 공고에서 같은 회사 사실을 수정하고 철회하면, 철회 표시는 B 질문에 저장된다. 두 reader는 `invalidatedAt is null`인 질문과 현재 source 결속을 통과한 답변만 후보로 읽는다.
- B 질문이 교체·무효화되면 철회 표시도 후보에서 사라져 A의 이전 답변이 다시 최신 답변으로 선택된다. 사용자가 철회한 사실이 관련 공고의 자격 판정에 재적용된다.
- 격리 PostgreSQL 재현: 철회 직후 관련 공고 평가 0건 → B 질문 무효화 → A의 평가 `satisfied` 재등장.
- 수정 방향: 회사 사실의 의미와 철회 순서를 질문 수명과 독립적으로 보존한다. 질문/원천 변경 때문에 이전 긍정·부정 답변이 되살아나지 않도록 API reader와 matcher reader를 함께 고친다.

### P2 — 공유 철회 뒤 기존 답변 공고에서 다시 답할 수 없음

- 위치: `apps/web/src/lib/server/matches/grantConfirmations.ts:838`.
- 공유 회사 사실이 철회되면 해당 질문 자체에 철회 표시가 있는 경우에만 빈 답변과 revision을 반환한다. A에 기존 일반 답변이 있고 B에서 철회했다면 A의 GET은 빈 목록을 반환하지만 A의 저장 revision은 DB에 남는다.
- UI는 revision을 0으로 보내므로 서버의 기존 revision과 달라 `confirmation_answer_conflict` 409가 난다. 다시 불러와도 동일하다.
- 격리 PostgreSQL 재현: `visibleAnswerCount=0`, 그 GET 결과로 재답변 시 `confirmation_answer_conflict`.
- 수정 방향: 값이 철회·상충으로 미해소여도 대상 질문의 현재 저장 revision은 반환한다. 최초 답변 질문·철회 질문·직접 답한 적 없는 관련 질문 모두에서 재답변을 검증한다.

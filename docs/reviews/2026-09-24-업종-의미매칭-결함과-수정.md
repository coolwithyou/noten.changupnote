# 업종 의미 매칭 결함과 수정

## 판단

사용자가 지적한 ICT 공고와 소프트웨어 회사의 연결은 서비스의 핵심 기능이다. 추천 0건을 재고 부족·검수 대기만으로 설명하면 원인을 충분히 설명하지 못한다. 현재 분석 지시와 매칭 코드 양쪽에 의미 연결이 빠져 있었다.

- 분석 지시: 신청기업의 산업 범위가 명확해도 KSIC·사업자등록 업종 표현이 없으면 `industry/text_only`로 남기도록 요구했다.
- 매칭: 업종 코드 및 문자열 겹침을 비교하며 ICT에 소프트웨어가 포함되는 관계를 표현하지 않았다.
- 실제 인도 BTS 저장 조건은 업종이 `text_only`다. 새 매칭 코드만 적용해도 이 과거 조건은 미해결로 남는다.

재고·발행 수치와 관측 시각은 [실제 사업자 추천 0건 진단](2026-09-24-실제사업자-추천0건-원인진단.md)을 참조한다. 그 문서의 조건부 건수를 실제 적합 공고 수로 해석하지 않는다.

## 구현한 범위

1. 추출·감사·검수의 공통 지시에서 명시적인 신청기업 산업 범위를 코드 없이도 업종 태그로 보존한다. ICT와 중소기업 규모를 분리한다. 기술·제품 보유, 인증·등록, 역할별 전제가 결합된 조건은 임의로 업종 태그 하나로 줄이지 않는다.
2. 매칭기에 방향이 있는 업종 포함관계를 추가했다. 응용·시스템·게임 소프트웨어 → 소프트웨어 개발 및 공급업 → 소프트웨어 → ICT, 프로그래밍 → 소프트웨어 → ICT, 호스팅 → ICT를 지원한다.
3. 상위 분야만 확인됐다고 세부 업종을 통과시키지 않는다. 같은 상위 분야에 속하는 서로 다른 세부 업종도 동등하게 취급하지 않는다. 소프트웨어 교육·소프트웨어를 사용하는 음식점 등을 단어 포함만으로 ICT 기업으로 판정하지 않는다.
4. 코드가 명시된 조건에는 이번 업종 포함관계를 추가 적용하지 않는다. 기존 코드 비교 경로를 유지한다. 미해결 원문, 검수 상태, 중소기업 여부를 자동으로 통과시키지 않는다.
5. 분석·검수 프롬프트와 매칭 ruleset 버전을 갱신했다. 과거 AI 검수 v8의 채택·보정 실적은 v9에 옮기지 않았다.

분류 참고: [OECD ICT 정의](https://doi.org/10.1787/b9576889-en), [OECD 디지털 산업 분류 설명](https://www.oecd.org/en/publications/oecd-handbook-on-compiling-digital-supply-and-use-tables_11a0db02-en/full-report/component-7.html). 이는 공고별 자격규정이나 한국 KSIC 코드의 대체 자료가 아니다.

## 최초 코드 수정 검증

- 패키지 빌드, 웹·관리자 typecheck 통과.
- 신규 업종 포함관계 테스트, 기존 matcher·KSIC·LLM 조건 정규화·공간 조건 통합 테스트 통과.
- 분석 계약·분석기·validator·블라인드 감사·감사 조정·AI 검수 비교·정규화 provenance 테스트 통과.
- 합성 모델 출력 → 실제 정규화 함수 → 실제 matcher 경로에서 소프트웨어 회사의 ICT 업종 통과와 중소기업 규모 미확인의 분리를 확인했다. **합성 입력이며 실제 모델 실행이나 운영 발행 증거가 아니다.**
- 개발 서버, 신규 모델 실행, 운영 DB 쓰기, 배포는 수행하지 않았다. UI 변경이 없어 브라우저 검증은 수행하지 않았다. 운영 추천 증가나 전체 산업 커버리지는 입증하지 않았다.

## 남은 인수 기준

이 수정은 ICT·소프트웨어 범위를 대상으로 한 첫 보완이다. 범용 산업 의미 분류나 기존 공고 복구가 완료된 상태가 아니다.

1. 인도 BTS의 전체 원문·첨부에서 산업 범위와 나머지 신청조건을 확인하고, 현재의 미해결 업종 조건을 출처가 결속된 구조화 조건으로 복구한다. 과거 분석·검수 영수증을 수정하거나 재사용해 새 해석을 승인된 것처럼 만들지 않는다.
2. 실제 모델의 새 출력이 공통 지시를 따르는지 검증한다. 모델 실행이 필요하면 프로젝트의 exact manifest 준비·승인 경로를 사용한다. 이 문서는 실행 승인이나 실행 산출물이 아니다.
3. 복구된 공고를 발행하고 실제 등록 회사로 결과를 확인한다. 업종은 근거와 함께 통과하고, 회사에 없는 중소기업 여부 등은 답변 가능한 확인사항으로 남아야 한다. 확인 질문 발행과 최종 카드 노출까지 확인해야 제품 인수가 끝난다.
4. 다른 산업의 실제 공고·회사 쌍으로 넓힐 때는 같은 분야, 상하위 분야, 유사하지만 다른 분야, 복합 전제의 기대 판정을 먼저 정한다. 추천 수 증가와 함께 실제 적합 공고의 누락 및 잘못된 추천을 평가한다.

최초 코드 수정 시점의 출시 판단: 이 코드 수정만으로 초대 베타의 추천 품질 문제가 해결됐다고 판단할 수 없다.


## 후속 실행 — 원문 복구

사용자의 후속 지시(필요한 작업을 모두 수행)에 따라 인도 BTS 한 공고를 대상으로 운영 입력을 복구했다.

- 공식 페이지의 본문출력파일 `2. 2026 BTS 모집 공고문.hwp`가 원본 payload에는 있었으나 보관 첨부에서 빠져 있었다. 기존 bounded BizInfo 보관 경로로 추가했고 로컬 pyhwp 변환을 완료했다. 이미 발행된 criterion은 publisher의 승격 보호로 보존됐다.
- 기존 PDF는 보관됐지만 변환이 skipped였다. 공식 다운로드와 R2 원본 SHA를 대조하고, 1페이지 PDF를 렌더링해 확인했다. 기존 PDF 복구 코어로 텍스트를 생성하고 변환 artifact로 등록했다. 모델 호출은 없었다.
- 이제 PDF·모집 공고문·신청서 3개 모두 입력에 포함된다. 입력 2,453자 → 4,851자. 새로운 입력 SHA `494cae0f5f17aa32138c03d9a4466eb1a25252390d0c67307d7381d5f5ca4dcc`, 첨부 manifest SHA `8ca92ef35be5b490463ce1fd4790d39bdf0f3b4f24d168f1dce3babbc49f31fb`.
- 모집 공고문에서 신청 대상(과학기술 및 ICT 중소기업), 서류평가·70점 기준, 항공·숙박 기업 부담을 확인했다. 평가 점수는 회사의 현재 자격 사실로 대신 입력하지 않는다.
- 이 변경은 입력 내용이 실제로 늘어난 source change다. 과거 입력의 분석을 현재 원문 분석으로 재결속하지 않고, 기존 launch 이력과 변경된 입력을 함께 검증한 새 matching-only manifest로 준비한다.
- 웹 프로덕션 빌드도 통과했다. 이후 분석·발행·배포·실제 계정 검증 결과는 추가 기록한다.

## 후속 실행 — 실제 분석·독립 검수와 교체 발행 경로

- PDF 텍스트 추출이 이미지 속 주요 분야를 누락한 사실을 실제 분석에서 확인했다. 원본 SHA가 같은 PDF 렌더링을 직접 대조하고 6개 분야 캡션과 전시장 범례를 별도 전사 구간으로 복구했다. 자동 OCR로 표기하지 않았으며 이전 R2 markdown은 보존하고 현재 artifact를 SHA 비교 후 교체했다.
- 최종 입력 SHA `b0fdfa16e848b8708864598a18cbdacaaf7d895e78b2e7669d67e7960229c42d`, 첨부 SHA `51a2c1c3804de0812458d9d20c089ec8397321b6ee5e4d177bcbc1974931c82a`.
- 첫 복구 분석 104.702초, 이미지 전사 포함 분석 87.676초. 독립 Codex 검수가 누락된 선정평가 요소를 지적해 formal repair를 수행했다(115.854초). 마지막 run은 `run-2026-09-24T134616.959Z-20b980`, receipt `ac6ea1db0c2058ce32f0eefd1bfb051c5d51c4cca6f3777f90fee95a4a48548d`다. 이는 단건 분석 시간이며 준비·검수·발행의 전체 처리 시간이나 p95가 아니다.
- `gpt-6-sol` 독립 재검수 PASS, aggregate `3136e5edf40722b073b760daeb9e993374fd34f831d6f3d2ace7bf5e9c5f8c4f`. 필수 업종·규모 2개와 선정평가 preferred 5개를 보존했다. 행사 주제를 신청기업 자격으로 확대하지 않았다.
- 발행 준비에서 기존 active release 때문에 `promotion_duplicate`로 차단됐다. 새 `--replace-active=<exact releaseId>`는 공고 1건에 한해 이전 immutable manifest/원장의 active·applied·run·현재 after snapshot을 검증한다. 새 분석·독립 검수와 모든 release gate를 통과해야 하며, 이전 release/receipt를 삭제·수정하지 않는다. 준비·승인·최초 쓰기에서 이전 상태를 확인하고 기존 writer의 baseline CAS를 유지한다. 과거 prepared revision은 적용된 동일 cohort·동일 run의 하위 revision일 때만 역사 예약으로 구분한다.
- 신규 교체 경계 테스트, release 집계 suite, promote suite, 웹 typecheck 통과. 실제 이전 BTS 발행의 after snapshot이 현재 DB와 같은 것도 읽기 전용으로 확인했다.

# 글리프 소규모 매칭 인수

## 목표와 순서

사용자 지시: 개별 분석의 반복 보정보다 작은 사용자 목표를 단계별로 완성한다.
첫 목표는 확인된 글리프 회사 정보와 현재 공고 원문을 비교해 실제 후보 유무를 설명하고,
그 판단이 실제 계정의 추천 이유·확인할 조건과 일치하는지 검증하는 것이다.

1. **정답 표본**: 현재 신청 가능한 공고 6~10건을 원문 모집 대상과 사업 유형으로 선정한다.
   현재 추천 여부로만 고르지 않는다. 후보 가능·확정 부적합·정보 부족 사례를 포함한다.
   공고별 근거 문구, 확인된 회사 사실, 모르는 사실, 기대 판정, 원문 결속을 남긴다.
2. **최소 수정**: 기대 판정과 실제 결과를 비교하고 첫 공통 원인만 수정한다.
   원문 누락, 분석 의미 오류, 매칭 오류, 노출 오류를 구별한다.
   무근거 자격 확정·원문 충돌 무시·기존 검수 보류 해제는 하지 않는다.
3. **실제 사용 확인**: 글리프 계정에서 공고 목록·추천 이유·추가 확인 안내를 확인한다.
   신규 코드의 로컬 검증과 운영 반영을 구별하고, 소스·배포·실제 화면 증거를 구분한다.

## 이번 단계의 종료 기준

- 표본 전체의 기대 판정과 실제 결과 차이가 설명된다.
- 실제 후보가 있다면 무엇이 맞고 무엇을 확인해야 하는지 근거가 있다.
- 첫 수정의 효과가 같은 표본과 관련 회귀 사례에서 확인된다.
- 실제 계정 확인 여부와 미완료 항목을 명시한다. 추천 수 증가를 보장하거나 정답을 바꾸지 않는다.

## 작업 운영

- Root: 원문 판정, 최소 수정 선정, 코드 검토, 실제 화면 인수.
- 기존 Sol 담당: 읽기 전용 회사·현행 공고·원문·시스템 판정 자료 수집. 중복 구현 없음.
- 신규 대량 분석과 단건 repair 재실행은 이번 자료 수집의 선행 조건이 아니다.
- 사용자 답변·회사 규모·인증·기술 보유 여부를 추정해 채우지 않는다.
- 검증은 바꾼 동작에 맞춘 최소 범위로 선택한다.
- 기존 exact19, 보류된 3건, 불변 실행 기록은 별도 유지한다.
- 상세 원문과 조회 자료는 영속 `spike-out/glyph-small-goal-20260925/`에 저장한다.
  비밀번호·토큰·사업자등록번호·개인 연락처는 평가 문서에 기록하지 않는다.

### 운영 화면에서 확인한 범위

- 실제 글리프 로그인 → dashboard의 조건부 BTS 후보 → 상세 자격 → 기업규모 확인 질문까지 이동했다.
- 질문은 공식 확인서 기준이며 값을 대신 입력하지 않았다. 운영 추천 수 증가는 아직 없다.

  후보에 포함되지 않는 사례이며, 현재 공고 자체가 전혀 없는 상황과 구별된다.
- 별도 발견: 상세의 `80%` 작성 지원 문구와 dashboard의 정보 준비율을 정확도처럼 표현한 문구는
  아직 검증 근거가 부족하다. 이번 자격 입력 수정의 성공 기준에 섞지 않고 후속 UX 항목으로 남긴다.

### 2단계: 첫 공통 수정 범위

반복 확인한 실패는 포털 검색 분류를 자격의 수치·지역 근거로 사용하는 것이다.
현재 Lab 입력은 `biz_enyy`를 실제로 `업력 조건`이라고 표시한다.
검색용 `biz_enyy`·`biz_trgt_age`·`supt_regin` 값을 자격 추출 입력에서 제외하고,
실제 신청대상 본문·첨부의 업력·연령·소재지 문장은 보존하는 작은 수정을 진행한다.
수집 원본·DB 검색 분류·기존 봉인 실행 결과는 수정하지 않는다.
수정 효과는 입력 회귀와 실제 저장 원문 오프라인 재조립으로 검증한다.
이 검증만으로 새 모델의 정확도나 운영 추천 증가를 선언하지 않는다.

입력 경계 수정 commit `f73a845`: 후단의 `mergeKStartupLlmCriteria`가 검색 필터에서 만든
결정론적 조건을 재주입하던 경로도 함께 차단했다. 실제 본문·첨부에 근거한 같은 축의 조건은
보존한다. 관련 입력·추출·pilot 소비 경로 회귀 4개, package build, web typecheck,
runtime freshness를 통과했다. 기존 pilot 전체 테스트에는 별도 normalization repair 순서
기대 실패가 남았으며 변경 전 기준선은 재현하지 않았다. 전체 테스트 통과로 보고하지 않는다.

실제 오프라인 재조립: 성수는 블록 5개·첨부 4개, 경기 일반상담은 블록 3개·첨부 2개를
그대로 유지했다. raw/첨부 hash는 같고 검색 필터 제거로 input SHA만 바뀌었다.
신규 입력 SHA를 기존 불변 분석의 결과로 재해석하지 않는다.

### 후속 준비에서 찾은 공급 오분류

성수 1건의 정상 준비를 시도했으나 기존 과거 이력 제외와 campaign의 `condition_review`
판정으로 막혔다. 원인은 DB에 남은 검색 분류 기반 `biz_age` 한 줄을 loader가 분석 산출물
존재로 간주했기 때문이다. 실제 발행 분석과 현재 결속된 검수 자산은 없었다.
이전 단계의 거부는 `seongsu-formal-preparation-boundary.md`에 보존했다.

최소 후속 수정은 readiness producer에서 **발행 증거가 없고 조건이 전부 확인된 검색 분류
출처인 경우**를 분석 누락으로 구별하는 것이다. 출처가 없는 과거 수동 조건, 실제 본문 조건,
유효한 발행 분석은 기존 검수 경로를 보존한다. 새로운 실행 예외나 gate 완화는 추가하지 않는다.

교정 commit `b0ef774`: 추가로 `parserVersion=kstartup-field-parser-v3` 및 `stableKey=null`을
모든 조건에서 확인할 때만 위 분기를 적용했다. 출처 누락·다른 파서·검수 안정키·발행 증거가
있는 사례는 기존 `present`/검수 흐름을 보존한다. loader 12·supply 9·campaign 29개 테스트와
web typecheck를 통과했다. 실제 성수 DB 재조회에서도 `analysis.status=missing` →
`condition_analysis` → `await_approved_model_run` → `source_changed/prepare_changed_source`를
확인했다. 원본 DB 조건과 과거 LabRun은 변경하지 않았고 모델 호출은 없었다.

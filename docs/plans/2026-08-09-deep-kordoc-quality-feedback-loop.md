# 딥분석·Kordoc 성공 기준과 품질 피드백 루프

작성일: 2026-08-09  
상태: 체크포인트 3 구현 완료, 제품 카나리 결속은 후속 범위
범위: 로컬 구독 분석실 산출물의 판정·관측·회귀 비교. 분석 프롬프트 자체와 운영 worker는 변경하지 않는다.

## 1. 목표

딥분석과 Kordoc의 성공을 단순한 프로세스 종료나 `error=null`로 정의하지 않는다. 한 공고가 다음 세 상태 중 어디에 있는지, 어떤 증거로 그렇게 판정했는지, 다음 자동 재처리 지점이 어디인지 일관되게 계산한다.

- **정상 완료**: 신청 가능 여부와 필수 입력을 바꾸는 쟁점이 없고 계약·원문 근거·독립 검수가 모두 확인됨
- **안전한 부분 완료**: 우대·랭킹 신호 또는 비필수 빠른 작성 필드만 보류하고 나머지는 안전하게 사용 가능
- **명시적 보류**: 신청자격·배제 조건, 필수 입력, 원본 누락처럼 결과를 바꿀 수 있는 쟁점이 남음

계약 파손과 모델 실행 실패는 별도의 **실패**로 유지한다. 아직 승격·제품 카나리를 실행하지 않은 상태는 성공이나 실패로 추정하지 않고 **미검증**으로 표시한다.

## 2. 성공 기준

### 2.1 딥분석

하드 게이트:

1. 입력 SHA-256과 입력 블록이 존재한다. 변환 불가 첨부는 숨기지 않고 `partial`로 남긴다.
2. 현행 프롬프트 버전이며 22축을 정확히 한 번씩 평가한다.
3. 발행 후보 criterion 전부가 실제 원문 span에 결속된다.
4. 추출 모델과 독립된 검수 결과가 종결된다.
5. required/exclusion 오류나 eligibility 누락이 없다.

조건부 통과:

- preferred 오류는 해당 랭킹 신호를 제외하고 `partial`로 둔다.
- ranking 영향 누락은 점수에 반영하지 않고 `partial`로 둔다.
- 원문 자체가 애매한 축은 판정을 발명하지 않고 `partial`로 둔다.

제품 준비 증거:

- 동일 run ID와 input SHA에 결속된 승격 receipt
- 승격된 분석 버전을 사용한 가상기업 매칭 카나리
- 불필요한 사용자 확인 질문이 없다는 제품 결과

### 2.2 Kordoc 빠른 작성

하드 게이트:

1. 발견한 HWP/HWPX 원본이 모두 처리 또는 명시적 스킵으로 종결된다.
2. 현행 Kordoc 계약, `claude-cli`, 채택 모델 provenance가 결속된다.
3. 지원 양식의 모든 후보가 판정되고 미처리 후보가 없다.
4. 필수 입력 후보가 unresolved로 남지 않는다.
5. 딥분석 run ID와 Kordoc parent run ID가 동일하다.

조건부 통과:

- 안전하게 확정한 필드는 materialize하고 비필수 unresolved 또는 구조 경고만 `partial`로 남긴다.
- 지원 양식이 없으면 실패가 아니라 `not_applicable`이다.

제품 준비 증거:

- field candidate artifact와 DB materialization receipt
- workspace 진입 시 런타임 LLM 호출 없이 저장 필드 로딩
- 실제 문서 채움·재파싱 검증에서 필드 위치와 값 일치

## 3. 품질 그래프

```text
입력 봉인 → 22축·근거 계약 → 독립 검수 → 딥분석 승격 → 매칭 카나리
                    ↑                              │
                    └──────── 피드백 ─────────────┘

Kordoc 원본·파싱 → 필드 판정 → 빠른 작성 반영 → workspace 카나리
                         ↑                          │
                         └────── 피드백 ────────────┘
```

두 그래프는 공고와 딥분석 run ID로 결속하지만 독립적으로 종결한다. Kordoc 실패가 올바른 22축 결과를 실패로 바꾸지 않고, 딥분석 실패도 이미 검증된 문서 파싱 산출물을 삭제하지 않는다.

## 4. 피드백 루프

### 실행 단위

- 결정 규칙으로 설명 가능한 문제는 코드와 테스트로 고정한다.
- 모델 판단이 필요한 문제는 실패한 노드의 후보만 최대 횟수 내에서 고성능 독립 모델로 재판정한다.
- 재판정 뒤에도 남은 필수 쟁점은 보류하며 강제 통과시키지 않는다.

### 30건 릴리스 단위

- 현행 정책의 최신 런 30건을 읽기 전용으로 평가한다.
- 이전 정책과 `passed / partial / held / failed / not_evaluated` 분포를 비교한다.
- 입력·근거·필수 필드 하드 게이트 악화가 있으면 새 정책을 채택하지 않는다.
- 개선은 전체 성공률뿐 아니라 차단 사유별 감소량으로 판단한다.

### 제품 단위

- 승격된 공고에 가상기업 매칭 카나리와 workspace 문서 채움 카나리를 결속한다.
- 제품 카나리 실패는 해당 분석 노드로 되돌리되 프롬프트를 자동 수정하지 않는다.
- 규칙·프롬프트 변경은 버전을 올리고 같은 30건 기준선으로 재평가한다.

## 5. 초기 운영 목표

아래 수치는 품질 추세를 보는 SLO이며 개별 공고를 억지로 통과시키는 기준이 아니다.

- 원문 근거 결속: 100%
- 22축 계약 완전성: 100%
- 필수 입력 unresolved: 0건
- 전체 빠른 작성 후보 판정률: 100%
- 비필수 unresolved 비율: 2% 이하
- 가상기업 매칭 카나리: 100%
- workspace 문서 채움 카나리: 100%
- 사용자 진입 시 LLM 호출: 0건

## 6. 구현 체크포인트

1. **품질 계약**: 순수 평가 모듈과 경계 테스트
2. **관측 그래프**: 기존 불변 산출물·검수·감사를 읽어 로컬 분석 센터에 표시
3. **30건 기준선**: 읽기 전용 CLI/JSON 보고서와 차단 사유 집계
4. **후속 제품 카나리**: 승격 receipt, 가상기업 매칭, workspace 채움 증거를 같은 그래프에 주입

체크포인트 1~3에서는 분석 모델 호출, DB 쓰기, 승격, 운영 worker 변경을 하지 않는다.

## 7. 실행 방법

현재 현행 정책 최신 런을 읽기 전용으로 평가한다. 모델 호출과 DB 쓰기는 없다.

```bash
pnpm lab:quality -- --limit=30
```

비교 기준을 불변 JSON으로 남길 때만 `--write`를 명시한다.

```bash
pnpm lab:quality -- --limit=30 --write
```

이후 정책 변경 결과를 이전 파일과 비교한다. 같은 공고의 준비도가 `passed/partial`에서
`held/failed`로 내려가면 하드 게이트 회귀로 별도 출력한다.

```bash
pnpm lab:quality -- --limit=30 --compare=spike-out/analysis-lab/quality-baselines/<기준선>.json
```

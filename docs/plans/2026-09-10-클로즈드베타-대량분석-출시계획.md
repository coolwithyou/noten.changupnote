# 지원 가능한 공고의 대량분석과 클로즈드 베타 출시

2026-09-10 사용자 방향 확정: **지원·매칭 가능한 공고를 빠르고 효율적으로 대량분석해
프로덕션에 공급하고 클로즈드 베타를 진행한다.**

이 문서가 다음 작업의 우선순위를 정한다. 앞선
[원천 불일치·조건 교정 계획](2026-09-10-원천불일치-조건교정-실행계획.md)은 공급을 방해하는
개별 문제를 해결할 때 사용하는 하위 계획이다. 모든 역사 오류의 조사 완료를 베타 시작의
선행조건으로 만들지 않는다.

## 성공 기준

분석 실행 횟수보다 **현재 지원 가능하고 실제 매칭에 공급된 공고 수**, 그 공고를 추가하는
속도·실패율, 베타 사용자의 지원 판단·신청 준비 성공을 본다.

- 모집 중·노출 가능·신청기간 유효한 공고를 실제 공급하며 중복 공고를 별도 성과로 세지 않는다.
- 확인된 조건으로 매칭하고 미확정은 조건부·확인 필요로 표현한다. 근거 없는 확정 탈락,
  알려진 자격 충돌, 개인정보·접근권한 결함은 실제 사용자에게 내보내기 전에 해결하거나
  해당 기능/대상을 승인된 방식으로 공급 범위에서 제한한다.
- 실행 중 개별 공고의 실패가 전체 처리를 막지 않고, 성공한 분석을 불필요하게 반복하지 않는다.
- 검증된 결과가 release와 실제 게시·매칭까지 이어지고, 오류 시 대상별로 되돌릴 수 있다.
- 실제 로그인 사용자가 사업자 입력 → 매칭 근거 확인 → 확인질문 → 신청 준비까지 수행한다.
  내부 테스트·익명 HTTP 응답을 이 인수의 대체 증거로 사용하지 않는다.

## 실행 순서와 산출물

| 순서 | 수행할 일 | 다음 단계에 넘길 결과 |
| --- | --- | --- |
| 1. 공급 재고와 실행 준비 확인 | 현재 유효 공고를 이미 공급 중 / 기존 결과 재사용·승격 후보 / 신규 분석 / 교정·보류로 집계. 현재 launch의 구조적 중단 원인과 수정 검증 상태 대조 | exact 후보 목록, 재사용 가능 수, 신규 분석 가능 수, 실제 실행 차단 원인 |
| 2. 승인 가능한 대량분석 준비 | 유효 재고와 현행 cohort 정책을 맞추고 input·첨부·실행 계약·동시성을 manifest로 봉인. 사용 가능한 시간과 처리량 근거로 규모 제안 | 바로 실행할 exact manifest, 예상 소요시간의 근거와 불확실성, 승인 범위 |
| 3. 대량 처리와 병목 측정 | 승인된 `lab:launch`로 연속 처리. 개별 실패 격리, 같은 계약의 실패 target만 재시도, 가능한 기존 작성 분석 재사용 | target별 terminal 결과, 시간·성공/보류/실패·재시도·재사용 실측 |
| 4. 검수된 결과를 서비스에 공급 | 기존 재사용 결과와 새 결과를 현재 source/검수/게시 계약으로 확인. 준비된 대상의 release·승격과 필요한 캐시 반영을 승인 범위 안에서 수행 | 실제 공급 증가, 대상별 매칭 대조, 비대상 보존, 복구 증거 |
| 5. 클로즈드 베타 실행 | 모집할 사용자군·기간·지원사업 범위를 확정하고 실제 계정의 핵심 경로 인수. 준비된 범위부터 초대·운영 | 사용자별 매칭/신청 준비 성공, 오류·이탈·피드백, 다음 개선 순서 |

1단계는 생산성을 확인하는 데 필요한 한 번의 현황 정리다. 재고 수·베타 인원·일정을 임의로
확정하지 않으며, 이 수치가 없다는 이유로 읽기 전용 준비를 멈추지는 않는다. 사용자 초대나
외부 발송은 전달할 내용과 대상을 확정하고 권한이 있을 때 수행한다.

## 빠르고 효율적으로 처리하는 원칙

- 현재 재고와 새 유입을 먼저 확인한다. 과거 실험의 고정 100건 요구와 현재 유효 재고가
  맞지 않으면 계약을 몰래 축소하거나 과거 공고를 끼워 넣지 않고, 실제 공급 목표에 맞는
  cohort 정책 변경안을 제시한다. 미분석 수와 전체 유효 공고 수는 구분한다.
- 같은 input·첨부·검수·작성 계약의 기존 결과는 재사용 가능성을 먼저 검증한다.
  아직 승격되지 않은 결과를 이미 사용자에게 공급한 것으로 세지 않는다.
- 현행 formal launch의 딥분석+신청서 필드 분석 계약을 유지한다. 속도를 위해 필드 분석을
  임의로 생략하지 않고, 검증된 재사용과 동시성·대기·재시도 병목부터 개선한다.
- 명목 API 환산 비용보다 실제 경과시간, 구독 인증/사용창, 재시도 낭비, 공급 가능한 결과당
  처리시간을 측정한다. 로컬 구독과 운영 API 경로는 기존 계약대로 분리한다.
- 개별 held·source unavailable·timeout은 target별로 종결하고 잔여 대상을 계속 처리한다.
  인증·manifest·공용 lease 등 전체 실행의 무결성을 잃는 문제만 cohort 착수를 중단한다.
- 실패율과 시간의 목표치는 첫 현행 실행과 베타 일정에 맞춰 고정한다. 과거 표본 또는
  오프라인 테스트 통과를 현행 대량 처리 성능으로 주장하지 않는다.

## 개별 교정의 우선순위

기존 [원천 조사](../evidence/deep-analysis/2026-09-10-source-drift-triage.md)는 폐기하지 않는다.
잘못된 exclusion, 업력 경계, 허용 예외 누락처럼 베타 대상의 지원 판단을 바꾸는 문제는
공급 전 해결 대상으로 둔다. 다만 해당 공고의 교정이 관련 없는 신규 공고의 준비·분석까지
막지 않게 한다. 원천 구성요소의 역사 조사와 범용 진단 도구 확장은 공급·실행 문제 해결에
필요한 범위로 한정한다.

현재 원천이 같은 kind 교정 후보, 새 첨부 검수 대상, 미승격 재사용 후보는 서로 다른
집합이다. 각 집합의 exact ID와 권한을 유지하면서 **어떤 작업이 검증된 공급을 가장 빨리
늘리는가**를 기준으로 착수 순서를 정한다.

## 측정과 완료 판정

| 관점 | 기록할 지표 | 통과 판단 |
| --- | --- | --- |
| 공급 | 현재 유효·중복 제거 후 재고, 검수 통과, 실제 게시·매칭 공급 수 | 각각의 집합과 차이가 설명되고 베타 사용자군에 실제 관련 공고가 존재 |
| 처리 효율 | 전체 경과시간, 시간당 검수 통과 결과, 공급까지의 지연, 단계별 대기·재시도 | 현행 실행으로 실측하고 병목 개선 전후 동일 기준 비교 |
| 분석 품질 | 조건별 근거·예외, 치명적 오류, held/failed 사유, 변경 영향 사례 | 게시 대상에 알려진 치명적 오류가 없고 불확실성을 표시 |
| 운영 안정성 | lease 상실 시 중단, 실패 격리·재시도, source 변경 거부, 게시 복구 | 해당 경로의 테스트와 실제 처리 증거를 구분해 확보 |
| 베타 경험 | 로그인·입력 저장·매칭·확인질문·신청 준비/다운로드·피드백 | 실제 계정의 단계별 인수와 사용자 피드백 확보 |

## 바로 다음 작업

**현행 유효 재고·재사용 가능 결과·launch 준비 상태를 한 번에 확인하고, 실행 가능한
대량분석 manifest 준비까지 진행하는 것**을 다음 착수 단위로 변경한다. 조사 범위 밖의
구조적 실행 차단이 있으면 실제 차단 원인만 먼저 해결한다.

사용자에게는 준비된 대상 수, 재사용/신규 분석/보류 수, 동시성, 시간 추정 근거, exact manifest를
제시한다. 현행 규칙상 live 모델 실행은 manifest 승인 후 시작하며, 승인된 동일 범위의 재시도에
반복 승인을 요구하지 않는다. release 처리·실제 승격·배포 권한은 각 범위대로 이어간다.

이번 문서 변경은 출시 목표와 작업 순서의 수정이다. 대량분석·서비스 데이터 쓰기·초대 발송은
아직 실행하지 않았으며, 계획 수립을 프로덕션 또는 베타 인수 완료로 기록하지 않는다.

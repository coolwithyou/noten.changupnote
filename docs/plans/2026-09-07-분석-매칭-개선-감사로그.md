## 0+1a 감사 기준

- 강등은 kind를 바꾸지 않고 근거·원래 축/연산자·사유를 보존해야 한다.
- 우대 unknown은 eligibility를 막지 않고 필수/배제 unknown은 임의 pass로 바뀌지 않는다.
- 공식 실패와 원천 정정 상태가 사용자 확인으로 우회되지 않아야 한다.
- 단순 배열 위치가 아니라 실제 변환 입력의 결속으로 before/after를 비교한다.
  중간 scope filter/drop 때문에 llm-N과 원 criterion index가 달라지는 경우도 고려한다.
- 고정 원차수 80건은 독립 검수 PASS나 승격 허가로 표시하지 않는다.
  receipt/run hash를 검증하며 원본 산출물을 수정하지 않는다.
- 관련 테스트 통과와 별도로 실제 diff·의미 변화·검증 도구의 자체 오류를 감사한다.

사전 피드백: `shadow-convert`의 중간 직무 조건 filter와 `promote`의 index 역산이
진단 도구에서 잘못된 전후 대조를 만들 수 있으므로 mapping 검증을 구현 담당에게 요청했다.
강등된 원래 축의 정정 상태가 확인 답변에 의해 우회되는지도 검토하도록 요청했다.

### 사전 조사와 감사 기준

- `analyze.ts`의 최종 run 저장은 Kordoc paired 실행 이후다. primary 진단 생성은
  primary 반환 전에 수행하고, 최종 run에는 동일 결과를 결속하도록 요청했다.
  진단 실패를 primary 모델 오류·launch 전체 STOP·추가 모델 repair로 둔갑시키지 않는다.
- snapshot은 원본 조건/input/첨부와 변환 계약·matcher·normalizer provenance 및 결과에
  결속한다. 역사 무필드는 unverified이며, 새 명시 binding의 불일치는 승격에서 차단해야 한다.
- 외부 wrapper의 공용 normalizer 버전은 Lab snapshot에만 남기지 않고 실제 extraction
  result/draft 소비 경로까지 전달한다. parser/prompt 일괄 bump나 운영 재분석 착수는 하지 않는다.
- 고정 원차수에서 실제 오류를 발견했다: `kstartup__178970`의
  `run-2026-09-05T090105.891Z-485180`, criterion #3은 ‘업력 조건: 3년미만’인데
  `lte/max_months=36`이다. artifact SHA는
  `3d84edf50e8b2091f8e68fd32a84b4fde8e76199f93fce108b2c72c8b3390500`.
  기존 inclusive matcher의 36개월 pass를 막는 좁은 원문 모순 보호를 요청했다.
  정수 월 계약에서 올바른 max35는 표현 가능하므로, 정상 경계 사례와 역사 오추출 사례를 구별한다.
- 원문 사례집은 실제 matcher 출력을 정답으로 복사하지 않으며, 소재지 OR·현재 제재/과거 위반·

## 후속 2단계 사전 감사 항목

사용자 후속 요청에 따라 동일 `gpt-5.6-sol / xhigh` 구현자를 재개했다.
1a~1c 미커밋 변경은 보존하며 root는 문서·독립 감사만 수행한다.
운영 DB·live 모델·승격·배포·커밋/push는 실행하지 않는다.

현재 코드 읽기에서 다음 경계를 확인했다. 이 목록은 1b 구현 범위를 확대하지 않으며,
2단계의 답변 계약 변경 때 함께 검증해야 할 항목이다.

- `CriterionConfirmation`과 선택지 평가가 legacy exclusion의 `disqualified: boolean`이다.
  required/preferred에 boolean을 재사용하지 말고 충족/미충족/확인불가를 명시해야 한다.
- `normalizeConfirmationOptions`는 `disqualifies` 누락도 false로 만든다.
  새 계약에서 불완전한 선택지를 자동 pass로 정규화하지 않는 음성 회귀가 필요하다.
- `submitGrantConfirmations`는 질문을 트랜잭션 전에 읽어 검증하고, 내부에서 현재 회사 권한과
  질문 버전을 다시 잠금/검증하지 않는다. 조회 후 권한 철회·질문 교체 경합을 차단해야 한다.
  기존 원천 정정 저장 경로의 트랜잭션 내 membership 재검사 패턴을 참고할 수 있다.
- 질문 테이블에는 이미 definition SHA·version·invalidated_at이 있으나 제출 DTO에는 없다.
  기존 원장을 확장해 질문 의미/원천 결속과 오래된 답변 재확인 정책을 강제해야 한다.
- 소스상 자동 검증과 실제 계정의 저장·재접속·회사 전환 인수는 별도 증거로 남긴다.

### 2단계 설계 승인과 추가 감사 경계

- 2a는 explicit `satisfied|unsatisfied|unknown` 계약 및 kind별 core 평가,
  2b는 기존 질문/답변 원장의 additive v2 결속·트랜잭션 CAS,
  2c는 검수된 사용자 확인 질문 발행 및 실제 화면 왕복으로 나눈다.
- v2 질문은 별도 criterion anchor를 같은 질문 행에 두고 legacy anchor는 비워,
  구 boolean reader가 새 unknown을 false/pass로 오독하지 않도록 한다.
  구 앱은 새 답변을 무시하여 미해소로 보존하는 호환이지 기능 동등성을 보장하는 것은 아니다.
- 답변 트랜잭션은 기존 grant publication 잠금과 회사/membership/question 잠금을 재사용한다.
  role 변경과 충돌하지 않는 KEY SHARE로 권한 검사를 끝내지 않는다.
  [PostgreSQL 공식 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html)를 확인했고,
  기존 격리 unix-socket Postgres harness에서 실제 경합 검증을 추가하도록 요청했다.
- core는 검수 defer 전 원판정 fail과 source dispute를 자가신고로 뒤집지 않아야 한다.
  원문 모순/분석 누락은 사용자 정보 부족으로 떠넘기지 않는다.
- 회사 A 저장 후 B로 전환했을 때 A의 늦은 PUT 응답을 B 카드에 반영하지 않아야 한다.
  같은 회사의 동시 답변도 answer revision으로 stale 쓰기를 거부한다.
- 질문 일부만 답변할 수 있어도 CTA를 열고, 남은 회사정보/원문 확인 행동을 구분한다.
  criterionId를 끝까지 보존하여 동일 문장의 다른 조건을 혼동하지 않는다.
  text_only criterion의 실제 확인 후 pass/fail을 DTO에서 다시 text_only로 덮지 않는다.
- 원장 v2 anchor/재발행/무효화/rollback/snapshot 경로의 결속을 함께 검증하고,
  명시적 다중선택 판정 계약 없이 문구로 결과 결합을 추정하지 않는다.
- UI는 기존 서비스 디자인을 유지하면서 설치된 shadcn 구성을 재사용한다.
  [Sheet](https://ui.shadcn.com/docs/components/base/sheet),
  [Toggle Group](https://ui.shadcn.com/docs/components/base/toggle-group),
  [Field](https://ui.shadcn.com/docs/components/base/field)의 공식 사용법을 확인했다.

### 2단계 중간 감사 — 아직 승인 전

- 신규 `CHECK`의 정규식·enum 비교는 NULL을 허용할 수 있어 전체 조건의 참 여부를 명시하도록
  피드백했다. [PostgreSQL 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)의
  CHECK/NULL 의미를 확인했다. criterion 삭제 시 FK SET NULL과 활성 질문의 필수 anchor 제약이
  충돌하므로 질문을 무효화한 뒤 연결을 해제하고, 답변 이력은 남기는 실제 DB 검증이 필요하다.
- 답변 저장뿐 아니라 조회·매칭 reader도 현재 원문 SHA를 비교해야 한다. 질문과 답변의 과거 SHA끼리
  일치하는 것만으로 원문 갱신 직후의 오래된 만족 답변을 재사용하지 않도록 요청했다.
- 기존 두 질문/답변 테이블의 RLS 정책 부재를 확인했다. 회사 membership 기반 답변 읽기와
  서버 전용 쓰기를 추가하고, non-bypass 역할의 교차 회사/직접 쓰기 차단을 격리 DB에서 검증한다.
- endpoint 문자열만 비교하는 UI 보호는 회사 A→B→A 및 닫기→재열기 경합을 놓친다.
  요청 세대까지 비교하고 stale 답변의 재로딩 동작을 검증하도록 요청했다.
- 자동 모델 질문 생성은 기존 legacy exclusion 계약을 유지한다. 이번 v2 발행 범위는 검수자가
  명시적으로 작성한 공고별 단일선택 질문이며, 실제 수동 artifact 입력→검수→발행 경로를 요구한다.
  테스트에서만 객체를 조립하거나 기존 immutable run을 수정하는 경로는 완성으로 인정하지 않는다.
  자동 생성 및 새 관리자 편집 GUI는 별도 후속 범위다.
- 중간 독립 core 검사 17개는 통과했다(chunk `b2e861`, exit 0). 세 kind×세 평가 상태,
  legacy bool의 required/preferred 재사용 차단, 공식 실패/정정 검토 우선 및 불법 enum의
  legacy fallback 차단을 포함한다. 이는 저장·UI·발행 전체의 완료 영수증은 아니다.
- 실제 normalizer의 `exclusive_upper_bound_mismatch`와 `sanction_cause_state_flattening`을
  수동 질문 분류기가 다르게 표기하던 문제를 발견해 수정 요청했다. 수정 후 두 조건의 관리자
  보류 독립 검사가 통과했다. 알려지지 않은 보류 사유·회사 공통정보를 일괄 사용자 질문으로
  분류하지 않는 방향으로 범위를 좁힌다.
- 별도 답변 계약 독립 검사 31개도 통과했다(chunk `5634c0`). 질문 결속 6개 필드의 변조,

## 2단계 첫 구현 최종 감사

판정: **2a·2b 및 2c 최초 수동 발행 왕복의 한정 범위 승인**.
동일 run의 수동 질문 개정, 다음 행동의 정밀 분류/UI 연결과 실제 계정 인수가 남아 있으므로
2단계 전체 완료로 표시하지 않는다.
구현은 `gpt-5.6-sol / xhigh`, 소스 읽기·수정 피드백·아래 독립 검증은 주 에이전트가 수행했다.

### 승인한 구현

- 기존 질문/답변 원장에 v2의 충족·미충족·확인불가 평가와 원천/조건/질문/답변 버전을 결속했다.
  legacy boolean은 exclusion에만 사용하고, 신규 질문의 legacy anchor를 비워 구 reader가
  새 unknown을 pass로 오독하지 않는다. 원장 병렬 신설 없이 additive migration 0081을 사용한다.
- 공식 실패와 원천 정정 검토는 자가신고로 해소하지 않는다. 검수 보류 전의 원판정과
  confirmed_by_user 출처를 구분하며, text_only의 실제 pass/fail 및 criterion ID가 카드까지 전달된다.
- 회사/권한/질문/원천/answer CAS를 짧은 transaction에서 검사한다. 기존 publication advisory와
  회사·membership·질문·원천 잠금을 사용하고, RLS는 회사 멤버 읽기 및 서버 전용 쓰기로 구성한다.
- 현재 DB 원문 결속의 batch 계산을 GET/PUT/매칭 reader/CTA/발행이 재사용한다.
  원문·첨부 drift를 최신 job 원장과 독립적으로 감지하고, 공고당 N+1 조회를 추가하지 않는다.
- 질문 일부만 확인 가능해도 CTA가 열린다. 회사정보/사용자 확인/원문·관리자 확인의 분류 메타데이터는
  추가했지만 아래에 기록한 정밀 분류와 실제 UI 소비는 남아 있다.
  기존 shadcn UI를 재사용하며 회사·공고 전환, A→B→A, 닫기·재열기·unmount 이후 늦은 응답을 차단한다.
- 실제 수동 CLI는 사람 조건 검수자와 질문 작성자를 구분한다. 새 파일은 run 목록에서 제외하고,
  원본 primary/run 검증 뒤 질문용 파생 입력에만 병합하며 release 근거에 sidecar SHA를 결속한다.
- 실제 publication port의 동일 질문 ID/답변 보존, source/정의 변경 시 새 ID/version 발행과
  restoreBeforeSnapshot의 v2 복원을 검증했다. 기존 snapshot의 NULL 컬럼 해시 drift는 제거했다.

## 후속 리뷰 보완 착수 — 재계산 최신성

사용자가 리뷰의 추천 순서를 승인했다. 구현자는 기존 `gpt-5.6-sol / xhigh`를 유지하고,
root는 재현·호출자 감사·문서 기록을 맡는다. 현재 항목은 착수 기록이며 완료 영수증이 아니다.

- `/tmp/cunote-review-20260907.mts`의 메모리 adapter + 실제 `refreshMatchStates(write:true)`로
  이전 satisfied 계산을 지연하고 최신 unsatisfied 계산을 먼저 저장한 뒤, 이전 eligible 결과가
  최종 저장값을 덮는 순서를 재현했다. 운영 DB 발생 증거는 아니다.
- **리뷰 설명 범위 정정**: `stateScopeFor(owned_read)`는 `user`이므로 실제 사용자 PUT의
  `recalculateGrantMatch`는 공유 `match_state`에 쓰지 않는다. 위 재현은 공유 system/background
  갱신의 순서 역전이며 사용자 PUT이 직접 공유 결과를 덮는 재현이 아니다.
  개인화 profile을 회사 공용 캐시에 쓰지 않는 기존 보호를 유지한다.
- 직접 저장 호출자는 profile question refresh, grant revision refresh, reviewed feedback refresh,
  공용 refresh다. 한 경로에만 guard를 추가하거나 오래된 company/grant 객체를 읽은 뒤 토큰만
  새로 발급하는 구현은 전체 보호로 인정하지 않는다.
- 답변 저장 commit 이후 재계산/annotation 실패가 저장 실패로 응답되는 문제는 별도로 검증한다.
  결과를 반환할 수 없으면 저장 영수증과 재계산 상태를 구분하고 오래된 카드를 성공처럼 내지 않는다.
- 잠금·격리 판정은 PostgreSQL 공식
  [격리 수준](https://www.postgresql.org/docs/current/transaction-iso.html)과
  [명시적 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)을 확인했다.
  긴 트랜잭션이나 프로세스 내 mutex만으로 다중 worker 문제를 해결하지 않는다.

후속 순서는 재계산 최신성 → 다음 행동/우대 질문 UI → 동일 run 질문 개정·철회 → 실제 인수다.
실제 인수 환경과 계정이 없는 상태를 운영 환경 사용 권한으로 해석하지 않는다.

### 재계산 최신성 보완 — 최종 감사 통과

첫 보완 단위의 로컬 코드·자동 검증을 통과로 판정한다. 전체 2단계나 운영 반영의 완료는 아니다.

- 공용 저장 port는 회사/공고 component 입력 revision과 계산 기준일을 필수로 받는다.
  단일 SQL snapshot에서 필요한 dedup component를 캡처하고, 짧은 저장 transaction에서
  revision·component·기준일을 검사한다. stale 결과는 savedCount에 포함하지 않는다.
- system/background 호출자는 binding 캡처 후 실제 입력을 다시 읽는다. scoped refresh도
  공고별 확인 답변을 계산에 반영한다. 개인화 owned_read는 계속 공유 상태에 쓰지 않는다.
- 구형 ruleset CLI의 직접 bulk write는 보호 port 이관 전까지 명시적으로 거부한다.
  dry-run은 보존했으며 runtime-only repository도 가짜 저장 성공을 반환하지 않는다.
- 답변 commit 이후 재계산/annotation 오류는 저장 영수증과 `refresh.status=failed`,
  `match=null`로 응답한다. 저장된 회사 화면은 카드 유무와 무관하게 재조회하고 안내를 표시한다.
- Postgres 통합 회귀는 실제 A/B 답변 경합, 최신 asOf의 동시 최초 저장, 실제 submit→재계산,
  user-scope 공유 쓰기 0, commit 후 계산 오류, RLS·mutator 권한·cascade·OLD target·markdown을 검증한다.
  UI는 응답 처리 결정과 기존 ABA/unmount 보호의 자동 검증이며 실제 브라우저 인수는 아니다.

목표는 같은 immutable run에서 질문 추가·수정·일부/전체 철회를 상위 immutable artifact로
표현하고, release가 exact 선택본을 계속 검증하도록 하는 것이다. 원본 run/최초 sidecar와
기존 답변 이력은 삭제하지 않으며, 새로운 파일이 생겨도 과거 release를 묵시적으로 최신 질문으로
바꾸지 않는다. 실제 공고를 대상으로 질문 artifact를 발행하지 않고 합성 fixture만 사용한다.

초기 코드 확인: 최초 sidecar는 `wx` 단일 경로라 개정이 불가능하다. generic/launch/deep-repair
source verifier는 모두 최초 파일 경로를 참조하고, release parser는 v2 질문이 0개인데 manual
hash가 있으면 거부하므로 전체 철회를 정확히 결속할 별도 계약이 필요하다. 빈 목록을 단순 허용하거나
이 검사를 삭제하는 방식 대신 의도한 철회와 선택본의 근거를 함께 검증하도록 피드백했다.

codebase-design은 개정 선택/검증을 공용 처리 경로에 모으는 데 적용한다. Postgres 지침의
짧은 transaction·권한 격리 기준으로 기존 발행/무효화/rollback의 답변 보존도 감사한다.
파일 저장은 [Node.js 공식 fs 문서](https://nodejs.org/api/fs.html#fspromiseswritefilefile-data-options)를
참조하며, 기존 불변 산출물 보존과 동시 쓰기 실패를 구분해 검증한다.

root의 `/tmp/cunote-revisions-root-baseline.mts`는 required/preferred/exclusion 3개 합성
조건으로 기존 동작을 독립 확인했다. 같은 run의 두 번째 저장은 EEXIST, 빈 items는 거부되며
원본 run과 최초 sidecar bytes는 유지됐다(4검사, chunk `128fe2`). 이는 현행 제한을 확인한
기준선이며 개정 기능 통과 증거가 아니다. 합성 디렉터리 외 DB/모델 호출은 없다.

구현 설계는 최초 파일을 revision 1로 보존하고 상위 rN 파일에 exact parent/hash·내용 결속과
전체 활성 질문 snapshot·철회 index를 기록한다. release는 grant/run/revision/hash를 명시적으로
선택하며 source/plan 양쪽이 같아야 한다. 역사 release의 선택 부재는 새 파일을 자동 채택하지
않는 의미로 보존한다. 추가로 canonical run 내용 결속·동일 bytes hash·전량철회의 명시성·
부분 철회 시 비수동 legacy 질문 보존을 감사 기준으로 전달했다. DB schema 확장은 계획하지 않는다.

첫 모듈 patch의 root 독립 검사는 순수 개정 계약 22개와 실제 filesystem 24개, 총 46개를
통과했다(chunk `03ea50`). 부분/전체 철회·재추가, 조용한 누락 거부, 내용/run 변조 거부,
동시 저장 1승, 잘못된 부모의 저장경로 미점유, selector key 순서 독립성, 역사 SHA-only/선택 부재
resolver의 안정성, run 목록 1개와 원본 bytes 보존을 확인했다. 저장 seam에서 부모 파일의 실제
chain을 검증하도록 보완했으며 초기 저장 함수는 revision artifact를 거부한다.
합성 파일은 `/tmp/cunote-revisions-root-fs-aZ6Jr0`에 남겼다. 이 시점은 release 연결·DB 왕복·
최종 집계 gate 이전이므로 전체 단위 완료가 아니다.

release 연결 뒤 root가 실제 plan/manifest/generic source 경로 23개와 실제 offline CLI
subprocess 16개를 추가 검증했다(chunk `170c76`, `fb3107`). 독립 구현 검사는 총 **85개**다.
r1→r2→전체 철회 r3→재추가 r4의 질문 수 3/2/0/1, unchanged definition 보존,
문구 변경의 새 definition, source/plan 결속 불일치 거부를 확인했다. manifest를 다시 hash한 뒤
선택 metadata를 변조해도 계약 검사가 거부하는지 확인했으며, 전체 수동 철회 때 비수동 legacy
질문은 남는다. CLI의 부모 옵션 누락·부모 hash 불일치·기존 경로 덮어쓰기를 거부하고,
반환 selector의 hash가 실제 파일 bytes와 일치함을 확인했다. revision 전용 초안에 부모 옵션이
없을 때 최초 파일로 잘못 저장되는 경로와 metadata key 순서 의존도 감사 피드백으로 수정했다.

이 85개는 합성 로컬 검증이며 실제 사람 검수나 운영 공고의 발행을 뜻하지 않는다.

### 동결 소스의 root 최종 검사

구현자 소스 12개를 `/tmp/cunote-manual-revisions-source-manifest.txt`에 동결한 후 root의

실제 plan/manifest/source 23(`4377f3`), 실제 offline CLI 16(`96608a`).

`/tmp/cunote-revisions-root-cli-2ZJKJm`이다. 이전 3개 검증 manifest에 이번 것을 최신 우선으로
합친 **107개 소스의 불일치 0**도 확인했다(chunk `0654ed`). 문서와 사용자 `next-env.d.ts`는

launch는 합성 receipt/검수 증거를 소비하는 실제 cohort fixture에서 exact 질문 선택본이
plan/source 양쪽에 전달되는지 회귀를 추가했다. deep-repair는 기존 receipt/readiness 회귀와
공유 resolver/source 코드 감사를 수행했으며, 실제 역사 deep-repair receipt 전체를 사용하는
개정본 E2E는 실행하지 않았다. 공용 filesystem 검증을 해당 E2E 통과로 표현하지 않는다.

이번 기능은 기존 publisher를 재사용하며 SQL/schema/migration을 추가하지 않았다.
격리 PG의 회귀는 합성 manual artifact→실제 plan→publisher→전체 철회→snapshot rollback을
거쳐 기존 답변 원장과 이전 질문 상태가 보존되는지 검증한다. 운영 DB에 이 테스트를 실행하지 않는다.

실제 계정의 저장·재접속·회사 전환 인수, 관리자 질문 편집 GUI, 자동 질문 생성, 운영 반영은 남아 있다.
`required other/text_only`의 annotation 전 준비도 제외도 이번에 변경하지 않았다.
스킬의 공용 계약 설계 원칙은 개정 선택/검증의 일원화에, Postgres 지침은 기존 짧은 발행 transaction과
답변 이력 보존의 감사에 적용했다. live 모델·실제 release·승격·운영 migration·커밋·push·배포는
실행하지 않았으며 기존 dirty 작업과 `apps/web/next-env.d.ts`를 보존했다.

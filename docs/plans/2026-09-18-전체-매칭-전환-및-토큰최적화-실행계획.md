이번 구현의 안전 계약:

1. 검수는 원문·추출 criteria와 함께 실제 매칭용 projection을 본다. 변환 후 같은 동작인 표기 차이는 결함으로 만들지 않는다.
2. `preferred`라는 추출 kind만으로 지적을 면제하지 않는다. 검수 근거상 자격에 영향 없는 ranking으로 확정된 경우만 점수에서 제외한다. 영향도 없는 역사 criterion 판정은 자동 ranking 승격하지 않는다.
3. 필수·제외 조건의 실제 오류, 영향도 불명확, 누락된 자격조건은 계속 차단한다. 삭제 후 적격으로 둔갑시키거나 사용자 입력 부족으로 바꾸지 않는다.
4. 모델의 `equivalent` 주장만으로 차단을 해제하지 않는다. 결정적 변환/실행 계약으로 확인 가능한 범위만 동등성 근거로 사용할 수 있다. 설명문 키워드만으로 역사 결과를 자동 해제하지 않는다.
5. 원천/packet/result/aggregate/projection 결속과 검수 coverage는 유지한다. 과거 결과를 수정하지 않고 파생 판정을 exact 근거에 결속한다. 새 출력 계약은 새 검수 버전에만 적용한다.
6. 기존 확정 PASS를 재분석하지 않는다. 이번 범위는 범용 OR 엔진, 전 HOLD의 조건부 노출, 지원서 트랙, 새 검수 레인·대시보드를 포함하지 않는다.

필수 인수 사례: 제외업종 `not_in`→`in` 변환의 동일 동작, 특정 트랙 조건의 전역 적용 오류 차단, 순수 가점 억제, 필수조건의 preferred 오분류 차단, unknown/누락/불완전 근거 보존, exact artifact 불일치 차단. 관련 promotion/review 집계 gate와 필요한 typecheck만 실행하고 전체 서비스 suite·build·브라우저·대량 live 품질실험은 실행하지 않는다.

### 기존 P1~P5 결과

- P1: `source_incomplete`만 새로 드러난 보정은 의미 회귀와 분리했다. 역사 run/receipt는 수정하지 않고, 완전한 패스 진단으로 재현되는 경우에만 현행 release admission에서 파생 판정한다. 새 의미·근거 오류와 불완전 진단은 계속 차단한다.
- P2: SHA 검증된 독립 검수 packet의 공통 규칙과 공고별 입력을 stdin으로 전달한다. 중복 파일 읽기 지시를 없애고 공통 prompt를 21,935자에서 14,500자로 줄였으며, 출력 schema·packet SHA·guide SHA·reviewer 결속은 유지했다.

- P4: 최대 100건·동시성 2의 기존 `matching_only` manifest들을 순차 child로 묶는 campaign index와 prepare/status CLI를 추가했다. 인덱스에는 live 권한이 없고 child별 기존 grant가 계속 필요하다. 개별 terminal 결과는 재실행하지 않으며 공유 중단 때 미착수 `skipped`만 재개한다.
- P5: 새 release/대시보드를 만들지 않았다. 기존 다중 receipt release 경로와 기존 관측 artifact를 재사용하며 실제 `lab:promote --write`, 배포, 운영 worker 변경은 이번 구현에 포함하지 않았다.

준비 명령은 `pnpm lab:matching-campaign -- --prepare --as-of=<canonical ISO> --allowed-stage=prepare`이고, 상태 확인은 `pnpm lab:matching-campaign -- --status --campaign=<sha256>`이다. 이 구현 과정에서는 실제 DB snapshot 준비, 모델 호출, grant, launch, lease, 서비스 쓰기를 실행하지 않았다.

최소 검증은 독립 검수 2개 파일, campaign 16개 사례, primary 보정, promotion, current inventory·launch status 계약과 웹 typecheck로 한정했다. 전체 suite·build·브라우저 검증은 변경 위험에 비해 중복이라 실행하지 않았다.

## 1. 결정 요약

목표는 공고를 완벽하게 해석하는 연구 시스템이 아니라, 사업주가 완성한 정보로 지원할 만한 공고를 찾는 서비스를 출시하는 것이다.
**매칭 단독으로 현재 대상 전체를 연속 처리하고, 안전한 결과부터 공급한다. 개별 실패 때문에 전체를 다시 분석하지 않는다.**

대규모 재설계나 모델 교체보다 다음 순서가 효과적이다.

1. 이미 확인한 과잉 보류 두 종류를 국소적으로 교정한다.
2. 검수 입력·도구 왕복을 줄이고 사용량을 기록한다.
3. 현재 재고 전체를 재사용·신규·복구·보류로 빠짐없이 분류한다.
4. 기존 최대 100건 manifest를 연결해 전체 범위를 연속 처리한다.
5. 검수 통과 결과의 release 준비를 진행하고, 별도 승인된 범위만 서비스에 반영한다.

신청서 필드 분석, 전체 22축 확정, 모든 공고 성공, 임의의 성공률 달성을 선행조건으로 두지 않는다.
다만 필수조건 반대 해석, 제외조건 누락, 예외·AND/OR·기간의 잘못된 구조화는 계속 차단한다.
프로필을 완성한다고 잘못 해석한 공고가 올바르게 되지는 않는다. 맞는 공고가 없으면 없다고 안내한다.

## 2. 근거와 아직 모르는 것

아래 실행 수치는 직전 실행 산출물 기준이다. 오늘 전체 DB 재고를 새로 집계한 수치가 아니다.

| 확인한 사실 | 계획에 반영할 판단 |

| matching20: 성공 6·실패 13·마감 제외 1 | 원천 결속 실패와 모델 의미 오류를 구분해야 한다 |
| 실패 13건의 새 결속 복구: 13/13 publishable | 매칭·지원서 분리와 material source 결속은 유지한다 |
| 위 두 실행의 고유 성공 19건 독립 검수: 통과 14·보류 5 | publishable을 곧바로 의미 품질 통과로 취급하지 않는다 |
| 통과 14 중 보정 이슈 카운터로 2건 release 제외 | 실제 잔여 오류와 과거 보정 카운터의 불일치를 고친다 |
| 나머지 12건 release approve 완료, 서비스 쓰기 미실행 | 기존 성과를 재분석하지 말고 별도 반영 범위를 잇는다 |
| 신규 inventory는 최대 100건이며 과거 준비 이력도 제외 | 수백 건 전체 처리를 위해 미착수·복구 대상을 별도 분류한다 |

이 19건은 matching20과 그 실패 복구의 고유 대상이다. 과거 **exact19** 실험과 합산하지 않는다.
현재 지원 가능한 전체 수량, 그중 이미 안전하게 재사용할 수 있는 수량, 실제 신규 모델 호출 수는 준비 시점의 읽기 전용 snapshot에서 확정한다.
과거 537건·84건 등의 수량을 오늘의 모집단으로 사용하지 않는다.

### 검수 토큰 기준선

직전 19건 검수의 완료 이벤트 합계:

- 입력 2,051,512 tokens, 그중 캐시 입력 1,230,208 tokens.
- 출력 41,321 tokens. 입력과 캐시 입력은 중복 합산하지 않는다.
- 완료된 command execution 39회.
- 공통 systemPrompt 21,935자 × 19건. 전체 packet 지침·입력 문자량 768,139자 중 약 54%가 공통 지침이다.

이는 **검수 레인에 한정한 관측치**다. primary 분석 전체 비용이나 보고되지 않은 실패 시도의 사용량을 포함하지 않는다.
문자 수를 토큰 수로 환산하거나, 구독 사용량을 API 청구액으로 환산하지 않는다.
큰 모델을 쓴다는 사실만으로 같은 입력의 토큰 수가 증가한다고 단정하지 않는다. 반복 입력·도구 왕복·보정과 추론 출력은 따로 측정한다.

## 3. 최소 목표 구조

```text
현재 모집·노출·기간·중복 상태 snapshot
  → 대상별 기존 결과·입력 결속 확인
  → 재사용 / 신규 분석 / 실패 복구 / 사유 있는 보류
  → 매칭 primary → 독립 검수 1회 → 통과 부분집합 release
  → 별도 승인된 서비스 반영 → 완성된 사업자 프로필로 추천
```

지원서 native 필드·편집 가능성 분석은 이 경로에 넣지 않는다.
단, 신청서 첨부에 자격조건이 있으면 매칭 입력으로 읽는다. “지원서 트랙 분리”를 “첨부 자격조건 무시”로 해석하지 않는다.
현재 matcher는 필수조건 실패·정보 부족·우대조건을 구분한다. 전체 matcher나 UI를 이번 작업에서 다시 만들지 않는다.

## 4. 구현 패키지

### P1. 실제 오류와 과잉 보류 분리 — 먼저 구현

모델 지정: 구현 `(sol-xhigh)` · 운영 `(astra-medium)` · 의미 계약 인수 `(astra-high)` 1회.
구현자가 수정과 최소 회귀 검증까지 소유한다. Astra 인수는 아래 A/B의 판정 차이를 함께 확인하는 한 번의 검토이며 공고별 추가 검수 레인이 아니다.

**A. 보정 후 source_incomplete를 신규 차단 오류로 세는 불일치**

- 대상: `validated-primary.ts`, `analysis-launch-promotion.ts`와 관련 테스트.
- 현상: 최종 publishable/conditional이면서 잔여 문제가 source_incomplete뿐인데 `blockingNewIssueAfterRepairCount` 때문에 제외된 2건.
- 변경: 이슈 전이와 최종 잔여 이슈 분류를 맞춘다. 새로운 의미 오류·근거 불일치는 계속 차단한다.
- 역사 run/receipt를 수정하지 않는다. 기존 판정 계층에서 exact run/input/validator 결속을 가진 파생 재판정 증거로 복구한다. 모델 재분석은 하지 않는다.
- 최소 검증: 실제 2건 오프라인 재생 + 진짜 신규 의미 오류가 계속 막히는 반례. 역사 실험 판정의 의미를 일괄 변경하지 않는다.

**B. 포털 요약 목록을 필수 추출로 강화한 검수 지침**

- 대상: `independent-review-codex-cli.ts`, `independent-review-packet.ts`, extractor의 관련 계약.
- 현상: 원래 “보존할 경우 open 목록”인 K-Startup `aply_trgt` 규칙이 검수에서 더 강하게 읽힐 수 있다.
- 변경: 원문 모집 자격과 포털 분류 목록을 구분하는 같은 규칙을 추출·검수에 적용한다. 전체 규칙 엔진을 새로 만들지 않는다.
- 해당 단독 finding의 보류 1건은 오판 의심이지 자동 통과가 아니다. 규칙 수정 후 필요한 exact 검수만 새 버전으로 수행한다.
- 다른 실제 오류 때문에 어차피 보류인 공고는 부수적인 finding 하나를 지우려고 재검수하지 않는다.

필수 자격과 무관한 우대·설명 오류도 그대로 노출하지 않는다. 이번에는 자동 부분 삭제·자동 승인 프레임워크를 만들지 않고 해당 대상만 격리한다.

### P2. 같은 모델에서 검수 입력 경량화 — P1과 같은 변경 묶음

모델 지정: 구현 `(sol-xhigh)` · 운영 `(astra-medium)`.
입력·스키마·재시도·사용량 기록이 함께 연결되므로 구현은 xhigh로 고정한다. 의미 규칙을 바꾸지 않는 입력 전달 최적화에는 별도 Astra high 검토를 추가하지 않는다.

- 대상: `independent-review-packet.ts`, `independent-review-codex-cli.ts` 및 두 파일의 테스트.
- 검증한 packet 내용을 stdin으로 직접 전달한다. 파일을 읽으라는 별도 에이전트 지시와 불필요한 파일 탐색 왕복을 없앤다.
- 공통 지침은 짧은 판단 규칙·출력 계약으로 정리한다. 중복 예시·서술을 줄이되 예외·기간·논리 연산·원문 근거 규칙은 보존한다.
- 고정 규칙·스키마를 앞에, 공고별 근거·조건을 뒤에 둔다. 규칙 버전·순서를 고정해 반복 prefix를 안정화한다.
- 사용하지 않는 packet 필드와 중복 직렬화를 제거한다. 조건·원문 근거 식별자는 유지한다. 원문을 단순 글자 수로 잘라 자격·제외조건을 누락시키지 않는다.
- 검수는 primary의 자기 평가·다른 검수 결론이 아니라 원문과 추출 조건을 대조한다. 조건 누락 확인에 필요한 원문 범위를 유지한다.
- 파일 읽기 없이 끝나는 것을 정상 경로로 하되, 지시만으로 도구 호출 0회가 강제된다고 가정하지 않는다. 실제 이벤트에서 호출 수를 관측한다.
- packet/input/model/reviewer 계약 결속과 JSON schema 검증은 유지한다. 기존 실행 권한·보호 설정은 변경하지 않는다.

**호출 원칙:** primary 1회 + 기존 제한 내 필요한 repair + 독립 검수 1회. 동일 결과에 상시 제2·제3 AI 감사 레인을 추가하지 않는다.
정보 부족만으로 이미 conditional인 결과를 더 확신시키려고 반복 호출하지 않는다. 전송 오류 재시도와 의미 보정 횟수를 별도 기록한다.
실패 시도에도 사용량이 있으면 합산하고, 없으면 0이 아니라 unknown으로 표시한다. 구독 창 소진 때 API로 자동 전환하지 않는다.

캐시는 입력 자체를 줄이는 방법과 다르다. OpenAI 공식 문서는 동일 prefix 재사용을 설명하지만 API의 캐시 옵션·가격을 Codex 구독 경로에 그대로 적용할 수 있다고 가정하지 않는다.
이 단계의 목표는 실측 감소이며 “50% 절감” 같은 미검증 수치를 완료 기준으로 약속하지 않는다.

### P3. 전체 재고 분류 — 누락 없는 한 번의 모집단 준비

모델 지정: 구현 `(sol-xhigh)` · 운영 `(astra-medium)`.
재사용·미착수·실패 복구·실제 변경의 분류와 이력 보존을 같은 구현자가 담당한다. 분류 집계 자체는 코드로 수행하며 공고별 분류에 LLM을 호출하지 않는다.

- 대상: `current-inventory-launch-production.ts`, `current-inventory-launch.ts`, 이력 reader와 기존 재사용·복구 경로.
- 모집단: `status=open`, `serving_state=visible`, KST 신청기간 내, 현행 중복 대표 공고 규칙을 만족하는 공고. 당일 마감은 포함하되 표시한다.
- 상태·기간·중복을 읽은 기준 시각과 고유 grant ID를 저장한다. “현재 공고”는 고정 snapshot이지 계속 늘어나는 무한 작업이 아니다.

| 분류 | 처리 |
| --- | --- |
| 현재 입력·계약에 결속되고 검수 통과한 결과 | 분석 재실행 없이 재사용/반영 준비 |
| primary 성공, 독립 검수 미완료 | 기존 결과를 검수만 수행 |
| 준비만 했고 미착수 | 활성 소유·실행 충돌 확인 후 기존 manifest 재사용 또는 새 준비 |
| 실행 이력 없는 신규 | matching_only 신규 준비 |
| 실패한 terminal 대상 | 기존 ancestry를 보존하는 복구 경로 |
| 원문·첨부의 실제 변경 | 해당 공고만 새 입력으로 준비; 이전 성공은 역사 증거로 보존 |
| 의미 품질 보류 | 원인과 다음 조치를 기록; 동일 입력 무의미한 재실행 금지 |
| 원문 없음·마감·비노출·중복 | 사유를 기록하고 실행 대상에서 제외 |

과거 표본의 “전체 역사 제외” 정책은 그대로 보존한다. 이를 운영 전체 재고의 완료 판정으로 재사용하지 않는다.
준비 이력만 있는 대상을 완료로 치거나, 다른 실행이 소유한 대상을 새로 가져오지 않는다.
모든 snapshot 대상은 위 분류 중 하나를 가져야 한다. **전체 수 = 재사용 + 실행 필요 + 사유 있는 보류/제외**의 고유 ID 합계가 맞아야 한다.
준비 시점 오류는 가능하면 해당 공고에 격리한다. 손상된 공통 이력·manifest 때문에 분류를 신뢰할 수 없으면 준비를 중단한다.

### P4. 수백 건 연속 처리 — 기존 runner를 얇게 연결

모델 지정: 구현 `(sol-xhigh)` · 실행 운영 `(astra-medium)` · 변화 없는 감시 `모델 없음`.
lease·grant·중단·재개·중복 실행 방지가 있는 제어 흐름이므로 xhigh를 배치한다. 기존 승인 계약을 변경해야 하는 쟁점이 생길 때만 `(astra-high)`로 판단을 요청한다.

100건 제한을 모든 reader·validator에서 한꺼번에 확대하지 않는다. **최대 100건짜리 기존 manifest들을 순서대로 실행**한다.
추가 산출물은 snapshot과 child manifest 목록을 연결하는 로컬 실행 인덱스다. 새 큐·서버·DB 스키마·독자 승인 체계를 만들지 않는다.

- 전체 exact ID, 하위 manifest SHA, 신규/복구 계보, 모델·프롬프트·계약, 동시성, 허용 단계가 준비 결과에 드러나야 한다.
- 사용자는 이 명시된 전체 범위를 한 번 승인한다. 내부에서는 기존 manifest별 grant를 기록하되 30건·100건마다 사용자에게 재승인을 묻지 않는다.
- runner는 기존 `lab:launch:prepare → lab:launch:grant → lab:launch` 경로를 사용한다. 인덱스 자체에 live 실행 권한을 부여하지 않는다.
- 초기 동시성은 검증된 2로 유지한다. 여러 manifest를 동시에 띄워 runtime lease를 경합시키지 않는다.
- 각 공고 착수 때 지원기간·입력·첨부의 현재 결속은 확인한다. 준비 snapshot만 믿고 마감되거나 변경된 대상을 실행하지 않는다.
- 공고별 failed/held/skipped는 기록 후 다음 대상으로 진행한다. 성공률이 낮다는 이유만으로 전체 정지·재시작하지 않는다.
- 인증·실행 창·lease 무결성 문제는 신규 착수를 중단한다. 정상 종료 뒤 같은 결속의 미완료 범위만 잇고, 비정상 lease 회수는 기존 별도 recovery 경계를 따른다.
- 재개 시 원본 terminal receipt를 읽어 완료 대상을 제외한다. 새 인덱스의 진행 숫자만 믿고 재실행하지 않는다.
- material 계약은 실행 중 동결한다. 운영 중 수정은 다음 revision에서 처리하고, 완료 결과를 버리거나 임의 대체 공고를 넣지 않는다.

앞부분 정상 처리 관측을 실행 준비 점검으로 쓴다. 별도 30건 표본을 만들고 재분석하는 단계를 추가하지 않는다.
준비가 오래 걸려 뒤쪽 공고가 변경되면 해당 target만 변경 사유로 격리한다. 새로운 분석 입력은 기존 승인의 단순 hash 갱신으로 간주하지 않는다.

### P5. 통과 부분집합 공급과 운영 지표

모델 지정: 집계·보고 구현 `(sol-high)` · release 결속/반영 경로의 코드 변경이 필요한 경우에만 구현 `(sol-xhigh)` · 운영 `(astra-medium)` · 정형 인계 작성 `(sol-medium)`.
기존 release 경로로 충분하면 반영 코드는 수정하지 않는다. 일반 집계 구현과 데이터 반영 계약 변경에 같은 모델 강도를 일괄 적용하지 않는다.

- 기존 승인된 12건은 새 검수·분석 없이 반영 후보로 유지한다. 실제 쓰기 직전 현재 DB·원천 결속은 기존 반영 경로가 검증한다.
- 새 통과 결과는 완료된 child 단위로 release 준비·집계·shadow·dry-run을 수행한다. 전체 수백 건의 종료를 기다릴 필요는 없다.
- 이미 승인된 처리 범위 안에서 release revision·내부 역할 분리를 잇는다. material 대상/입력이 바뀐 범위와 서비스 쓰기는 별도로 구분한다.
- `lab:promote --write`, 배포, 운영 worker 활성화는 이 계획 작성이나 모델 실행 승인에 포함하지 않는다.
- 공유 dirty tree 때문에 provenance 검증을 완화하지 않는다. 검증된 exact commit의 격리 작업 공간을 재사용한다.

운영 요약은 한 화면 분량이면 충분하다: 모집단 수, 재사용 수, 신규 성공/실패/보류, 검수 통과, 반영 준비, 실제 serving, 남은 사유.
사용량은 primary/review/repair/전송 재시도별 입력·캐시 입력·출력·가능한 추론 출력·시간을 기록한다.
공고당 사용량뿐 아니라 **실제 공급 가능한 고유 공고당 사용량**도 본다. 동일 성공을 중복 집계하지 않는다.
변화 없는 감시는 스크립트가 담당하고, 사건이 있을 때만 모델을 호출한다.

## 5. 모델 배치와 해석 경계

이번 고성능 GPT 사용 목적은 **판단이 어려운 구조·우선순위를 한 번 정리해 이후 시행착오를 줄이는 것**이다.
채팅/개발 모델 선택과 실제 공고 primary/reviewer 선택은 별개다.
“현재 모델로”를 분석 레인의 전면 GPT 전환으로 확인받기 전에는 기존 실행 모델을 유지하는 것이 기본안이다.

다음 표를 이 계획의 **개발·운영 모델 배정 기준**으로 사용한다. 각 파트의 모델 지정 문구와 동일하게 유지한다.

| 파트 | 구현/설계 담당 | 운영 담당 | 추가 인수 조건 |
| --- | --- | --- | --- |
| 전체 구조·판정 계약 확정 | `(astra-high)` | `(astra-medium)` | 이미 확정된 설계의 반복 검토 없음 |
| P1-A 보정 이슈 카운터 교정 | `(sol-xhigh)` | `(astra-medium)` | P1-B와 묶어 `(astra-high)` 의미 인수 1회 |
| P1-B 포털 메타데이터 규칙 정합화 | `(sol-xhigh)` | `(astra-medium)` | P1-A와 같은 인수에 포함 |
| P2 packet·검수 실행 경량화 | `(sol-xhigh)` | `(astra-medium)` | 의미 계약이 바뀔 때만 `(astra-high)` |
| P3 재고 분류·재사용 | `(sol-xhigh)` | `(astra-medium)` | 이력/재사용 계약 변경 쟁점만 `(astra-high)` |
| P4 기존 launch 연속 처리 | `(sol-xhigh)` | `(astra-medium)` | 승인/lease 계약 변경 쟁점만 `(astra-high)` |
| P5 집계·사용량·진행 표시 | `(sol-high)` | `(astra-medium)` | 정상 집계에 추가 AI 인수 없음 |
| P5 release 결속/반영 코드 변경, 필요한 경우만 | `(sol-xhigh)` | `(astra-medium)` | 반영 안전 계약 변경 쟁점만 `(astra-high)` |
| 문서·정형 인계 | `(sol-medium)` | `(astra-medium)` | 기존 증거 정리, 새 의미 판정 없음 |
| 변화 없는 감시·반복 집계 | 모델 없음, 스크립트 | 모델 없음 | 사건 발생 시 `(astra-medium)` 호출 |

약칭은 아래 exact 모델 ID와 reasoning effort를 뜻한다. 기본값에 의존하지 않고 작업을 배정할 때 둘 다 지정한다.

| 약칭 | 모델 ID | reasoning effort |
| --- | --- | --- |
| `(sol-medium)` | `gpt-5.6-sol` | `medium` |
| `(sol-high)` | `gpt-5.6-sol` | `high` |
| `(sol-xhigh)` | `gpt-5.6-sol` | `xhigh` |
| `(astra-medium)` | `gpt-6-astra` | `medium` |
| `(astra-high)` | `gpt-6-astra` | `high` |

모델 지정은 개발 작업 배정이며 실제 세션 전환이나 모델 실행이 완료됐다는 뜻이 아니다. 가용하지 않은 조합은 임의 대체하지 않고 보고한다.
구현 모델은 관련 테스트와 수정까지 담당한다. 정상 완료된 모든 파트를 Astra로 재검토하지 않는다.
같은 원인이 두 번의 수정·최소 검증에도 해결되지 않거나, 자격 의미·공유 계약·승인 범위의 결정이 필요한 경우에만 `(astra-high)`에 좁은 쟁점을 전달한다. 모델 상향이 새 실행/쓰기 승인을 뜻하지 않는다.
전체 대화 이력을 모든 구현자에게 복제하지 않는다. 담당 패키지·계약·파일·최소 인수 사례만 전달하고 중복 코드 검토를 상시 배치하지 않는다.

이 배정은 작업 위험과 기존 역할 합의를 반영한 프로젝트 판단이며 모델별 절감률을 실측한 결과가 아니다.
OpenAI Docs로 [Sol 모델·effort](https://developers.openai.com/api/docs/models/gpt-5.6-sol)와 [Astra 사용 안내](https://developers.openai.com/api/docs/guides/latest-model)를 확인했다. 공식 안내는 모델 확인에 사용하고, 과잉 검증 방지를 위해 인수 범위는 위 조건으로 제한한다.

**실제 데이터 처리 모델:** 직전 primary는 Claude Opus-5 구독 경로, 독립 검수는 GPT Sol의 Codex 구독 경로였다. 채팅 모델 변경만으로 이 설정이 바뀌지 않는다.
신규 실행의 model/effort/transport는 준비 manifest에 명시한다. primary를 GPT로 통일하기로 선택한다면 adapter·출력 계약 변경을 별도 항목으로 추가하며, 이번 최소 개선의 필수 선행 작업으로 몰래 넣지 않는다.
로컬 구독과 운영 API 경계를 유지하고, 모델 가용성 부족을 임의 상위 모델·API 전환으로 해결하지 않는다.

## 6. 구현 순서와 최소 검증

| 순서 | 끝났다고 볼 증거 | 하지 않을 검증 |
| --- | --- | --- |
| 1. P1+P2 | 실제 과잉 보류 사례/진짜 오류 반례, packet 결속·stdin 전달·출력 검증 | 19건 전체 모델 재분석 |
| 2. P3 | 재사용·미착수·실패·변경·중복의 분류 테스트와 수량 보존 | DB 쓰기·새 전체 품질 실험 |
| 3. P4 | mock runner로 100+1 분할, 완료 건 재개 제외, 개별 실패 계속, 공유 오류 중단 | 테스트용 수백 건 live 호출 |
| 4. 공유 계약 마무리 | 관련 집계 gate 1회; 하위 포함 검증은 재사용 | 동일 SHA의 중복 typecheck/build/전체 suite |
| 5. 전체 exact 준비·승인 후 실행 | 첫 완료 건들에서 출력 결속·사용량 관측 후 같은 cohort 계속 | 별도 표본 생성·매 묶음 재승인 |

prompt/transport 변경의 실제 의미 품질은 오프라인 테스트만으로 완료라고 주장하지 않는다.
새 실행의 통상 독립 검수 결과와 exact disputed target 재검수로 확인한다. 테스트용 검수 레인을 추가하지 않는다.

P1~P4 완료 후에는 작은 품질 개선 아이디어를 이유로 전체 처리를 계속 미루지 않는다.
출시 전 필수 작업은 이 네 패키지로 고정하고, 새로운 발견은 실제 자격 오판·공유 실행 무결성 문제인지 먼저 분류한다.

## 7. 완료 기준과 이번 범위 밖

전체 분석 작업의 완료는 다음을 뜻한다.

- snapshot의 모든 고유 공고가 재사용·실행 완료·사유 있는 보류/제외 중 하나로 설명된다.
- 지원서 작업 없이 matching_only 처리됐고, 성공한 공고를 불필요하게 재분석하지 않았다.
- 통과 결과는 반영 가능한 subset으로 준비됐으며 실제 serving은 별도 수치로 보고된다.
- 입력 부족을 eligibility 확정으로 바꾸지 않았고, 확인된 필수조건 실패는 계속 제외된다.
- 남은 보류는 원인·다음 조치가 있어야 하지만 100% 자동 해결을 요구하지 않는다.

이번에는 신청서 분석 확대, 새 모델 플랫폼, 전면 matcher 개편, UI 리디자인, 새 큐/대시보드, 다중 AI 감사, 임계값 완화, 전 공고 재분석을 하지 않는다.
중장기에는 첫 전체 실행의 실패·사용량 분포를 보고 실제 반복 원인부터 고친다. 모델 다운그레이드 실험은 그 다음이며 출시의 선행조건이 아니다.

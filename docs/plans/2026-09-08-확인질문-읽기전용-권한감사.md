# 확인질문 읽기 전용 권한과 응답 경합 감사

2026-09-08. 기준 `50e8549`. 상태: **읽기 전용 수정·한정 인수·격리 환경 종료 확인 통과**.

[자연 화면 인수](2026-09-08-확인질문-화면인수.md)에서 발견한 viewer 쓰기 컨트롤 문제를
다음 한정 단위로 수정한다. 사용자 지정 sol/xhigh 구현자가 코드·회귀를 담당하고 root가
설계 피드백·독립 감사·실제 화면 인수·문서·커밋을 담당한다.

## 계약과 검증 기준

- 질문 GET의 최신 회사 권한을 명시적으로 반환한다. 기존 서버 PUT 권한 검사는 유지한다.
- 화면은 해당 회사·공고·열림 세대의 조회 성공과 명시적 편집 가능 값이 있을 때만 편집한다.
  로딩·오류·응답 필드 누락·범위 전환에서는 허용하지 않는다.
- 조회 전용도 질문과 저장된 답변을 읽을 수 있고, 읽기 전용 안내와 비활성 선택지를 본다.
- 조회 후 권한 철회로 저장이 거부돼도 실패를 성공으로 표시하지 않으며 다시 쓰기를 막는다.
- 과거 GET/PUT·닫기/재열기·A→B→A·StrictMode 응답은 현재 범위와 구분한다.
- 사용자별 프로필 공유 정책, 회사 역할 캐시, 매칭 준비도·공고 노출 gate는 바꾸지 않는다.

shadcn 및 React 스킬에 따라 기존 Sheet/ToggleGroup을 재사용하고 새로운 디자인 체계를
추가하지 않는다. 공식 [Sheet](https://ui.shadcn.com/docs/components/base/sheet),
[Toggle Group](https://ui.shadcn.com/docs/components/base/toggle-group),
[Alert](https://ui.shadcn.com/docs/components/base/alert) 계약을 확인했다.
agent-browser 스킬에 따라 전용 세션에서 실제 로그인·DOM 조작을 검증하고, PostgreSQL
지침에 따라 exact 격리 DB 원장을 대조한다. 모의 응답 컴포넌트 회귀와 실제 API 인수는 별개다.

## 완료 경계

공유 DTO/인증 화면 변경이므로 관련 회귀·프로젝트 집계 gate·격리 production HTTP/UI 인수를
수행한다. 실행별 소스 해시를 기록하고 같은 소스의 상위 gate에 포함된 검사는 중복하지 않는다.
기존 `apps/web/next-env.d.ts` 사용자 변경과 4010 개발 서버는 보존한다. 원격 DB·OAuth·R2·
모델 실행·승격·배포·원천 정정 관리자 전체 인수·3~6단계는 이 단위의 완료 범위가 아니다.

## 구현 중 독립 감사

GET은 기존 `canWriteCompany(access.role)` 정책을 재사용하고 개인화 응답에
`Cache-Control: private, no-store`를 명시한다. 내부 원장 조회 함수의 반환형은 DTO에서
`canSubmit`을 제외해 읽기 함수가 권한을 임의로 만들어내지 않게 했다.
현재 OpenAPI는 app-v1 경로만 소유하고 web confirmations는 수록하지 않는다. 이 변경을 위해
고아 schema나 신규 app 경로를 추가하지 않으며 기존 명세 검증으로 비회귀를 확인한다.

root는 loaded scope 4종 × status 3종 × open 2종 × 권한 값 6종의 독립 144조합에서
현재 세대·성공한 조회·명시적 true만 허용함을 확인했다(`47142e`). 문자열 `"true"`·숫자 1·
필드 누락도 허용하지 않는다. 이 순수 검사는 실제 DOM 이벤트·인증/DB 인수를 대체하지 않는다.

root의 시트 감사 피드백으로 효과 실행 전 첫 render도 loaded/current scope를 비교해 잠그고,
선택·저장 handler 진입에서도 현재 ref를 다시 비교한다. PUT 401/403이면 현재 scope에서만
편집을 잠그고 미저장 draft를 마지막 GET 답변으로 되돌린다. 멤버십 제거와 역할 강등을 모두
포함하며, 오래된 scope의 권한 오류는 현재 화면을 잠그지 않아야 한다.

초기 route 단위 테스트는 원장 함수의 default DB client 평가 때문에 500으로 실패했다.
테스트 환경에 실제 DB 주소를 주입하지 않고, 인증·원장 의존성을 stub한 별도 HTTP handler
계약 테스트로 분리했다. 이 검사는 역할→권한 필드 투영 및 write guard 호출 경계의 증거이지
실제 인증/DB 권한 증거가 아니다. 분리한 route 및 scope 회귀는 통과했다(`b36d56`).

### 감사 도구 오류와 재실행 구분

editor 첫 저장은 실제 성공했으나 기본정보 0/4인 계정의 프로필 패널이 후속 조회 뒤 열려,
root의 ‘아무 dialog도 없어야 한다’ 대기가 timeout됐다. 재시도에서는 이미 로그인된 `/login`
redirect와 닫히는 패널의 overlay도 도구 대기에 영향을 줬다. 확인질문 패널의 종료·실제 PUT
200·원장 증가를 분리하고, 패널 overlay 제거 및 기존 세션을 확인한 뒤 정상 재실행했다.
이 과정의 revision 3~5 성공 저장과 최종 revision 6 영수증을 구분한다. 실패한 root 도구
실행을 제품 저장 실패나 추가 인수 통과로 세지 않는다. 제품 소스 변경은 없었다.

owner의 기본정보는 4개, editor/viewer는 0개라는 기존 사용자별 portable 프로필 정책도
그대로다. 회사 공동작업의 정보 공유 의미·프로필 패널 재진입 UX는 별도 검토 항목이며,
이 권한 수정에 공유 범위 변경을 섞지 않았다.

## 다음 한정 단위

읽기 전용 결함과 해당 요청 범위의 경합 회귀는 닫고, 다음은 계획 3단계의 **매칭 준비도와
신청서 작성 준비도 분리**다. 특히 검수된 required other/text_only가 사용자 확인 질문에
도달하기 전에 제외되는 경로를 오프라인 사례와 명시적 계약으로 정리한다. 이를 이유로 노출
gate를 임의로 풀거나 실모델 실행·운영 승격을 시작하지 않는다.

실제 로그인은 로컬 합성 Credentials이며 외부 이메일 소유권/OAuth 증거가 아니다. 합성 serving
registry는 실제 release 승인 E2E가 아니다. 원천 정정 관리자 전체 여정·외부 OAuth/R2·자연
설정 페이지의 모든 경합·전체 2단계 및 3~6단계·운영 적용은 별도 경계로 유지한다.

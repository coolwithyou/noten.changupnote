# 신규 공고 딥분석·RHWP 분석시간 단축 구현 계획

작성: 2026-09-11 KST. 전달 대상: **sol-xhigh 구현 세션**.
상태: **구현 계획**. 이 문서 작성으로 코드 구현·새 모델 실행·서비스 반영이 완료된 것은 아니다.

## 1. 구현자에게 전달할 작업 지시

> 아래 증거와 현재 코드를 먼저 대조한 뒤, 승인된 구현 범위에서 딥분석의 불필요한 보정 호출을 줄여라.
> 정규화와 검증의 의미 충돌, 빈 선택 메타데이터, 진전 없는 반복 보정을 우선 수정하고,
> 업력 경계·포털 분류의 정확성, RHWP 결과의 exact 재사용, 단계별 시간 관측을 이어서 구현한다.
> 기존 정상 판정과 fail-closed 실행 경계를 보존하며 오프라인 회귀·관련 집계 gate를 통과시킨다.
> 결과는 검토 가능한 diff, 테스트 증거, 개선 전후 비교, 새 실행을 위한 exact successor manifest로 제출한다.
> 이 계획을 전달받았다는 이유로 live 모델 실행을 시작하지 않는다. 새 material contract의 manifest는
> 사용자에게 대상·RHWP 재사용/신규 분석·모델·동시성까지 보여주고 승인된 후 정식 lab:launch로 실행한다.
> 서비스 DB 승격, release approve, 배포, 운영 worker 활성화는 이번 구현·성능 검증 범위에 넣지 않는다.

구현 세션의 `sol-xhigh`와 실험에서 사용하는 모델은 구분한다. 딥분석·RHWP 분석은
`claude-opus-5 / Claude 구독`, 독립 검수는 `gpt-5.6-sol / ChatGPT 구독`을 유지한다.
모델 변경, 독립 검수 제거, 검증 임계 완화로 시간을 줄이는 계획이 아니다.

## 5. 단계 B — 정규화와 validator의 목록 의미 계약을 일치

최우선 대상은 `deep-analysis/extractor.ts`의 `normalizeCriteria`와 `normalizeCriterionValue`다.
현재 target 이름이 검증된 source span에 포함되면 문자열 규칙으로 `list_semantics`를 다시 계산한다.
이때 `value.note` 일부는 처리하지만 top-level `criterion.note`는 남아 구조 값과 설명이 충돌할 수 있다.

구현 순서:

1. 현행 open/closed 판정 helper와 validator의 의미 모순 검사, repair의 동일 개념 처리를 나란히 정리한다.
2. 작은 공통 판정 함수 또는 기존 helper 확장으로 **원천 종류 + 검증된 인용 + 명시적 제한/예시 + 현재 주장**을 함께 평가한다.
3. 포털 요약 `trgetNm`·기존 K-Startup 요약 필드와 상세 자격 문서의 목록을 구분한다. 단순히 Bizinfo라는 이유로 모든 목록을 open으로 바꾸지 않는다.
4. 명시적 배타·제외 표현은 보존하고, OR 분기는 서로 다른 자격 축을 합치거나 모두 충족해야 하는 조건으로 바꾸지 않는다.
5. raw의 open/closed를 무조건 신뢰하거나, 일반 명사 `업체/농가`만으로 배타성을 확정하지 않는다.
6. 확정할 근거가 부족하면 현행 계약이 지원하는 unresolved/held 경로로 남긴다. 새 enum 도입부터 시작하지 않는다.
7. 판단이 바뀌면 validator가 소비하는 구조 값과 의미 주장 모두 일관되게 구성한다. 모순 note만 삭제해 통과시키지 않는다.
8. 정규화의 semantic 변경 사유를 테스트 가능한 값으로 반환하거나 관측한다. 해당 관측 값을 사용자 서비스 데이터에 자동 저장하지 않는다.

창원시 신청서의 `회사, 조합 및 단체` 문구는 추가 근거 후보이지 공고의 참가 자격과 동일하다는 확정 근거가 아니다.
해당 표현의 적용 범위를 확인하지 않고 eligibility를 넓히지 않는다.

완료 기준:

- 같은 입력을 반복 정규화해도 의미가 다시 바뀌지 않는다(idempotence).
- 창원시 재현에서 코드가 같은 open/closed 모순을 재생산하지 않는다. 최종 open/closed/held 결정의 원문 근거가 설명된다.
- 포털 분류 사례가 통과하고, 상세 자격의 명시적 closed 목록과 exclusion 반례가 유지된다.
- validator의 blocking issue를 완화하거나 오류를 숨기는 식으로 통과시키지 않는다.

## 6. 단계 C — 빈 선택 메타데이터의 결정적 정리

정선군 첫 패스의 `covered_dimensions: []` 하나 때문에 전체 22축 결과를 46.221초 동안 재생성했다.
현재 validator는 해당 키가 없으면 허용하지만, 있으면 올바른 축의 비어 있지 않은 고유 목록을 요구한다.

구현 지침:

1. 기존 `repair.ts`의 결정적 보정 경로와 정규화 순서를 먼저 확인하고 한 경로에 통합한다.
2. **정확히 빈 배열인 optional covered_dimensions**가 어떤 축도 주장하지 않고,
   허용된 criterion 형태이며 다른 근거·OR 의미를 잃지 않는 조건에서만 해당 키를 생략한다.
3. `null`, 문자열, 잘못된 축, 중복 축, 혼합 타입, 비어 있지 않은 유효 배열을 동일한 cleanup으로 지우지 않는다.
4. `DEEP_ANALYSIS_CROSS_AXIS` 관련 prompt에 적용 축이 없으면 키를 생략한다는 계약을 명확히 한다.
5. 수정 전후를 기록하고 전체 validator를 다시 실행한다. 다른 오류가 남으면 정상 repair/held 경로를 따른다.

완료 기준: 정선군 synthetic replay는 fake primary 1회 후 publishable이며 이 형식 오류 때문에 모델 repair를 부르지 않는다.
유효 covered_dimensions와 원문의 복합·OR 조건은 보존되고, 의미 오류를 가진 결과는 여전히 차단된다.

전체 응답 대신 JSON patch를 생성하게 하는 보정 방식은 첫 구현에서 제외한다.
작은 형식 오류를 먼저 제거한 뒤에도 전체 생성 시간이 주요 병목일 때 별도 설계한다.

## 7. 단계 D — 진전 없는 보정을 의미 기준으로 중단

`validated-primary.ts`의 `validationRepairStateSignature`는 Markdown·note·axis comment 등 전체 결과를 포함한다.
창원시처럼 blocking issue와 핵심 값은 같고 문장만 바뀌어도 다른 상태로 판단될 수 있다.

구현 지침:

1. 전체 결과 signature를 일괄 폐기하지 말고, **확실히 비교 가능한 blocking issue 종류**에 한해 의미 진전 비교를 추가한다.
2. fingerprint에는 issue code/path, 해당 criterion의 dimension/kind/operator/핵심 value,
   검증된 source/evidence 결속과 오류에 직접 관련된 의미 주장을 포함한다.
3. 무관한 Markdown·다른 축의 comment 수정은 해당 issue의 진전으로 세지 않는다.
4. note가 의미 검증의 대상이므로 note를 전부 무시하지 않는다. 실제 모순 해소·근거 변경·값 변경은 진전으로 인식한다.
5. 동일 fingerprint가 repair 후 남으면 다음 불필요한 repair를 멈추고 명시적 종료 사유를 남긴다.
6. 비교 규칙이 없는 issue는 기존 제한·종료 규칙을 유지한다. 오류 코드가 같다는 이유만으로 중단하지 않는다.
7. 기존 최대 repair 횟수 2, abort/timeout, source incomplete 처리, target 오류 격리 정책을 유지한다.

주의할 기존 테스트:

- `validated-primary.test.ts`의 `sameIssueProgressCalls`는 축 설명이 바뀌면 세 번째 호출로 진행하는 동작을 명시적으로 허용한다.
- 동일 파일에 과거 seq35 no-progress synthetic fixture가 이미 있다. 이번 사례와 중복 구현하지 않는다.
- 기존 테스트를 단순 삭제하지 않는다. 특정 의미 충돌에만 새 비교를 적용할 경우 이 정상 경로를 유지하고,
  더 넓은 계약을 변경한다면 설명 변경이 실제 진전인 경우와 무관한 경우를 각각 증명한다.

완료 기준:

- 창원시 유형의 진전 없는 synthetic sequence는 primary + 첫 repair 이후 불필요한 세 번째 호출이 0회다.
- 동일 issue라도 핵심 값·검증된 근거·모순 주장이 개선되면 기존 상한 안에서 다음 보정을 허용한다.
- 단계 B로 처음부터 오류가 사라지는 정상 경로와, 오류가 계속될 때 빠르게 실패하는 경로를 별도 측정한다.

## 8. 단계 E — 독립 검수에서 드러난 품질 문제와 입력 준비

### 업력의 엄격한 경계

현재 `packages/core/src/matching/match.ts`의 `evaluateBizAge`는 `min_months/max_months`를 포함 경계로 비교한다.
`operator`만 `lt`로 바꿔도 84개월 포함 문제를 해결한다고 볼 수 없다.

1. profile의 월수 계산과 반올림·정수 여부, 기준일, canonicalization, matcher 소비 경로를 확인한다.
2. 현행 정수 월수 계약이 확인되면 `7년 미만 → max_months=83`, `7년 이하 → max_months=84` 표현을 우선 검토한다.
3. 실제 계약이 날짜 기준의 더 정밀한 판정을 요구하면 조용히 83으로 치환하지 말고 공유 계약 변경 필요성을 분리한다.
4. 원문의 직접 근거가 있는 경우에만 deterministic 정규화/검사를 적용한다. `7년 이내`, `7년차`, 예외 조항을 같은 표현으로 취급하지 않는다.
5. 83/84/85개월, 하한 미만·이상, 예비창업자, exclusion, 복합 기간 조건과 원문 미확인 경우를 회귀 검증한다.

첫 구현은 기존 월수 계약 안에서 해결하는 것을 우선하며 matcher 전면 개편은 하지 않는다.
포털 분류 문제는 단계 B의 공통 판정에서 함께 해결하고 별도 Bizinfo 특례를 중복 추가하지 않는다.

### 상세 PDF 누락

IR클리닉은 상세 지원대상 PDF가 `conversionStatus=skipped`, markdown 없음인 상태에서 region/size `input_missing`이 남았다.
모델을 다시 부르는 것만으로 원문이 생기지 않는다.

- 기존 `inputPreparation`·`pdfTextOcrRecovery.ts`를 먼저 조사한다.
- prepare의 읽기 전용 보고에 문서 역할, 현재 변환 상태, 누락 이유, 관련 축과 recovery 가능 여부를 표시한다.
- 확실하지 않은 문서 역할을 필수 자격 문서로 단정하지 않는다.
- 원문 확보 작업과 모델 repair를 구분한다. 자동 재수집·변환 업로드·DB/R2 쓰기를 이번 단계에 넣지 않는다.
- `input_missing`만 남은 conditional을 전부 차단하는 새 admission gate를 만들지 않는다.
- 원문이 실제 보완되면 input/attachment SHA가 바뀌므로 기존 source binding과 RHWP 재사용 가능성을 다시 확인한다.

## 9. 단계 F — 기존 RHWP 재사용 경로를 필요한 만큼 확장

RHWP 캐시를 새로 만들기 전에 현재 구현을 활용한다.
`application-roundtrip/reuse.ts`는 source·model·transport·contract·engine·artifact hash를 검사하고,
새 LabRun에 `reusedFromRunId`를 가진 artifact를 materialize하는 경로를 이미 제공한다.

현재 제한은 `independent-review-repair-launch-production.ts`에 있다.
`findings.length > 0`인 `reviewRepair`와 source run 일치가 있을 때만 roundtrip reuse binding을 만든다.
따라서 **IR클리닉의 검수 지적 기반 repair**와 달리, **창원시처럼 primary 실패로 검수 defect가 없는 target**은
유효한 필드 분석 결과가 있어도 같은 경로에서 재사용되지 않을 수 있다.

구현 순서:

1. 기존 reviewed repair 사례의 binding과 테스트를 유지한다.
2. primary 실패·application 성공 사례에 필요한 별도 provenance 변형을 설계한다.
   예를 들어 검수 지적 기반 repair와 실패 primary의 유효 application 재사용을 구분하는 discriminated binding을 사용한다.
3. 실제 검수 지적이 없는데 가짜 `reviewRepair`나 aggregate 결속을 만들어 조건을 통과시키지 않는다.
4. manifest 생성·정규화·검증·실행 소비·receipt·관측을 함께 갱신한다. 기존 v1 artifact의 의미를 소급 변경하지 않는다.
5. 이전 source LabRun/RHWP run 및 artifact SHA, grantId, input/attachment/parsed markdown SHA,
   model/transport/field contract/engine, ready 또는 conditional/CONTINUE 상태를 exact 검증한다.
6. unresolved·held·failed application, source drift, 손상·누락 artifact는 재사용을 거부한다.
   manifest가 재사용을 승인한 경우 실패를 숨기고 새 RHWP 모델 호출로 fallback하지 않는다.
7. deep-only 수정과 실제 field runtime 변경을 구분한다. field contract가 바뀌었는데 동일 버전이라는 이유로 재사용하지 않는다.
   반대로 무관한 전체 git SHA 변화만으로 무조건 field 재분석을 요구하지 않는다. 검증 가능한 semantic dependency 결속을 사용한다.
8. 새 결과에는 재사용 출처를 명시하고 기존 run은 수정하지 않는다. RHWP의 역사 duration/usage를 이번 신규 작업량으로 합산하지 않는다.

완료 기준:

- seq 1의 기존 review repair 재사용 경로가 유지되고 seq 2의 적격 field artifact를 정직한 provenance로 재사용할 수 있다.
- 적격 재사용 target의 신규 RHWP 모델 요청은 0회다. primary 딥분석·후속 독립 검수는 정상 실행 대상이다.
- hash/source/contract 불일치 및 held 반례가 모델 착수 전에 거부된다.
- partial 구조 경고와 제외된 입력 위치는 그대로 보존한다. 재사용으로 물리 필드 검수·사용자 문서 UAT가 완료됐다고 주장하지 않는다.

이 단계는 launch 공유 계약에 영향을 줄 수 있으므로 B~E와 변경 단위를 나누어 검토한다.
호환성을 안전하게 확정할 수 없으면 재사용을 강제하지 말고 새 manifest에서 신규 RHWP 분석 필요를 정확히 표시한다.

## 10. 단계 G — 시간을 단계별로 관측

관측 목표는 공고 대기, CLI 슬롯 대기, 실제 요청, 파싱·정규화·검증, RHWP 병렬 시간을 구분하는 것이다.
기존 `analysis-execution-observation.ts`와 transport scheduler를 확장하며 별도의 중복 실행기를 만들지 않는다.

최소 이벤트 필드:

| 분류 | 필드/의미 |
|---|---|
| 결속 | manifest/run/target, request ID, primary/repair/application/review 단계 |
| 시간 | enqueue/start/end ISO 시각, 같은 프로세스 안의 monotonic duration |
| 보정 | attempt, reason, before/after semantic fingerprint, 결과·종료 이유 |
| 재사용 | reused/new, source run/artifact SHA, 이번 신규 요청 수 |
| 신뢰 | sealed receipt 근거인지 별도 observation인지, 누락·불완전 여부 |

- Claude CLI 전체 실행 시간에서 provider 내부 네트워크·추론 시간을 알 수 없으면 합쳐서 기록한다. 추정값을 실측으로 표시하지 않는다.
- 서로 다른 프로세스의 monotonic clock을 직접 빼지 않는다. 집계는 request ID와 명시적 시작/종료 이벤트로 결속한다.
- 기존 receipt가 봉인하지 않은 target 시작으로 계산한 queueWait는 현재 unverified다.
  첫 구현은 append-only sidecar로 계측하고, sealed 증거가 필요하면 receipt 버전을 명시적으로 설계한다.
- 로그 누락을 이유로 정상 분석 결과를 실패시키거나 lease/admission 의미를 바꾸지 않는다. 관측 누락을 따로 표시한다.
- 인증 토큰·계정 credential·전체 prompt를 로그에 남기지 않는다. 재현용 before/after는 허용된 최소 구조와 해시 중심으로 기록한다.
- 미래 실행에서 이벤트를 수집하며 과거 receipt에 타임스탬프를 소급 삽입하지 않는다.

완료 기준: deterministic clock/fake scheduler 테스트로 큐 대기·실행·병렬 중첩·재사용 집계가 검증된다.
wall/work/token 값을 분리하고, 중첩된 RHWP 시간을 중복 합산하지 않는다.

## 11. 검증 계획과 실행 순서

단계별로 관련 테스트를 먼저 실행하고, 최종 동일 source에서 범위에 맞는 집계 gate를 한 번 실행한다.
상위 gate에 포함된 하위 테스트는 같은 source에서 불필요하게 반복하지 않는다.
아래 명령은 작성 시 `package.json`에 존재한다. 실행 전 실제 포함 테스트와 외부 접근 여부를 확인한다.

| 변경 범위 | 직접 검증할 테스트/집계 |
|---|---|
| 정규화·결정적 repair·진전 판정 | `deep-analysis/repair.test.ts`, `validator.test.ts`, `analysis-lab/validated-primary.test.ts`, `extractor-confirmation.test.ts`; `lab:quality:test`, `verify:deep-analysis-contract`의 포함 범위 확인 |
| 업력·목록 매칭 | `pnpm test:matching-unit`, 관련 contracts/canonicalization 테스트 |
| launch·reuse·observation | `pnpm lab:launch:test`, `independent-review-roundtrip-reuse.test.ts`, `deep-repair-runtime-provenance.test.ts` |
| RHWP 재사용 | `pnpm lab:roundtrip:test`, `application-roundtrip/reuse.test.ts`의 실제 포함 여부 확인 |
| 독립 검수 packet | `pnpm lab:independent-review:test`; 이것만으로 repair launch 전체 검증이 되는 것은 아님 |
| transport를 실제 수정한 경우 | `pnpm lab:transport:test`, abort/timeout 관련 회귀 |
| package 출력 일치 | 필요한 package build 후 `pnpm verify:package-runtime-freshness` |
| 공유 계약을 변경한 최종 상태 | 관련 suite + 프로젝트 집계 `pnpm test` |

개별 web 테스트의 기존 실행 형식:

```bash
TSX_TSCONFIG_PATH=apps/web/tsconfig.json node --import tsx apps/web/src/lib/server/analysis-lab/validated-primary.test.ts
```

DB schema 변경은 계획하지 않는다. 실제 구현이 DB 변경을 필요로 하면 로컬 artifact 설계로 해결 가능한지 먼저 검토하고,
필요 범위·migration·PostgreSQL integration 검증을 별도 제시한다. 기존 dirty DB 변경을 이번 성능 수정에 끌어들이지 않는다.
테스트 환경 문제·기존 실패는 재현 근거와 변경 영향 여부를 구분해서 보고한다.

권장 변경 단위:

1. 재현 fixture + 목록 의미 계약 + 빈 메타데이터 정리.
2. no-progress 판단 + 업력 경계 + 입력 누락 관측.
3. RHWP 재사용 provenance 확장과 호환성 검증.
4. 시간 계측 + 최종 집계 검증 + 후속 manifest 준비.

prompt·validator·runtime이 바뀌면 현행 버전 정책에 따라 필요한 material version을 갱신한다.
무관한 모듈의 버전을 일괄 올리거나, manifest 불일치를 피하려고 이전 runtime hash를 사용하지 않는다.
commit 요청을 받으면 이번 범위만 한글 메시지로 commit하고 `Co-Authored-By`를 넣지 않는다.

## 12. 후속 exact 실행 준비와 승인 경계

이번 3건의 원래 승인과 terminal receipt는 역사 증거다.
변경한 prompt/validator/package runtime으로 원래 grant를 재사용하거나 generic CLI로 우회 실행하지 않는다.

### 준비 대상

- **seq 0 정선군:** 독립 검수 지적 0. 기존 성공 결과 보존, 정규화 개선은 오프라인 replay로 검증한다.
- **seq 1 IR클리닉:** 검수 지적 2개를 해결하는 successor 후보. RHWP 재사용 여부와 누락 PDF 상태를 명시한다.
- **seq 2 창원시:** non-publishable 실패를 해결하는 successor 후보. 단계 F의 exact RHWP 재사용 가능성을 확인한다.

새 코드의 관련 gate와 runtime freshness를 통과한 뒤, 기존 aggregate를 검증해서 다음 준비 경로를 사용한다.
아래 `<...>`는 실제 검증한 파일 경로로 치환할 자리이며 그대로 실행하는 명령이 아니다.

```bash
pnpm lab:independent-review:repair:prepare -- \
  --aggregate=<검증한-review-aggregate.json> \
  --original-sequences=1,2 \
  --include-non-publishable=true \
  --concurrency=1
```

이 준비 경로는 현재 `independent-review-repair-launch-cli.ts`에 존재한다.
이번 aggregate의 defect 2개와 non-publishable target을 exact 검증한다.
원래 3건을 신규 재고 selector에 강제로 넣거나 historical exclusion을 끄지 않는다.
마감·source drift로 후보가 부적격이면 임의 대체하지 않고 exact 변경 내용을 보고한다.

사용자에게 제출할 manifest 표에는 다음을 포함한다.

- 전체 manifest SHA, 원래 grant/run/sequence 결속과 변경한 material contract.
- 두 대상의 제목·ID·현재 open/visible·현재 KST 신청기간·당일 마감 여부.
- 현재 input/attachment SHA, source 보완 필요 여부와 이전 값의 차이.
- primary 모델·구독 transport, 독립 검수 모델·구독 transport, 동시성.
- 대상별 RHWP 신규 분석/재사용/불가, source RHWP run·artifact·field contract 결속.
- 예상 신규 호출 범위, 최대 repair 상한, 변경된 종료·재사용 규칙.
- DB 쓰기 상한은 공식 launch의 runtime lease 제어이며 분석 결과는 로컬 artifact라는 점.

승인 후에만 새 manifest의 `lab:launch:grant → lab:launch`와 공식 독립 검수·집계 경로를 실행한다.
정확한 플래그는 현행 CLI usage로 확인한다. target별 추가 재승인을 만들지 않는다.
같은 manifest·material binding의 오류 재시도는 기존 승인 범위 정책을 따른다.

실행 직전 계정·한도와 DB snapshot은 다시 확인한다. 지난 실행의 다음 정보는 현재 잔여량의 증거가 아니다.

- Claude 분석 CLI는 당시 `sw@noten.im` Max였다. Claude Desktop 로그인과 별도로 `claude auth status --json` 및 실제 CLI 계정의 한도를 확인한다.
- ChatGPT 검수는 당시 `sw@ba-ton.kr` Pro였다. 해당 검수 프로세스의 `CODEX_HOME`과 실제 인증 계정을 기준으로 잔여량을 확인한다.
- Claude 자식 환경의 API credential/provider override 제거와 Max preflight를 유지한다. 잔여량을 조회하지 못하면 추정 퍼센트를 표시하지 않는다.
- 마지막 DB 종료 snapshot은 paused/generation 397/owner·expiry 없음/active deep·application lease 0·0이었다.
  새 launch 시 현행 DB snapshot과 cohort lease를 공식 경로에서 검증한다.
- 전용 GCP config의 재인증 만료로 당시 최신 worker 조회는 미확인이었다. 과거 observe_only 기록을 현재 확인으로 바꾸어 쓰지 않는다.
  로컬 target마다 gcloud 재인증을 반복하거나 성능 검증을 이유로 운영 worker를 재배포하지 않는다.

서비스 승격 `lab:promote --write`, release approve, 배포, worker observe_only 해제는 이 후속 실행의 자동 단계가 아니다.

## 13. 개선 효과 판정과 최종 산출물

### 오프라인 완료 기준

| 항목 | 통과 조건 |
|---|---|
| 형식 보정 | 빈 covered_dimensions 사례의 추가 모델 호출 0, 전체 validator 통과 |

| no-progress | 무관한 서술 변경만 반복될 때 불필요한 다음 호출 0, 실질 진전은 허용 |
| 업력 | 현행 월수 계약과 일치하는 strict/inclusive 경계·matcher 회귀 통과 |
| RHWP reuse | 적격 target 신규 field 호출 0, 손상·drift·부적격 재사용 거부 |
| 관측 | queue/execution/work/wall/reuse 집계 정확, 신뢰 수준·누락 명시 |
| 실행 안전성 | 기존 launch admission·Max 인증·lease·오류 격리·불변 artifact 보호 유지 |

### 승인 후 live 비교 기준

1. seq 1의 기존 검수 지적 2개가 해결됐는지 새 independent review로 확인한다.
2. seq 2의 반복 semantic 오류가 해결되어 publishable이 되는지, 새 독립 검수에서 문제가 없는지 확인한다.
3. 원문 미확보로 남는 input_missing/conditional과 미해결 오류를 분리한다. 검수 완료를 RHWP 물리 위치 UAT 완료로 표시하지 않는다.
4. primary/repair/field/review 호출 수와 단계별 시간, 총 wall, 재사용 작업량을 이전 target과 비교한다.
5. 빠른 실패만으로 성능 목표를 달성했다고 하지 않는다. 총 독립 검수 통과 건수와 그때까지의 총시간을 함께 보고한다.
6. successor 2건은 신규 3건 기준선과 작업 구성이 다르다. RHWP 재사용 효과와 primary 수정 효과를 분리하며 단순 batch wall 비율을 쓰지 않는다.
7. 일반 신규 공고의 처리량 개선은 이후 승인한 비중복 신규 cohort에서 같은 모델·동시성으로 확인한다.
   이번 두 건의 재시도를 대규모 성능 실험으로 확대하지 않는다.

최종 제출물:

- 변경 이유와 근거가 연결된 diff 및 관련 코드 위치.
- 실제 artifact에서 추출한 fixture와 synthetic fixture 구분표.
- 수행한 테스트·최종 source/runtime 식별자·미실행 검증 및 남은 위험.
- 오프라인 호출 수·판정 비교 JSON/Markdown, 계측 이벤트 예시.
- exact successor manifest와 대상별 RHWP 재사용 검증 결과, live 승인 전/후 상태.
- live 승인을 받았다면 새 immutable receipt·독립 검수 aggregate·시간 비교·lease 해제 증거.
- 남은 개선 후보는 별도 목록으로 기록: 공고 동시성 확대, 부분 JSON repair, source recovery 실행 등.

# 확인답변 격리 인수

2026-09-08. 상태: **실제 인증 HTTP·DB 인수 및 독립 동시성·장애 감사 통과**. 기준 커밋 `6dea17c`.
자연 UI 전체 여정과 조회만으로 재계산 복구하는 인수는 남아 있다.

앞선 [실제 로그인 기반](2026-09-08-로컬-실로그인-인수.md)을 재사용한다. 사용자는 개발 환경
구성과 필요한 중간 커밋을 승인했다. sol/xhigh는 인수 도구를 구현하고 root는 설계·실행 증거를
독립 감사한다. 기존 `apps/web/next-env.d.ts` 변경은 이번 작업과 커밋에서 제외한다.

## 실행 범위

새 Unix socket 전용 PostgreSQL, 소스 복사본, 임시 비밀번호를 사용하는 실제 Credentials 및
production Next handler만 사용한다. 운영 공고/회사·외부 원문·모델·결제·이메일을 사용하지 않는다.
합성 발행은 실제 plan/publisher를 사용하지만 실제 release 검수·승인 E2E를 의미하지 않는다.
질문 철회를 DB의 `invalidated_at` 직접 수정으로 대체하거나 답변 HTTP handler에 no-op 재계산을
주입하지 않는다. 제품 권한·노출 gate를 테스트 편의로 완화하지 않는다.

## 기대값과 증거 경계

| 항목 | 확인할 불변식 | 현재 상태 |
| --- | --- | --- |
| 저장·재조회 | owner/editor 값·evaluation·revision과 DB 일치; HTTP 200과 재계산 성공 별도 | 통과 |
| 재로그인 | 로그아웃·세션 소멸 후 새 세션에도 같은 회사 답변/revision 보존 | 통과 |
| 회사별 격리 | A/B 서로 다른 답변, A-only editor는 B 조회/쓰기 불가 | HTTP·DB 통과; 늦은 응답 UI는 미실시 |
| 쓰기 거부 | viewer A 403·editor B 403 전후 전체 원장 해시 불변 | 통과 |
| 두 요청 충돌 | 동일 revision에서 하나만 증가, 다른 요청 409 | 실제 동시 PUT 통과; 두 탭 UI 복구는 미실시 |
| 개정·철회·복원 | 바뀐 질문만 재확인, 변경 없는 답변 보존, 수동 철회 후 비수동 질문/답변 유지, snapshot 복원 | 통과 |
| 자연 UI | 실제 목록→질문→저장→재조회 | 미실시: 합성 serving release registry 미구성 |
| 계산 실패 복구 | 저장 성공과 계산 실패 구분, 저장된 답변 보존 | 실제 DB 장애·후속 PUT 복구 통과; 조회만으로 계산 복구는 미실시 |

원장 읽기/쓰기 HTTP 인수, matcher 판정 검증, 자연 UI 인수는 별도 결과로 보고한다.
특히 `match:null`·`refresh.status=failed`인 200은 답변 저장 성공만 뜻한다.
privileged server DB role을 사용하는 이 경로는 NOBYPASSRLS 검증이 아니다.
required other/text_only의 현행 준비도 한계는 후속 준비도 분리의 근거로 남긴다. 이번 합성
공고의 목록 미노출은 serving release registry 미구성으로 기록하며 준비도만의 실패로 단정하지
않는다. 조회 목록만으로 쓰기 권한 또는 늦은 응답 UI 보호를 증명하지 않는다.

## 검증 방법

도구에만 변경이 있으면 해당 회귀·새 실제 HTTP/DB 실행·원본 제품 소스 동일성·diff/문서 검사를
수행한다. 공유 제품 코드 수정이 필요하면 먼저 실패를 재현하고 관련 suite/집계 gate 범위를
다시 정한다. 같은 소스의 이미 통과한 상위 gate를 중복 실행하지 않는다.

PostgreSQL 지침에 따라 거부/충돌 전후 DB 상태와 transaction 종료를 확인하고, codebase-design
지침에 따라 fixture 발행/관측을 좁은 인터페이스 안에 둔다. agent-browser는 전용 세션을 쓰고
검사 후 닫는다. 외부 인증 없이 실제 로그인/로그아웃은 기존
[NextAuth REST 계약](https://next-auth.js.org/getting-started/rest-api)을 따른다.
동시 요청 검사는 [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
동작과 실제 제품 lock/CAS 구현을 기준으로 한다.

## 진행 증거

기준 커밋 `6dea17c`는 이전 검증 소스 107개·관련 문서 6개·실제 로그인 도구 4개를 포함한다.
원본 `next-env.d.ts`는 제외했다. 이전 집계/PG/관련 suite 로그 SHA를 다시 확인했고(`cc8440`),
소스 107개 동일성(`ff9613`), runtime 27개(`10a8f1`), diff·문서 검사를 통과한 후 커밋했다.

첫 fixture 감사에서 임시 root를 prefix로만 확인하던 코드를 exact realpath/소유 marker 검증으로
보완하고, 원장 해시를 값/revision 일부가 아닌 전체 answer 행으로 확장하도록 피드백했다.
root 독립 CLI 검사에서 넓은 root·TCP URL·알 수 없는 action·잘못된 marker 4개를 모두 DB 연결
전에 거부했다(`0713d1`). 이 검사는 DB를 시작하지 않았고 합성 경로만 사용했다.

첫 실제 저장 실행 `cunote-product-uat-pg-Vl6Dy7/receipt.json`은 r1 발행, 질문 2개/답변 0개
조회, owner A의 v2 `satisfied`+legacy `clear` 저장과 재조회를 통과했다(`df5c1b`).
재계산은 기본 제품 경로 그대로이며 `eligible`, `plannedCount=1`, `savedCount=0`,
`status=not_persisted_user_scope`였다. 사용자별 계산 결과를 공용 상태에 쓰지 않는 경로이며
실패나 공용 상태 저장 성공으로 해석하지 않는다. 07:55:48 KST에 PG가 정상 종료됐다(`d48c15`).
이때 제품 코드 diff는 없었다(`dbcddd`). 확장 시나리오의 완료 증거는 후속으로 추가한다.

확장 no-hold 실행 `cunote-product-uat-pg-kvAuKz/receipt.json`은 회사별 분리, editor A 저장,
viewer A/editor B 403와 원장 불변, stale answer 409와 원장 불변, 새 세션의 답변 revision 2,
r2 변경/추가와 legacy 답변 유지, manual 전량 철회·rollback을 통과했다(`94badc`).
source manifest 2,204개 SHA는 `47fc00303f39a1fdac525406ff3dc81699912032879c02d2e7f79fa250865e90`,
root 독립 manifest·권한·workspace 참조 검사도 통과했다(`eb7b5c`).
이 실행의 새 로그인은 아직 기존 세션 logout과 직접 연결되지 않았으므로 후속 실행에서 보완한다.

root의 fixture exact-include typecheck가 통과했다(`66236c`). repo에 보존한 CLI guard 회귀 4개도
root가 재실행했다(`74b0b8`). 이는 root 독립 guard 원본과 별개로 재사용 가능한 회귀다.
기존 runtime 27개(`4da823`)와 제품 소스 107개 동일성(`4da27a`)을 다시 확인했다.

## 최종 실행·독립 감사

최종 no-hold 실행 `cunote-product-uat-pg-FYzS1t/receipt.json`에서 실제 logout→세션 없음→새
로그인 후 답변 revision 2를 확인했다(`a7088b`). root는 helper 추출 중 잘못된 변수 참조를 찾아
수정하도록 했고 수정 후 실제 handler 실행을 통과했다. Node 실행·cleanup은 성공했지만 외부
zsh wrapper가 readonly 변수 `status`를 사용해 exit 1을 낸 기록은 구분한다. 최종 hold wrapper는
`uat_exit`으로 고쳤으며 exit 0이다. 이 차이를 제품 오류나 검증 성공의 누락으로 숨기지 않는다.

최종 hold 실행은 아래 임시 경로에 남아 있다. 임시 산출물은 영구 CI 저장소가 아니며,
`connection.json`은 생성 비밀번호를 포함하므로 출력·커밋하지 않는다.

```text
PG/receipt root:
/private/var/folders/90/3_v527vj59d6wv2ql7_k6rzm0000gn/T/cunote-product-uat-pg-OQTgEu
Source manifest:
/private/var/folders/90/3_v527vj59d6wv2ql7_k6rzm0000gn/T/cunote-product-uat-source-lDc1Wp/source-manifest.json
```

`receipt.json`과 `confirmation-fixture-receipt.json`은 실제 인증 왕복·발행/철회/rollback의
결과다. migration 83개와 packages/web/admin production build를 통과했다. source manifest는
2,205개, SHA `1b47eb3cd4e16fe0d12ecccf4e6f8c1bad3a159b755d99852a40adcddcfbd30c`이며
no-hold와 동일하다. root의 전체 파일·0700/0600·복사본 내부 workspace 참조 검사는 통과했다
(`6548a1`). build로 생긴 복사본의 두 `next-env.d.ts`만 예외이며 원본은 변경하지 않았다.

root는 별도 브라우저 실제 로그인과 독립 SQL로 아래 4개 검사를 통과했다(`82609f`).
증거는 `root-answer-browser-audit.json`, 관측 화면은 `root-answer-surface.png`다.

- 동일 revision 2에서 두 PUT를 동시에 전송해 200/409, 최종 revision 3을 확인했다. 승자의
  `no/unsatisfied`는 실제 matcher의 `fail/confirmed_by_user`, `ineligible`에 반영됐다.
  회사 B 답변은 그대로였다.
- 격리 DB의 `profile_source_corrections`에만 일시 lock을 잡고, 답변 commit 이후 그 조회를
  기다리는 정확한 제품 backend 1개를 식별해 취소했다. 코드 hook/가짜 응답 없이 HTTP 200,
  `refresh=failed`, `match=null`, 저장된 revision 4 보존을 확인했다. lock 해제 후 실제 PUT는
  revision 5·`eligible`로 복구됐다. **이 복구는 후속 저장이며 목록 GET만의 복구가 아니다.**
- viewer의 회사 A PUT 403과 전체 답변 원장 SHA 불변을 확인했다.
- A-only editor의 회사 B GET/PUT 403과 전체 답변 원장 SHA 불변을 확인했다.

## 다음 한정 단위

합성 자료에 정상 serving release registry와 회사 기본정보를 구성한 뒤, 실제 목록→질문→저장→
재접속·회사 전환 UI를 인수한다. 제품 gate는 완화하지 않는다. source/release 결속과 준비도
제외를 각각 관측해 막힌 원인을 분리한다. 늦은 응답·두 탭 충돌 UI, 조회만의 계산 실패 복구,
원천 정정 관리자 화면과 공식 관측 종결도 아직 인수 완료가 아니다.

루트 동시성·장애 브라우저 감사 스크립트는 이번에는 `/tmp` 독립 감사로 실행했으며 repo의
기본 runner에 포함된 회귀라고 주장하지 않는다. 후속 자연 UI 인수에서 재사용 가능한 자동
회귀로 옮길 수 있다. 외부 OAuth/R2, 실제 release 승인 E2E와 사용자 최종 인수는 별도이며,
이 결과를 전체 2단계·3~6단계·운영 출시 완료로 확대하지 않는다.

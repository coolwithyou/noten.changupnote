# 확인질문 자연 화면 인수

2026-09-08. 기준 `4475188`. 상태: **정상 질문 화면의 한정 인수 통과, 조회 전용 UX 수정·늦은 응답 검증 잔여**.

이전 [확인답변 HTTP·DB 인수](2026-09-08-확인답변-격리인수.md)의 다음 단위다.
사용자가 승인한 개발용 격리 환경·필요한 중간 커밋 범위에서 진행한다. 구현은 기존
`gpt-5.6-sol / xhigh`, 설계 피드백·독립 감사·문서는 root가 담당한다.
기존 사용자 변경 `apps/web/next-env.d.ts`와 4010 개발 서버는 보존한다.

## 범위와 성공 기준

기존 Unix socket 전용 PostgreSQL과 production build/start 인수 도구를 확장한다.
정상 serving release 결속과 회사 기본정보를 합성 자료로 구성하되 제품 노출·권한·준비도 gate를
완화하지 않는다. 기존 required other/text_only fixture는 한계 관측용으로 보존하고, 자연 화면에서
질문을 열 수 있는 현행 계약의 사례와 구분한다. 합성 발행 원장은 실제 사용자 검수·운영 release
승인 E2E의 증거가 아니다.

| 검사 | 성공 기준 | 상태 |
| --- | --- | --- |
| 정상 목록 진입 | 실제 로그인 후 `/matches`의 공고 카드에서 질문 열기 | 통과 |
| 저장·목록 반영 | UI 선택/저장 뒤 실제 DB 값·revision 및 목록 판정/건수 일치 | 통과 |
| 재접속 | 화면 재방문과 질문 재진입에서 저장 선택 복원 | 통과; 실제 로그아웃/로그인 포함 |
| 회사 전환 | 설정의 실제 사업자 전환 후 A/B 답변 혼합 없음 | 통과; 늦은 응답 경합은 별개 |
| 두 탭 충돌 | 두 실제 질문 창의 같은 revision 저장은 하나만 성공, 충돌 창 재조회 복구 | 통과 |
| 조회 복구 | 저장 후 계산 실패를 성공 판정으로 표시하지 않고 실제 조회 경로로 복구 | 통과; 추가 PUT 없이 자동 GET |
| 권한 | 조회 전용의 화면 쓰기 동작 및 서버 거부 후 원장 보존 | 서버 403·원장 보존 통과; 쓰기 컨트롤 활성화 결함 |

`/matches`의 정본 데이터 경로는 `/api/web/company-matching`이다. 기존의 직접
`/api/web/matches/:grantId/confirmations` 검증을 자연 UI 인수로 다시 세지 않는다.
늦은 응답 검사는 실제 화면 범위·요청에 한정하고, 페이지 이동으로 기존 문서가 파기된 결과와
같은 컴포넌트의 A→B→A 응답 무효화를 구분한다. 실행하지 못한 항목은 그대로 남긴다.

## 구현·감사 원칙

agent-browser 스킬로 전용 브라우저 세션·실제 로그인·DOM 조작·화면 관측을 수행한다.
생성 비밀번호는 stdin/0600 파일 안에서만 소비한다. PostgreSQL 스킬에 따라 exact 임시 DB의
행과 전체 원장 해시를 확인하고, 장애 주입 시 유한 lock·정확한 backend만 대상으로 한다.
React 지침의 요청 의존성 및 기존 shadcn/Base UI Sheet·ToggleGroup 계약을 확인하되
서비스 디자인을 이 작업 때문에 변경하지 않는다.

공식 구성 문서는 [Sheet](https://ui.shadcn.com/docs/components/base/sheet)와
[Toggle Group](https://ui.shadcn.com/docs/components/base/toggle-group)을 확인했다.
프로젝트는 기존 Base UI 구성 그대로다. 기존 테스트·소스 동일성이 유효한 경우 그 gate 영수증을
재사용하고, 새 인수 도구와 변경된 제품 코드가 있다면 각 영향 범위에 맞게 추가 검증한다.

## 잔여 경계

외부 OAuth/R2·실제 운영 발행·모델 실행·원천 정정 관리자 화면·전체 3~6단계는 이 단위와 별개다.
완료한 한정 결과만 커밋하며 운영 배포 또는 계획 전체 완료로 확대하지 않는다.

## 준비·no-hold 실행 증거

root가 제품 검증 소스 107개를 대조했고 불일치 0이었다(`8cc14c`). 새 fixture는 별도 정상
공고 `40000000-0000-4000-8000-000000000002`에 서울/부산 region required와 preferred
other/text_only 질문을 발행한다. A/B owner가 모두 볼 수 있고 우대 미확인은 자격을 막지 않는
사례다. 기존 #1은 정상 registry도 구성한 뒤 rollback snapshot과 registry after SHA가 같은지
확인한다. #1의 A는 필수 unknown, B는 기존 필수 미충족이라는 서로 다른 상태를 보존한다.

발행 자료는 실제 합성 LabRun/LabReview의 canonical SHA, 현재 source revision, manual revision
선택, before/after snapshot에 결속한다. 원장의 actor·git/build digest·모델 표시는 **합성값**이며
실제 모델 실행이나 release 승인 영수증이 아니다. 실행 소스 증거는 별도 source manifest다.

root의 피드백으로 넓은 원천 결속을 실제 run/review 해시로 좁히고, 프로필 관측시각을 약관
동의 시각과 분리했다. 실제 응답의 `teaser.profileView` 경로 오류도 수정했다.
첫 실행은 postgres-js JSON parameter 인코딩에서 실패해 명시적 JSON 문자열/`::jsonb`로
보완했다. 두 번째 실행은 공용 self_declared 입력이 portable user-answer 정책으로 제외되어
기본정보 known 검사가 실패했다. 이를 제품 gate 완화로 해결하지 않고 owner-scoped 실제
저장 행으로 구성했다. **다른 멤버가 owner의 사용자별 프로필을 공유한다는 증거는 아니다.**

세 번째 실행은 `FINAL_EXIT=0`, migration 83개, packages/web/admin production build와 기존
인증/저장/개정/철회 시나리오, 실제 `/api/web/company-matching`을 모두 통과했다(`882bc2`).
owner의 A/B에서 기본정보 4축 known, #2 `eligible`/질문 1개/답변 0개를 확인했다.


최종 hold도 동일한 2,205개 source manifest로 packages/web/admin build·83개 migration·기존
HTTP 시나리오를 통과했다. root가 복사본 전체 해시·권한·workspace 참조를 독립 재확인했다
(`b3ac66`). 합성 응답 주입이나 인증 cookie 위조 없이 실제 password 폼과 UI 버튼을 사용했다.

장애 주입은 이 실행의 Unix socket DB에만 한정했다. `profile_source_corrections`에 짧은
트랜잭션 lock을 걸고 답변 commit을 독립 확인한 뒤, 해당 lock을 기다리는 exact 앱 backend
하나만 취소하고 lock을 해제했다. 관측 fetch wrapper는 실제 응답을 복제해 읽었으며 대체하지
않았다. 기본 원장 6행과 신규 공고 A/B 2행의 범위를 유지했다. preferred 미충족에서 legacy
`disqualified=true` 저장 필드를 전체 공고 탈락으로 해석하지 않고 실제 matcher 결과와 구분했다.

추가 늦은 GET 검사는 **미완료**다. A의 revision 6 실제 응답 전달을 지연시키고 별도 탭 UI로
revision 7을 저장한 뒤, root helper가 펼친 카드의 메뉴 `aria-expanded=false`를 접힌 카드로
오인해 메뉴 overlay를 열었다. 재진입·오래된 응답 해제 후 상태 보존 검사를 끝내기 전에
600초 hold가 종료됐다. 이는 확인된 제품 race 실패도 통과도 아니며, 같은 회사 닫기/재열기와
in-place A→B→A 경합 모두 후속 검증으로 남긴다. 선택자·탭 ID·브라우저 실행 환경 불일치로
발생한 앞선 root 도구 오류도 성공 영수증과 구분했고, 두 탭 충돌은 정상 재실행으로 확인했다.

hold는 09:20:09 KST 정상 종료, `FINAL_EXIT=0`이다(`c5fa39`). root가 PostgreSQL shutdown
(`e08e04`) 및 57133/57134 listener 0(`d1f699`)을 확인하고 전용 브라우저 두 세션을 닫았다.
기존 4010 개발 서버·사용자 `next-env.d.ts` 변경은 보존했다. 원격 DB·R2·모델·메일·배포는 0회다.

## 감사 판정과 다음 순서

이 단위의 인수 도구는 커밋 가능하지만 **조회 전용 UX를 포함한 전체 인수 완료는 아니다**.

1. 질문 GET이 확인한 최신 회사 권한을 `GrantConfirmationsResult.canSubmit` 같은 명시 필드로
   반환하고 `ConfirmationSheet`의 선택/저장을 읽기 전용으로 만든다. Programs 등에 역할을
   중복 캐시하지 않는다. 서버 PUT 권한 검사는 계속 정본이며 UI 플래그로 대체하지 않는다.
   계약/OpenAPI 사용처·route·component 회귀와 실제 owner/editor/viewer 화면을 검증한다.
2. 늦은 GET 닫기/재열기 및 회사 전환 경합을 별도 유한 실행으로 끝내고, root `/tmp` 감사 중
   재사용 가치가 높은 시나리오를 저장소 자동 회귀로 옮긴다. 현재 6종 독립 증거를 기본 runner의
   지속적인 UI 회귀라고 주장하지 않는다.
3. 사용자별 portable 프로필 때문에 owner는 기본정보 4개, viewer는 0개로 관측됐다. 이는 현행
   정책에 따른 결과이나 회사 공동작업 UX의 의미 검토가 필요하다. 편집 권한 수정에 프로필 공유
   정책 변경을 끼워 넣지 않는다. required other/text_only 준비도 한계는 후속 3단계로 유지한다.

기존 제품 소스 107개의 동일성이 유지되어 직전 관련 suite·PG·집계 gate 증거를 재사용했다.
이번에 전체 `pnpm test`를 다시 실행하지 않은 이유는 제품 계약/코드 변경이 없기 때문이다.
새 도구는 위 실제 production build/HTTP/DB 실행·typecheck·guard 회귀로 검증했다.

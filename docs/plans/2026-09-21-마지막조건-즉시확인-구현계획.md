# 마지막 조건 즉시 확인과 지원 기회 발견 구현 계획

> 2026-09-22 보정: 이 문서는 사용자 화면과 마지막 질문 판정의 상세 명세다. 공급체계 전환의 진행 상태·모델 배정·남은 실행 순서는 [조건 확인 중심 공급체계 전환 종합계획](../research/2026-09-22-조건확인-공급체계-전환-종합실행계획.md)을 정본으로 사용한다. 아래 과거 상태와 P4 체크포인트는 당시 기록이며 T0~T7의 전체 완료를 뜻하지 않는다. 충돌하는 실행 순서와 모델 배정은 종합계획을 우선한다.

작성일: 2026-09-21 KST
상태: 승인된 코드·오프라인·읽기 전용 범위의 구현과 검증 완료. 2026-09-21 P1~P3의 정확한 마지막 질문 증명, 전체 후보 우선 집계, 카드 안 답변·판정·신청 준비 연결을 구현했다. P0/P4는 기존·신규를 구분하지 않는 공통 A~D loader로 현재 재고를 조사했고, 런타임과 같은 질문 적격성 및 최신 serving 결속을 사용한다. 모델 실행·질문 데이터 발행·공고 재분석·DB 변경·배포는 수행하지 않았다.
목표: 사용자가 지원 기회를 먼저 보고, 남은 조건을 목록에서 쉽게 답한 뒤 신청 준비로 이어가게 한다. 기존 모집 공고와 앞으로 유입될 공고에 동일한 규칙을 적용한다.

## 0.1 2026-09-22 P4 전환 확장 체크포인트

P1~P3의 카드 내 질문 왕복을 유지하면서 P4의 기존·신규 공고 준비 경로를 다음 순서로 확장했다.

1. 조건 해소 주체를 `company_profile | user_confirmation | admin_source_review`로 분리했다.
2. 회사 사실 답변은 동일 의미·scope·유효기간일 때만 다른 공고에 재사용하도록 결속했다.
3. 공고 원문 변경은 영향 종류별 최소 단계에서 재개하도록 분류했다.
4. 현재 open·visible·지원기간 내 legacy 질문을 strict v2 노출과 read-only shadow 비교했다.
5. 사람 검수가 가능한 22개 질문만 현재 source revision·criterion·legacy 질문에 결속된 불변 packet으로 만들었다.
6. 관리자 로컬 검수 화면에서 정확한 manifest와 packet 22개를 다시 검증하고, 모든 항목의 verdict·평가 극성·답변 해소 범위를 명시한 content-addressed 결정 세트를 내보내게 했다.

22개는 기존 A~D의 B 완료 공고가 아니다. legacy `yes/no`의 평가 극성과 `company_fact | per_notice`
공유 범위를 사람이 확정해야 기존 deterministic draft와 release 경로로 이동할 수 있는 전환 후보다.
2026-09-22 snapshot에서 22개 모두 exclusion criterion이고, 기존 reusable 표시는 company_fact 11개와
per_notice 11개지만 이 표시는 검수 증거일 뿐 자동 승인값으로 사용하지 않는다. 저장 답변은 0건이다.

다음 순서는 이 화면으로 사람의 명시 결정 수집 → 승인 후보만 기존 v2 draft/release adapter로 변환 → 17개 criterion
구조 수리 → 회사 프로필로 직접 판정할 3개 질문 제거 경로 shadow 검증이다. packet 생성은 질문 발행,
migration, 서비스 DB 쓰기, 모델 재분석을 승인하지 않는다. 이 순서는 아래 P4 원칙인 공통 준비도 함수,
미검수 질문 발행 금지, 부분 실패 격리, 중복 실행 방지를 그대로 따른다.

## 1. 합의한 제품 방향

- 카드의 중심은 공고의 지원 내용, 확인된 조건, 남은 구체적인 질문과 답변 버튼이다.
- 실제로 마지막 질문 하나만 남았다면 “이 조건 하나만 확인하면 돼요”를 보여준다.
- 상세 화면이나 접힌 영역을 열지 않고 목록에서 바로 답한다.
- 답변 후 같은 카드에서 자격조건 충족 여부와 다음 행동을 보여준다.
- 사용자 답변으로 해결할 수 없는 공고 검수 문제는 사용자 질문으로 위장하지 않는다.
- 모든 공고를 동일한 처리 경로로 지원한다는 뜻이지 모든 공고를 질문 하나로 축약한다는 뜻은 아니다.
- 지원 자격조건 충족, 접수 중, 최종 선정, 신청서 작성 가능, 제출 완료는 서로 다른 상태다.

이 문서는 [9월 20일 개선 계획](2026-09-20-매칭-이해와-다음행동-개선계획.md)의 후속 실행 기준이다.
기존 조건 설명·공급·질문·원문 검수 작업을 재사용하고, 목록의 정보 우선순위와 마지막 질문 판정 기준은 이 문서로 구체화한다. 기존 계획 전체가 완료됐다고 간주하지 않는다.

## 2. 확인한 현재 상태와 미확인 사항

첨부 화면에는 후보 8건이 있지만 “자격 충족이 확인된 공고는 아직 없지만”, 큰 답변 저장 안내,
0건 묶음과 접힌 카드가 먼저 보인다. 이 숫자는 해당 화면의 관측값이며 전체 서비스 재고 수가 아니다.

2026-09-21 KST 읽기 전용 DB 조사에서는 `status=open`, `serving_state=visible`, KST 신청 기간 안인
528건을 같은 준비도 함수로 분류했다. 결과는 A 36건, B 0건, C 4건, D 488건이다. 주 blocker는
분석 없음 479건, 첨부 근거 없음 468건, 조건 검수 미완료 13건, 조건 구조 미완료 9건,
source revision 변경 9건이다. 한 공고는 부원인을 여러 개 가질 수 있으므로 blocker 합은 528과 같지 않다.
A는 특정 회사에 대해 “질문 하나만 남음”을 뜻하지 않고, 현재 source·serving promotion·조건·런타임에서
답할 수 있는 reviewed v2 질문 준비가 일치한다는 뜻이다. B가 0건이므로 이번 조사 시점에는 질문만
추가하면 되는 기존 공고가 없으며, C/D는 원문·첨부·분석·검수 보완 없이는 질문을 발행하지 않는다.

## 3. 공통 판정 계약

### 3.1 마지막 질문 후보의 필수 조건

서버의 공통 projection에서 아래 조건을 모두 확인해야 `one_question_away`로 표시한다(명칭은 제안).

1. 현재 신청 가능 기간이고 서비스 노출 가능한 공고다. 기간 불명·마감은 제외한다.
2. 검증된 분석 결과이며 discovery-only, 필수 조건 누락·검수 보류가 없다.
3. 확정된 필수·배제 조건 불일치가 없다.
4. 남은 자격 판정 장애물을 실제 유효한 질문 하나의 답변으로 모두 해소할 수 있다.
5. 질문이 현재 원문 revision·조건·질문 정의/버전과 결속되어 있고 현재 사용자에게 답변 권한이 있다.
6. 허용된 답변 중 적어도 하나를 기존 매처에 적용하면 모든 자격 gate가 통과한다.
7. 뒤에 추가 필수 질문이나 공고 원문 검수가 남지 않는다.

`dimension=1`, `confirmationQuestionCount=1`, 전체 정보 완성도만으로 판정하지 않는다.
같은 축에 독립 조건 두 개가 있거나 OR/AND·예외·배제 조건이 있으면 기존 의미 구조로 평가한다.
우대 질문은 자격 확정에 필요한 질문 수에서 제외한다. 복합 조건을 하나의 예/아니오로 뭉개지 않는다.

가능한 답변의 영향 검사는 모델 호출이나 서비스 DB 쓰기 없이 기존 매처의 순수 평가 경로를 활용한다.
숫자·구간 질문은 대표값 추정 대신 정의된 구간의 의미를 검증한다. 확정을 증명할 수 없으면 일반 질문 후보로 둔다.
질문이 재사용되는 범위에서 계산을 공유하고 목록 카드마다 DB 조회를 추가하지 않는다.

### 3.2 화면용 상태

| 상태 | 표시 | 행동 |
| --- | --- | --- |
| 자격조건 충족 | 조건에 맞는 공고 | 신청 준비하기/신청 방법 보기 |
| 마지막 질문 | 이 조건 하나만 확인하면 돼요 | 질문과 선택지 즉시 노출 |
| 여러 질문 | 확인할 조건 N개가 있어요 | 첫 질문 즉시 노출, 순차 진행 |
| 사용자 질문 + 원문 검수 | 먼저 답할 수 있는 조건이 있어요 | 질문과 별도 남은 검수 내용을 함께 표시 |
| 원문 검수만 남음 | 공고에서 더 확인할 내용이 있어요 | 정확한 문구·원문 위치·확인 방법 |
| discovery/분석 미준비 | 모집 중인 공고 | 원문 보기, 자격 질문 수 추정 금지 |
| 확정 불일치·마감 | 사유와 실제 모집 상태 | 근거 보기·다른 공고 탐색 |

projection은 기존 eligibility/recommendationTier를 덮어쓰지 않는다. `ready`는 신청서 자동 작성 가능을 의미하지 않는다.
공통 계약에는 표시 상태, 실제 남은 질문 수, 대표 질문, 해결 조건 식별자, 추가 검수 여부,
질문 scope/version, 기준 시점과 재판정 freshness를 포함한다. 필요한 필드만 기존 DTO에 추가하고 파생 상태를 새 DB enum으로 저장하지 않는다.

## 4. 화면과 상호작용

### 4.1 첫 화면

- 상단에서 지원 기회와 확인 행동을 함께 제시한다. 큰 저장 완료 안내, 부정적 0건 안내는 제거/축소한다.
- “조건에 맞는 공고”는 존재할 때 노출하고, 마지막 질문 묶음은 접지 않고 상단의 주요 영역에 둔다.
- 마지막 질문 후보가 있으면 “질문 하나로 지원 여부를 확인할 공고 N건이 있어요”를 사용할 수 있다.
- 해당 후보가 없으면 “남은 조건을 확인하고 지원할 공고를 찾아보세요”처럼 실제 상태에 맞게 분기한다.
- 0건 묶음을 숨기고 전체 대조 수·실제 표시 수·질문 영향 수를 구분한다.
- 카드 순서는 자격 충족 → 마지막 질문 → 여러 질문 → 원문 확인 후보를 기본으로 한다.
- 같은 묶음에서는 마감 임박을 우선하고 기존 관련성 순위를 보조로 사용한다. 오늘 마감은 텍스트로 표시한다.
- 질문 계획과 집계는 pagination 이전의 권한 있는 전체 후보에서 수행한다. 상위 8건에 없다는 이유로 마지막 질문 후보를 놓치지 않게 한다.

### 4.2 카드

순서: 공고명·지원 내용·마감 → 확인된 조건 요약 → 남은 구체적 질문 → 답변 선택지 → 원문 근거.
실제 확인된 조건만 요약하며 “다른 필수 조건은 충족했어요”는 3.1을 만족할 때만 사용한다.

- 주 질문과 선택지는 기본 노출한다. 긴 조건 근거와 부가 정보만 접는다.
- 단순 확인은 예/아니오/잘 모르겠어요로, 수치·날짜는 적절한 기존 입력 UI로 제공한다.
- 지역·기간·대상 등 답변에 필요한 맥락을 질문 바로 옆에 제시한다.
- “잘 모르겠어요”에는 실제 확인 방법과 원문 근거를 제공하고 다음 공고를 계속 볼 수 있게 한다.
- 저장 버튼을 추가로 누르지 않아도 명시적인 선택으로 제출한다. 선택 중·저장 실패·재시도를 해당 카드에 표시한다.
- 답변 변경 경로를 제공하고 서버 저장 성공 전 자격 충족으로 낙관적 전환하지 않는다.
- 데스크톱·모바일 모두 카드 제목, 질문, 선택지의 읽기 순서를 유지한다. 버튼은 키보드·터치로 쉽게 조작 가능하게 한다.

### 4.3 답변 이후

1. 현재 질문 binding과 회사/세션 scope로 기존 API에 답변을 제출한다.
2. 서버가 최신 원문·질문 버전을 확인하고 답변을 저장한 뒤 기존 매처로 재판정한다.
3. 해당 카드에 조건 변화와 다음 행동을 표시하고 공통 질문의 영향 공고도 갱신한다.
4. 성공 직후 카드를 다른 위치로 이동시켜 사용자가 놓치게 하지 않는다. 결과를 읽을 때까지 위치·포커스를 유지하고 다음 탐색 시 정렬을 반영한다.
5. 자격조건 충족이면 신청 준비 행동을, 불일치면 해당 이유와 다른 공고를, 모름이면 남은 확인 방법을 보여준다.

저장은 됐지만 재판정에 실패하면 “답변을 저장했어요. 결과를 다시 불러와 주세요”와 재조회 행동을 표시한다.
원문이 변경됐으면 오래된 답변을 판정에 쓰지 않고 최신 질문을 다시 가져온다.
재요청·중복 클릭·네트워크 재시도는 중복 효과가 없어야 한다. 기존 답변 원장은 삭제하지 않는다.

### 4.4 답변 재사용과 로그인

- 회사 공통 사실은 동일한 의미·유효기간·출처 범위에서 여러 공고에 재사용한다.
- 특정 공고의 이전 의사·참여 약속은 공고별 답변으로 유지한다. 질문 문장이 같다는 이유로 합치지 않는다.
- 이미 성공한 동일 의미 질문을 즉시 반복하지 않는다. 범위 질문 이후 정밀 질문 등 의미 있는 후속 질문은 보존한다.
- “모름”은 기존 TTL/재질문 정책을 유지하고 사용자 변경 또는 새 조건을 동일 질문 억제로 가리지 않는다.
- 비로그인에서도 현재 허용된 질문은 바로 답하게 한다. 저장 회사 권한이 필요한 경우 입력 맥락을 보존해 로그인 후 복귀한다.
- 비로그인 답변을 임의 회사에 귀속시키거나 로그인 시 검증 없이 병합하지 않는다.
- 티저·저장 회사 결과·공고 상세가 같은 projection과 판정 결과를 사용한다. 앱 API도 계약 회귀를 확인한다.

## 5. 기존 공고 보완과 신규 공고 처리

### 5.1 기존 공고 준비 상태 조사

P0에서 현재 KST 신청 기간·노출 상태와 최신 source/input/attachment revision을 기준으로 모집단을 만든다.
공고별 준비 상태와 사용자별 남은 질문 상태를 별도로 집계한다.

| 분류 | 상태 | 조치 |
| --- | --- | --- |
| A | 현재 유효한 조건·활성 질문 준비 | 새 UI/공통 projection 연결, 재분석 없음 |
| B | 검수된 조건·근거 존재, 질문 누락 | 기존 deterministic 초안 → 질문 검수 → 기존 release/promotion 경로 |
| C | 원문 존재, 조건 해석·구조·검수 미완료 | 원문 대조와 구조 보완 우선, 필요 부분만 재분석 후보화 |
| D | 원문 변경·첨부 누락·분석 없음 | 최신 원문 확보/변경 범위 분석 경로로 분류 |

보고서에는 기준 시각, 전체 수, 분류별 수, 질문 누락 수, blocker 코드, 원문 revision,
검수/보완 결과를 기록한다. 합계가 모집단과 일치해야 하며 한 공고에 복수 원인이 있으면 주 분류와 부원인을 구분한다.
실제 회사 정보·답변 원문을 보고서에 넣지 않는다. 질문 초안 생성은 활성 질문 발행이 아니다.

### 5.2 신규 유입의 공통 처리

기존 분석·검수 경로에 다음 준비도 검사를 연결한다.

원문 확보 → 기존 분석/구조화 → 조건 검수 → 답변 가능한 조건의 질문 준비도 검사 →
누락 질문 초안 → 질문 의미·선택지 검수 → 기존 승인된 발행 경로 → 최신 매칭 갱신 → 동일 화면 노출.

- 기존 공고 보완과 신규 공고 모두 같은 준비도 함수와 질문 발행 계약을 사용한다.
- 신규 유입 시 기존 질문이 충분하면 생성 단계를 건너뛴다.
- grant/source revision/criterion/question definition 단위로 중복 생성을 방지한다.
- 원문 내용 변경 시 영향받는 질문과 답변의 유효성을 다시 확인하고 stale 매칭 캐시를 무효화한다.
- 관측 시각만 변경된 경우 재분석·재질문을 유발하지 않는다.
- 질문 준비 실패는 해당 공고를 원문 확인 경로로 남기고 이유를 운영 목록에서 추적한다. “하나만”으로 승격하지 않는다.
- 이 연결은 신규 유료 모델 자동 실행이나 observe_only 해제를 뜻하지 않는다. 현재 승인된 분석 경로를 유지한다.

## 6. 구현 작업과 의존성

| 단계 | 작업·주요 파일 | 산출물과 완료 기준 |
| --- | --- | --- |
| P0 | 현재 diff/운영 기준선 확인, 기존 공고 읽기 전용 준비도 조사, 비로그인/저장 회사 경로 대조 | A~D 수량·누락 이유·대표 사례, 수정 범위 확정. 운영 접근이 없으면 조사 미실행으로 명시 |

순서: P0 → P1 → P2 → P3. P4는 P0의 분류와 P1 계약을 토대로 수행하고 P5에서 통합한다.
첫 구현 단위는 P1~P3으로 작동하는 한 질문 왕복을 만든다. P4 없이 전체 기존·신규 공고 지원 완료를 선언하지 않는다.
일반 사용자 디자인 시스템을 유지한다. 새 관리자 검수 UI가 필요할 때만 기존 shadcn 기반 화면을 확장한다.
새 의존성·DB 테이블·별도 질문 엔진은 기존 구조로 해결되지 않는 필요가 입증될 때만 도입한다.

### 6.1 파트별 담당 모델과 reasoning effort

아래 배정은 이 작업의 난도·위험에 따른 실행 계획이며 모델별 가격이나 성능 측정 결과가 아니다.
사용자는 모델별 분담 구현을 요청했으며, 이번 턴의 범위는 계획 업데이트다. 실제 에이전트 착수는 후속 구현 단계에서 한다.
기본 조정자는 `gpt-5.6-terra` / `medium`으로 두고, 기본 실행에서 `gpt-6-astra` 호출은 0회로 계획한다.
현재 세션 모델을 자동으로 변경했다고 간주하지 않는다. 실행 환경이 조정자 모델 전환을 지원하지 않으면
현재 조정자는 짧은 분담·결정·통합 보고만 맡고 실제 구현은 아래 지정 모델에 위임한다.

| 파트 | 담당 모델 | Effort | 정확한 작업 범위 | 검토·승급 기준 |
| --- | --- | --- | --- | --- |
| P0 기준선·준비도 조사 | `gpt-5.6-luna` | medium | scoped diff와 기존 경로 탐색, A~D 읽기 전용 조사 및 미확인 항목 정리 | terra가 모집단·분류 기준만 확인. 스키마 해석이 모호하면 해당 부분만 terra로 이관 |
| P1 공통 판정·DTO | `gpt-5.6-terra` | high | 실제 질문 단위, 마지막 질문 증명, 복합 조건·전체 후보 집계·계약 테스트 | sol/high가 변경된 의미 계약과 반례만 1회 검토. astra는 기본 배정하지 않음 |

sol은 상시 병렬 구현자가 아니라 P1/P2와 P4의 중요한 경계 검토에만 사용한다.
P5에서 P1/P2/P4의 기존 검토를 반복하지 않는다. 새 위험이나 수정된 계약이 있을 때만 해당 부분을 다시 검토한다.
이 배정은 개발 에이전트 모델에 관한 것이다. 공고 분석용 모델·transport·live 실행 권한은 변경하지 않는다.

### 6.2 astra 사용 조건

다음 중 하나가 실제 증거로 확인되고 terra/sol의 제한된 검토로 해결되지 않을 때만
`gpt-6-astra` / `high`를 사용한다. 어려워 보인다는 이유나 최종 확인이라는 이유만으로 호출하지 않는다.

- 복합 조건·예외·배제의 의미에 대해 기존 계약과 신규 판정이 충돌하고, 반례를 만들었지만 해법이 결정되지 않음.
- 회사 소유권·원문 revision·질문 발행 권한 사이의 충돌로 잘못된 자격 확정 또는 데이터 오염 가능성이 남음.
- 같은 재현 실패에 대해 가설이 다른 수정 2회가 실패하고, 원인이 여러 공유 모듈의 계약에 걸쳐 있음.

승급 전 재현 사례, 실패 가설, 관련 함수·diff, 결정이 필요한 질문을 짧게 묶는다.
astra에는 해당 문제의 원인 판정·최소 수정안만 요청한다. 전체 저장소 조사·일상 구현·테스트 로그 정리·상시 모니터링을 맡기지 않는다.
결과는 terra가 구현·검증하고 호출 이유와 해결 결과를 증거 기록에 남긴다.
조건 충족 시 기존 구현 승인 범위 안에서 승급하며, 모델 승급만을 이유로 사용자 재승인을 요구하지 않는다.

### 6.3 토큰과 중복 작업을 줄이는 실행 규칙

1. **필요한 문맥만 전달:** 전체 대화 fork 대신 파트 목표, 관련 문서 절, 소유 파일, 확정 계약, 검증 명령, 금지 사항을 전달한다. 모델/effort 지정 시 `fork_turns=none`을 기본으로 사용한다.
2. **작업당 소유자 1명:** P1의 DTO/core, P2의 답변 경로, P3의 화면, P4의 준비도 경로 소유권을 명시한다. 의존 계약은 담당자에게 요청하고 임의로 동시 수정하지 않는다.
3. **기본 순차 실행:** P0→P1→P2→P3의 의존 순서를 지킨다. P4는 P1 계약 확정 후 파일이 겹치지 않고 독립적으로 진행할 수 있을 때만 P3와 병행한다. 기본 최대 구현 에이전트 2명, 리뷰는 필요한 시점에만 실행한다.
4. **기존 기반 재사용:** 기존 테스트·질문 폼·API·검수·발행 경로를 먼저 읽고 새 엔진·중복 API·범용 프레임워크를 만들지 않는다.
5. **탐색·출력 제한:** 관련 경로를 rg로 좁혀 필요한 함수와 diff만 읽는다. 전체 로그·전체 package.json·전체 기록을 반복 전달하지 않는다. 실패 로그는 원인 구간만 포함한다.
6. **검증 영수증 재사용:** 소스 상태, 명령, 통과/실패, 증거 경로를 기록한다. 같은 상태의 상위 gate가 포함한 검증은 반복하지 않는다. 미커밋 변경이 있으면 SHA뿐 아니라 scoped diff 식별값도 기록한다.
7. **짧은 작업 결과:** 완료 시 변경 파일, 동작 변화, 검증 결과, 남은 blocker, 다음 담당자에게 필요한 계약만 반환한다. 조정자는 구현 내용을 다시 서술하거나 재탐색하지 않는다.
8. **국소 승급:** luna가 의미·권한 문제를 발견하면 해당 부분만 terra로 넘긴다. 같은 실패를 무작정 반복하거나 파트 전체를 astra로 다시 수행하지 않는다.
9. **검증 기준 유지:** 토큰 절약 때문에 7장의 계약 테스트·브라우저 인수·운영 경계를 생략하지 않는다. 자동화 가능한 확인은 모델 추론 대신 도구 결과로 판단한다.
10. **별도 비용 약속 없음:** 사용자가 숫자 예산을 지정하지 않았으므로 토큰 상한·절감률을 임의로 약속하지 않는다. 실행 환경이 제공하는 사용량만 기록하고, 제공되지 않으면 사용량 미측정으로 표시한다.

## 7. 검증 계획

### 7.1 필수 자동 검증 사례

- 마지막 유효 질문 하나, 충족 답변 → 자격 충족·신청 준비 행동.
- 같은 질문의 불충족 답변 → 불일치, 모름 → 미확인 유지.
- 같은 축의 독립 질문 두 개 → 하나만으로 표시하지 않음.
- OR/AND·예외·배제 조건 → 답변 극성과 매처 의미 보존.
- 필수 조건 충족 + 우대 미확인 → 자격 확정 방해 없음.
- 사용자 질문 하나 + 공고 검수 하나 → 마지막 질문 후보 제외.
- discovery·누락 원문·stale 질문·마감·확정 불일치 → 확정 약속 없음.
- 공통 프로필 답변 → 관련 여러 공고 재판정, 공고별 약속은 다른 공고에 전파되지 않음.
- 회사 A→B→A 전환 중 지연 응답, 로그인 전후 전환 → 다른 scope로 결과 누출 없음.
- 저장 성공/재판정 실패·중복 제출·새로고침·답변 변경 → 일관된 저장 및 표시.
- 답변 성공 후 동일 질문 반복 억제, 의미 있는 후속 질문은 유지.
- 질문 없는 신규 공고의 B 분류 → 초안·검수·발행 후 새 UI 연결; C/D는 과장 표시 없이 원문 경로 유지.
- 원문 내용 변경/메타데이터만 변경 → 각각 무효화/유지, 과거 답변 원장 보존.
- pagination 밖 마지막 질문 후보, 전체/표시/영향 공고 수 → 누락·중복 없는 집계.

### 7.2 실행할 검증 조합

변경한 core/컴포넌트/route의 직접 테스트 후 공유 계약 영향에 맞춰 아래 gate를 실행한다.

- `pnpm verify:service-usecases`, `pnpm verify:match-transitions`
- `pnpm test:profile-answer-consistency`, `pnpm verify:match-state-refresh`
- 질문 준비 경로 변경 시 `pnpm test:confirmation-question-draft`
- DTO 변경 시 `pnpm verify:openapi`, 타입/패키지 영향에 `pnpm typecheck`
- 통합 gate `pnpm test:product-journey`; 질문 원장/트랜잭션 변경 시 격리된 DB에서 `pnpm test:product-postgres`
- release 시 프로젝트의 필수 집계 gate 적용. 상위 gate가 포함하는 하위 검증은 같은 소스 상태에서 반복하지 않는다.

현재 문서 작성에서는 테스트를 실행하지 않는다. 구현 시 package.json의 실제 script와 필요한 환경을 재확인한다.

### 7.3 브라우저 인수

기존 실행 서버·포트를 먼저 확인한다. 서버가 없으면 사용자에게 실행을 요청하며 임의 dev 서버를 시작하지 않는다.

비로그인 및 저장 회사 사용자 각각 모바일/데스크톱에서 다음을 확인한다.

1. 첫 화면에서 공고의 지원 내용·남은 질문·답변 버튼이 접힘 없이 보인다.
2. 단일 선택 질문을 목록에서 한 번 눌러 제출하고 같은 자리에서 결과를 읽는다.
3. 충족 결과에서 실제 신청 준비 또는 신청 방법 경로로 이어진다.
4. 부정/모름 답변 후에도 다른 후보 탐색이 유지된다.
5. 로그인 필요 경로에서 입력 맥락·회사 소유권이 보존된다.
6. 긴 한글 질문·버튼 줄바꿈·포커스·키보드·상태 알림을 확인한다. 색상만으로 상태를 구분하지 않는다.

화면 캡처와 실제 저장·재판정 결과를 함께 증거로 남긴다. fixture 검증을 운영 데이터 적용 증거로 대체하지 않는다.

## 8. 적용 범위, 운영 경계와 되돌리기

이 문서 작성 승인은 모델 실행·운영 데이터 쓰기·배포 승인이 아니다. 후속 구현 지시의 승인 범위를 확인해 진행한다.
읽기 전용 조사·오프라인 테스트·초안 준비에는 live 모델 실행 Gate R을 적용하지 않는다.
실제 부분 재분석이 필요하면 대상과 변경 상한을 구체화한 뒤 해당 실행 권한을 따른다.
질문 검수·release prepare/approve와 서비스 반영은 기존 역할·승격 계약을 유지한다.
같은 승인 범위의 재시도나 source ID 갱신만으로 반복 승인을 만들지 않는다.

운영 적용 순서: 코드 검증 → scoped commit/push → 승인된 코드 배포 → 승인된 질문 데이터 반영 →
해당 source의 매칭 갱신 → 실제 고객 경로 스모크. 각 단계의 실행/미실행을 별도로 기록한다.

되돌리기: 새 목록 표현과 projection 소비를 이전 호환 경로로 되돌릴 수 있게 한다.
질문 데이터는 기존 revision rollback 경로를 사용하며 새 답변 원장을 삭제하지 않는다.
원문 revision 무효화·권한 검사·기존 자격 판정은 UI rollback에도 유지한다.

## 9. 성공 기준과 실행 체크리스트

기존 match journey 계측을 먼저 확인하고 필요한 이벤트만 확장한다.
노출된 마지막 질문 카드 수를 분모로 첫 답변률, 답변 성공률, 자격 충족 전환,
신청 준비 진입률과 결과 이탈률을 관찰한다. 질문 revision과 표시 상태별로 나누고 개인 답변 원문은 수집하지 않는다.
오류율·답변 변경률·반복 질문률을 함께 확인한다. 현재 기준값이 없으므로 개선 수치를 미리 약속하지 않는다.

- [x] P0 실제 모집단과 준비도 조사 기록
- [x] P1 마지막 질문의 의미 계약과 pagination 전 전체 후보 집계 검증
- [x] P2 답변 저장·재판정·권한·버전·실패 경로 검증
- [x] P3 카드에서 질문→답변→같은 카드 판정→신청 준비 브라우저 인수
- [x] P4 기존 공고 보완 대상 처리 또는 남은 blocker 명시
- [x] P4 신규 공고도 같은 현재 재고 loader·준비도 계약을 통과하는 fixture 증거
- [x] P5 코드 검증·읽기 전용 데이터 조사·미배포·운영 고객 경로 미실행 상태를 각각 기록

완료는 “문구가 바뀜”이 아니라, 마지막 질문 대상에서 추가 필수 질문이나 숨은 검수 없이 답변 결과를 보여주고,
기존·신규 공고의 준비도 부족을 탐지·보완하는 공통 경로가 작동하는 상태다.

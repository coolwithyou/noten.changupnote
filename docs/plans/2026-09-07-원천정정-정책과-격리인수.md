2026-09-07 사용자가 추천안대로 진행하도록 승인했다. 정책 재확인을 요구하지 않는다.
이 문서는 [제품 여정 인수검증](2026-09-06-제품여정-인수검증.md)의 정책 대기 항목을 대체한다.

2026-09-08 추가 승인: 사용자가 개발 단계의 배포·가상 테스트환경 구성을 자율에 맡겼다.
환경 준비는 더 이상 사용자 입력 대기로 두지 않는다. 우선 [로컬 실제 로그인 인수](2026-09-08-로컬-실로그인-인수.md)를

## 확정 정책

- 직접 입력 정보는 사용자가 수정하고 재매칭한다. 모든 입력을 관리자 승인제로 만들지 않는다.
- 공식 API·공개명단의 값은 사용자 주장으로 덮어쓰지 않는다. 접수 당시 값·출처·기준일과
  사용자 설명을 별도로 저장한다. 설명만으로 자격 충족·탈락을 확정하지 않는다.
- 정정 검토 중인 축만 매칭의 `unknown`으로 처리한다. 다른 조건 평가와 신청서 준비는 계속
  가능하다. 해당 축의 기존 공고별 자기 확인 답변으로 정정 보류를 우회하지 않는다.
- 공식값 교체는 공식 원천의 갱신 또는 원문으로 증명되는 내부 수집·해석 오류 수정에 한정한다.
  내부 오류는 기관 자체의 갱신을 기다릴 필요가 없다. 임의 관리자 입력은 공식 관측값이 아니다.
- 기존 운영자의 `support/admin/owner` 역할이 검수한다. 별도 조직·상시 이중 승인제를 만들지 않는다.
- 접수·검수 완료·기관 갱신·최종 신청 제출은 서로 다른 상태다.

## 구현된 처리 흐름

1. 저장한 회사의 편집 권한으로 `/support/source-corrections?companyId=...`에서 정정 요청을 제출한다.
   서버가 읽은 공식 스냅샷과 기존 문의 티켓을 한 트랜잭션으로 저장한다. 같은 사용자·회사·축의
   진행 중 요청은 재시도 시 재사용한다. 변경된 설명은 기존 티켓의 후속 메시지로 전달하거나
   요청 철회 후 새 요청으로 접수한다. 최초 설명을 조용히 덮어쓰지 않는다.
2. 관리자 `/source-corrections`에서 검토 시작 또는 원천 확인 대기로 처리하고 공개 사유를 기록한다.
3. 기관 정보 갱신·공개명단 갱신·내부 처리 오류 수정은 기존 원천 수집/갱신 경로로 수행한다.
   이 정정 화면은 임의 값 편집기나 모든 원천을 강제 새로 수집하는 버튼이 아니다.
4. 요청자가 `서비스 보유 원천 재확인`을 실행하면 서버가 현재 공식 자료를 다시 읽어 관측 스냅샷을
   보존한다. 외부 유료 API 호출, 원천 캐시 무효화, 기관 정보 수정은 실행하지 않는다.
5. 관리자는 검토 중 상태에서 동일 원천의 갱신된 관측값이 있을 때만 `갱신값 검수 완료`할 수 있다.
   근거가 부족하거나 원천값을 유지해야 하면 사유를 안내하고 종결한다. 완료 버튼은 회사 값을
   직접 쓰지 않으며, 이미 원천 경로로 반영된 값을 검수한다.

상태: `open → reviewing ↔ waiting_source → resolved|rejected`, 사용자 `withdrawn`.
버전 충돌은 409로 처리한다. 최초 스냅샷·설명은 수정 불가, 이벤트는 exact revision으로 한 건씩
추가한다. 원장 보존은 무기한 개인정보 보존을 뜻하지 않으며 회사/계정/문의 삭제의 기존 FK
cascade 경로를 따른다. 사용자 DB 역할은 자신의 요청만 읽고 직접 원장 쓰기는 할 수 없다.

일반 문의의 resolved 상태를 원천 정정 완료로 소비하지 않는다. 별도 정정 원장의 상태가 정본이다.
운영자의 처리 사유는 정정 원장과 기존 문의의 공개 메시지에 함께 남기며 이메일 자동 발송은 없다.
현재 정정 화면에는 별도 증빙 파일 업로더를 추가하지 않았다. 기존 문의 첨부 경로는 남아 있고,
그 파일 자체를 공식값으로 승격하는 기능은 제공하지 않는다.

현재 제공하는 공식 값·제공자·완전성이 검수된 스냅샷과 달라지거나 관측 시각이 과거로 돌아가면
해당 축은 다시 확인 필요가 된다. 같은 사실을 최신 시점에 재확인한 경우는 보류를 재개하지 않는다.
새 정정 요청은 같은 요청자·축의 역사 요청을 대체하며, 다른 요청자의 열린 정정은 유지한다.
읽기 중 정정 원장을 조회하지 못하면 정상 판정으로 후퇴하지 않고 요청을 실패시킨다.

### 후속 질문 기능의 최소 인수 시나리오

아래 표는 최초 계획 당시 모두 `UNEXECUTED`였던 전체 인수 기준이다. 2026-09-08 후속
[확인답변 격리 인수](2026-09-08-확인답변-격리인수.md)에서 실제 인증 HTTP·DB의 저장·복원·
회사별 격리·권한 거부·동시 409·개정/철회/rollback은 통과했다. 실제 DB 장애 후 답변 보존과
후속 PUT 복구도 확인했지만 **조회만의 복구·자연 UI·늦은 응답·두 탭 UI는 미실시**다.
sol/xhigh 구현과 root 독립 감사의 exact 소스·migration 83개·합성 fixture 결속은 위 문서에 있다.

| 시나리오 | 실제 계정 인수에서 확인할 결과 |
|---|---|
| 저장·즉시 재조회 | owner/editor 답변 값·revision·판정·근거 일치. 우대만 미확인이면 자격을 막지 않고 관리자 확인은 사용자 답으로 우회하지 않음 |
| 재계산 실패 복구 | 격리 환경에서만 실패를 주입. 저장된 답변은 유지되고 stale 판정을 성공처럼 내지 않으며 재조회로 복구 |
| 로그아웃·재로그인 | 새 인증 세션에서 같은 회사의 답변·revision·판정 복원 |
| 회사 전환 | A+B owner가 A→B→A 전환해도 회사별 답변이 섞이지 않음. 전환 전 늦은 응답이 현재 화면을 덮지 않음 |
| 조회 전용·오소속 | A viewer의 A 쓰기, A-only editor의 B 조회/쓰기는 거부. 원장·답변 revision은 불변 |
| 두 탭 충돌 | 같은 revision N에서 첫 저장만 N+1, 두 번째는 409. 재조회 후 최신값을 표시하고 과거 답변을 덮지 않음 |
| 개정·철회·되돌리기 | 합성 r1→r2→전체 철회를 명시 선택. 변경 없는 질문/답변은 유지, 변경된 질문은 재확인, 철회된 질문은 비활성화. 비수동 질문·답변 이력을 보존하고 rollback으로 이전 snapshot 복원 |

질문을 읽은 뒤 source/definition이 바뀌거나 철회됐으면 과거 화면의 저장이 거부돼야 한다.
원천 정정의 접수→검수→공식 관측 기반 종결은 기존 인수 기준을 그대로 이어간다.
required other/text_only의 현행 준비도 제외에 걸리면 해당 자연 UI 여정은 막힌 것으로 기록한다.
테스트를 통과시키기 위해 노출 gate를 완화하거나, 직접 API 검증을 자연 UI 인수로 대체하지 않는다.

gitignored `.env.product-uat.local`에는 운영 파일을 통째로 복사하지 않고 아래 필요한 값만 구성한다.

주입값·원격 DB 상태는 이 정적 검사로 증명할 수 없으므로 실제 연결 후 별도 검증한다.

## 검증 및 인수 기준

- 정책 단위: 원천값 보존, 해당 축 unknown, 다른 조건 정상 평가, 사용자 주장/과거 원천 반려,
  내부 오류 수정 관측 검수, 검수 후 원천 불일치 보류.
- PostgreSQL: 81개 migration, 중복 접수, 역할·회사 격리, 직접 SQL 쓰기 차단, 이력 변조 차단,
  관리자 실제 트랜잭션의 exact revision 경쟁·공개 사유·문의 동기화.
- 제품 집계·매칭·프로필 경로·migration 검증 결과는 후속 영수증에 기록한다.
- 현재 웹 서버에서 비로그인 정정 진입이 callback을 보존한 로그인 화면으로 이동함을 확인했다.
  활성 정정 화면의 시각 QA·실제 OAuth·R2·기관 양식 다운로드 인수는 아직 수행하지 않았다.

최종 인수는 정보 완성 → 매칭 이유 확인 → 정정 접수·검수 → 신청서 수정·저장 → 로그아웃 →
재로그인 → 회사 전환 → 문서 재개·다운로드를 지정 계정으로 끝까지 수행하는 것이다.
조회 전용·다른 회사·과거 revision 요청은 쓰기 없이 거부되어야 한다.

공식 참고: [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html),
[Supabase 프로젝트 CLI](https://supabase.com/docs/reference/cli/supabase-projects-create),
[R2 버킷 한정 토큰](https://developers.cloudflare.com/r2/api/tokens/).

## 1. 목표와 범위

목표는 **사용자가 사업자 정보를 완성할수록 근거 있는 판정이 늘어나고,
검수된 공고가 신청서 준비 상태와 독립적으로 매칭에 공급되는 제품**이다.
분석량·구조화율·적격 공고 수 자체를 높이는 것이 목표는 아니다.
정보가 완성되어도 부적격일 수 있으며, 공고 원문이 불명확하면 미확인을 유지해야 한다.

이번 계획은 다음 세 결과물을 순서대로 만든다.

1. 원문 → 분석 → 매칭용 조건 사이에서 의미가 보존되는 변환·검증 경로.
2. 공통 사업자 정보와 공고별 확인을 구분하고, 답변 후 판정·근거가 일관되게 갱신되는 흐름.
3. 검수·승격·노출을 연결해 실제 공급량과 대량 처리 효율을 설명하는 관측·운영 절차.

포함하지 않는 일:

- 22축 전부 확정을 서비스 진입 요건으로 만드는 변경.
- 서술형·불명확한 조건의 자동 통과, 사용자 주장으로 공식 원천 덮어쓰기.
- 모든 복합 조건을 표현하는 새 범용 규칙 언어, 분석 플랫폼 전면 재작성.
- 기존 불변 receipt 수정, 과거 분석의 일괄 재실행·운영 데이터 일괄 덮어쓰기.
- 승인되지 않은 live 모델 실행·승격·배포·worker 활성화.

## 3. 실행 순서와 의존성

### 후속 리뷰 반영 — 2단계 완결 전 보완 순서

1. **재계산 결과 최신성 보장**: 답변 저장 CAS와 별개로, 계산에 사용한 답변·회사정보·공고
   입력을 결과 저장 시 검증한다. 이전 계산이 늦게 완료되어 최신 판정을 덮는 순서를 차단한다.
   공용 저장 경로와 직접 호출자를 조사하고, 오래된 결과의 거부를 저장 성공 건수에 넣지 않는다.
   답변 저장 성공 이후 재계산 실패는 답변 저장 실패와 구분하며 stale 카드를 성공 응답으로 내지 않는다.
   실제 PostgreSQL의 `write:true` 경합과 운영용 재계산 orchestration을 테스트한다.
   새 DB 컬럼만 추가했다고 구버전 writer에 이 보호가 생기는 것은 아니다. 운영 적용 시에는
   migration과 보호된 writer 배포를 결속하고 구버전 갱신 실행이 남지 않았는지 별도로 확인한다.
   상태: **코드·자동 검증 및 독립 감사 통과 / 운영 미반영**. 입력 revision은 별도 원장으로
   보관하며 실제 사용자 owned_read의 개인화 계산은 공유 상태에 쓰지 않는 기존 경계를 유지했다.
2. **행동 분류와 질문 UI 연결**: 회사 공통정보·공고별 사실·관리자 원천 검수를 구분하여
   실제 화면 행동으로 연결한다. 우대 질문은 자격 조건을 막지 않으면서 적격 카드에서도 답할 수 있게 한다.
   상태: **코드·자동 검증 및 독립 감사 통과 / 실제 계정 인수·운영 미반영**.
   미확인 사유 5종을 ruleset v12와 화면에 결속했다. 우대 질문 진입·부분 답변 뒤 질문 유지·
   stale annotation 제거·혼합 hard admin 조건의 잘못된 확정 약속·StrictMode 응답 누락을 보완했다.
   `needs_core_review` OPS 재고 비노출 정책은 유지한다.
   검수된 질문이 있어도 required other/text_only가 annotation 이전에 제외되는 현행 한계는
   후속 준비도 분리에서 별도로 다룬다. UI가 질문을 열 수 있다는 증거와 실제 노출 admission을 구분한다.
3. **동일 run 질문 개정·철회**: 기존 run/질문 artifact를 보존하고 상위 질문 개정본을
   exact release에 결속한다. 문구 수정 때문에 모델을 재실행하거나 원본 파일을 덮지 않는다.
   상태: **코드·자동 검증 및 독립 감사 통과 / 실제 계정 인수·운영 미반영**.
   연속 revision·정확한 부모/run/hash 검증·전체 활성 snapshot·명시적 철회와 release 선택을
   구현했다. 최신본 자동 채택은 없고 역사 release의 SHA-only/선택 부재 의미를 유지한다.
   launch 선택 결속은 합성 cohort로 검증했다. deep-repair는 기존 suite와 공유 resolver 감사
   범위이며 실제 역사 receipt 전체 E2E는 남아 있다.
4. **실제 인수 후 3단계**: 격리 계정으로 저장·재접속·회사 전환·충돌 복구를 확인한다.
   계정/환경이 없으면 해당 인수만 미완료로 명시하고 운영 환경으로 대체하지 않는다.

현재 runtime과 다른 primary snapshot은 계속 fail-closed한다. 5단계 자산 공급 전에
모델 무호출의 현행 재검증 증거를 별도로 봉인하는 경로를 마련한다. 과거 snapshot을 재작성하거나
버전 일치 검사를 완화하는 방식은 사용하지 않는다.

위 구현은 기존 지정 `gpt-5.6-sol / xhigh`, 주 에이전트는 설계 피드백과 독립 감사를 맡는다.
이번 승인은 로컬 구현·검증 범위이며 운영 migration·승격·배포·live 분석 권한은 포함하지 않는다.

기본 순서는 **0 → 1 → 2 → 3 → 4 → 5 → 6**이다.
0단계의 관측 기준을 전 단계에서 재사용한다. 4단계 조회 개선은 1단계 이후 독립적으로 먼저 처리할 수 있지만,
편의상 그것만 완료하고 사용자 확인 흐름을 뒤로 미루지 않는다.
5단계의 읽기 전용 자산 조사는 먼저 수행할 수 있으며, 실제 반영은 관련 계약·인수 검증 이후다.
각 단계는 독립적으로 검증 가능한 변경 단위로 나누고, 코드·자동 검증·실제 인수·운영 반영 상태를 따로 기록한다.

### 0단계 — 재현 사례와 관측 기준선 고정

변경 범위:

- 임시 진단 코드의 필요한 부분을 재현 가능한 오프라인 테스트/보고 도구로 옮긴다.
  원본 run·receipt는 수정하지 않고 grant/source revision/manifest/run hash와 선택 이유를 기록한다.
- kind 변경, 동일 근거의 다른 조건, 3년 미만 경계, 시군구·지사 OR, 현재 제재/과거 위반,
  필수 서술형 확인, 원천 정정 상태를 최소 회귀 사례로 고정한다.
- 각 사례는 원문 근거로 정한 기대값과 충족/불충족/정보 부족 회사 입력을 갖는다.
  기대값을 현행 matcher 출력에서 자동 생성하지 않는다.
- 저장소에 넣는 fixture는 필요한 최소 조건·근거·합성 회사만 포함한다.
  운영 자격증명·사용자 개인정보·원문 전체를 fixture에 복제하지 않는다.
- 실행 성공, 변환 통과, 독립 검수, 승격, 노출의 분모·식별자·시각을 먼저 정의한다.

완료 기준:

- 네트워크·모델 호출·DB 쓰기 없이 리뷰의 핵심 오류를 재현한다.
- receipt를 합산할 때 skipped가 이전 terminal 결과를 지우지 않으며, 후속 보정의 원본 관계가 구분된다.
- 최소 하나의 사례가 현재 동작과 제품 규칙의 차이를 드러낸다. 알려진 실패를 기존 정상 suite에 방치하지 않고
  수정과 회귀 테스트를 같은 구현 단위로 연결한다.

### 1단계 — 조건 의미 보존과 매칭용 변환 검증

주요 위치:

- `packages/core/src/bizinfo/llm-criteria.ts`
- `packages/core/src/criteria/canonicalize.ts`
- `apps/web/src/lib/server/analysis-lab/shadow-convert.ts`
- `apps/web/src/lib/server/analysis-lab/validated-primary.ts`
- `apps/web/src/lib/server/analysis-lab/analysis-launch-promotion.ts`

작업:

1. 예약 축·근거 부족에 따른 강등에서도 required/preferred/exclusion을 보존한다.
   원래 축·연산자·근거와 강등 사유를 남기고, unknown을 필요한 조건에만 적용한다.
2. 중복 검사를 근거 문장만의 동일성으로 해결하지 않는다. 같은 문장의 필수/우대·서로 다른
   원래 축은 구별하고, 정말 동일한 조건만 의미·질문 연결을 유지하며 합친다.
   허용할 수 없는 충돌은 정확한 항목과 사유를 반환하며 조용히 삭제하지 않는다.
3. 분석 결과 → 실제 matcher 입력을 만드는 변환·진단 인터페이스를 한 곳에 둔다.
   primary 이후 오프라인 점검, shadow, promotion이 같은 변환 결과를 사용하도록 한다.
   기존 함수를 재사용·통합하며 동일 규칙의 별도 validator를 추가하지 않는다.
4. 의미 변경·탈락·강등의 항목별 보고를 반환한다. 표현만 낮춘 정상 강등과
   필수 조건 손실·우대의 배제 전환 같은 오류를 구분한다.
   기존 release 품질 검사에 연결하되 새 사용자 승인 절차를 만들지 않는다.
5. matcher/변환/실행 provenance 중 실제 변경된 계약만 버전을 갱신한다.
   영향 있는 저장 결과·캐시를 식별하며 무관한 git SHA 변화로 전체 재분석을 요구하지 않는다.

완료 기준:

- 고정 표본에서 승인 없는 kind 변경 0개, 무보고 조건 탈락 0개.
- 우대 정보 미확인만으로 eligibility가 conditional/ineligible이 되지 않는다.
- 필수 불일치·확정 결격은 유지되고, unknown은 자동 pass로 바뀌지 않는다.
- 변환 오류 사례는 의미 보존 결과 또는 항목별 명시적 보류로 설명된다.
- 변환 전후 실제 matcher 판정 차이는 회귀 정답에 의해 설명되고 예상 밖 차이 0개.

출고 범위: 변환기·검증·테스트만 먼저 반영 가능한 단위. 운영에 저장된 과거 조건 변경은 5단계에서 별도 취급한다.

### 2단계 — 필수 조건 확인과 사업자 정보 완성 연결

주요 위치: contracts의 확인 답변 DTO, `packages/core/src/matching/match.ts`,
`analysis-lab/promote.ts`, 웹의 공고별 질문 저장·조회 및 프로필/매칭 결과 경로.
기존 질문·답변 저장소를 먼저 확장하고 병렬적인 새 답변 원장을 만들지 않는다.

첫 구현 단위는 **검수자가 명시적으로 작성한 공고별 단일선택 v2 질문**의
발행→저장→조회→매칭 왕복이다. 기존 모델의 자동 질문 생성은 legacy exclusion 계약을
유지하며, 새 관리자 질문 편집 GUI나 모든 서술형 조건의 자동 질문화는 포함하지 않는다.
회사 공통정보·원문 모순·근거 미확정 조건은 이 수동 경로로 우회하지 않는다.
2a 평가 계약, 2b 원장/권한/버전 결속, 2c 수동 발행 및 사용자 화면 연결로 나누어 검증한다.
실제 로그인/재접속/회사 전환 인수는 격리 계정과 환경을 연결한 후 별도 완료 판정을 한다.
최초 수동 발행·저장·조회·매칭과 publication/rollback은 자동 검증 및 독립 감사를 통과했다.
현재 CLI는 최초 파일과 같은 run의 수동 질문 개정·추가·부분/전체 철회를 지원한다.
기존 불변 파일을 유지하며 상위 artifact를 exact release에 선택/결속한다. 행동 분류 UI도 연결해
검수 대기·원천 정정 unknown을 회사정보 보완으로 잘못 안내하는 문제를 보완했다.
두 단위의 코드·자동 검증은 통과했으나 실제 격리 계정 인수는 남아 있다. 이를 확인한 뒤 3단계로 간다.
required other/text_only가 annotation 전에 제외되는 OPS 준비도 한계는 3단계에서 별도로 다룬다.
입력 형식과 제한은 [수동 질문 운용 안내](../explainers/검수된-공고별-확인질문-v2-발행.md)를 따른다.

작업:

1. 먼저 필수 서술형 조건을 세 종류로 분류한다.
   **회사 사실로 판단 가능 / 공고별 사용자 확인 가능 / 원문·관리자 확인 필요**.
   분석 누락·근거 충돌을 사용자 정보 미완성으로 넘기지 않는다.
2. 사용자 확인 가능한 required 조건에만 근거와 적용 범위를 가진 질문을 발행한다.
   질문 문구의 긍정/부정 표현을 보고 pass/fail을 추측하지 않고, 각 선택지의 평가 의미를 계약으로 고정한다.
   일반 사업자 정보는 회사에, 해당 공고만의 판단은 회사+공고+조건에 결속한다.
3. 답변은 충족/미충족/확인불가를 표현하고 사용자 확인 출처를 표시한다.
   exclusion의 “결격 해당/비해당”도 같은 평가 결과 모델로 명시적으로 변환한다.
   preferred 답변은 우대 판단에만 영향을 주며 기본 자격을 막지 않는다.
4. 기존 `disqualified` 답변은 legacy exclusion에만 호환 변환한다.
   과거의 false를 신규 required에 재사용하거나, 미응답을 비해당으로 바꾸지 않는다.
5. source revision, 조건 의미·질문 버전 변경 시 해당 답변만 재확인 대상으로 만든다.
   의미가 같은 질문의 ID/답변은 유지한다. 근거 없는 회사 간·공고 간 재사용을 막는다.
6. 공식 원천의 확정 실패와 source dispute는 사용자 확인으로 뒤집지 않는다.
   보류 사유·수정 가능한 정보·원천 정정 진입을 구분해 보여 준다.
7. 반복되는 시군구·지사/공장·기준일 요건은 빈도와 근거를 확인한 후 별도 작은 단위로 정형화한다.
   첫 구현은 모든 22축의 새 프로필 필드를 만드는 일이 아니라 확인 가능한 required의 저장→평가 왕복이다.

완료 기준:

- required 충족→pass, 미충족→fail, 확인불가→unknown; exclusion과 preferred도 의도한 의미로 동작한다.
- 공식 실패/정정 검토는 자가신고로 해소되지 않는다.
- 저장→새로고침→로그아웃/재로그인→회사 전환→재계산 후 답변·판정·근거가 일치한다.
- owner/editor만 허용된 회사에 저장 가능하며 viewer·다른 회사·과거 버전 쓰기를 차단한다.
- 표본의 모든 미해소 필수 조건은 **사용자 확인 / 회사 정보 보완 / 원문·관리자 확인** 중 하나의 다음 행동을 갖는다.
  실제 해소율은 별도로 보고하고 100% 해소나 100% 적격을 요구하지 않는다.

호환/배포: 저장 계약이 바뀌면 additive migration과 구버전 reader 호환을 먼저 준비한다.
노출을 되돌려도 신규 답변 이력은 보존하며, 구버전 앱이 새 답변을 잘못 해석하지 않도록 한다.

### 3단계 — 매칭 준비도와 작성 준비도 분리

주요 위치: launch receipt/status 계약과 reader, `analysis-launch-promotion.ts`,
application precompute release admission, 제품의 공고/작성 준비도 표시.

작업:

- primary 결과, 매칭 변환/검수 상태, 신청서 필드 준비 상태를 별개로 표현한다.
  transport 오류·lease 손실 같은 공유 실행 실패와 개별 기능의 품질 보류도 분리한다.
- 매칭 승격은 출처·현재 입력/첨부 결속·매칭용 변환·독립 검수로 판정한다.
  작성 자산은 해당 문서의 SHA/분석 계약/검수 증거가 맞을 때만 제공한다.
- 작성 미준비 공고도 매칭 후보로 보여 줄 수 있지만 “바로 작성 가능”으로 표시하지 않는다.
  이용 가능한 공식 원문·외부 신청 경로를 안내하고 사용자 요청 없는 유료 생성은 시작하지 않는다.
- 역사 receipt는 수정하지 않는다. 충분한 원본 증거가 있을 때만 새 파생 판정으로 해석하고,
  증거가 없으면 legacy 전체 held를 임의로 매칭 ready로 올리지 않는다.
- 기존 `--require-kordoc` release의 의미는 보존한다. 새 matching-only release가 준비되지 않은
  Kordoc 자산을 끼워 넣거나 검증을 우회하는 통로가 되지 않도록 한다.
- 동일 원본 SHA·모델·분석 계약·검수 상태의 신청서 결과를 재사용한다.
  오래된 held를 성공처럼 재사용하거나 primary 교정 때문에 항상 전체 신청서를 재분석하지 않는다.

완료 기준:

- 매칭 ready/작성 held, 매칭 held/작성 ready, 둘 다 ready, 둘 다 held 조합을 회귀 검증한다.
- 원래 13건은 재분석 없이 원인을 재분류하되, 독립 검수와 current binding이 충족된 건만 승격 후보가 된다.
- 기존 receipt의 해시·권한 의미가 보존되고, 기능별 표시와 실제 사용 가능 기능이 일치한다.

### 4단계 — 승격 조회의 중복 전송·검증 제거

주요 위치: `repositories/drizzle.ts`, `analysis-serving/promotionServing.ts`,
`analysis-serving/promotionReleaseContract.ts`, `serviceData.ts`.

작업:

- applied item의 작은 결속 정보와 release별 manifest를 나눠 읽는다.
- 한 조회 내 동일 release manifest의 해시 검증은 1회로 줄이고 item별 run/plan 검사는 유지한다.
  후보 필터와 reviewed metadata hydration에서 같은 검증 결과를 재사용한다.
- 먼저 요청 범위 재사용으로 개선한다. 프로세스 캐시는 필요성이 측정된 경우에만
  manifest SHA 키·크기 상한을 갖춰 추가하고 release 활성 상태의 정본으로 쓰지 않는다.
- 조회 도중 rollback·새 승격이 발생하는 경우 일관된 snapshot 또는 마지막 상태 재검증을 적용한다.
  캐시 무효화·승격 후 노출 지연 상한도 명시한다.

완료 기준:

- 같은 DB snapshot/asOf에서 변경 전후 공고 집합·criteria·review provenance가 일치한다.
- manifest 검증 횟수는 공고 수가 아니라 서로 다른 release 수에 비례한다.
- 고정 기준선에서 해당 manifest 전송 부분을 약 40.6MB→1.9MB 수준으로 축소한다.
  전체 응답 크기나 전체 지연이 같은 비율로 줄어든다고 주장하지 않는다.
- cold/warm 조회를 분리해 전송량·쿼리 수·검증 시간·총 시간을 측정한다.
  운영 p95 목표는 반복 측정 후 정하며 기존 2회의 약 6초를 운영 p95로 쓰지 않는다.
- hash 불일치, 상태 변경, rollback, item binding 불일치의 기존 차단을 유지한다.

### 5단계 — 기존 검수 자산의 공급 회복과 제품 인수

읽기 전용 조사부터 시작한다.

1. 승인 후 미적용 47건, 후속 독립 검수 PASS 결과, 현재 서비스 90건을 별도 집합으로 분리한다.
2. 각 자산의 현재 모집기간·노출 상태·원본/첨부 SHA·최종 검수·변환 결과·기존 승격을 비교한다.
   kind 변경이 이미 서비스에 들어갔는지도 원본 분석과 발행 결과를 대조해 확인한다.
3. 결과는 재사용 가능 / 재검수 필요 / 새 분석 필요 / 마감·원천 소실로 분류한다.
   정확한 판정을 할 증거가 없는 행은 보류하며 “승인됨”만으로 현재 유효하다고 하지 않는다.
4. 필요하면 검증된 같은 cohort의 상위 release revision을 준비한다.
   material binding이 같은 승인 범위는 이어가고, 대상·입력·허용 쓰기 상한 변경만 재확인한다.
5. 격리 환경에서 새 required 확인, 원천 정정, 작성 미준비 표시, 문서 저장/재개를 실제 계정으로 인수한다.
6. 승인된 exact 서비스 쓰기/배포 범위에서만 제한 반영하고, 기준 SHA·migration·release·alias·live smoke를 기록한다.
   승격된 내용과 실제 카드 노출 영수증을 대조하고 문제가 있으면 해당 release/기능만 되돌린다.

완료 기준:

- 조사 집합의 모든 건에 재사용/보류 사유가 있으며 자동으로 새 대체 대상을 추가하지 않는다.
- 승격 적용 전후 조건·질문·기존 답변의 보존과 rollback을 검증한다.
- 실제 서비스 반영은 승인·DB 적용·배포 SHA·인증 인수 증거를 갖춘 범위만 완료로 기록한다.
- 원문 불확실성과 사용자 정보 부족이 화면에서 구별되며, 허위 작성 가능 표시가 없다.

외부 의존: 전용 UAT DB/R2/OAuth와 owner/editor/viewer/ops 계정 연결.
현재 접근 상태는 재확인이 필요하며, 이를 기다리는 동안 0~4단계 오프라인 개발을 중단할 필요는 없다.
비밀값은 gitignored 환경 파일로 연결하고, 운영 DB나 다른 고객 조직을 인수 환경으로 재사용하지 않는다.

### 6단계 — 대량 분석 효율 개선과 확대

전제: 앞 단계에서 매칭 소비 계약과 검수·공급 지표가 마련되어야 한다.
관측 없는 동시성 상향이나 같은 실패의 무제한 재실행은 하지 않는다.

작업:

- 공고별 queue wait, 모델 실행, 변환, 교정, 검수, lease 중단, 작성 분석 재사용을 별도 계측한다.
  중첩 실행 시간의 합을 wall time이나 비용으로 오인하지 않는다.
- 현재 빈출하는 list semantics·경계값·지역/역할 귀속 문제를 회귀 사례와 최초 프롬프트/결정적 변환에 반영한다.
  원문을 추정해야 하는 오류는 결정적 교정으로 위장하지 않고 검수/원천 보완으로 보낸다.
- primary만 잘못됐고 신청서 자산은 현재 계약과 일치하면 신청서 분석을 재사용한다.
  동일한 오류가 반복되면 원문/계약/모델 응답을 분류하고 근거 없는 추가 재시도를 막는다.
- lease 만료·갱신 실패는 fault-injection 테스트로 재현한다.
  lease를 잃은 실행은 계속하지 않으며, 개선은 관측·제한 재시도·안전한 종료/재개에 초점을 둔다.
- 신규 재고는 실행 직전 다시 조회한다. 리뷰 당시 25건이라는 수치를 현재 재고로 고정하지 않는다.
  기존 100건 계약을 유지하려면 부족분 확보, 축소하려면 새 exact 범위 확정이 필요하다.
- 필요한 live 실험은 승인된 exact manifest 안에서 수행한다.
  오프라인으로 증명 가능한 문제를 확인하려고 모델을 다시 호출하지 않는다.

완료 기준:

- 분모를 고정한 unique 공고당 모델/교정 호출 수, 독립 검수 재결함률, 검수 PASS당 소요,
  마감 전 실제 공급량을 변경 전후 비교한다.
- 정확도 개선은 독립 원문 기대값과 오류 유형별 판정으로 증명한다.
  검수 기준을 완화해서 얻은 처리량 증가는 개선으로 세지 않는다.
- 확대 폭은 재고·구독 실행 여건·shared failure 관측에 따라 결정한다.
  사전 근거 없이 “100건/시간” 같은 처리량을 약속하지 않는다.

| 변경 유형 | 최소 관련 검증 | 추가 인수 |
| --- | --- | --- |
| 변환·matcher 의미 | `test:matching-unit`, `lab:shadow:test`, `lab:promote:test`, 관련 새 회귀 | 고정 원문 사례의 변환→matcher 대조 |
| 분석·release 계약 | `verify:deep-analysis-contract`, `lab:launch:test`, `lab:release:test` | legacy receipt·해시·승격 권한 보존 |
| 답변 저장·권한 | `test:profile-answer-consistency`, `test:product-journey`, `test:product-postgres` | 실제 역할별 저장·재로그인·회사 전환 |
| DB migration | `verify:db-migrations`, 격리 PostgreSQL 새/기존 데이터 호환 | 적용·구버전 reader·rollback 계획 |
| 조회 최적화 | `verify:service-data`, serving provenance 회귀, 전후 snapshot 대조 | cold/warm 성능과 상태 변경 반영 |
| 공용 계약/여러 경로 출고 | `pnpm test`, `verify:package-boundaries`, 영향 suite | 출고 후보 exact 소스 기준 CI·인수 |

위 명령은 앞으로의 검증 계획이지 이번 작성에서 실행한 결과가 아니다.
상위 집계 gate가 포함한 하위 검증은 같은 소스에서 중복 실행하지 않고 영수증을 재사용한다.
최종 인수 환경이 없으면 “코드·자동 검증 완료 / 실제 인수 미완료”로 표시하며 출시 완료라고 하지 않는다.

호환성 원칙:

- 새 reader/저장 계약의 호환을 먼저 확보하고 노출·writer를 나중에 연다.
- 잘못된 kind 변환으로 돌아가는 코드 rollback을 기본 복구책으로 삼지 않는다.
  문제가 있으면 새 기능 노출·해당 release를 제한하고 마지막 안전한 상태로 복구한다.
- 기존 원문·receipt·답변 이력을 보존한다. 과거 분석과 현재 기대값은 덮어쓰지 않는다.
- 실행 권한과 배포/승격 권한을 분리하되, 같은 승인 범위의 재시도·상위 revision 때문에
  사용자 재승인을 반복해서 요구하지 않는다.

## 5. 진행 기록과 첫 착수 단위

각 단계의 작업 기록에는 다음을 남긴다.

- 변경된 인터페이스·동작과 제외 범위.
- 테스트/보고서·소스 SHA·기준 데이터 hash 및 예상 밖 판정 변화.
- 코드 / 자동 검증 / 실제 인수 / 운영 반영 각각의 상태.
- 보류 사유, 다음에 필요한 외부 입력 또는 승인 범위.

**첫 착수 단위는 0+1단계 중 “kind 보존과 실제 matcher 회귀”다.**
우대→배제 재현 fixture를 먼저 고정하고 변환기를 수정한 뒤,
고정 80건을 무모델 재투영하여 종류 변경·누락·판정 차이를 보고한다.
다음 단위에서 중복 조건/최종 변환 계약을 정리한 후 2단계의 required 확인 저장→평가를 진행한다.
이 순서로 가장 위험한 의미 오류를 작은 변경으로 먼저 제거하고, 새 기능이 잘못된 변환 위에 쌓이지 않게 한다.

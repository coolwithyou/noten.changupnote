## 목표와 이번 계획의 도착점

현재 공급의 잘못된 제외 조건과 누락된 신청 요건을 고칠 수 있도록 **조건별 근거·수정 전후
차이·매칭 영향·복구 방법을 갖춘 교정 제안**을 만든다. 경고 건수를 줄이는 것이 성공 기준은
아니다. 당장 시작할 다음 작업의 도착점은 모델 호출과 서비스 쓰기가 없는 검수 자료 및
오프라인 교정 후보다. 이후 구현이 필요하면 기존 release 경로에 필요한 최소 변경을 명시한다.

이 계획은 과거 2026-09-10 03:50~03:53 KST 스냅샷을 출발점으로 삼는다. 82공고/481조건,
대상 수와 마감 여부는 실행 시 재확인하며, 문서 숫자를 현재 운영값으로 고정하지 않는다.

## 실행 순서

### 1. 실행 가능한 검수 자료를 먼저 고정

- 정식 serving inventory와 A/B/C 대상의 현재 grant/item/release/run, source/input/attachment
  SHA를 재조회한다. 기간 종료·새 결속·중복·추가 drift는 명시적으로 분류하고 대체 공고를 넣지 않는다.
- DB 읽기는 읽기 전용 repeatable-read로 묶고, R2 읽기는 객체 SHA와 전후 DB binding으로
  검증한다. snapshot 시각과 코드 출처를 함께 기록한다.
- `/tmp`에만 있는 조사 스크립트를 기존 source loader와 inventory를 재사용하는 좁은
  읽기 전용 도구로 정리한다. 원문 전체를 Git에 넣지 않고, 로컬 gitignored 자료 묶음에
  원본 run·자료 hash·출처·인용 위치를 보관하며 저장소에는 비식별 요약과 재현 방법을 둔다.
  과거 raw/첨부 상태가 보관돼 있지 않으면 `historical_evidence_missing`으로 남긴다.
- 산출물: 현재 대상 manifest, 공고별 검수 자료, 마감/원천 변경/증거 부재 목록.
- 통과 조건: 선택 ID 집합과 결과 집합 일치, 중복·누락 0, 기존 run/receipt 변경 0,
  모델 호출·서비스 DB/R2 쓰기 0. 전체 공급 재조회는 자동 대상 확대의 권한이 아니다.

### 2. A의 조건별 수정안을 작성

첫 검수는 경계 오류가 명확한 **모두의 창업(178952)**과, 대안 경로·제외 누락 및 kind
불일치가 겹친 **광명 가상오피스(178930)** 두 건으로 검수 양식을 고정한다. 두 건에서
수정 전후 조건과 매칭 사례를 작성한 뒤 나머지 5건을 같은 양식으로 진행한다.

| --- | --- | --- |
| 1 | 모두의 창업 / 178952 | 7년 미만과 이내, 트랙별 이종창업·사업자등록 시점, 제외 조건의 예외 |
| 1 | 광명 가상오피스 / 178930 | 타 분야 기업의 참여 대안, 체납·휴폐업 등 제외, 원본 kind와 현재 저장 kind |
| 2 | 서울창업허브M+ / 178915 | 포털·포스터 업력 충돌과 신산업 예외. 미투입 공고 PDF의 보관 원문을 먼저 확인 |
| 2 | 싱가포르 블록체인 / 179068 | 10년 경계, 채무불이행·체납·체불·휴폐업과 원문 예외 |

각 수정안은 원문 인용과 출처, 기존 criterion ID/index, 변경 유형(유지·수정·추가·판단 유보),
예외/OR 경로, 예상 매칭 변화, 추가 확인 사유를 포함한다. 문서끼리 충돌하면 첨부라는 이유로
일괄 우선하지 않는다. 판정 불가 조건은 원문과 불확실성을 보존하고 확정 탈락으로 바꾸지 않는다.

산출물은 7건의 조건별 검수표와 대표 사업자 fixture다. 이는 정식 독립 검수 receipt가 아니다.
원본 run과 과거 검수 receipt를 고치지 않으며 외부 검수 CLI·분석 모델을 자동으로 실행하지 않는다.

### 3. B의 교정 제안을 오프라인으로 생성

- source revision뿐 아니라 현재 input·attachment SHA와 게시 run, 기존 검수 결속을 다시
  확인한다. 조건을 충족한 대상만 원본 의미를 보존한 현행 projection과 비교한다.
- 원본 kind 복원이 실제 인용 의미와 맞는지 확인한다. 24조건 모두를 단순 SQL 치환하지 않는다.
- 기존 `current-matching-projection-revalidation.ts`는 immutable run과 현재 projection의
  진단을 재사용할 수 있지만 **promotion 권한도 신규 독립 검수도 제공하지 않는다**.
  launch receipt 기반이 아닌 역사 deep-repair 대상에는 이 도구를 억지로 적용하지 않는다.
- `promote.ts`, release source 검증 및 원장 경로에서 이미 공급 중인 item의 교정을 안전하게
  준비할 수 있는지 격리 fixture로 확인한다. 부족한 경우 새 파이프라인 전체를 만들지 않고
  현행 source/projection을 검증된 교정 revision으로 연결하는 최소 변경을 설계한다.
- 산출물: grant별 변경 전후 plan, 재사용 가능한 증거와 새 검수가 필요한 증거 목록,
  기존 CLI 지원 여부 및 필요한 구현 범위. A의 2건과 C의 5건은 B에 몰래 합치지 않는다.

### 4. C는 원천 revision 구성요소를 대조

과거 source artifact·보관 raw·첨부 inventory로 원래 revision을 재구성할 수 있는지 확인하고,
현재 `prepareInput.ts` / `sourceRevision.ts`의 구성요소와 비교한다. 공고 필드, rawHash,
첨부 URI/이름/내용 SHA/변환 상태를 구분한다.

- 내용 변화가 확인되면 조건 검수 필요 대상으로 명시한다.
- 관측 정보 또는 준비 파이프라인 변화만이라고 입증되면 근거와 재봉인 가능성만 제안한다.
- 과거 구성요소가 없으면 원인 미확정으로 남긴다. 텍스트 SHA 동일만으로 승인하지 않는다.

C의 미확정 건 때문에 독립적으로 근거가 갖춰진 A/B 전체를 막지는 않는다. 각 교정 후보는
자신의 현재 material binding과 검수 결과로 판정한다.

### 5. 실제 반영 전에 교정안과 복구 계획을 검토 가능하게 정리

- 최종 후보마다 exact grant/run/source revision, 추가 또는 재사용할 검수 증거,
  게시 전후 criterion/question, 답변과 매칭 캐시 영향, 되돌릴 snapshot을 묶는다.
- 의미가 달라진 질문의 기존 답변을 자동 승계하지 않는다. 의미가 같은 질문은 현재 계약에
  따라 보존 가능 여부를 검사하고, 무효화·재확인이 필요한 수를 별도로 제시한다.
- 기존 active item을 교정할 새 release가 현재 게시 snapshot을 기준으로 CAS 검증하는지,
  원래 release 및 변경 없는 공고·질문·답변을 보존하는지 격리 DB에서 검증한다.
- 운영 영향 범위가 확정된 제안을 먼저 만들고 기존 승인 범위의 존재를 확인한다. 새로운
  exact release 범위의 승인이 필요하면 이 시점에 한 번 요청한다. 같은 범위의 revision
  재시도나 내부 준비자/승인자 분리만으로 반복 사용자 승인을 만들지 않는다.

## 검증 기준과 실행 권한

| 단계 | 완료 증거 | 이번 기획 이후 별도로 다룰 실행 |
| --- | --- | --- |
| 문서·읽기 전용 조사 도구 | 구문, exact ID/hash, source 변경 감지, 링크, 무쓰기 검증 | DB/R2 조회는 조사 범위 내 수행 가능 |
| 교정 계약 구현이 필요한 경우 | kind 보존, source 변경 거부, 경계/예외/세부사업 fixture, 질문·답변·cache 영향 회귀 | 공유 계약 변경이므로 관련 suite + `pnpm test` + `pnpm test:product-postgres` |
| release 준비·gate·approve | exact 대상·현행 근거·수정안·복구 계획 및 승인 범위 결속 | `lab:release --prepare`도 DB prepared 원장을 생성하므로 읽기 전용으로 취급하지 않음 |
| 서비스 승격 | 승인된 release, 현재 snapshot 재확인, 대상별 결과·비대상 불변·복구 검증 | `lab:promote --write`는 별도 서비스 변경 권한 필요 |
| 배포·운영 설정 변경 | 해당 변경이 필요한 이유와 배포/실행 검증 | 배포, Cloudflare, observe_only 해제는 이번 기획에 포함되지 않음 |

공유 계약을 바꾸지 않는 문서·조사 단계에서 전체 suite를 반복하지 않는다. 상위 gate에
포함된 하위 검사는 동일 소스에서 중복 실행하지 않는다. 추후 실제 반영을 한다면 정식
serving/monitor와 대상 한정 매칭 대조를 수행하고, 사람이 확인해야 할 화면은 URL과 절차를
갖춘 HTML 인수 가이드로 제공한다. 단일 실행을 24시간 관측·실계정 인수로 확대하지 않는다.

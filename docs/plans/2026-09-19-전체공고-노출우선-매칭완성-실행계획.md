# 전체 공고 노출 우선 매칭 완성 — 토큰 최적화 실행계획

작성일: 2026-09-19 KST
상태: P1~P4 제품 코드 구현 완료. P5의 실제 데이터 집계·배포·사용자 노출은 미실행.

## 1. 사용자 의도와 바꾸는 순서

“확실하지 않아도 감추는 것보다 보여주는 것이 낫다”를 제품 원칙으로 삼는다.
**공고 노출은 기본, 확정적인 자격 판단에는 근거 필요, 추가 분석은 품질 향상 작업**이다.
미확정 공고도 매칭 화면의 후보로 접근 가능하게 하되 ‘지원 가능 확정’으로 표현하지 않는다.
사업자 정보를 완성해도 남는 공고 해석 문제를 추가 프로필 질문으로 떠넘기지 않는다.

기존 ‘전체 재고 → 보류 재검수 → 통과분만 노출’에서
**‘전체 재고 → 안전한 기본 정보로 즉시 후보 노출 → 검증된 조건으로 매칭 → 필요한 부분만 개선’**으로 전환한다.
83건 보류 해소, 신청서 분석, 모든 자격 축 확정을 출시 선행조건에서 제외한다.
이 문서는 이전 계획의 노출 선행조건과 다음 실행 순서를 대체한다. 기존 승인·receipt는 변경하지 않는다.

  이는 해당 시점과 코호트의 결과이며 현재 전체 공급량을 다시 조회한 수치가 아니다.
- [기존 검수 기록](../research/2026-09-19-매칭-HOLD-영향도-분리-및-오프라인-재분류.md):
  140건 중 56 verified / 1 conditional / 83 blocked. 해당 83건을 실제 오류 83건으로 해석하지 않는다.

  `requireDeepAnalysisPromotion: true`를 요구한다. 미승격 공고는 matcher 이전에 모집단에서 빠진다.
- `repositories/drizzle.ts`는 승격 원장으로 공급 대상을 필터한다. 프런트에는

- 따라서 모델 재분석만 늘리는 대신, **기본 공고 후보 공급과 검증된 분석 공급을 분리**해야 한다.
  단순히 위 필터를 false로 바꾸면 미검증 criteria까지 흘러갈 수 있으므로 그렇게 구현하지 않는다.

## 3. 노출과 판단 계약

아래는 제품 의미이며 구현 전에 새 DB enum을 무조건 추가하라는 지시가 아니다.
기존 상태와 DTO를 우선 재사용하고, 후보의 분석 근거 수준은 eligibility와 별도로 구분한다.

| 상태 | 사용자에게 보여줄 내용 | 판단·정렬 규칙 |
| --- | --- | --- |
| 현재 원문에 결속된 검증 결과 | 확인된 부합 조건, 불일치, 남은 확인 사항 | 기존 matcher 사용. 검증됐다는 이유만으로 적격 확정하지 않음 |
| 공고 해석 미확정·분석 미실행 | 제목·주관기관·모집기간·원문 링크, ‘지원 조건 확인 필요’ | 후보 노출. 불확실한 조건으로 적격/탈락 확정·맞춤 점수 산출 금지 |
| 회사 정보만 부족 | 확인할 회사 정보와 질문 | 실제로 사용자가 답할 수 있는 것만 질문 |
| 검증된 필수조건 불일치 | ‘현재 사업자 정보와 조건 불일치’와 근거 | 맞춤 추천 우선순위에서 제외. 전체 공고 검색·상세 접근은 유지 |
| 마감·접수 예정·모집상태 미확인 | 사실에 맞는 상태와 원문 | 현재 접수 중 분모와 분리. 마감 정보를 적격 탈락과 혼동하지 않음 |
| 삭제·비공개·원문 식별 불가·안전상 노출 금지 | 허용된 안내만 제공 | 기존 공개/보안 제한 유지. 분석 불확실성과 별개 |

핵심 불변조건:

1. 검증된 조건 0개도 기본 공고 노출이 가능하다. 다만 ‘조건이 없으니 전부 적격’이라는 빈 집합 판정을 금지한다.
2. 검증되지 않은 조건·LLM 요약은 경고를 붙였다는 이유로 사실처럼 노출하지 않는다.
   current source가 확인된 메타데이터와 실제 원문만 사용하고 추정 설명은 생략한다.
3. 조건 누락·source drift·모델 실패가 있어도 기본 공고 자체는 유효할 수 있다.
   위험한 분석 결과는 격리하고 유효한 기본 공고로 fallback한다. 해시 검증을 면제하지 않는다.
4. 알려진 자격 오류를 단순 ‘회사 정보 부족’으로 바꾸거나 조건을 삭제한 뒤 적격으로 만들지 않는다.
5. 부분 조건을 사용하려면 해당 조건의 근거 결속이 증명돼야 한다. 조건별 근거 분리가 불가능한
   legacy HOLD는 전체 분석을 판단에서 제외하고 기본 정보로만 노출한다. 조건별 검수 플랫폼을 새로 만들지 않는다.
6. 공고 소재지·운영기관 지역·포털 업종 분류를 지원자 제한으로 추정하지 않는다.
7. 불확실한 후보도 기본 결과 화면에서 존재와 일부 카드가 보이게 한다. 숨겨진 설정/추가 분석 버튼 뒤에만 두지 않는다.
   ‘추천 공고’와 ‘조건 확인이 필요한 공고’를 구분하고 목록별 건수·더보기·검색으로 전체 접근을 보장한다.
8. 미확정 후보에는 적합도 퍼센트나 확인되지 않은 추천 이유를 만들지 않는다.
   관련 근거가 없으면 마감/최신순으로 표시하고 ‘관련성 높은 추천’이라고 부르지 않는다.
9. 원문 확인·관심 저장·기존 상세 이동을 제공한다. 신청서 자동 작성 가능 여부는 별도 readiness를 유지한다.
10. 기존 promotion 노출 영수증과 분석 품질 지표를 기본 후보 노출의 증거로 재사용하지 않는다.

## 4. 구현 순서와 파트별 모델

모델 배정은 개발·운영 담당 역할이다. 이 문서로 세션을 전환하거나 분석 모델을 실행하지 않는다.
`sol = gpt-5.6-sol`, `astra = gpt-6-astra`; 괄호 뒤쪽은 reasoning effort다.

| 파트 | 구현 | 운영 | 범위와 완료 기준 |
| --- | --- | --- | --- |
| P0 의미 계약 확정 | `(astra-high)` | 없음 | 본 문서의 노출/판단 구분 확정. 이미 결정한 구조 재검토 반복 없음 |
| P1 공급 모집단·안전 projection | `(sol-xhigh)` | 정형 집계 모델 없음, 예외 `(astra-medium)` | 미승격 후보를 읽되 미검증 criteria가 판정에 들어가지 않음. 고유 ID 분류 합계 일치 |
| P2 matcher·캐시·API 계약 | `(sol-xhigh)` | 모델 없음 | 빈 조건은 미확정, 신뢰할 수 없는 조건으로 탈락시키지 않음. 전 경로 동일한 근거 수준 사용 |
| P3 결과 화면·상세 안내 | `(sol-high)` | 모델 없음 | 미확정 공고도 기본 화면에 보임. 정확한 안내·원문 접근·검색/페이지네이션 |
| P4 증분 처리·토큰 통제 | `(sol-xhigh)` | 스크립트, 예외만 `(astra-medium)` | 변경 없는 결과 재사용, 조회 시 LLM 0, 실패해도 후보 공급 유지 |
| P5 통합 인수·배포 준비 | 구현 담당 `(sol-xhigh)`, 의미 쟁점만 `(astra-high)` 1회 | `(astra-medium)` | 관련 집계 gate 1회, 핵심 사용자 흐름 확인, exact 배포 준비 |

다음 개발은 **P1+P2 → P3 → P4 → P5** 순서로 진행한다. P0는 이 문서가 기준이다.
각 파트마다 새 세션에 전체 대화를 전달하지 않는다. 이 문서 + 변경 파일 + 남은 쟁점만 전달한다.
정상 완료 파트를 Astra가 전부 재검수하지 않는다. 모델 선택은 프로젝트의 업무 배정 판단이며
모델별 절감률이나 정확도 향상을 측정했다는 뜻은 아니다.

### P1. 현재 모집단과 후보 공급

- 기존 current inventory/campaign 분류와 repository를 재사용해 지원 기간 내 공개 공고를 한 번 읽는다.
- `discovery/base candidate`와 `verified matching evidence`를 같은 공고 ID에서 합성한다.
  기존 44건은 검증 경로를 그대로 유지하고 미승격 공고는 별도 안전 projection으로 제공한다.
- 읽기 원칙: 현재 유효한 기본 데이터만, 신뢰할 수 없는 criteria/요약/질문은 제거하되
  미확정 이유를 남긴다. 가짜 promotion row 또는 publishable receipt를 생성하지 않는다.
- 공고별 현재 분류는 검증 결과 사용 가능 / 기본 후보만 사용 가능 / 비노출 사유 중 하나다.
  신규·변경·검수 필요·오류는 별도 처리 상태로 관리하고 이 상태만으로 공고를 숨기지 않는다.
- 전체 목록 limit에 의해 미처리 공고가 누락되지 않도록 기존 sentinel/페이지네이션을 유지한다.

### P2. 한 곳에서 안전한 매칭 입력 조립

- 기본 정보와 검증된 근거를 합성하는 작은 공통 모듈을 기존 공급 경로에 둔다.
  API/카드/상세마다 별도의 fallback 정책을 만들지 않는다.
- 논리적으로 `근거 수준`, `미확정 사유`, `사용 가능한 criteria`, `source revision`을 전달한다.
  기존 DTO로 표현할 수 없는 값만 최소 확장한다. 우선 파생값을 사용하고 DB migration은 필요할 때만 한다.
- 근거가 불완전한 공고에 대해 zero criteria/부분 조건 일치를 적격으로 확정하지 않는다.
  반대로 실제 검증된 필수조건 실패만 불일치 판단에 사용한다.
- 회사 정보가 완성돼도 원문 미확정이면 원문 확인 상태를 유지한다. 자동 질문을 억지로 생성하지 않는다.
- 기본 후보는 검증 결과가 필요한 기존 match-state를 오염시키지 않도록 조회 시 파생한다.
  캐시 결속에는 회사 profile revision, 공고 content revision, evidence 상태/계약 버전을 반영한다.
- 기본 후보→검증 결과, 원문 변경, 마감 전환 때 영향 있는 공고의 결과만 무효화한다.

### P3. 노출 의미를 화면 끝까지 유지

- 기존 고객용 디자인과 카드·상세를 재사용한다. 관리자 UI 재설계·새 대시보드는 만들지 않는다.
- 기본 결과에서 ‘추천’과 ‘조건 확인 필요’를 구분하고, 후자의 카드·건수·더보기를 제공한다.
- 권장 문구: ‘관련 공고를 찾았어요. 일부 지원 조건은 공고문에서 확인해 주세요.’
  관련성을 계산할 근거가 없는 경우에는 ‘모집 중인 공고예요. 지원 조건을 확인해 주세요.’로 표시한다.
- 분석 오류는 지원자의 잘못처럼 표현하지 않는다. 미분석 공고에 ‘지원 불가’·‘마감’ 표시 금지.
- 전체 공고 검색에서 확인 필요/검증된 불일치도 찾을 수 있게 하고 맞춤 추천과 검색 범위를 구분한다.

### P4. 추가 분석을 필수가 아닌 증분 개선으로

- 신규 유입은 기본 노출부터 한다. 분석·검수는 이미 승인된 실행 범위 안에서 후속 수행한다.
- 동일 입력·모델·프롬프트·validator 계약의 성공 결과를 재사용한다. 수집 시각 변화만으로 재분석하지 않는다.
- 의미 있는 원문 변경만 재분석 대상이다. 기준 문서 전체의 누락을 검사해야 하는 경우까지
  무조건 짧은 문맥으로 잘라 보내지 않는다. 근거 문맥이 부족하면 확대하거나 미확정으로 남긴다.
- 결과를 목록에서 열거나 새로고침하는 행위는 LLM 호출을 발생시키지 않는다.
- 최초 구현에서는 클릭 기반 자동 분석, 관심도 큐, 새로운 스케줄러/오케스트레이터를 만들지 않는다.
  기존 runner/campaign을 사용하고 우선순위는 수집된 확실한 마감 정보·실제 변경 등 결정적 데이터로 정한다.
- 반복되는 의미적 미확정은 자동 재시도 사유가 아니다. 차후 계약에서 자동 모델 보정은 최대 1회,
  그 뒤에도 미확정이면 후보 노출을 유지하고 다음 공고로 간다. 현행 실행 중 계약을 소급 변경하지 않는다.
- 일시적 전송 장애 재시도는 기존 제한을 사용한다. 인증·lease·구독 창 소진은 공통 중단 규칙을 유지한다.
- 운영 API worker의 observe_only는 유지한다. 상시 유료 분석 활성화는 별도 운영 정책·실행 상한 승인 후다.

### P5. 프로덕션 전환

- 코드/계약 검증, 실제 공급 집계, 브라우저 사용자 여정을 서로 다른 증거로 기록한다.
- 배포 전 현재 데이터에 대한 읽기 전용 후보 분류로 기존 공급 보존과 추가 노출 범위를 확인한다.
- 승인된 배포에서 기능 플래그로 후보 노출 경로를 켠다. 문제 시 해당 경로만 끄고 기존 검증 공급은 유지한다.
- 마감/기간 변경 반영, 중복 제거, 안정적인 정렬·페이지네이션, source/evidence 변경 후 캐시 갱신을 확인한다.
- 실제 데이터 쓰기·외부 사용자 노출·배포의 exact 범위를 확인한 뒤 진행한다. 이전 44건 공급 승인을
  미승인 코호트의 일괄 promotion이나 자동 운영 실행으로 확대하지 않는다.

## 5. 토큰 최적화 규칙

| 작업 | LLM 필요 여부 | 규칙 |
| --- | --- | --- |
| 기본 공고 노출, 목록·상세 조회 | 불필요 | 요청당 모델 호출 0 |
| 사업자 정보 변경 후 매칭 | 불필요 | 기존 조건 엔진·검증된 근거로 계산 |
| 재고/마감/중복/원천 SHA/상태 집계 | 불필요 | 코드와 기존 저장 데이터 사용 |
| 동일 입력·계약의 성공 결과 | 불필요 | 원문/첨부/계약 결속 확인 후 재사용 |
| 기존 HOLD의 기본 후보 노출 | 불필요 | 불확실한 분석을 승인하지 않고 노출 가능 데이터만 사용 |
| 신규·실제 변경 원문 분석 | 승인 범위에서만 필요 | 공고별 결과 재사용, 회사별 동일 공고 재분석 금지 |
| 추천 품질에 영향을 주는 미확정 보정 | 필요할 때만 | 영향 있는 조건·근거 중심. 무변경 자동 반복 금지 |
| 변화 없는 감시 | 불필요 | 스크립트, 사건 발생 때만 운영 모델 |

개발 토큰도 제한한다. 파일 탐색 범위를 파트로 한정하고, 구현자가 관련 테스트까지 소유하며,
이미 통과한 같은 코드의 검증을 다른 모델이 반복하지 않는다. 다중 AI 감사와 별도 샘플 실험을 추가하지 않는다.

primary/reviewer 런타임 모델은 기존 승인 설정을 유지한다. 위 Sol/Astra 표는 개발·운영 담당이지
분석 레인의 자동 교체가 아니다. 로컬 구독과 운영 API 경계도 유지한다.
API cache 가격·동작을 구독 환경의 절감액으로 환산하지 않는다. 실제 사용량이 없으면 unknown이다.

최소 관측 지표는 기존 로그/보고서에 추가한다. 새로운 대시보드나 계측 전용 모델은 필요 없다.

- 기본 후보 노출 커버리지와 검증된 매칭 커버리지를 별도 표시한다. 후보 노출 증가를 정확도 향상으로 보고하지 않는다.
- 현재 모집단에서 공급되지 않는 공고의 수·사유, 처리 backlog의 가장 오래된 대기 시간.
- 신규 노출까지 걸린 시간, 의미 있는 변경 공고당 모델 호출/입출력 토큰, 무변경 재실행 수.
- 실패 시도/보정/검수 사용량도 합산하며, 미보고 사용량을 0으로 쓰지 않는다.
- 이번 목표: 노출/조회 LLM 0, 동일 입력·계약의 성공 분석 중복 실행 0. 금액 절감률은 측정 전 약속하지 않는다.

## 6. 필수 검증과 중단선

기능별 관련 테스트로 아래 계약을 고정한다. 공유 DTO/core 변경이 있으면 프로젝트 규칙에 맞는
관련 집계 gate 1회를 실행하고, 그 안에 포함된 하위 suite/typecheck/build는 다시 실행하지 않는다.

1. 승격 없는 유효 공고도 기본 후보에 포함되고 기존 검증 공급이 유지된다.
2. criteria 0개/오류/누락/원문 변경으로 적격이나 부적격이 잘못 확정되지 않는다.
3. profile 완료 후에도 원문 미확정은 회사 정보 부족으로 둔갑하지 않는다.
4. 확인된 필수조건 실패와 가점 미확정을 구분하며 임의 점수/추천 근거를 만들지 않는다.
5. 마감·비공개·중복 제한, 기본 후보→검증 결과/원문 변경의 캐시 갱신이 유지된다.
6. 목록/상세/회사 정보 변경의 정상 사용자 요청에서 모델 호출이 0이다.
7. 실제 접속 가능한 환경에서 검증 공고·미확정 공고·명확한 불일치 각 1사례로 사용자 흐름을 확인한다.
   새 테스트 캠페인이나 전 공고 브라우저 순회는 하지 않는다. 개발 서버는 사용자가 실행한다.

근거 불명확한 자동 적격/탈락, 공개 범위 침범, 기존 검증 공급 손실만 출시 차단 사유다.
일부 미확정 공고나 모든 검수 경고를 제거하지 못했다는 이유만으로 전체 노출 전환을 중단하지 않는다.

## 7. 완료 정의와 범위 보존

**지금 접수 가능한 공개 고유 공고가 검증 수준에 맞게 모두 접근 가능하고, 정상 사용자 요청은
LLM 없이 작동하며, 신규·변경 공고가 추가 수작업 연결 없이 같은 경로로 공급되는 상태**가 목표다.
100% 적격 판정, 100% 정밀 분석, 모든 신청서 자동 작성은 이번 완료 기준이 아니다.

현재 전체 수량은 실행 시 한 번의 최신 snapshot으로 확정한다. 이전 공급 44건, 제외 13건,
역사 HOLD 83건을 오늘 모집단이나 상호 배타적인 전체 잔여 집합으로 간주하지 않는다.

원 exact19와 기존 campaign은 계속 분리한다. exact19 seq0 신청서 후속이나 서비스 승격을 이 계획으로
승인하지 않는다. 원장 불변성과 실행 권한은 그대로 보존한다. 새 후보 노출의 운영 적용 범위에
과거 미승인 exact 대상이 포함되면 적용 전에 명시하고 해당 범위를 확인한다.

## 9. 2026-09-19 구현 결과

- `MatchingEvidence`(`verified | discovery`)를 매칭 적격도와 분리했다.
- 승격 원장의 source revision과 현재 원문·첨부 revision이 정확히 같은 경우만
  `verified`로 사용한다. 미승격·원문 변경·근거 불가는 `discovery`로 투영한다.
- `discovery`에서 criteria, facets, 금액, 혜택, 의무, 제출 서류, 접수 방법,
  첨부 payload를 제거했다. 적격/탈락·개인화 점수·추천 근거·자동 질문을 만들지 않는다.
- 대시보드·티저·상세에 `원문 확인 필요`로 노출하고, 상세의 주 행동은
  지원서 자동 작성이 아닌 공고 원문 확인으로 고정했다.
- `discovery`는 match-state·confirmation question 저장 대상에서 제외했다. 목록·상세·프로필
  변경은 기존 규칙 엔진만 사용하며 모델을 호출하지 않는다.
- `MATCH_DISCOVERY_CANDIDATES_ENABLED=true`로만 새 경로를 켠다. false에서는 기존
  승격 공고 전용 경로를 그대로 유지한다.
- 실제 모집단 읽기 전용 집계, 플래그 활성화, 배포, 브라우저 인수는 P5로 남겼다.

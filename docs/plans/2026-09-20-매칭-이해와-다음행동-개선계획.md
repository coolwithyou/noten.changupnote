# 매칭 결과 이해와 다음 행동 개선 계획

작성일: 2026-09-20 KST
상태: 사용자 구현 승인 후 W0 기준선 및 W1~W4의 1차 코드 구현·로컬 검증 수행. W5 행동 저장 경로와 W6 오프라인 복합 조건 검증 기반까지 추가. 운영 활성화·전체 계측·복합 조건 소비자 통합·W7~W8은 미완료.
목표: 사용자가 후보를 발견하고, 현재 판단의 이유와 다음 행동을 이해해 실제 신청 검토를 이어가도록 한다.

## 1. 제품 목표와 범위

첫 화면에서 사용자가 다음 세 질문에 답할 수 있어야 한다.

1. 내가 살펴볼 공고는 무엇인가?
2. 어떤 조건이 맞고, 무엇이 아직 확인되지 않았는가?
3. 지금 무엇을 하면 어떤 부분이 해결되는가?

확정 공고가 0개여도 후보가 있으면 탐색·조건 확인이 가능한 결과 화면을 제공한다.
확인되지 않은 자격을 충족으로 바꾸거나 관련 없는 공고를 맞춤 추천으로 포장하지 않는다.
접수 중, 회사의 자격 충족, 선정 가능성, 신청서 작성 준비는 서로 다른 의미로 유지한다.

계획 작성 후 사용자가 “구현을 시작해줘”로 코드 구현을 승인했다.
1차 변경과 검증·잔여 범위는 [구현 검증 기록](../research/2026-09-20-매칭-행동개선-1차-구현검증.md)에 기록한다.
후속 범위는 [2차 구현 검증](../research/2026-09-20-매칭-행동개선-2차-구현검증.md)에 기록한다.
배포·모델 분석·서비스 DB 승격·운영 worker 활성화는 수행하지 않았다.

실제 원인별 비중을 측정한 결과는 아니며, 이를 W0에서 분리 측정한다.

## 3. 사용자에게 보일 상태와 행동

### 3.1 공고 단위 상태

서버 판정과 표시용 설명을 분리하되, 표시가 판정을 재추정하지 않게 한다.
기존 eligibility/reviewGate/matchingEvidence/status와 action을 한 공통 projection에서 소비한다.
이름은 구현 전 기존 DTO와 대조해 확정하며, 새 DB enum·저장 테이블은 기본 선택이 아니다.

| 상황 | 주 안내 | 주 행동 | 함께 밝혀야 할 내용 |
| --- | --- | --- | --- |
| 접수 중 + 검증된 자격 충족 | 확인된 자격조건에 맞아요 | 신청 방법 확인 | 최종 선정·제출 완료를 의미하지 않음 |
| 사용자 답변만 필요 | 회사 정보 N가지를 확인해 주세요 | 해당 질문에 답하기 | 답에 따라 충족 또는 미충족으로 판정 |
| 사용자 입력과 원문 검토가 함께 필요 | 회사 정보 N개·공고 조건 M개 확인이 필요해요 | 해결 가능한 질문부터 확인 | 입력 후에도 원문 조건 M개는 남음 |
| 서비스 분석 한계만 남음 | 아직 판단하지 못한 조건이 있어요 | 해당 원문 근거 보기 | 사용자의 정보 부족이 아님 |
| 원문 자체가 모호함 | 모집기관 확인이 필요한 조건이에요 | 확인할 질문과 공식 연락처 보기 | 연락처가 검증된 경우에만 제공, 자동 연락 없음 |
| discovery만 있음 | 모집 중인 공고를 살펴보세요 | 공고 원문 보기 | 맞춤 자격 판단 전, 가짜 조건 수·점수 없음 |
| 검증된 필수조건 불일치 | 현재 조건과 맞지 않는 항목이 있어요 | 불일치 근거 보기 | 마감과 구분, 전체 검색 접근은 유지 |
| 접수 예정·마감·기간 불명 | 실제 모집 상태 표시 | 일정/다른 공고 확인 | 자격 충족 여부와 분리 |

검토 작업이 실제 생성되지 않았다면 “검토 중”, 처리 기한이 없다면 “곧 알려드려요”를 쓰지 않는다.
자격 미확정인 카드의 주 행동을 일괄 신청서 작성으로 연결하지 않는다.

### 3.2 조건 단위 설명

각 required/exclusion 조건은 아래 정보를 가진다. preferred는 별도 우대 영역으로 유지한다.

- 안정적인 criterion ID 및 원문 revision 결속
- 사람이 이해할 공고 조건 문장
- 비교한 회사 값과 값의 출처/자가 확인 여부
- 충족 / 미충족 / 미확인 상태
- 미확인 원인: 회사 정보, 공고 해석, 근거 누락, 원문 모호, 공식정보 정정 등
- 해결 주체와 정확한 행동 대상: profile field, 검수된 question ID, source locator
- 행동으로 해소되는 조건과 남는 조건

원문 인용·문서·페이지 위치는 실제 저장 근거가 있을 때만 표시한다. 페이지가 없으면 문서/원문 링크와
찾을 문장을 제공하고, 외부 접근 실패 시 공고 상세로 복귀할 수 있게 한다.
raw label을 정규식으로 잘라 의미를 만들어내지 않는다. 원문 근거가 없으면 부족함을 명시한다.

## 4. 작업별 모델과 실행 순서

아래는 **개발 에이전트 모델** 배정이다. 서비스의 추출/검수 모델 변경이나 사용자 요청 시 LLM 호출 추가가 아니다.
공식 문서에서 모델 ID와 effort를 확인했고, 현재 세션 도구에서도 두 모델을 선택할 수 있다.
이 저장소에서 모델 간 비교 실험을 한 것은 아니므로 “최적”은 복잡도·변경 위험·인수인계 비용에 따른 추천이다.

| 작업 | 담당 모델 / reasoning_effort | 이유 | 선행 |
| --- | --- | --- | --- |
| W0 현재 상태·원인 집계 | gpt-5.6-sol / high | 기존 코드와 저장 자료를 좁게 추적하고 재현 보고서 작성 | 없음 |
| W1 설명·행동 계약 | gpt-6-astra / high | 불확실성·판정·다음 행동 사이 의미 충돌 해결 | W0 |
| W2 결과 화면·집계 | gpt-5.6-sol / high | 확정된 상태 계약을 UI/API에 적용 | W1 |
| W3 공고별 조건 카드·상세 | gpt-5.6-sol / high | 기존 디자인과 상세를 유지하는 화면 구현 | W1, W2 |
| W4 질문·답변 후 변화 | gpt-5.6-sol / xhigh | 질문 선정, 저장, 캐시, 복귀 흐름의 여러 경계 연결 | W1~W3 |
| W5 계측·1차 통합 인수 | gpt-5.6-sol / high | 사용자 여정 재현과 지표 검증, 기존 P5 통합 | W2~W4 |
| W6 복합조건 표현·평가 | gpt-6-astra / high | OR/AND·예외·열린 목록과 세 상태 논리의 의미 보존 | W0, W1; W5 후 구현 권장 |
| W7 기존 근거·확인 질문 공급 개선 | gpt-5.6-sol / xhigh | 기존 release/질문 결속·캐시 경로 재사용 | W0, W1; 복합조건은 W6 |
| W8 2차 인수·운영 효과 평가 | gpt-5.6-sol / high | 동일 기준 전후 비교와 배포 증거 정리 | W6, W7 |

1차: W0 → W1 → W2 → W3 → W4 → W5. 사용자가 이해하고 행동할 수 있는 제품을 먼저 검증한다.
2차: W6 → W7 → W8. 실제 자동 판정 가능 범위를 넓힌다. 1차 출시를 전 공고 재분석에 묶지 않는다.
모든 단계는 기본적으로 구현자 한 명씩 순차 진행한다. 동일 공유 파일의 동시 수정을 피한다.
총괄은 통합·검증·승인 범위 유지 담당이며, 완료한 정상 작업을 다른 모델이 매번 전부 재작성하지 않는다.
Sol이 의미 충돌로 막힐 때만 Astra high에 재현 사례·선택지·영향 파일을 전달해 제한적으로 검토한다.

## 5. 상세 작업 명세

### W0. 현재 화면과 0건 원인 기준선

산출물: source SHA·환경·플래그 상태·데이터 시점이 명시된 읽기 전용 진단 보고서와 익명/합성 회귀 fixture.

1. 기존 P5 증거, 현재 checkout, Preview/Production 적용 상태를 구분한다. 재사용 가능한 gate를 확인한다.
2. 같은 snapshot으로 공개 고유 공고 → 접수 상태 → verified/discovery → 회사별 판정 → 화면 노출 수를 센다.
3. verified의 미확정 원인은 다중 라벨로 기록하고, 요약용 대표 원인은 명시적 우선순위로 하나만 선택한다.
   합계는 고유 공고 수와 일치시킨다. 혼합 원인을 하나로 지워버리지 않는다.
4. 검증된 미충족·입력 부족·원문 검토·미분석·일정 불명을 분리한다. 집계 실패를 0건으로 표시하지 않는다.
5. 회사별 “확정 0건”, “후보도 0건”, “다음 행동 없음” 비율을 별도 계산한다.
   실제 사용자 표본에 접근할 수 없으면 기존 가상 기업 matrix 결과라고 표시하며 전체 사용자 통계로 일반화하지 않는다.
6. 한·독 세미나의 최신 원문/공급 revision을 확인해 세 조건·OR 관계·포털 요약의 역할을 fixture로 보존한다.
   기존 분석 산출물만으로 현재 자격 사실을 확정하지 않는다.

완료 기준: 8개 표시 제한과 실제 전체 후보 수가 분리되고, 0건 발생 원인을 재현 가능한 사례로 설명할 수 있다.
민감한 회사 값·식별자·원문 답변은 보고서/계측에 저장하지 않는다.

### W1. 공통 설명과 다음 행동 계약

변경 시작점: contracts, core match-card/select-match-cards, 서버의 confirmation action annotation,
웹 logic. matcher 적격도와 표시용 설명을 중복 계산하는 새 엔진은 만들지 않는다.

1. 기존 ruleTrace, unresolved_reason, confirmationNextAction, reviewGate를 공통 projection으로 연결한다.
2. 조건별 reason/owner/action 및 카드별 counts/primaryAction/remainingBlockers를 파생한다.
3. 카드별 주요 상태는 배타적으로 정하고 조건 원인은 복수 보존한다. 전체 후보 수는 고유 ID로 센다.
4. 전체 충족을 막는 card-level extraction/review 문제도 별도 보존한다.
   trace에 미확정이 없다는 이유만으로 공고 전체를 확정하지 않는다.
5. primary action은 접수 상태와 판정을 확인한 후 정한다. 미확정이면 사용자 해결 가능 항목을 우선하되
   해소되지 않는 원문 문제가 남는다는 사실을 같은 화면에 명시한다.
6. DTO 추가는 additive로 시작하고 레거시 값은 보수적인 안내로 호환한다. DB 변경은 필요성이 입증될 때만 한다.

완료 기준: 동일 공고·회사·revision이면 티저/대시보드/상세가 같은 상태와 행동을 설명한다.
기존 eligible/ineligible 판정은 1차에서 불변이다. 검증된 질문 없이 임의 자가확인으로 승격되지 않는다.

### W2. 결과 화면을 후보와 행동 중심으로 변경

대상: ResultsHero, Programs, logic, build-teaser/build-dashboard 및 실제 API 집계 경로.

1. 후보가 있을 때 확정 0건만을 큰 제목으로 내세우지 않는다.
   관련성 근거가 있으면 “우리 회사와 관련된 공고를 확인해 보세요”, discovery뿐이면
   “모집 중인 공고를 살펴보세요”를 사용한다. 숫자는 서버 전체 집계가 있을 때만 붙인다.
2. 화면 순서: 결과 요약 → 다음 행동 또는 후보 목록 → 상세 분석 범위/전체 프로필 완성도.
   기존 긴 분석 범위 설명과 20개 프로필 게이지는 보조 영역으로 이동한다.
3. 자격 충족 확인 / 내 정보 확인 / 공고 조건 확인 상태를 제공한다.
   접수 예정·마감은 별도로 표현하고, 확정 불일치 공고는 전체 검색에서 근거와 함께 접근 가능하게 한다.
4. 사용자 입력+원문 검토 혼합 카드는 두 상태를 설명하되 전체 합계에서는 한 번만 센다.
5. 각 목록에 전체 N건·현재 M건을 구분하고, 기존 페이지네이션/전체보기로 계속 접근하게 한다.
   teaser의 기본 8개를 전체 원문 검토 건수로 표시하지 않는다.
6. 추천 근거가 부족한 공고를 마감 임박만으로 맞춤 추천처럼 정렬하지 않는다.
   검증된 관련성, 해결 가능한 행동을 우선하고 discovery 탐색은 별도 문맥을 준다.
7. 후보가 정말 없으면 검색 범위 조정·전체 모집 공고 보기 등 실제 동작하는 탐색 행동을 제공한다.
   없는 알림 구독·관심 저장 기능을 문구만으로 약속하지 않는다.

완료 기준: 확정 0/후보 있음, 후보 0, discovery만 있음, 오류/로딩, 페이지 추가의 다섯 상태가 구분된다.
모든 CTA는 유효한 목적지와 복귀 흐름을 가진다. 빈 숫자 대신 로딩/조회 실패를 정확히 표시한다.

### W3. 조건 카드와 상세에서 “왜, 무엇을” 설명

대상: ExpandedProgramCard, criterionEvidencePresentation, grant-overview 및 관련 상세 컴포넌트.

1. 카드 접힌 상태에도 핵심 미확정 이유와 행동을 짧게 보여준다.
2. 펼치면 모든 필수/제외 조건을 행별로 제공한다. 기본 순서는 미충족 → 사용자 확인 → 원문 확인 → 충족.
   긴 목록은 “나머지 N개 보기”로 이어지되 확인 필요 조건 총수와 일치해야 한다.
3. “0/3 충족”을 “충족 확인 0 · 미충족 0 · 미확인 3”으로 변경한다.
   조건 자체가 추출되지 않았거나 전체성 gate가 남으면 분모를 완전한 자격 목록처럼 표현하지 않는다.
4. 공고 조건 / 회사 정보 / 현재 판단 / 다음 행동을 한 단위로 읽게 한다.
   모바일에서는 행을 세로로 쌓고 핵심 CTA를 가로 스크롤 밖으로 밀지 않는다.
5. “기타 원문” 대신 검증된 구체 설명을 제공한다. 구체화할 근거가 없으면 “이 조건을 아직 해석하지 못했어요”로 표시한다.
6. 입력 버튼은 필요한 필드/검수 질문을 직접 연다. 일반 기업정보 폼 첫 화면으로 보내지 않는다.
7. 조건 전체 보기와 공고 상세가 같은 링크라면 하나로 통합하고, 외부 공고 원문은 구분한다.
8. 상태는 색상뿐 아니라 텍스트로 전달하고, 펼침/닫힘·초점 복귀·키보드 조작을 확인한다.

완료 기준: 한·독 세미나 사례에서 세 조건 모두 설명되며 “GBC 입주 AND 유럽 진출 희망”으로 왜곡되지 않는다.
해당 조건의 실제 current 원문을 확인하기 전에는 이 사례를 사용자에게 확정 자격 안내로 배포하지 않는다.

### W4. 질문과 답변의 결과를 연결

대상: question-planner, build-teaser, profile answer/refresh, ConfirmationSheet와 결과 영향 표시.

1. needs_core_review 카드라도 일부 profile-resolvable 조건이 검증돼 있으면 질문 후보가 될 수 있게 한다.
   discovery·검수 전 조건·원문 모호 항목을 자동 질문으로 만들지 않는다.
2. 질문 선정은 “전체 판정이 끝나는 공고 수”와 “일부 조건을 해소하는 공고 수”를 나눠 평가한다.
   두 값의 중복과 counting scope를 계약에 명시하고, 이미 답한/공식 원천 수정 필요 항목은 재질문하지 않는다.
3. 질문 전 “이 답변은 N개 공고의 회사 유형 확인에 사용돼요. 별도 원문 확인 조건은 남아요”처럼 영향을 안내한다.
   N을 계산할 수 없으면 숫자를 생략한다. 답변이 항상 지원 가능을 만든다고 약속하지 않는다.
4. 답변 후 “회사 유형 확인 완료 → 남은 공고 조건 2개”처럼 해소/잔여를 표시한다.
   판정이 미충족으로 바뀌면 그 이유와 다른 후보를 보여준다. 실제 변화가 없으면 그 이유를 설명한다.
5. 7/20 게이지 대신 현재 선택한 공고/후보에 필요한 항목을 우선한다. 전체 프로필 완성도는 설정/보조 영역에 남긴다.
6. 회사 저장·로그인 필요 시 공고와 질문 맥락을 보존하고 복귀한다. 회사 변경·중복 제출·저장 실패·stale 응답을 처리한다.
7. 답변 저장 후 관련 회사/공고 캐시와 서버 집계를 갱신한다. 다른 회사 정보나 다른 원문 revision 답변을 재사용하지 않는다.

완료 기준: 혼합 상태에서 유용한 질문을 제공하면서도 답변만으로 원문 검토가 사라지지 않는다.
이미 답한 질문 무한 반복 0, 서버 저장 실패 시 성공 표시 0, 동일 사용자 흐름에서 모델 호출 0.

### W5. 계측과 1차 사용자 여정 인수

기존 노출/피드백 계측을 재사용한다. 별도 분석 대시보드나 이벤트 수집 서비스를 도입하지 않는다.

- 상태별 결과 노출, 카드 열기, 조건 보기, 질문 시작/완료, 답변 뒤 조건 해소, 공식 신청/원문 이동을 기록한다.
- 이벤트에는 버전·상태·행동 종류와 필요한 가명 키만 포함한다. 회사 값·원문 답변·사업자번호는 보내지 않는다.
- 클릭을 실제 지원 완료로 집계하지 않는다. 자동 테스트/가상 기업 이벤트는 운영 지표에서 제외한다.
- 1차 핵심 지표: 첫 유효 행동까지 시간, 질문 완료율, 답변 후 조건 해소율, 다음 행동 없는 결과 비율.
- 보조 지표: 자격 확정 0건 비율, 후보 0건 비율, 원문 검토 잔여율. 노출량 증가를 적격 정확도 향상으로 계산하지 않는다.
- 베이스라인과 출시 후 같은 정의·대상으로 비교한다. 트래픽 차이·신규 공고 유입을 기록하며 단순 전후 차이를 인과로 단정하지 않는다.

이 단계는 기존 P5의 후보 노출·실제 로그인·페이지네이션 검증과 합친다. 반복 캠페인을 새로 만들지 않는다.
대표 사용자를 대상으로 카드 한 개를 읽고 “조건/미확정 이유/다음 행동”을 설명하게 한다.
초기 정성 인수 목표는 5명 중 4명이 진행자 설명 없이 세 질문에 답하고 행동을 선택하는 것(통계적 효과 증명 아님).
실제 참여자가 없으면 자동 검증과 사람 UAT를 별개로 보고한다.

완료 기준: W2~W4 대표 여정과 아래 회귀 행렬 PASS, 개인정보 없는 계측 검증, Preview 화면 증거 확보.
Production 전환은 승인된 exact 소스로 별도 수행한다.

### W6. 복합조건과 열린 목록의 의미 보존

먼저 기존 조건 AST/표현/평가 지원을 조사하고 부족한 seam만 확장한다. 범용 규칙 엔진 재작성은 하지 않는다.

1. 대표 원문에서 공통 조건 AND 대안 경로(anyOf)와 하위 조건(allOf)을 분리한다.
   한·독 사례의 잠정 구조는 “분야 조건 AND (GBC 입주 OR 유럽 진출 희망)”이며 current 원문 검수가 선행한다.
2. 세 상태 논리: OR는 하나 pass면 pass, 전부 fail일 때 fail, 그 외 unknown.
   AND는 하나 fail이면 fail, 전부 pass일 때 pass, 그 외 unknown. 빈/손상 그룹은 적격으로 만들지 않는다.
3. 불필요해진 OR의 다른 분기 입력은 요구하지 않는다. 확인된 경로와 채택 이유를 설명에 보존한다.
4. 예시·열린 목록은 목록 밖이라는 이유만으로 fail시키지 않는다. 포털 요약 대상 유형을 본문 자격보다 강하게 해석하지 않는다.
5. preferred·평가·신청 준비·행정 안내를 자격 요건과 구분한다. confidence 임계 완화나 문구 삭제로 충족률을 올리지 않는다.
6. 기존 flat 조건·receipt와 호환하며 schema/validator/runtime material 변경 영향을 명시한다.
   기존 immutable 분석 결과를 수정하지 않고 버전이 있는 검증된 projection으로 처리한다.

완료 기준: 대표 OR/AND/예외/열린 목록·미확정 truth table 회귀 PASS와 기존 매칭 golden cases 회귀 확인.
자격이 바뀌는 사례마다 원문 근거와 before/after를 제공한다. 첫 릴리스는 제한된 지원 표현만 허용한다.

### W7. 기존 근거와 검수 질문을 우선 재사용

1. W0 집계에서 실제 노출·마감·사용자 해결 가능성이 높은 미확정 유형부터 처리한다.
   관측 노출 자료가 없으면 임의 인기도 점수를 만들지 않고 현재 공개 상태·마감 등 검증된 기준을 쓴다.
2. 각 건을 기존 근거 재사용 / 결정적 projection 보정 / 검수 질문 보완 / 새 분석 필요로 분류한다.
3. 서술형 조건이라도 명확한 사실 질문으로 만들 수 있고 current provenance가 검증되면
   기존 confirmation-question-draft와 독립 검수 경로로 공급한다. 브라우저에서 즉석 생성하지 않는다.
4. 분야·법적 자격 등 사용자의 단순 예/아니오로 확정할 수 없는 조건은 검토 경계를 유지한다.
5. 기존 receipt 재사용은 input/attachment/질문 결속을 검증한다. 새로운 모델 실행은 준비된 exact manifest 승인 범위를 따른다.
6. release 준비·승인·promotion 쓰기와 웹 배포를 구분하고, 실제 반영 후 현재 serving에서 읽히는지 확인한다.

완료 기준: 처리한 exact 대상마다 미확정 감소/질문 전환/미변경 이유를 기록하고 다른 공고의 판정이 변하지 않는다.
신청서 분석·전체 재분석·worker 활성화를 이 작업의 필수 선행조건으로 넣지 않는다.

### W8. 2차 인수와 운영 결과

- 같은 fixture snapshot에서 설명·판정·질문 전후 차이를 비교한다.
- 새 조건 표현의 false eligible/false ineligible 사례가 발견되면 해당 projection 공급을 중단하고 원인을 수정한다.
- 확인 가능한 근거를 늘린 실적, 기본 후보 노출, 사용자 행동 개선을 각각 보고한다.
- 승인된 배포 뒤 exact URL/alias/소스, 실제 로그인 여정, 원문/회사 변경 후 캐시 갱신을 확인한다.
- 문제 시 이번 UI 변경을 이전 소스로 되돌리되 기존 discovery/verified 공급은 보존한다.
  데이터 projection 변경은 기존 release 복구 절차로 다루며 코드 rollback만으로 DB 복구가 됐다고 보고하지 않는다.

## 6. 검증 계획

| 사례 | 반드시 확인할 결과 |
| --- | --- |
| 확정 0, 후보 있음 | 빈 결과 아님, 후보의 구체적 다음 행동 제공 |
| discovery만 있음 | 자격·관련성·조건 분모 추정 없음, 공식 원문 접근 |
| 프로필 질문 1개/여러 개 | 해당 필드로 이동, 답변 후 재판정, 지원 가능 보장 문구 없음 |
| 입력+원문 혼합 | 입력 후 잔여 원문 조건 유지, 총수·부분 해소 수 정확 |
| 원문 검토만 남음 | 불필요한 회사정보 요구 없음, 검토 이유·근거 제공 |
| 모든 trace pass + 전체성 gate | 전체 자격 확정으로 잘못 표시하지 않음 |
| 검증된 hard fail | 미충족 이유 명시, unknown/마감과 구분 |
| 우대만 미확인 | 필수 자격 차단 안 함 |
| OR 한 경로 충족/전부 실패/일부 미확정 | W6 truth table와 설명 일치 |
| 열린 목록 밖·포털 요약 | 자동 탈락 없음, 근거 수준 유지 |
| 마감·예정·기간 불명·비공개·중복 | 기존 공급 정책 유지, 유효 상태와 건수 일치 |
| 8건 초과 결과 | 전체/표시 수 분리, 다음 페이지 중복·누락 없음 |
| 회사 변경·로그인 복귀·저장 실패 | 맥락 보존, 다른 회사 혼입 없음, 실패를 성공으로 표시하지 않음 |
| 원문 revision 변경·stale 응답 | 오래된 답변/근거로 확정 안 함, 캐시 무효화 |
| 360/390/768/1440px | 핵심 조건·CTA 잘림 없음, 키보드·초점·상태 텍스트 확인 |

실행 명령은 현재 package.json에 있는 다음 항목을 기준으로 선택한다.

- UI/질문 국소 변경: 관련 logic/render/refresh 테스트 + 영향 앱 typecheck.
- 공유 계약 변경: 관련 suite와 `pnpm test` 프로젝트 집계 gate를 최종 exact 소스에서 1회 실행한다.
  포함된 typecheck·product-journey·matching-eval·service-usecases·match-transitions 등을 동일 소스에서 중복 실행하지 않는다.
- 개발 중 빠른 피드백: `pnpm test:profile-answer-consistency`, `pnpm verify:matching-eval`,
  `pnpm verify:service-usecases`, `pnpm verify:match-transitions` 중 변경과 관련된 항목만 선택한다.
- 계약 스키마 변경 시 `verify:openapi`, `verify:grant-criteria-schema`의 포함 여부를 점검한다.
- 테스트가 DB/브라우저 환경을 요구하면 기존 실행 조건을 먼저 확인하고 mock PASS와 실제 통합 PASS를 구분한다.
- 브라우저는 현재 실행 중인 서버/Preview를 사용한다. 개발 서버가 없으면 사용자에게 실행을 요청한다.

1차는 사용자 입력→상태 변화→다음 행동까지, 2차는 원문→조건 해석→판정→현재 serving까지 증거를 남긴다.
모든 테스트 PASS가 사용자 이해도 검증이나 Production 배포를 대체하지 않는다.

## 8. 모델 선정 근거와 완료 보고 형식

- [GPT-5.6 Sol 공식 문서](https://developers.openai.com/api/docs/models/gpt-5.6-sol): complex professional work 및 high/xhigh effort 지원.
- [GPT-6 Astra 공식 문서](https://developers.openai.com/api/docs/models/gpt-6-astra): 복잡한 추론·코딩·연구 작업과 high effort 지원.

문서 확인일은 2026-09-20이다. 작업별 배정은 이 프로젝트의 엔지니어링 판단이며
정확도·속도·비용 우월성을 벤치마크로 입증했다는 의미는 아니다. 가격 절감률·구현 시간을 약속하지 않는다.
Sol 중심으로 실행 연속성을 유지하고, 의미 설계 난도가 큰 W1/W6에 Astra를 사용한다.
서비스 분석 레인의 기존 모델·구독/API 정책은 변경하지 않는다.

각 작업 완료 보고는 아래 형식을 따른다.

```text
작업 / 담당 모델·effort / exact 소스:
사용자에게 바뀐 행동:
변경 파일과 계약:
통과 검증 및 재사용한 gate:
실행하지 않은 검증·사유·남은 위험:
Preview / 실제 사용자 UAT / Production / 서비스 데이터 반영 상태:
다음 작업에 전달할 입력:
```

전체 완료는 사용자가 후보를 발견하고, 조건과 미확정 이유를 이해하고, 유효한 다음 행동을 수행하는
흐름이 검증됐을 때 선언한다. 실제 자격이 맞는 공고가 없는 경우에도 사실대로 설명하고 탐색 경로를 제공한다.

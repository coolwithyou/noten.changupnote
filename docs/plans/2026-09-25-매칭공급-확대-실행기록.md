# 매칭 공급 확대 — 실행과 평가

기준일: 2026-09-25 KST. 담당: 현재 세션 단일 실행자.

## 목표와 범위

사용자 승인한 순서: 현행 누락 집계 → 업종·조건 보완 → 원문 복구·분석·발행 → 독립 평가·실제 계정 인수 → 다음 수집 반복 검증.

현재 모집 중 고유 공고를 조사하고, 수집원과 다음 작업 상태를 층으로 나눈 100건을 평가 대상으로 고정한다. 합성 초기기업 10개는 평가 전용이며 실제 고객 정보에 쓰지 않는다. 신청서 자동작성은 매칭의 선행 조건으로 삼지 않는다.

새 live 모델 cohort는 입력 복구와 코드 검증 후 exact manifest로 제시한다. AGENTS.md의 manifest 승인 경계는 유지한다. 과거 BTS 실행 권한을 다른 공고의 launch grant로 재사용하지 않는다. 기존 raw·원문·분석 receipt는 보존한다.

## 2. 발견한 공통 결함과 수정

### 원문 목록과 공급 판정

기존 Lab 입력은 archive 행만 읽었다. 기업마당 `printFileNm/printFlpthNm`의 별도 공고문이 raw.attachments에도 archive에도 없으면 입력 누락 경고 자체에서 빠질 수 있었다. 원래 입력으로 51/100건이 첨부 unavailable/truncated였고, 선언 목록까지 포함한 입력에서는 70/100건이었다. 차이 19건은 새 수집 실패가 아니라 기존 누락의 추가 발견이다.

- 기업마당 원문 파일과 K-Startup 상세 첨부 선언을 공통으로 합친다.
- 선언됐지만 보관되지 않은 첨부는 Lab 입력·첨부 manifest에 unavailable로 남긴다.
- 운영 입력 준비와 source revision 계산도 같은 선언 목록을 사용한다.
- 공급 판정의 ‘첨부 행 하나 이상이면 complete’를 제거하고 선언별 원본 SHA·storage key·URL을 확인한다.
- 같은 이름의 파일이라도 URL이 바뀌면 이전 보관본으로 채우지 않는다.
- 원본 보관 완료와 텍스트/이미지 의미 커버리지는 별개다. 입력 준비와 독립 원문 검수가 후자를 확인한다.

### 업종 의미

기존 ICT 정책 포함관계에 저장소의 KSIC 대분류·중분류 계층을 연결했다. 음식·의류·가구 제조, 도소매, 창고, 연구개발, 영상 등에서 정확한 업종 라벨 또는 회사가 이미 보유한 KSIC로 상위 업종을 판정한다.

- 하위→상위만 허용하고 부모·형제 업종으로 세부 활동을 추정하지 않는다.
- ‘정보통신업’ 통계 분류와 ‘ICT’ 정책 개념을 동일시하지 않는다.
- 6자리 세무 업종코드나 대분류 접두와 중분류가 모순인 코드는 새 경로의 근거로 사용하지 않는다.
- AI·바이오·친환경 등 제품·기술 요건은 일반 업종에서 자동 추론하지 않는다. 원문/실제 사업 사실과 추가 확인이 필요하다.
- 매칭과 관련성 점수가 동일한 방향성 관계를 소비한다. ruleset은 v16이다.

분류 관계는 [기존 KSIC 모듈](../../packages/core/src/industry/ksic.ts)을 재사용한다. 개념의 동의어·포함·연관을 구별하는 설계 참고: [W3C SKOS](https://www.w3.org/TR/skos-reference/). 콘텐츠 정책범위와 산업분류가 일대일이 아님을 확인하는 공식 자료: [한국콘텐츠진흥원 연계표](https://welcon.kocca.kr/cmm/fms/CrawlingFileDown.do?atchFileId=FILE_b297e8ac-4fa5-4526-a31e-d2185eb8fd74&fileSn=3). 이 자료만으로 조건부 활동을 무조건 포함관계에 넣지 않았다.

### PDF 이미지

텍스트가 200자 이상이면 OCR을 건너뛰던 복구 경로를 수정했다. 이미지 목록을 읽고 이미지가 있거나 목록을 확인하지 못하면 시각 OCR을 요구한다. native text와 OCR은 출처를 구별해 함께 보존한다. 20페이지 상한·신뢰도 기준을 낮추지 않으며 실패는 해당 원문에 남긴다. 원본 PDF가 보관됐으면 사용자가 미리보기를 열어 pdf artifact를 만들기 전에도 복구할 수 있다.

## 3. 평가

`tools/matching-coverage.ts`가 고정 표본과 serving snapshot을 읽어 10개 최소 프로필 × 100건을 실제 matcher로 실행한다. 회사 규모·인증·제품 보유를 추정하지 않는다.

- prediction과 독립 review packet을 분리하고 정답 칸은 null로 둔다.
- review는 source input SHA·회사 프로필·평가 시각에 결속한다.
- `conditional`이어도 `needs_core_review`인 결과는 서비스 후보 회수 성공으로 세지 않는다.
- 독립 정답이 없으면 precision/recall은 null이다.
- 공급 확대 전 snapshot의 1,000쌍: 후보 2쌍, 내부 검토 945쌍, 비추천 53쌍. 이는 정확도가 아니라 현재 노출 분포다.

실행 예:

```sh
pnpm exec tsx --tsconfig apps/web/tsconfig.json tools/matching-coverage.ts \
  --snapshot=spike-out/coverage-20260925-normalized.json \
  --sample=spike-out/coverage-20260925-evaluation-sample.json \
  --output=spike-out/coverage-evaluation-new
```

새 출력 디렉터리를 사용하며 기존 영수증을 덮어쓰지 않는다. 독립 검수 결과 배열은 `--reviews=<path>`로 전달한다. source가 바뀌면 이전 검수 hash를 재사용하지 않는다.

## 4. 운영 처리와 남은 단계

원문 복구 사전 계획: 고정 표본 안에서 기업마당 34건·첨부 48개, K-Startup 27건·첨부 48개. local HWP 변환·macOS OCR을 사용하며 유료 LLM API 호출은 없다. 공고별 결과·실패를 보존하고 기존 publisher의 승격 분석 보호를 유지한다.

실행 결과·검증 및 새 모델 exact manifest는 후속 절에 기록한다. 원문 복구 성공을 분석·발행·추천 성공으로 집계하지 않는다. 검증 중인 코드가 곧 운영 배포를 뜻하지 않는다.

### 종료 기준

1. 표본 100건의 원문·현재 분석·검수·발행 상태와 최소 다음 작업이 설명된다.
2. 필요한 대상만 exact manifest로 분석하고 publishable 결과를 독립 검수·승격한다.
3. 독립 정답 평가 및 실제 글리프 계정에서 조건·질문·조회 갱신을 확인한다.
4. 이후 새 수집 이벤트를 같은 판정으로 처리하고 성공 자산의 모델 호출 0회 재사용을 확인한다.
5. 관찰되지 않은 신규 유입·처리시간 분포·산업 범위는 완료로 선언하지 않는다.

## 5. 2026-09-25 실행 결과

- exact 표본의 61개 공고 작업, 첨부 96개를 원문 복구 대상으로 처리했다. 작업 수준 실패 0이지만 첨부 실패는 기업마당 5개·K-Startup 5개다. 이 수치를 첨부 96개 성공으로 해석하지 않는다.
- 원본 PDF 49개를 추가 복구해 47개 성공·2개 보류. native+OCR 22개, 로컬 렌더 OCR 9개, native text 16개다. 보류 2개는 페이지 OCR 신뢰도 0.565/0.530으로 기준 0.600을 충족하지 못했다.
- DB/R2의 실제 복구 결과를 다시 읽은 100건 입력에서 누락·잘림 없는 공고는 30→91건이다. ZIP의 검증된 자식 파일로 내용을 확인한 경우를 포함한다. 나머지 9건에는 읽지 못한 첨부 15개가 남았다. 원문 의미를 전부 사람 검수했다는 뜻은 아니다.
- 복합 PDF 1건(홍릉벤처밸리)의 원본 SHA 확인·1페이지 렌더 대조에서 업력 7년, 주소 이전 3개월, 부담금 표를 입력 전문에서 확인했다. 전체 47개에 대한 시각 검수는 아니다.
- 이전 실행 파일의 실제 바이트·입력 SHA·첨부 SHA를 결속하는 `legacy_material`을 추가했다. 실제 입력이 바뀐 경우만 재준비하며, 입력이 같은 역사 실행은 기존 결과 검수로 남긴다. 계약 버전 변화만으로 재실행하지 않는다.
- 100건 분류: 현재 원문 변경 55건·신규 5건은 matching-only 준비 대상, 기존 결과 검수 24건·보류 16건. 보류에는 원문 누락 9건이 포함된다. 새로운 모델 호출은 0회다.
- 분류 SHA: `002beb69ea282adc5e5469a4a7b06061094b5d6081567a95d20f1230bff5046d`. 입력 구조·복구 상태 검토이며 독립 자격 심사 정답은 아니다.
- 복구 후 로컬 코드로 조회한 운영 데이터에서 검증된 분석 노출은 64→29건이다. 새 원문과 옛 분석의 결속이 달라져 발생한 보류를 포함한다. 즉시 추천 증가로 보고하지 않으며 새 분석·검수·발행 후 다시 측정한다. 글리프의 조건부 후보 1건은 유지됐다.

### 검증 증거

패키지 빌드, 웹 typecheck·production build, 딥분석 계약 집계 gate, 공고 readiness 집계 suite, 격리 PostgreSQL 공급 통합 테스트를 통과했다. 업종 의미·매칭·관련성·입력·평가·campaign 및 역사 파일 변조/변경 여부 회귀를 통과했다. 새 테스트는 관련 package script에 연결했다.

영수증은 gitignored `spike-out/coverage-20260925-*`에 원본 유지한다. source/input baseline, 복구별 결과, v3 재조회, 분류·평가 행렬이 각각 별도 파일이며 덮어쓰지 않는다. 메인 dirty checkout은 수정하지 않았다. 신규 코드의 배포·새 LLM 실행·독립 정답 평가·새 유입 반복 검증은 아직 수행하지 않았다.

# 작성 중심 창업노트 — 상세 구현 계획

작성: 2026-09-30 KST. 상태: **계획 작성 완료 / 격리 브랜치 구현 진행 중**.

계획 작성 뒤 사용자가 상세 구현 시작을 요청했다. 제품 방향은 아래 사용자 합의를 따른다. 이 문서는 구현·테스트 완료나 배포·운영 모델 실행 승인을 의미하지 않는다. 계획 작성 기록은 [PROGRESS-authoring-first-plan-20260930.md](../../PROGRESS-authoring-first-plan-20260930.md), 현재 구현·검증과 남은 일은 [PROGRESS-authoring-first.md](../../PROGRESS-authoring-first.md)를 따른다.

## 1. 제품 결정과 성공의 정의

> 회사 자료를 한 번 정리하면, 지원사업마다 요구하는 사업계획서와 제안서를 더 빠르게 작성할 수 있다.

- **핵심 가치:** 회사 자료 재사용 → 공고·양식에 맞는 작성 → 검토·수정 → 실제 파일 완성.
- **매칭의 역할:** 명백한 부적합을 줄이고 검토할 후보의 우선순위를 정한다. 모든 조건의 완벽한 확정을 요구하지 않는다.
- **작성 진입:** 회사 권한과 사용할 자료·문서의 준비 상태로 결정한다. 매칭 결과가 `conditional`이거나 일부 정보가 없어도 작성할 수 있다.
- **정직한 구분:** 검토 후보, 확인한 조건, 작성 기능, 문서 저장, 실제 제출은 서로 다른 사실이다. 후보 수를 지원 가능 수로, 다운로드를 제출 완료로 표시하지 않는다.
- **시간 측정:** 초안 생성까지가 아니라 사용자가 검토·수정해 사용할 수 있는 파일까지 걸린 시간을 잰다. 인증·자료 준비·실패 복구·운영자 개입도 별도 포함한다.

### 1.1 이번 방향에서 변경되는 우선순위

| 기존 관심 | 이번 계획의 결정 |
|---|---|
| 전 공고의 정밀 판정·전량 사전 분석 | 선택한 공고와 실제 작성에 필요한 양식부터 처리 |
| 사업자번호 조회 → 매칭 결과가 필수 관문 | 공고를 알고 온 사용자는 작성으로 직접 진입 |
| 기업 정보 전부 수집 후 사용 | 현재 문항에 필요한 정보만 조회·질문 |
| 모든 양식 항목의 자동 입력 | 안전하게 연결된 항목은 자동 반영, 나머지는 문안 제안·직접 편집 |
| 매칭 성공률이 주 지표 | 작성 시간·수정 부담·문서 품질·반복 사용이 주 지표 |

### 1.2 첫 제품 범위와 가설

- 첫 고객 가설: 아스카웍스와 유사한 소규모 서비스·소프트웨어 기업의 대표 또는 실무자. 고객군은 검증 대상이며 전체 시장으로 일반화하지 않는다.
- 첫 문서 범위: 공공 지원사업 사업계획서 및 그에 수반되는 신청서. 일반 영업 제안서·입찰·R&D의 복잡한 예산 작성까지 한 번에 확대하지 않는다.
- 첫 검증: 실제 공고 양식 3종, 실제 사용자 5명. 파일 1종에서 전체 경로를 먼저 완결한 뒤 나머지 2종에 적용한다.
- 이미 있는 공고의 링크·ID로 바로 작성하는 경로는 첫 범위에 포함한다. 미등록 공고 URL 자동 수집과 독립 양식 업로드는 후속 P6로 분리한다.
- 시간 절감·유료 이용 의사는 아직 검증되지 않았다. 기존 기능이 존재한다는 사실만으로 이를 달성했다고 간주하지 않는다.

## 3. 사용자 흐름과 화면 변경

### 3.1 첫 사용자 경로

1. **공고 선택:** 추천 후보에서 선택하거나 서비스에 등록된 공고 링크를 붙여 넣는다.
2. **작성 시작:** 회사 선택과 중요한 자격 쟁점만 보여준다. 22축 입력 완료를 요구하지 않는다.
3. **이번 사업 설명:** 무엇을 하려는지, 누구의 어떤 문제를 해결하는지, 목표·일정·예산을 알고 있는 만큼 입력한다. 모르겠음·나중에 작성도 허용한다.
4. **자료 연결:** 저장된 회사 사실·연락처를 선택하고 기존 회사소개서·계획서를 연결한다. 새 외부 조회는 현재 필요한 사실에 한정한다.
5. **문항별 작성:** 양식의 문항과 작성 요구를 보여주고, 기존 내용·초안·추가 질문을 함께 제공한다.
6. **검토·반영:** 사실 근거와 계획 제안을 구분하고 사용자가 선택한 내용만 문서에 적용한다.
7. **저장·다운로드:** 서버 저장 상태를 확인하고 파일을 내려받는다. 재접속하면 같은 문서와 작성 상태로 돌아온다.
8. **다음 공고 재사용:** 승인한 회사 사실과 공통 설명을 가져오되 이번 공고 전용 일정·예산·목표는 자동 확정하지 않는다.

### 3.2 기존 화면 활용

- 기존 `applications`를 작성 중 문서로 복귀하는 주 진입점으로 사용한다. 첫 베타에서 사이드바 전체 재설계는 하지 않는다.
- `grant-overview`의 주 CTA는 실제 capability에 따라 `작성 시작` 또는 `문서 열기`다. 미확인 자격은 설명하고 작성 접근 권한과 혼동하지 않는다.
- `apply-workspace`는 문서와 문항별 작성 패널을 중심으로 유지한다. 채팅은 보조이며 사용자가 매번 빈 채팅에 프롬프트를 입력하게 하지 않는다.
- `match-results`는 관련 후보와 제외 이유를 보여준다. 근거 없는 적합도 백분율과 `지원 가능 N건` 약속을 제거할 범위를 정한다.
- 모든 자격 조건을 먼저 체크해야 본문을 쓸 수 있는 흐름은 만들지 않는다. 중요한 불일치는 작성 시작 시 보여주되 기존 작성본을 잠그거나 삭제하지 않는다.
- 기간이 지난 공고는 새 모집 후보에서 제외하되 저장된 작성본은 열고 내보낼 수 있다.
- 기존 클라이언트 디자인 체계와 컴포넌트를 사용한다. 관리자 전용 shadcn 규칙을 이유로 사용자 화면의 디자인을 일괄 교체하지 않는다.

## 4. 유연한 후보 탐색 정책

새 후보 선택 정책은 matcher의 적격성 판정을 덮어쓰지 않고, 탐색용 projection을 추가한다. 예시 신규 위치는 `packages/core/src/matching/discovery-policy.ts`다.

### 4.1 자동 제외의 범위

- 마감·취소가 명확한 공고, 예외·선택 분기와 기준일까지 확인한 필수조건 불일치만 기본 후보에서 제외한다.
- OR 조건은 가능한 분기가 모두 불일치할 때만 제외한다. 하나라도 확인되지 않은 분기가 있으면 보류가 아니라 검토 후보로 유지한다.
- 우대조건 불충족은 제외 사유가 아니다. 업종 키워드 불일치·상호 유사도·프로필 빈값도 단독 제외 근거가 아니다.
- `source_changed`, 추출 없음, 오래된 회사정보는 확정 불일치로 사용하지 않는다.
- 신청기간 미확인은 `접수 여부 확인 필요`, 미래 시작은 `모집 예정`으로 분리한다. 마감 공고와 섞지 않는다. 날짜만 있으면 KST 당일 마감은 유지하고 시각이 있는 경우 시각을 반영한다.
- 제외 항목은 삭제하지 않는다. 이유·근거·기준일과 `제외된 공고 보기`를 제공한다.

### 4.2 순위와 설명

- 기본 순위는 사용자 선택 분야·회사 사업 설명·공고 분야·지역 범위·마감 정보의 관련성을 사용한다. 첫 구현은 설명 가능한 기존 relevance/ranking 조합을 우선한다.
- 관련성의 약한 신호는 정렬에만 쓰고 자격 확정에는 사용하지 않는다. `전국 대상`, `이전 허용`, `소프트웨어 분야 관련` 같은 관측 가능한 이유를 표시한다.
- 내부 점수는 선정 확률이나 지원 가능 확률로 노출하지 않는다.
- 선택한 공고는 후보 순위가 바뀌어도 작성 목록에서 유지한다.
- 이 정책은 521건의 무조건 노출을 목표로 하지 않는다. 반복·중복 공고와 무관한 후보를 줄이면서 누락 비용을 측정한다.

## 5. 회사 자료와 작성 근거 계약

### 5.1 기존 사실을 재사용하고 새 자료 영역을 한정

- 법적 기본정보와 매칭 사실은 기존 회사·프로필 원장을 사용한다. 연락처는 기존 `company_application_profiles`/`user_application_profiles`를 사용한다.
- 새 자료는 **회사 공통 자료**와 **이번 신청 전용 자료**로 범위를 나눈다. 회사소개서 안의 특정 프로젝트 매출·과거 목표를 회사 전체의 현재 실적으로 자동 승격하지 않는다.
- 첫 버전은 텍스트 직접 입력과 텍스트 추출 가능한 PDF를 지원한다. HWP/HWPX 자료는 현재 변환 경로로 안전하게 읽히는 범위에서 확장한다. 스캔·암호화·손상 파일은 읽지 못한 상태를 표시하고 직접 입력을 제공한다.
- 원본 → 추출문 → 사용자가 확인한 사실/설명 → 문항 초안의 관계를 보존한다. 출처 충돌은 병합·평균하지 않고 선택을 요청한다.

### 5.2 신규 계약 초안 — 구현 시 기존 타입과 중복 제거

| 계약 | 최소 데이터 | 불변식 |
|---|---|---|
| `WritingSource` | companyId, scope, 원본/텍스트 revision, MIME·SHA, 출처 종류, 관측 시각, 접근 상태 | 회사 범위에서만 읽기. 공고의 공개 첨부 저장소와 섞지 않음 |
| `WritingBrief` | draftId, 이번 사업 목표·제품·고객·기간·예산, revision | 미입력 허용. 회사의 과거 사실과 미래 계획 구분 |
| `WritingSection` | 문항 ID, 문서/source revision, 제목, 요구사항, 분량·평가기준 근거, 안전한 field/paragraph binding 또는 null | 연결 위치를 확신할 수 없으면 자동 반영 불가, 문안 생성은 가능 |
| `WritingSuggestion` | sectionId, 근거 revision 목록, 초안, 사실/계획/질문 구분, 생성 상태, 수락·반영 revision | 생성과 반영 분리. 오래된 초안을 최신 편집본에 자동 덮어쓰지 않음 |

이 명칭은 신규 제안이다. 현재 구현된 타입·테이블로 표시하지 않는다. 실제 스키마를 늘리기 전에 기존 draft metadata·agent runs와 중복 여부를 확인한다.

### 5.3 저장 구조와 API 제안

- 재사용: `grant_document_drafts`, 기존 문서 revision·agent run·사용량 원장, 회사 권한 검사, private R2 접근 계층.
- 추가 후보: `company_writing_sources`(회사/신청 범위와 immutable source revision), `document_writing_briefs`(draft별 입력·낙관적 잠금), `document_writing_sections`(문항·근거·binding·상태). 초안 제안은 기존 run/suggestion 원장을 확장할 수 있으면 별도 중복 원장을 만들지 않는다.
- source rows는 `(company_id, id)`로 권한을 검사하고 내용 SHA 중복 제거도 회사 내부에서만 한다. 동일 파일을 가진 다른 회사의 존재·자료를 노출하지 않는다.
- 제안 API: `/api/web/companies/[companyId]/writing-sources`, 그 아래 업로드 완료/철회 경로; `/api/web/document-drafts/[draftId]/writing-brief`, `/writing-sections`, `/writing-suggestions`. 신규 경로는 모두 **계획 경로**이며 구현 여부를 별도 표시한다.
- 기존 `/studio-snapshots`, `/agent-suggestions`, `/field-agent-suggestions`, `/field-answers`, `/profile-autofill`, `/download`를 유지한다. 불필요하게 v2 작성 API 전체를 새로 만들지 않는다.
- 모든 쓰기는 owner/editor 정책에 맞추고 viewer·다른 회사 접근은 거부한다. 요청의 companyId만 믿지 않고 draft/source의 소속을 서버에서 확인한다.
- 업로드는 용량·MIME·실제 파일 서명·추출 크기를 제한하고 서명 URL을 짧게 유지한다. 로컬 변환은 자원 제한된 프로세스에서 수행한다. URL 수집 확장 시 내부 주소 접근·리다이렉트 우회도 차단한다.
- 회사 자료의 철회/삭제 시 후속 검색·모델 전송을 중단한다. 기존 사용자가 승인해 저장한 문서에 텍스트가 남는다는 점은 설명한다. 보존/삭제 규칙은 기존 계정 삭제 정책과 연결한다.
- 마이그레이션 번호는 실행 시 할당한다. 현재 다른 세션의 `0086` 변경을 덮어쓰거나 재사용하지 않는다. 생성 SQL·역방향 호환·기존 draft 읽기를 격리 DB에서 검증한다.

### 5.4 요청·상태·실패 계약

- source 상태는 업로드/입력 수신 → 추출 중 → 사용 가능 또는 추출 실패이며 철회가 별도로 존재한다. `사용 가능`은 읽을 수 있다는 뜻이고 회사 사실의 진실성을 인증한 상태가 아니다.
- section은 미작성 → 초안 있음 → 사용자 수정/검토 → 반영됨으로 관측한다. 새 자료나 편집본 때문에 제안이 오래되면 기존 문서를 지우지 않고 재검토 대상으로 표시한다.
- 생성 요청에는 draft/section, source revision 목록, brief revision, base document revision, idempotency key를 결속한다. 서버가 실제 접근 가능한 자료로 다시 구성하고 클라이언트가 보낸 자유 source ID를 그대로 신뢰하지 않는다.
- 긴 실행은 `202 + runId`와 상태 조회로 응답한다. 완료·실패·취소를 구분하고 재시도는 같은 실행 결과를 반환하거나 명시적인 새 요청으로 처리한다. 같은 요청의 중복 과금을 막는다.
- 반영 요청은 승인한 suggestion과 base revision을 포함한다. revision 충돌은 `409`, 권한 거부는 `403`, 입력/근거 불일치는 `422`, 예산·빈도 제한은 기존 오류 계약에 맞춘 `429`로 처리한다. 실패한 반영은 문서를 부분 저장하지 않는다.
- 기존 route error/DTO 관례와 같은 의미의 코드가 있으면 재사용한다. 새 웹 API 때문에 모바일 API의 기존 필수 필드를 바꾸지 않는다.

## 6. 문항별 초안 생성과 안전한 문서 반영

### 6.1 처리 단계

1. **문항 구성:** 양식과 공고의 작성 요구를 읽고 문항·평가기준·분량·금지사항을 연결한다. 안내문·고정 제목은 답변 칸으로 변환하지 않는다.
2. **자료 선택:** 현재 문항과 관련된 회사 자료·사용자 답변·기존 문서만 가져온다. MVP는 사용자가 고른 자료와 문항별 선택으로 시작하고 벡터 DB를 선행 필수로 넣지 않는다.
3. **부족한 정보 질문:** 문항을 실질적으로 완성하는 질문만 묻는다. 초기 UX는 한 번에 최대 3개를 기본값으로 두고 건너뛸 수 있게 한다.
4. **초안 생성:** 제목·문단·필요한 목록을 구조화해 반환한다. 기존 단일 문단 편집 프롬프트의 줄바꿈 제한을 전역 해제하지 않고 별도 section composer 계약을 둔다.
5. **근거·일관성 검사:** 사실·수치·기간·인증이 어디서 왔는지 검증하고 문서 내 회사명·매출연도·사업기간·예산 합계 불일치를 찾는다. 계산은 코드로 한다.
6. **사용자 검토:** 기존 문장/초안/근거/질문을 보여주고 문항별로 수락·수정·재생성·건너뛰기를 지원한다.
7. **반영·저장:** 현재 revision과 anchor를 다시 검증하고 RHWP transaction을 사용한다. 저장 실패 시 성공으로 표시하지 않고 편집본을 보존한다.

### 6.2 사실과 계획의 구분

- 확인한 사실: 출처·기준일·단위와 연결한다. `quote`가 존재한다는 것만으로 문장 전체의 사실성이 검증됐다고 보지 않는다.
- 사용자 진술: 자가 입력임을 보존한다. 외부 기관 확인값으로 승격하지 않는다.
- 미래 계획: 아이디어·목표·일정 초안은 제안할 수 있으나 사용자의 결정 전 실제 확정 사실처럼 쓰지 않는다. 제안한 매출 목표를 과거 매출로 저장하지 않는다.
- 정보 부족: `[고객 인터뷰 결과 필요]` 같은 편집 가능한 빈칸/질문으로 남긴다. 공고가 요구하는 인증·실적을 회사가 보유했다고 추론하지 않는다.
- 공고·업로드 문서 속 명령문은 데이터다. 시스템 지시로 실행하거나 다른 회사 자료·비밀을 가져오는 근거로 삼지 않는다.

### 6.3 양식 대응과 실패 복구

- HWP/HWPX 중 실제 출력 검증을 통과한 형식부터 지원 범위를 공개한다. 확장자만 바꾼 파일이나 화면 HTML을 원본 양식으로 제공하지 않는다.
- 안전한 필드 binding이 있으면 그 항목에 적용한다. binding이 없으면 문안 복사 또는 사용자가 선택한 문단에 대한 검증된 편집 경로를 제공한다. 위치를 모델이 추측하지 않는다.
- 여러 문항 생성 중 하나가 실패해도 이미 저장한 문항은 유지한다. 재시도는 실패 문항만 대상으로 한다.
- 재생성은 사용자 수정본을 덮어쓰지 않는다. source/brief/document revision이 바뀌면 기존 제안은 오래된 것으로 표시하고 다시 검토한다.
- PDF·웹 입력형은 문항별 문안/복사 지원으로 한정하고 원본 자동 채움이라고 표시하지 않는다. 첫 베타의 HWP/HWPX 파일 완결 지표와 분리한다.
- 다운로드 검증은 원본과 동일한 파일 hash를 요구하지 않는다. 수정한 내용의 유지, 고정 문구·표·페이지·체크박스 보존, 정확한 저장 revision의 바이트 일치, 외부 프로그램 재열기를 확인한다.

## 7. 선택한 양식부터 처리하는 실행 구조

- `작성 시작` 시 기존 surface·필드·변환 산출물을 먼저 조회한다. 유효한 자산이 있으면 재분석하지 않는다.
- 양식 분석이 필요하면 기존 `applicationPrecomputeQueue`의 source SHA·analysis version·lease·중복 방지를 재사용한다. 쓰기 요청은 명시적 사용자 행동에서 발생시키고 일반 목록 GET가 유료 처리를 시작하지 않게 한다.
- 변환, 양식 항목 분석, 문항 초안 생성, 자격 판정을 각각 진행·오류로 관측한다. 전체 공고 딥분석의 실패가 문서 직접 편집을 차단하지 않게 한다.
- 초기 파일럿은 선정한 3종에 한정한 사전 준비 또는 승인된 bounded 실행으로 검증한다. 운영 전체 worker를 먼저 활성화하지 않는다.
- 신규 사용자 대면 문항 생성은 운영 API 경로·기존 예산 원장을 사용한다. 로컬 구독 CLI를 서비스 요청 처리 서버로 연결하지 않는다.
- source/양식 분석의 중복 방지 키는 exact 문서 SHA와 분석 계약 버전이다. 개인 초안 생성에는 company/draft/section/brief/source/document revision과 요청 키를 더해 회사 간 재사용을 금지한다.
- 생성 요청·동시성·시간 제한·실패 과금·취소·재시도 상한을 사용량 원장과 연결한다. 구체 모델/단가는 실행 시 공식 문서·계약으로 확인하고 문서 속 과거 모델명을 새 기본값으로 확정하지 않는다.
- `observe_only` 상태에서는 실제 처리가 시작되는 듯한 대기 UI를 만들지 않는다. 요청 접수와 실행 가능 시점을 구분한다.

## 8. 국내 기업정보 연동의 우선순위

기존 [소싱 설계](2026-07-11-matching-data-sourcing.md)와 [CODEF 통합 검토](../research/2026-07-14-codef-provider-consolidation-review.md)를 폐기하지 않는다. **작성 시간·중복 입력 감소** 기준으로 적용 순서를 바꾼다.

| 순서 | 정보 | 우선 경로 | 연결 전 확인 |
|---|---|---|---|
| 1 | 회사명·주소·연락처·기본 업종 | 기존 NTS/팝빌/APICK 캐시와 작성 프로필 | 현재 값·정정 경로·사업장 범위. 연락처와 매칭 주소를 혼동하지 않음 |
| 2 | 중소기업·여성·장애인·창업기업 확인 | 실제 확인서/기존 SMPP·창업 확인 캐시, 필요한 상품 검증 | 확인서 종류·유효기간. 조회 없음은 미보유 확정이 아님 |
| 3 | 매출·재무·납세 관련 증빙 | 소유자 동의 기반 CODEF 후보, 기존 DART/금융위의 실제 커버리지 | 과세표준≠회계 매출, 국세≠지방세, 연도·기간·단위, 신생기업 수록 여부 |
| 4 | 고용·보험·IP | 근로복지공단/보험·KIPRIS 등 기존 경로 | 보험 가입자 수와 공고상의 근로자 정의, 권리 상태·회사 식별 |
| 후속 | 신용·광범위 기업정보 | NICE 또는 대체 계약 후보 | 실제 문항 수요·사업자 수록률·최소 약정·보관 조건을 확인한 뒤 선택 |

- CODEF 활성화 선행: company+user+consent version 범위의 저장·철회·접근 계약, 실제 상품 endpoint/parser, 실계정 인증과 표본 기업 응답 검증. 현재 bizNo-global/shared cache를 그대로 읽도록 열지 않는다.
- NICE demo는 실제 기업 사실의 근거로 사용하지 않는다. 데모 호출 성공과 운영 계약·실데이터 검증은 별도다.
- 쿠콘·하이픈은 이미 있는 비교 견적 초안을 활용한다. 공급자 전면 교체를 작성 MVP의 선행 조건으로 만들지 않는다.
- 필요한 정보가 서류·사용자 입력으로 먼저 확보되면 작성 실험을 진행한다. 이때 API 자동 확보율로 집계하지 않는다.
- 공급자 선정 지표: 실제 반환된 유효 사실 비율, 인증 완료·추가 승인 횟수, 줄어든 작성 항목/시간, 실패·빈 응답 포함 비용, 캐시 허용 범위.
- 2026-09-30 공식 문서 재조회에서 [CODEF 공식 가이드](https://developer.codef.io/)는 진입 화면만 확인됐고 상세 상품·계약은 검증하지 못했다. [팝빌 공식 FAQ](https://developers.popbill.com/guide/bizinfocheck/faq/checklist)는 조회 결과가 없어도 비용이 환불되지 않을 수 있고, 신용평가 당시 정보가 현재 보유 정보와 다를 수 있다고 안내한다. 따라서 조회 성공을 최신 사실 확보로 집계하지 않고 빈 응답·정정 비용을 포함한다. 계정별 사용 권한·실제 단가·계약은 구현 시 별도로 확인한다.

## 9. 실행 단계·변경 범위·완료 기준

순서: **P0 → P1 → P2 → P3 → P4 → P5**. P6는 P5 결과로 정한다. 단계별 완료 기록은 진행 파일에 남기며 구현을 맡긴 뒤 되돌릴 수 있는 다음 작업은 계속한다. 외부 사용자·운영 의존성이 있더라도 독립적인 로컬 검증은 진행한다.

첫 구현은 **양식 1종 + 실제 회사 자료의 텍스트 입력 1개 + 핵심 서술 문항 3개**로 P1~P3을 끝까지 연결한다. PDF 자료함 전체, 모든 정보원, 전체 문항 분석을 먼저 완성하려 하지 않는다. 이 경로가 저장·다운로드까지 동작한 뒤 PDF 자료 재사용과 나머지 2종 양식으로 확장한다. P4의 새 공급자 계약이 늦어져도 P5의 작성 가치 검증은 기존 정보와 사용자 증빙으로 진행한다.

### 첫 구현 묶음 — 검토 가능한 변경 단위

| 순서 | 작업 | 의존성 | 해당 변경의 인수 기준 |
|---|---|---|---|
| W1 | 작성 CTA를 자격 판정과 분리 | P0의 기존 경로 확인 | discovery + 편집 가능한 양식은 작성으로 연결. PDF 미리보기만으로 원본 자동 채움을 약속하지 않음 |
| W2 | 회사 텍스트 자료와 신청 brief 저장 계약 | 기존 회사·draft 권한 | 새로고침 후 복원, 타 회사 접근 거부, 버전 충돌 시 사용자 입력 보존 |
| W3 | 자료 입력·선택과 brief 작성 UI | W2 | 자료 1개와 이번 사업 설명을 저장하고 다음 접속에서 재사용 |
| W4 | 서술 문항 3개와 원문 위치·요구사항 연결 | 실제 첫 양식 | 제목/안내와 답변 칸 구분, 불확실한 위치는 자동 반영하지 않음 |
| W5 | 문항별 생성·질문·근거 검증 | W2·W4 | 미입력 사실을 만들지 않음. 회사 실적과 미래 계획 구분. 실패 문항만 재시도 |
| W6 | 초안 검토·선택·반영·Undo·재개 연결 | W3·W5 | 사용자 승인 내용만 반영, 오래된 revision 거부, 저장 후 재열기에서 내용 유지 |
| W7 | 다운로드·외부 재열기와 작성 시간 측정 | W6 | 실제 파일 보존 확인과 수동 기준선 확보. 코드 통과와 시간 절감 성과는 별도 기록 |
| W8 | 나머지 양식 2종·PDF 자료·유연한 탐색 확장 | 첫 파일의 W7 결과 | 실패 유형을 기록하며 범용화. 공고 ID별 예외 하드코딩으로 통과시키지 않음 |

각 묶음은 변경 파일·관련 테스트·미실행 인수를 진행 파일에 기록한다. W1~W7을 연결한 뒤 전체 자료함이나 정보원 확대에 투자한다. 실제 사용자 일정은 미리 확보하되, 파일럿 참여자 모집·연락은 별도 사용자 지시 없이 실행하지 않는다.

### P0. 기존 경로와 표본 확정 — 기반 검증

- [ ] 기존 dirty 작업과 충돌을 확인하고 구현용 격리 checkout을 만든다. 필요한 선행 변경만 소유자·diff를 확인해 반영한다.
- [ ] 실제 양식 3종을 확보한다. 서술형 위주, 기업정보·표 포함, 복합 표/분량 제약의 차이를 포함한다. 첫 양식은 구현용, 나머지 2종은 전이 검증용이다.
- [ ] 현재 지원 범위의 양식 1종으로 로그인→작성→수동 편집→저장→재접속→다운로드→외부 재열기를 실행하고 실패를 분리한다.
- [ ] 기존 원본 SHA·양식 revision·기간·출처를 기록한다. 신청이 마감되면 작성 엔진 회귀 파일로는 남기되 현재 지원 후보와 분리한다.
- [ ] 회사 자료는 실제 사용자 동의로 받고 비공개 저장한다. 아직 확보되지 않았으면 합성 자료 검증으로 구분한다.

변경 범위: 기존 작성 경로의 실제 실패를 해결하는 최소 범위. 신규 화면·정보원·전량 분석은 선행하지 않는다.

완료: 양식 1종의 파일 왕복과 권한 격리 증거. 실패하면 작성 품질 모델을 확장하기 전에 파일 경로를 보정한다.

검증: V1·V2 및 §10의 실제 브라우저/외부 파일 확인. 기존 인수 결과와 새 결과를 섞지 않는다.

### P1. 매칭과 독립된 작성 진입·재개

- [ ] `grant-overview`, `applications`, workspace page의 연결을 정리해 등록된 공고에서 바로 작성한다.
- [ ] `conditional`/discovery 공고에서도 올바른 회사 권한과 양식이 있으면 직접 편집한다. 중요 자격 쟁점은 별도로 노출한다.
- [ ] 기존 직접 편집/항목 제안/원본 미지원 상태를 실제 기능별로 표시하고 전체 미완성처럼 묶지 않는다.
- [ ] 새 양식 준비 요청과 중복·진행·실패 상태를 연결한다. 기존 precompute 정책을 유지하고 실행 여부를 사실대로 표시한다.
- [ ] 저장된 작성본에서 같은 회사·공고·문서로 복귀한다. viewer와 관리자 미리보기는 쓰기를 생성하지 않는다.

대상: `workspaceData.ts`, `workspaceReadiness.ts`, `WorkspaceView.tsx`, `GrantOverviewView.tsx`, `applications`, `annotateWriteSupport.ts`, 필요 시 contracts/route policy.

완료: 정밀 매칭 없이 작성 시작·저장·재개 가능. 거짓 자동작성 약속·타 회사 접근·중복 초안 0건.

검증: V1·V2·V5. 새 큐 연결을 바꾸면 `applicationPrecomputeWorker.test.ts`와 materialization 테스트 추가.

### P2. 회사 자료와 이번 사업 설명

- [ ] 텍스트/PDF 자료를 회사·신청 범위로 저장하고 추출 상태·출처·철회를 지원한다.
- [ ] 기존 프로필/연락처를 불러오고 이번 사업의 목적·고객·차별성·일정·예산을 별도 brief로 저장한다.
- [ ] 알려진 사실, 사용자 진술, 아직 정하지 않은 계획을 구분한다. 과거 문서의 연도·숫자를 현재 사실로 자동 채택하지 않는다.
- [ ] 자료 선택과 승인한 공통 설명을 다음 공고에 재사용한다. 회사마다 별도 저장·접근·캐시 키를 사용한다.
- [ ] DB migration·DTO·API를 additive로 추가하고 기존 draft를 이관 없이 읽는다.

대상: §5의 신규 writing source/brief 모듈, schema/repositories/contracts, `applicationAutofillProfile.ts`, 기존 프로필·자료 UI.

완료: 다른 두 공고에서 같은 회사 자료를 재사용하고, 다른 회사에서는 읽을 수 없다. 철회한 자료는 새 생성에 전달되지 않는다.

검증: V2·V3·V5. 신규 source/brief 통합 테스트는 §10의 격리 DB 방법을 사용한다.

### P3. 문항별 초안·질문·반영

- [ ] 양식의 문항과 공고 요구를 연결하는 section 계약 및 버전 결속을 만든다.
- [ ] 기존 `fieldSuggest`의 근거·질문·사용량 처리를 재사용하고 section composer를 추가한다. 기존 문단 편집 API는 유지한다.
- [ ] 회사 자료와 brief에서 문항별 초안을 만들고 사실/계획/정보 부족을 구분한다.
- [ ] 사용자 수락→안전한 위치 반영→revision 저장→Undo 경로를 연결한다. 불확실한 위치는 문안 제공으로 제한한다.
- [ ] 문서 전반의 숫자·연도·사업명·예산 합계를 검사하고 고정 문구·서명란·확약 내용을 임의 작성하지 않는다.
- [ ] 실패·중단·재생성·오래된 revision을 처리하고 사용자의 수정을 보존한다.

대상: 기존 documents grounding/fieldSuggest/documentAgent 모듈, 신규 section composer/brief 근거 공급, apply-workspace 문항 패널, RHWP transaction.

완료: 실제 첫 양식에서 사용자가 자료를 넣고 주요 서술 문항을 생성·수정·반영·내보내기 가능. 남은 2종은 공고 ID별 하드코딩 없이 지원 범위 안에서 재현한다.

검증: V1·V2·V3·V5, 승인된 모델 품질 평가와 양식 3종 실제 UAT. 합성 응답 테스트만으로 초안 품질 통과를 선언하지 않는다.

### P4. 후보 탐색과 최소 정보원 보강

- [ ] §4 정책을 적용해 확실한 불일치만 제외하고 관련 후보·미확인·모집예정을 구분한다.
- [ ] 작성 중 문서와 후보 순위를 분리하고 제외 이유·복원 가능한 탐색을 제공한다.
- [ ] 파일럿에서 반복 입력 시간이 가장 큰 정보 항목부터 기존 캐시/확인서를 연결한다.
- [ ] 신규 유료 정보원이 필요하면 실제 상품·동의·비용·커버리지 검증 후 한 경로부터 추가한다. 연결 지연은 작성 MVP를 막지 않는다.
- [ ] `target_type=법인`과 `일반기업`처럼 분류 체계 차이를 새 데이터 조회로 덮지 않는다. 정확한 의미 매핑 또는 미확인으로 남긴다.

대상: 신규 discovery policy, 기존 relevance/ranking/build-teaser와 카드 UI, productProfile source 정책 및 필요 provider adapter.

완료: 명백한 부적합이 줄고, 모호한 지역/OR/우대조건 때문에 유효 후보가 사라지지 않는다. 보강 정보가 실제 줄인 입력 시간·질문 수를 기록한다.

검증: V4·V5, 20개 이상 조건 경계 사례와 실제 후보 표본의 사람 대조. 관측 표본 수를 전체 모집단 정확도로 해석하지 않는다.

### P5. 실제 작성 파일럿과 지속 여부 결정

- [ ] 5명·3종 양식의 관측 계획을 고정한다. 사용자당 최소 한 번의 전체 작성 경로를 확보하고 가능한 사용자는 다른 공고 재사용까지 관측한다.
- [ ] 현재 사용하는 한글·기존 문서·범용 AI 방식과 비교한다. 같은 문항을 두 번 쓴 학습 효과를 줄이기 위해 비슷한 문항/과제의 순서를 교차한다.
- [ ] 사용 시간·수정량·필수항목 누락·사실 오류·외부 파일 재열기·운영자 개입·API 비용·반복 사용을 수집한다.
- [ ] §11의 계속/축소/중단 기준으로 판단하고 기능 추가는 결과에 종속시킨다.

완료: 실사용 근거가 있는 판단 보고서. 사용자 미확보·실계정 인증 미실행은 미실행으로 보고하며 합성 UI 테스트로 대체하지 않는다.

### P6. 파일럿 통과 후 확장

- 미등록 공고 링크/개인 양식 업로드: 회사 전용 writing project를 만들고 grantId를 선택 연결한다. 비공개 파일을 공용 grant/raw/R2 자산으로 등록하지 않는다. 기존 grant-bound workspace의 권한·revision 서비스는 재사용하되 별도 프로젝트 식별자를 도입할 필요를 검토한다.
- 자료 자동 검색: 자료량과 검색 실패 측정 후 필요한 경우에만 회사 범위 검색 인덱스를 추가한다.
- 기업정보원 확대: CODEF/NICE/대체 공급자 중 실제 시간 절감과 비용이 증명된 상품만 확장한다.
- 다른 제안서 유형·다회사 컨설턴트·전체 자동화는 첫 파일럿 결과 후 별도 범위를 정한다.

## 10. 검증 명령과 증거

아래는 구현 단계에서 실행할 검증이다. 이번 문서 작성에서 실행한 것으로 표시하지 않는다. 파일명은 2026-09-30 로컬 확인 기준이며 구현 시 변경된 suite를 반영한다.

### V1 — 문서·작성 로컬 suite

```bash
pnpm test:apply-workspace
pnpm test:document-agent
pnpm test:profile-autofill
```

변경한 기능을 포함하는 suite만 선택한다. 상위 suite에 포함된 하위 테스트는 같은 SHA에서 반복하지 않는다.

### V2 — 영속성·권한·동시성

- 기존 `apps/web/src/lib/server/documents/documentJourneyPostgres.integration.ts`와 `applicationAutofillProfile.integration.test.ts`의 호출 경로·데이터 생성 범위를 먼저 확인한다.
- 현재 `pnpm test:product-postgres`는 전용 Unix socket 임시 PostgreSQL에서 회사 쓰기·정정뿐 아니라 `verifyDocumentJourneyPostgres`도 호출한다. 기존 DATABASE_URL/PG 설정을 제거하는 이 격리 실행 경로를 재사용한다.
- 새 자료/brief/초안 권한·중복 요청·경합·복구·migration 검증을 기존 runner에 연결한다. 별도 실행이 필요하다고 확인될 때만 `tools/test-writing-postgres.mjs`를 추가하며 동일 검증을 중복 실행하지 않는다.
- 실제 기관 HWP/HWPX fixture를 필수로 확인하려면 파일과 manifest를 준비한 뒤 `CUNOTE_REQUIRE_INSTITUTION_FORM_FIXTURES=1 pnpm test:product-postgres`를 사용한다. 일반 실행의 fixture SKIP은 실제 양식 통과가 아니다.
- 이 문서 왕복 테스트는 격리 PostgreSQL과 메모리 파일 저장소를 사용한다. 통과해도 실제 R2·로그인·브라우저 다운로드·외부 한글 재열기의 증거를 대신하지 않는다. 운영 환경변수를 읽는 DB 테스트를 대신 실행하지 않는다.

### V3 — 근거·초안·자료

```bash
pnpm exec tsx --tsconfig apps/web/tsconfig.json apps/web/src/lib/server/documents/fieldSuggest.test.ts
pnpm exec tsx --tsconfig apps/web/tsconfig.json apps/web/src/lib/server/documents/documentAgentPrompt.test.ts
```

V1에 포함되면 별도 반복하지 않는다. 신규 section composer/source 테스트에는 다음 사례를 넣는다: 다른 회사 자료, 철회·오래된 근거, source injection, 공고 요건의 회사 실적 오인, 과거 매출과 목표 매출, 사용자 수정 보존, 단락/표 위치 불명확, 생성 일부 실패, 예산 합계·연도 불일치.

### V4 — 후보 탐색과 외부 정보

```bash
pnpm exec tsx packages/core/src/matching/match.test.ts
pnpm exec tsx packages/core/src/matching/relevance.test.ts
pnpm exec tsx --tsconfig apps/web/tsconfig.json apps/web/src/lib/server/productProfile/resolveProductCompanyProfile.test.ts
```

신규 `discovery-policy.test.ts`에는 KST 경계, OR·예외·이전 허용, 우대조건, 불명확한 지원기간, raw/source 변경, 긍정 전용 데이터의 조회 없음, 기존 저장 문서 접근을 포함한다. 미반환값을 false로 바꾸지 않는 provider fixture도 필요하다.

### V5 — 공유 계약과 통합 gate

```bash

pnpm verify:openapi
pnpm verify:route-policy
```

공유 DTO·API·DB 변경 시 관련 suite와 위 프로젝트 집계 검증을 수행한다. UI/서버 번들 연결을 바꾸면 `pnpm --filter @cunote/web build`를 추가한다. 삭제했던 광범위 E2E/디자인 하네스를 복원하지 않고 실제 영향 범위의 검증을 유지한다.

### 실제 사용자·파일 증거

- 사용자가 실행한 서버 또는 승인된 환경에서 실제 인증·회사 권한·자료 선택·생성·반영·저장·재접속·다운로드를 확인한다. 개발 서버를 임의로 시작하지 않는다.
- 지원 대상 원본/수정본을 별도 보존하고 로컬 한글 등 대상 외부 프로그램에서 열어 필수 표·문구·분량·입력 내용이 유지되는지 확인한다. 도구가 없으면 이 검증은 미실행이다.
- 코드 테스트, 합성 브라우저, 실제 provider 응답, 실제 사용자의 시간 절감, 배포 결과를 서로 다른 증거로 기록한다.

## 11. 파일럿 지표와 결정 규칙

### 11.1 고정할 관측 정의

| 지표 | 정의 |
|---|---|
| 작성 소요 시간 | 자료 준비·인증·입력·검토·수정·다운로드 검증까지의 사용자 active time. 서버 대기는 별도 wall time도 기록 |
| 초안 채택 | 그대로 사용/수정 사용/폐기한 문항 수. 승인 클릭만으로 품질을 판정하지 않음 |
| 사실 품질 | 잘못된 수치·실적·인증·연도·회사 식별, 근거 없는 단정, 필수 내용 누락 |
| 양식 품질 | 원본의 고정 문구·표·문항 보존, 저장 후 값 유지, 외부 재열기, 분량 제약 |
| 재사용 가치 | 다음 공고에서 다시 묻지 않은 사실, 재사용한 설명, 절약 시간 |
| 운영 비용 | 회사 조회·문서 분석·생성·실패 재시도·저장 + 운영자 검수 시간. 로컬 구독 실험비와 운영 API 비용 분리 |
| 수요 | 다시 사용한 행동, 정해진 가격의 유료 시험 참여. 인터뷰의 호감 답변과 구분 |

이벤트는 기존 사용량/초안/제안 원장을 우선 이용한다. 필요한 추가 이벤트 예: writing_started, source_attached, section_suggested, suggestion_accepted, draft_saved, download_completed, writing_resumed. 본문·개인정보를 이벤트 payload에 넣지 않는다.

### 11.2 초기 의사결정 기준 — 목표이며 현재 성과 아님

- **계속:** 비교 가능한 작성 과제에서 사용자 시간 중앙값 50% 이상 감소, 양식 3종 모두 검증된 파일 왕복, 사실 오류의 유형·빈도를 설명 가능, 최소 5명 중 3명이 다음 공고에 재사용하거나 구체 가격의 유료 시험에 참여. 작은 표본이므로 시장 적합성 확정이 아니라 제한 베타 지속 근거다.
- **품질 보류:** 잘못된 회사 사실·서명·확약을 자동 확정하거나 저장본 손실·회사 간 자료 노출이 나오면 해당 기능 노출을 중단하고 수정한다. 표본에서 사고 0건이어도 전체 무오류를 주장하지 않는다.
- **범위 축소:** 문안 작성은 시간을 줄이지만 양식 반영이 반복 실패하면 검증한 양식 유형에 한정한다. 특정 고객군에서만 효과가 있으면 그 고객군에 집중한다.
- **중단 검토:** 사용자가 초안을 대부분 다시 쓰거나, 운영자가 대신 작성하는 시간이 지속적으로 필요하거나, 실제 운영 비용을 반영한 가격에 수요가 없으면 전면 기능 확장을 멈춘다.
- 검증된 양식 밖의 실패를 숨기지 않는다. 지원 가능 범위와 전체 시도 분모를 함께 보고한다.

2주는 **첫 가치 검증의 권장 투자 상한**이며 모든 P0~P6 구현 완료 예상이 아니다. 첫 구현용 양식에서 실패한 지점과 남은 비용을 기록하고 상한에서 재판단한다. 계약·사용자 일정 때문에 관측이 없으면 성공 대신 검증 미완료로 결론낸다.

## 12. 전환·배포·독립 진행

- 새 자료/초안/후보 정책을 독립적으로 끌 수 있게 적용 범위를 분리한다. 기존 document-agent/field-editor 플래그를 전역적으로 의미 변경하지 않는다.
- 기존 저장본은 새 기능이 꺼져도 읽고 다운로드할 수 있게 한다. additive migration과 읽기 호환을 유지하고 롤백에 데이터 삭제를 요구하지 않는다.
- 배포 전 exact commit·타입/계약 검증·권한 검증·양식 증거를 결속한다. 운영 반영은 해당 범위의 명시적 승인과 프로젝트 배포 규칙에 따른다.
- Gate R은 해당 로컬 대량 모델 실행에 적용한다. 읽기·오프라인 검증·계획 문서에 확대하지 않는다. 운영 API worker 활성화와 사용자 자료 전송 범위도 기존 계약을 따른다.
- 새 유료 조회·모델 실행·실계정 인증·운영 DB migration·배포·외부 사용자 모집은 구현과 구분해 구체 대상/비용/데이터 범위를 준비한다. 이미 승인된 동일 범위는 식별자 변경만으로 재승인을 요구하지 않는다.
- 이번 계획을 이유로 다른 세션의 코드·디자인 작업을 중단하거나 덮어쓰지 않는다. 구현 착수 시 겹치는 범위만 조정한다.

# 지원 가능 미분석 502건 — 구독 모델 매칭분석 실행계획

작성일: 2026-09-20 KST
계획 기준 소스: `8668796681416ed92f8938c7e3b490c193bdc4c8`
상태: 계획 작성 완료. campaign prepare·grant·모델 실행·release·서비스 쓰기는 미실행.

## 1. 목적

현재 서비스는 분석이 없어도 공고를 `discovery`로 보여준다. 이 계획의 목적은 공고 노출을 다시
막는 것이 아니라, 현재 지원 가능한 discovery 공고를 기존 구독 모델 경로로 점진적으로
`verified` 매칭 결과로 전환하는 것이다.

완료 기준은 502건을 억지로 모두 `publishable`로 만드는 것이 아니다. 고정 snapshot의 모든
대상을 재사용·검수·신규 분석·원문 변경·복구·품질 보류·실행 중 마감으로 빠짐없이 결산하고,
안전한 결과만 공급하는 것이다. 한 공고의 실패나 HOLD가 다른 공고의 진행을 막지 않는다.

신청서 필드 분석, Kordoc, RHWP 작성 준비도, 전체 22축 확정은 이번 매칭 분석의 선행조건이 아니다.
단, 첨부 문서 안의 자격조건은 매칭 원천으로 계속 읽는다.

## 2. 현재 기준선

2026-09-20 15:38 KST Production DB 읽기 전용 집계:

| 구분 | 건수 |
| --- | ---: |
| `open + visible + 신청 종료 전 + 중복 대표` 공고 | 542 |
| 현재 원문에 결속된 `verified` 매칭 결과 | 40 |
| 현재 유효한 매칭 결과가 없는 `discovery` | 502 |
| `discovery / unreviewed` | 493 |
| `discovery / source_changed` | 9 |

이 502건은 제품 serving 관점의 미분석 수다. `unreviewed`는 현재 공급 evidence가 없다는 뜻이지,
역사 분석 artifact가 전혀 없다는 뜻은 아니다. 따라서 **502건을 곧바로 502회 재분석하지 않는다.**
준비 시점의 campaign 분류가 기존 결과 재사용, 검수만 필요, 실제 신규 실행 수를 확정한다.

현재 수치는 실행 권한이나 exact target manifest가 아니다. 준비 시점에 마감·신규 유입·원문 변경이
발생하면 새 snapshot 수량과 502건 기준 집합의 차이를 별도로 보고한다.

## 3. 고정 원칙

1. 로컬 구독 실행만 사용한다. `ANALYSIS_LAB_TRANSPORT=claude-cli`이며 API fallback은 금지한다.
2. 매칭은 `matching_only`로 실행한다. 신청서 분석 실패가 매칭을 HOLD시키지 않는다.
3. 현재 input·attachment·validator·prompt에 결속된 결과는 재사용한다.
4. `publishable`은 모델 실행 종결 상태이지 서비스 공급 완료가 아니다. 독립 검수와 release를 분리한다.
5. target-local `held|failed|source drift`는 해당 공고만 격리하고 다음 공고를 계속한다.
6. manifest/grant 손상, Max 인증 공통 실패, lease 충돌·상실, 프로세스 abort, 사용창 소진만 공유 중단이다.
7. 공유 중단 후에는 같은 child의 실제 미착수 `skipped`만 재개한다. 성공·HOLD 결과를 재실행하지 않는다.
8. 공고가 실행 중 마감되면 실패율을 낮추려고 대체 대상을 넣지 않고 `closed`로 결산한다.
9. 사용자 승인은 exact campaign 전체에 한 번 받는다. child별 grant는 원장 역할 분리이며 사용자 재승인이 아니다.
10. `lab:promote --write`는 실제 서비스 쓰기이므로 분석 실행 승인과 분리한다.

| AI 독립 검수 | `claude-fable-5 / claude-cli` | 새 primary 결과와 검수 미완료 재사용 결과 | 원문·criteria 대조 1회 |

API로 전환하지 않는다.

## 5. 실행 구조

```text
현재 지원 가능 snapshot
  -> 502 serving gap과 current material 결속
  -> 재사용 / 검수만 / 준비 미착수 / 신규 / source_changed / terminal 복구 / HOLD / 제외
  -> 실제 live 대상만 matching_only child manifest
  -> child 순차 실행, concurrency 2
  -> publishable 결과 독립 검수
  -> 안전한 부분집합 release 준비
  -> 별도 승인 후 서비스 promotion
```

### P0. 대량 실행을 위한 최소 보강

현재 campaign은 child당 최대 100건, 동시성 2를 지원한다. 과거 41건 실행에서도 lease 만료와
사용창 중단이 있었으므로 502건을 100건 단위로 시작하지 않는다.

- `lab:matching-campaign --prepare`에 `--child-size=25`를 추가한다.
- 허용 범위는 1~100이며, 선택값과 각 child target 수를 campaign index에 봉인한다.
- 동시성은 검증된 2로 유지한다. child manifest 여러 개를 동시에 실행하지 않는다.
- `--status`가 가리키는 다음 child 하나만 grant·launch하는 얇은 `run-next` 경로를 추가한다.
- `run-next`는 새 큐·DB schema·독자 lease를 만들지 않고 기존 `lab:launch:grant` 또는 `lab:launch`의
  exact 명령만 출력한다. 명령을 내부에서 자동 실행하지 않는다.
- 운영자가 사용자 승인 campaign SHA를 입력한다. CLI는 승인 사실을 추정하지 않고 campaign SHA,
  다음 child SHA, 현재 paused runtime·lease 0만 검증한다.
- shared stop과 사용창 종료에서는 자동으로 다음 child를 시작하지 않는다.

모든 502건이 실제 live 대상이라는 최악의 경우 child는 `25 x 20 + 2`로 최대 21개다. 재사용·검수만
필요한 대상은 primary child에서 빠지므로 실제 child 수와 모델 호출 수는 더 작을 수 있다.

최소 검증은 campaign CLI/partition/status/다음-child 계약, launch grant 결속, lease 재개 사례와
웹 typecheck로 제한한다. 전체 제품 suite·브라우저·신청서 suite는 실행하지 않는다.

### P1. 읽기 전용 snapshot과 누락 없는 분류

기준 명령 형식:

```bash
pnpm lab:matching-campaign -- \
  --prepare \
  --as-of=<canonical-ISO> \
  --allowed-stage=launch \
  --child-size=25
```

준비는 모델 호출·runtime lease·서비스 DB/R2 쓰기 없이 아래를 content-addressed artifact로 봉인한다.

- exact target ID와 관측 시각
- 현재 input/attachment/material source SHA
- `reusable`
- `primary_review_required`
- `prepared_not_started`
- `new`
- `terminal_recovery`
- `source_changed`
- `quality_held`
- `excluded`
- child manifest SHA 목록과 모델·prompt·validator·package runtime

분류 합계는 snapshot 고유 ID와 정확히 같아야 한다. 제품의 502 serving gap과 campaign의 실행 필요 수가
다르면 기존 미승격 분석, 검수 미완료, 품질 HOLD, 마감 변화로 차이를 설명한다. 설명되지 않는 차이는 STOP이다.

### P2. exact campaign 한 번 승인

prepare 결과에서 다음을 사용자에게 한 번 제시한다.

- campaign SHA와 classification SHA
- snapshot 수량 및 502 기준 집합과의 차이
- 카테고리별 수량
- 실제 primary 호출 예정 수
- 검수만 필요한 수
- child 수·각 target 수·모델·동시성
- 당일 마감과 source_changed 수
- 실행 상한: matching-only launch와 receipt 종결까지

승인 후 각 child에 `analysis-launch-grant-v1`을 발급하지만 target별·child별 사용자 재승인을 요구하지 않는다.
material contract가 바뀌어 campaign을 재준비하면 새 campaign SHA를 승인받는다.

### P3. 첫 child를 운영 canary로 사용

첫 25건은 별도의 품질 실험이 아니라 실제 campaign의 첫 child다. 완료 뒤 아래만 확인하고 정상이라면
같은 승인 범위에서 다음 child로 계속한다.

- Max 인증이 `claude.ai/firstParty/max`
- API credential과 provider override가 자식 프로세스에 전달되지 않음
- exact child manifest/grant/receipt 결속
- runtime lease 갱신과 종료 후 반환
- publishable/held/failed/skipped 합계가 25
- 공유 중단이 아닌 개별 오류가 다음 target을 막지 않음

publishable 비율이나 HOLD 비율은 admission gate가 아니다. 일부 품질 결과가 나쁘다는 이유로 전체를
중단하지 않고 원인별 target을 격리한다. 공통 프롬프트·validator 결함이 반복되어 잔여 전체를 오염시킬
근거가 있을 때만 Astra 판단으로 STOP한다.

### P4. 나머지 child 연속 실행

- `caffeinate -i` 아래에서 child 하나씩 실행한다.
- child 종료 receipt와 lease 반환을 확인한 뒤에만 다음 child를 시작한다.
- 첫 child 실측 처리시간으로 같은 Max window에서 안전하게 끝낼 수 있는 다음 child 수를 계산한다.
- 사용창 여유가 불확실하면 child 경계에서 멈춘다. target 중간에 임의 종료하지 않는다.
- shared stop이면 status가 제시한 같은 child의 `skipped`만 기존 grant 권한으로 재개한다.
- source drift가 발견된 공고는 현재 child에서 격리하고 다음 snapshot의 `source_changed`로 재준비한다.
- 정상·변화 없음 감시는 모델을 호출하지 않는다.

역사 처리량 약 23건/시간을 단순 상한 참고로 쓰면 502건 전부 신규인 경우 primary 종결만 약 22시간
규모다. matching-only의 실제 속도는 다를 수 있으므로 이는 SLA가 아니다. 첫 child 실측 후 총 작업창
예상만 갱신하고, 속도를 맞추려고 동시성을 3~4 또는 다중 child 병렬로 올리지 않는다.

### P5. 검수와 부분 release

- 재사용 가능한 검수 결과는 그대로 사용한다.
- `primary_review_required`는 primary를 다시 돌리지 않고 검수만 수행한다.
- 신규 publishable에는 Fable 독립 검수를 1회 수행한다.
- Sonnet 감사와 Opus adjudication은 기존 policy가 요구한 대상에만 실행한다.
- 매칭 판단에 영향 없는 신청서 품질 HOLD는 매칭 release를 막지 않는다.
- 필수조건 반대 해석, 제외조건 누락, 근거 없는 적격, 영향 불명 오류는 해당 공고만 차단한다.

최대 50개 안전 결과 단위로 release 후보를 만들 수 있다. 각 wave는 aggregate → shadow → dry-run을
한 번씩만 수행한다. 한 공고의 shadow 오류는 기존 subset continuation 계약으로 그 공고만 제외하고,
정상 결과를 다시 분석하지 않는다.

release approve까지의 오프라인 처리는 exact 승인 범위로 이어갈 수 있지만, 실제
`lab:promote --write`는 서비스 DB 변경이므로 별도 명시 승인을 받는다. promotion 후에만 제품
`matching_evidence=verified` 수가 증가한다.

## 6. 토큰 최적화 규칙

1. **가장 큰 절감은 호출 제거다.** 기존 exact 결과 재사용 > 검수만 > 신규 분석 순으로 처리한다.
2. matching-only에서 신청서 roundtrip·Kordoc·필드 repair를 호출하지 않는다.
3. primary는 공고당 기본 1회다. 순수 `ambiguous|input_missing`을 없애려고 반복하지 않는다.
4. 독립 검수는 공통 지침 prefix를 고정하고 검증된 packet을 stdin으로 전달한다.
5. 원문·첨부는 동일 내용 중복을 제거하되 자격·제외·예외·기간 근거를 글자 수로 임의 절단하지 않는다.
6. 전송 오류 재시도와 의미 repair를 별도 집계한다. validator가 특정하지 않은 전면 재시도는 금지한다.
7. 결과가 conditional이어도 확인된 축이 2개 이상이고 criterion mismatch가 없으면 기존 정책대로 공급 후보가 될 수 있다.
8. 동일 입력의 held를 모델만 바꿔 반복하지 않는다. 원인·다음 조치를 기록한다.
9. usage sidecar에서 lane별 input/output/cache tokens와 요청 수를 기록한다. 누락 usage는 0이 아니라 unknown이다.
10. 구독 창 소진은 정상적인 공유 중단으로 처리하며 유료 API fallback을 사용하지 않는다.

## 7. GO / STOP / 재개 기준

GO:

- exact snapshot과 502 기준 집합 차이가 설명된다.
- child별 input/attachment/material SHA와 package runtime이 봉인된다.
- runtime은 `paused`, owner/expiry 없음, active deep/application lease 0이다.
- Cloud Run main worker는 `observe_only`다.
- Max 인증 preflight와 credential 제거가 통과한다.
- 이전 child receipt와 lease 반환이 확인된다.

target-local 격리 후 계속:

- 공고 마감·비노출·중복 전환
- source/input/attachment drift
- 개별 timeout·invalid response·HTTP 오류
- semantic HOLD 또는 validator 불통과
- 신청서 관련 보류

전체 신규 착수 STOP:

- campaign/manifest/grant/receipt hash 불일치
- 공통 Max 인증 실패 또는 API 경로 의심
- runtime lease 충돌·상실·갱신 실패
- 프로세스 abort 또는 Max window 소진
- 공통 prompt/validator 결함이 잔여 target 전체에 영향을 준다는 반복 증거

재개:

- 같은 material binding과 같은 child라면 미착수 `skipped`만 기존 승인으로 재개한다.
- 성공·held·개별 failed receipt는 보존한다.
- 입력 또는 실행 계약이 바뀌면 해당 대상만 새 manifest로 재준비한다.
- 임의 대체 target을 넣거나 다음 날 신규 공고를 기존 campaign에 추가하지 않는다.

## 8. 완료 보고

분석 campaign 완료 시 아래 수량을 서로 섞지 않고 보고한다.

- 기준 snapshot과 실행 중 마감/변경 수
- 역사 결과 재사용 수
- primary 재실행 없이 검수만 한 수
- 실제 Opus primary 호출 대상·종결 수
- publishable / conditional / held / failed / skipped
- Fable 검수, Sonnet 감사, Opus adjudication 요청 수
- child별 시작·종료·shared stop·resume와 최종 lease 반환
- lane별 token telemetry와 unknown usage
- release 준비·approve 수
- 실제 promotion 수와 서비스 `verified` 증가 수
- 남은 discovery를 원인별로 분리한 수

`publishable` 수를 서비스 반영 수로 부르지 않고, 매칭 완료를 신청서 작성 완료로 부르지 않는다.

## 9. 이번 계획의 실행 경계

이 문서는 계획만 확정한다. 다음은 아직 수행하지 않았다.

- child-size/run-next 구현
- 502건 exact campaign prepare
- 사용자 live 실행 승인
- grant·모델 호출·runtime lease
- 독립 검수·release prepare/approve
- `lab:promote --write`
- 운영 worker 활성화

다음 단계는 P0 최소 보강을 구현하고 관련 계약만 검증한 뒤, P1 읽기 전용 prepare로 exact campaign
SHA와 실제 모델 호출 대상 수를 만드는 것이다. 그 결과를 사용자에게 제시해 campaign 전체 실행 승인을
한 번 받은 후 P3~P4를 연속 수행한다.

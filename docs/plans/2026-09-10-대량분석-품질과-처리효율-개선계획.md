## 0. 재현 자료와 정답을 고정한다

- 보고서의 수동·무호출 검증 26개를 출발점으로 `seq → grant ID → run/input/attachment SHA →
  document/field/criterion ID → 기대 의미 → 재현 방법` 목록을 만든다. sidecar는 정식 receipt와
  구분하고, 원본이 없으면 재현 불가로 표시한다. 원문 전체와 개인정보를 새로 Git에 복제하지 않는다.
- 현재 함수에서 실패하는 최소 사례와 정상 대조군을 함께 둔다. 관측된 결함과 추가 의심을
  분리하고, seq 1의 대안 자격 경로처럼 미확정인 사례는 원문 판정부터 수행한다.
- 신청서 필드는 입력 여부, 작성 주체, 질문, 선택 개수, 주 양식 여부, 쓰기 위치를 각각 채점한다.
  anchor 성공 여부만으로 의미 정답을 대신하지 않는다.
- 정상 HWP/HWPX 저장(seq 9/21), 진짜 복수 선택(seq 17), 실제 트랙별 조건 차단(seq 19),
  자동 근거 교정(seq 33)을 대조군에 포함한다.
- 풀 연결을 쓰는 조사 스크립트는 transaction-local read-only를 사용한다. 종료 후 다른 작업에
  설정이 남지 않는 격리 테스트와 SQLSTATE 기록을 추가한다.

완료 기준: 모든 알려진 문제에 재현 fixture 또는 증거 부족 사유가 있고 기대 결과를 원문으로
설명할 수 있다. 다운로드·파싱·triage·모델·검증·교정·anchor·대기를 분리하는 측정 기준을 정한다.

## 1. 정규화·검증·교정이 같은 의미를 따르게 한다

구현 위치: `apps/web/src/lib/server/deep-analysis/extractor.ts`, `validator.ts`, Lab 추출·repair 경로.

- **seq 35:** raw `list_semantics`를 open/closed 어느 쪽으로 넣어도 closed 값과 열린 목록 설명이
  함께 남는 재현을 고친다. 창업기업 분류와 법인/개인 구분을 나눠 원문의 의미를 먼저 확정한다.
  open을 강제하거나 validator를 우회하는 방식으로 통과시키지 않는다.
- 정규화 전후 값, 변경 규칙과 사유를 제한된 진단 정보로 보존한다. 반복 정규화해도 의미가
  다시 변하지 않아야 한다. validator 오류와 repair 지시가 동일한 조건을 참조하게 한다.
- 같은 정규화 결과·검증 오류가 반복되면 구조적 충돌로 분류한다. 변경 없는 전체 응답을 다시
  생성하는 요청을 줄이되, 근거가 부족한 값을 자동 확정하지 않는다.
- **seq 11:** 복합 OR criterion과 관련 축의 결속을 명시한다. OR을 독립 필수 조건들로 쪼개지
  않고 축 검증을 통과하게 한다.
- **seq 27/19:** 신청자인 제조기업의 공통 조건과 다른 역할·트랙 조건이 섞인 경우를 구분한다.
  단어 포함만으로 공고 전체에 role split을 적용하는 오탐을 줄인다.

완료 기준: seq 35의 값/설명 모순 0, 동일 오류의 무변경 반복 요청 0, seq 11 OR 의미 보존,
seq 27 정상 공통 조건 보존, seq 19의 실제 트랙 조건 전역화 차단 유지. 원래 raw 응답이 남지
않은 부분은 합성 재현임을 표시한다.

  찾는다. 구역마다 작성 주체, 신청 단계, 원문 위치를 결속한다.
- seq 5/17/23/31의 합본 양식과 seq 11의 참여제한 질문 7개·기업명·서명·동의 항목을 복구한다.

- `not_applicable`의 근거를 양식 없음, 지원 형식 없음, 원문 부재, 분석 보류로 구분해 전달한다.

  자동 완료 처리하지 않는다.

### 입력 의미와 선택 제약

- seq 1의 고정 문구 3개와 seq 10의 심사표·일정·목록 6개는 입력에서 제외하고,
  seq 1의 핸드폰·희망 지원기간·기술지원 요구내용은 복구한다.
- 휴리스틱 확신도와 구역 의미가 충돌하면 재판정한다. 안내 placeholder와 실제 기입 값을
  구별하고 모든 필드를 일괄 모델 검토로 보내지 않는다. 재판정 요청 수도 함께 측정한다.
- seq 2/3/6의 동의 질문을 실제 선택지에 연결하고 고정 보유기간 등을 입력에서 제외한다.

  빈 선택의 허용 여부는 원문 필수성에 따르며 동의 의사를 추정하거나 미리 채우지 않는다.
- 실제 중복 선택 허용(seq 17)은 유지한다. 같은 모양의 체크박스라도 의미가 다르면 제약을

### 쓰기 위치와 완료 판정

- held seq 0/8/13/19/22/38의 실패 필드를 조사해 문서·표·행·열·질문 문맥에 결속한다.
  위치를 유일하게 확인하지 못하면 보류를 유지하며 임의로 쓰지 않는다.
- 구역 누락, 필수 입력 누락, 선택 모순, 위험한 anchor가 남은 결과는 자동 작성 준비 완료로
  노출하지 않는다. 안전하게 제외된 optional 항목의 conditional 처리는 현행 정책을 유지한다.
- 가상값으로 필드 생성→편집 계획→저장→재파싱을 검증하고, 이후 Studio RHWP에서 선택·저장·
  다운로드·다시 열기와 표/체크박스/페이지 레이아웃을 확인한다.

완료 기준: 알려진 오탐·누락과 단일 선택 위반 0, 주 양식·필수 부속 양식 선택 정확,

## 3. 매칭 의미와 원문 커버리지를 보강한다

### 평가 점수와 자격·우대 조건

- seq 2/3의 동일 매출 점수표를 일관되게 표현한다. 지원 자격, 독립 우대 조건,

- `<`/`<=`와 상·하한 포함 여부, 단위, 구간별 점수를 보존한다. 기존 계약으로 안전하게
  표현할 수 없으면 원문을 text_only로 유지하고 평가 점수를 자동 계산하지 않는다.
- 모든 경계의 직전·동일·직후 합성 사업자를 평가한다. 같은 점수표의 중복 pass 0,
  무관한 required/exclusion 변화 0을 확인한다.
- seq 1의 비영리/조합 대안과 SME required의 scope를 원문으로 판정한다. 실제 허용 대안이라면
  매칭에서 AND로 막지 않도록 수정하고 근거 부족이면 conditional로 남긴다.

### ZIP과 HML

- seq 25의 ZIP은 부모 archive와 자식 5개를 SHA·추출 상태·입력 포함 여부로 연결한다.
  모든 멤버의 투입이 입증된 경우에만 부모의 중복 미변환 경고를 제거한다.
  일부 누락·실패·잘림·중첩 archive와 seq 0/4/19의 유사 사례도 검증한다.
- seq 29 HML은 읽기용 변환부터 구현한다. XML 파서의 외부 엔티티를 비활성화하고 문단·표·
  출처 위치를 보존한다. 깨진 문서와 지원하지 않는 구조는 명시적으로 보류한다.
  텍스트가 늘었다는 이유로 모든 자격 축이 확정됐다고 판정하지 않는다.
- HML 원문 읽기와 RHWP 편집 지원을 별도 capability로 기록한다. 기존 조건부 매칭 원칙
  (확인 축 2개 이상, 남은 것이 순수 ambiguous/input_missing)은 유지한다.

완료 기준: seq 25의 거짓 누락 고지 제거와 실제 누락 경고 유지, seq 29 지원자격 본문·위치
추출 검증, 동일 점수표의 구간 배타성, 예외 경로 보존. 원문 SHA 또는 변환 계약이 바뀐 결과는
새 input revision으로 검증하며 기존 receipt를 고치지 않는다.

## 4. 재개와 재사용을 정교하게 하고 시간을 줄인다

구현 위치: `apps/web/src/lib/server/analysis-lab/launch-batch-production.ts`, `launch-status.ts`,
`claude-cli-transport.ts`, 신청서 문서별 실행 및 artifact/release admission 경로.

- 실패를 사용창 소진·일시 오류·지속 검증 충돌·필드 위치 보류·source drift로 분류한다.
  재개 dry-run에 정확 대상, 재실행 단계, 재사용 SHA, 제외 이유를 출력한다.
  원인별 선택 기능은 기존 grant의 부분집합만 허용하고 임의 대체 대상을 넣지 않는다.
- primary가 유효하고 신청서만 실패했다면 불변 primary receipt를 부모로 연결하고 실패한
  문서·필드만 새 보완 artifact로 만든다. 입력·첨부·관련 모델/validator/planner 계약과
  release admission에서 재사용을 검증한다. 기존 CLI에 이 기능이 있다고 가정하지 않는다.
- 계약 변경 영향으로 primary 자체를 다시 검증해야 하면 그 단계를 생략하지 않는다.
  보완 결과와 원 primary의 결속이 모호하면 재사용을 거부한다.
- 모델 요청 시작/완료, 검증/repair, 문서 planner, queue wait, anchor 진행을 이벤트로 남긴다.
  실행 중 실패 이벤트에도 이미 저장된 단계 결과를 표시한다. **최종 42/42 결과 결속은 정상**이므로
  이를 영구 artifact 누락 복구 문제로 확대하지 않는다.
- transport가 제공하는 사용창 오류 코드·reset 시각을 민감값 없이 보존한다. 시각이 없으면
  unknown으로 표시한다. 반복 모델 호출로 잔량을 탐색하거나 API로 자동 우회하지 않는다.
- seq 0의 문서별 순차 모델 대기를 분리할 때 다운로드/파서 자원 제한과 공용 모델 요청 상한을
  함께 둔다. 대상 동시성 2와 실제 모델 동시성은 따로 계측한다. 문서 큐 공정성,
  취소·lease 상실·사용창 종료 시 신규 요청 중단을 검증한 뒤 제한된 범위에서 성능을 비교한다.
- `parseDurationMs`에 모델 시간이 포함되는 기존 의미를 명시하고 순수 파싱 지표를 추가한다.
  겹치는 primary/application 시간을 합산하지 않는다. seq 25의 반복 재판정도 요청별로 분해한다.

완료 기준: 성공 단계의 불필요한 모델 재실행 0, 재개 대상 확대 0, receipt 덮어쓰기 0,
고아 lease 0, 중단 후 신규 요청 0. 인증·lease·manifest 오류의 전체 중단과 개별 오류 격리를 유지한다.

## 5. 검증·배치 재개·베타 공급 순서

### 구현 검증

| 변경 범위 | 필요한 증거 |
| --- | --- |

| 정규화·validator·matching | 해당 실제 회귀 + `pnpm test:matching-unit`, `pnpm lab:experiment:test` |
| 신청서 역할·필드·편집·admission | 해당 회귀 + `pnpm lab:roundtrip:test`, 관련 canary/admission 테스트 |

| 사용자 RHWP 경로 | HWP/HWPX 실제 저장·재파싱 + Studio 브라우저·시각적 인수 |

실제 변경 범위에 따라 최소 조합을 선택하고 집계 gate에 포함된 하위 검사를 같은 소스에서
중복 실행하지 않는다. 외부 파서·SDK/API를 추가하거나 바꿀 때는 구현 전 공식 문서를 확인한다.
현재 문서 작성에서는 코드 테스트와 모델 실행을 수행한 것으로 기록하지 않는다.

### 남은 대상과 수정 결과

현재 grant의 retry selector 결과는 **seq 35,41,42,43,44,45,46의 7건**이다.
35는 지속 검증 실패, 41은 사용창 실패, 42~46은 미착수다. held 6건은 이 선택 집합에 없다.

1. 무호출 회귀와 저장 fixture로 변경을 검증한다. 기존 결과의 수정 영향 목록을 만들고,
   의미 결함이 있는 publishable/complete도 목록에 포함한다.
2. 재개 전 현재 공고의 open/visible·신청기간과 input/attachment SHA를 재확인한다.
   만료·drift 대상은 명시적으로 제외/보류하고 대체하지 않는다.
3. **동일 material binding의 retry**는 기존 grant 권한을 유지한다. 다만 현재 `--retry-errors`가
   지속 실패 35도 포함하므로 수정·원인별 분리 없이 반복 실행하는 것을 우선 작업으로 삼지 않는다.
4. **실행 계약이 바뀌면** 변경과 영향 대상·재사용 부모를 새 exact manifest에 봉인하고 기존 승인
   범위와 대조한다. 새 실행 계약 범위의 모델 실행 승인을 받은 뒤 launch 경로로 실행한다.
   일반 신규 재고에 과거 대상을 섞지 않고 결함 보완 대상은 별도 exact repair 범위로 추적한다.
   문서 commit/hash 변경이나 동일 계약 재시도만으로 재승인을 만들지 않는다.
5. 새 결과의 원문 의미·필드·저장 검증을 수행한 뒤 release 후보를 만든다. 알려진 결함은 해당
   결과의 공급을 보류하며 관련 없는 정상 공고의 처리까지 막지 않는다. 현행 Kordoc release
   admission을 유지하며 primary publishable만으로 신청서 완료를 주장하지 않는다.
6. 서비스 승격·배포는 각 승인 범위에서 수행하고 게시 후 실제 매칭과 신청 준비 흐름을 확인한다.
   사람의 인수 항목은 실행 시 확인한 URL·단계·기대 결과를 담은 HTML 가이드로 제공한다.
   개발 서버는 사용자가 실행하는 프로젝트 규칙을 따른다.

### 성공 지표와 확장 판단

- **정확도:** 알려진 재현 결함 전부 해결 또는 공급 보류, 정상 대조군 회귀 0.
  신규 표본은 형식·합본·선택·점수표·조건부 매칭을 나눠 독립 원문 검수하고 분모를 기록한다.
  입력 필드 precision/recall, 주 양식 누락, 질문·선택 제약 오류를 별도로 보고한다.
- **효율:** 동일 입력·문서 복잡도·품질 기준에서 p50/p95, 교정 요청 수·시간, 단계 재사용률,
  시간당 의미 검수 통과 결과를 비교한다. p95와 불필요한 교정 시간 **20% 감소를 첫 실측 목표**로
  삼되 보장치나 launch admission으로 사용하지 않는다. 표본 구성이 다르면 층별로 보고한다.
- **공급:** 현재 유효한 분석 결과→의미 검수 통과→release 승인→실제 게시→사용자 매칭·작성 가능
  수를 각각 기록한다. 현재 18.70건/시간과 새 의미 검수 통과 처리량을 같은 지표처럼 비교하지 않는다.
- **중단 판단:** 사용자 대신 동의 선택, 잘못된 위치 쓰기, 자격 의미 손상은 해당 결과 공급을
  차단한다. 공용 인증·manifest·lease 무결성 또는 사용창을 잃으면 전체 신규 착수를 중단한다.
  품질 비율·시간 목표 미달은 개선 자료이며 target별 재승인 gate로 만들지 않는다.

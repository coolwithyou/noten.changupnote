### 재현한 최우선 차단: release가 역사 실행 계약을 읽지 못함

`analysis-launch-promotion.ts:loadLaunch`가 실행 admission용 `normalizeAnalysisLaunchManifest`를
사용한다. 실제 최근 terminal receipt 4개(41건 원본/재개, 6건 복구, 19건 신규)의 manifest를 읽으면
전부 `launch source/existing run 정책 결속이 잘못됐습니다.`로 거부된다.
현재 v18로 버전이 바뀌었다는 이유로 정상 종료한 v15/v17 결과까지 서비스 연결 전에 막히는 상태다.
각 receipt 디렉터리의 independent-review manifest/aggregate도 0개다.
따라서 **통과55건을 그대로 promote하면 된다는 계획은 실행할 수 없다.**

개선 단위:

1. release의 종료 receipt 소비와 신규 live 실행 admission을 분리한다.
   기존 `completed-analysis-launch-reader.ts`의 검증 범위를 확인해 재사용한다.
2. 원 manifest/grant/terminal receipt/run SHA·target·sequence·실제 역사 계약 tuple을 검증한다.
   미완료·변조·모르는 tuple·다중 leaf·current source drift를 임의로 수용하지 않는다.
3. 매칭과 작성 준비도를 독립 판정한다. 과거 필드맵을 v18로 이름만 바꾸거나 모든 역사 버전을
   자동 허용하지 않는다. 새 validator로 영향받는 의미는 오프라인 재검증하고, 불가능한 대상만 보류한다.
4. 독립 검수 입력 생성 경로도 같은 소비 문제가 있는지 확인한다. exact 원문 기반 검수 결과를
   생성·집계한 뒤 release prepare/aggregate/shadow/dry-run/approve로 연결한다.
5. 회귀: 실제 v15/v17 종료 receipt, 재개 skipped 보존, 현행 v18, SHA 변조, 미완료, source drift,
   매칭만 ready/작성 held 사례. 관련 promotion/launch suite와 집계 gate로 검증한다.

위 차단은 후속 구현에서 수정했다. 아래 실행 기록을 따른다. 이 절의 v18은 최초 진단 시점이며, 필드 문맥 변경을 반영한 현행 계약은 v19다.

- 비허용 네트워크에서 첫 화면·로그인·매칭·작성 진입 확인. ops/dev 보호는 유지되는지 확인한다.
- 오픈 실패 시 신규 작성 진입 제한/해당 release 롤백 경로를 사용한다. 사용자의 기존 문서는 보존한다.
- 오픈 뒤 수집 → 입력 준비 → 검수 → 승인된 반영 책임을 정한다. observe_only인 운영 worker가
  내일 새 공고도 자동 분석할 것이라고 가정하지 않는다.

# 반복 재분석의 구조 진단과 Jev 도입 검토

작성: 2026-09-22. 범위: 신규 공고에도 반복 적용할 처리 구조와 TypeSafe Jev의 적합성. 구현·실행 승인이 아니라 조사와 설계 제안이다.

## 판단

가장 큰 설계 문제는 **분석 산출물의 통과와 사용자가 조건을 확인해 지원 여부를 판단할 수 있는 상태가 서로 다른데, 전자를 주된 작업 완료 단위로 운영한다는 것**이다. 추출 성공 후 변환·독립 검수·질문·발행의 요구사항을 뒤늦게 맞추고, 실패 이유가 상위에서 넓은 보류 상태로 합쳐지면서 개별 공고를 다시 조사하게 된다.

모델의 실제 의미 해석 오류도 존재한다. 모든 보류를 과도한 규제로 보거나 342건을 그대로 발행해도 된다고 해석하면 안 된다. 그러나 더 좋은 모델이나 개별 예외만으로 이 구조를 해결할 수는 없다. **원문에 근거한 조건, 그 조건의 해소 방법, 변경 의존성, 다음 작업을 하나의 계약으로 연결**해야 한다.

이 판단은 아래 코드·과거 실행 증거를 종합한 아키텍처 평가다. 전체 342건의 개별 미반영 사유를 증명한 결과와 구분한다.

## 조사 기준과 확인 범위

- 현재 작업 폴더 HEAD `d134b49`에는 다른 작업의 미커밋 변경이 있다. 이를 수정하지 않았다.
- 최근 배포 작업의 clean checkout `/private/tmp/cunote-last-question-release`, HEAD `526283d`도 대조했다. 이번에는 배포 상태를 다시 조회하지 않았다.
- 최근 업종 확인 질문 패치는 clean checkout에 있으며 주 작업 폴더에는 없다. 구 코드만 보고 업종 질문이 여전히 전혀 지원되지 않는다고 결론내리지 않았다.
- 직전 조사에서 현재 모집 공고 537건의 집계와 로컬 분석 이력을 대조했다. 이번 검토에서 DB를 다시 집계하지 않았다. 숫자는 그 시점의 스냅샷이다.
- 웹 조사는 TypeSafe 공식 소개·API·모델·한계·개인정보 문서를 사용했다. Jev API 호출, 계정 연결, 공고/기업 데이터 업로드는 하지 않았다.

## 반복을 만드는 구체적 구조

### 1. 서비스 반영 증거의 부재가 분석 부재로 바뀐다

`apps/web/src/lib/server/productReadiness/grantReadinessLoader.ts`의 `normalizeGrantReadinessEvidence`는 유효 promotion이 없으면 `analysis.status=missing`으로 만든다. 첨부 준비도 역시 실제 보관·변환 상태 대신 promotion의 attachment manifest 유무로 판단한다.

`loadCurrentValidPromotions`는 실패한 run, 잘못된 evidence, 현행 DB snapshot 불일치 등을 걸러낸 뒤 유효 promotion만 반환한다. 소비자에게는 왜 탈락했는지보다 ‘없음’이 남는다. 서비스 신뢰 검사를 유지하는 것은 맞지만, 진단 결과까지 존재하지 않는 것으로 바꾸는 것은 잘못이다.

직전 대조에서 `analysis_missing` 486건 중 399건은 과거 publishable run이 있었고, 그중 342건은 applied 이력이 없었다. 이것은 342건이 즉시 발행 가능하다는 뜻이 아니라, **추출을 다시 돌리기 전에 이어서 할 일이 있는 자산을 분석 없음으로 관측하고 있다는 증거**다.

개선: `analysis 존재/검수 상태/현행성/발행 상태/질문 준비`를 독립 기록하고, 유효성 검사도 `{status, reason, evidence, nextAction}`을 반환한다. 사용자에게 보류해야 한다는 사실과 운영자가 재분석해야 한다는 결론은 별개다.

### 2. 필요한 질문을 이미 만들어 둔 질문에서 역산한다

같은 loader의 `promotionEvidence`는 `promotionPlan.questions`에 있는 v2 질문을 `eligibleQuestionCriterionStableKeys`로 사용한다. 아직 작성하지 않은 질문은 기대 목록에도 들어가지 않는다.

직전 집계의 질문만 추가하면 되는 공고 0건은 ‘질문이 필요 없다’는 근거로 쓸 수 없다. A 7건도 필수/제외 text_only 조건을 포함했다. 다만 text_only라고 모두 사용자 질문 대상인 것은 아니므로, 전부 누락 질문이라고 단정하지도 않는다.

개선: 질문 수요는 **검수된 조건과 해소 방식**에서 계산하고, 실제 질문과 차집합을 구한다. 질문 생성 실패는 별도 작업으로 남겨야 한다. 이 계약 없이는 UI를 개선해도 새 공고의 질문 재고가 자동으로 생기지 않는다.

### 3. 표현 방식과 해소 주체가 혼합돼 있다

`text_only`는 자동 비교가 어렵다는 표현 형식이다. 그러나 원문 의미가 불명확한 경우, 회사 사실이 비어 있는 경우, 사용자가 직접 답할 수 있는 서술형 조건이 모두 이 경로에 걸릴 수 있다.

배포 작업 checkout의 `classifyManualConfirmationCriterion`는 근거 검증, 강등 이유, 원래 축을 검사하고 `other`/`industry`를 사용자 확인 대상으로 허용한다. 이 보호는 의미 오류를 사용자 답변으로 덮지 않기 위해 필요하다. 동시에 새로운 축마다 허용 여부를 추가하는 방식은 질문의 적합성을 표현하는 완성된 계약이 아니다.

개선: 다음 두 축을 분리한다.

- **원문 해석:** 검증됨 / 자료 누락 / 해석 충돌 / 표현 계약 미지원.
- **회사 비교:** 충족 / 미충족 / 회사 사실 필요 / 공고별 확인 필요.

원문 의미가 검증된 조건에 회사 사실만 없으면 질문을 만들 수 있다. 원문에서 ‘일반기업’의 범위를 확정하지 못했다면 사용자에게 약관 해석 책임을 넘기지 말고 근거 검수를 해야 한다. 법인이라는 값만으로 일반기업 범주에 자동 포함·불포함 처리하지 않는다.

### 4. 서로 다른 변경이 넓은 재처리 분기로 모인다

`matching-inventory-campaign.ts`는 input, attachment, contract 차이를 `source_changed`로 묶고 `prepare_changed_source`를 지정한다. legacy 이력은 일반 quality hold로 분류한다. 이것이 실제 모델 재실행을 자동 수행한다는 뜻은 아니지만, 후속 작업을 구체적으로 선택하기에는 분류가 넓다.

`sourceRevision.ts`의 source revision은 raw hash, 공고 필드, 첨부를 함께 묶는다. material revision은 이미 추가돼 rawHash를 제외한다. 따라서 ‘rawHash 분리가 전혀 없다’는 진단은 틀리다. 그러나 material projection에도 상태·기간·지원 내용·첨부 변환 상태 등이 포함되고, product readiness는 전체 source revision 일치를 사용한다. 소비 단계마다 유효성을 보는 범위가 다르다.

9월 18일 조사에서는 실패 13건의 실제 입력·첨부 해시가 동일했고 12건은 rawHash 교체만으로 차이를 재현했다. 이후 matching-only 실행 결속을 좁히는 패치가 들어갔다. 이는 이미 해결한 부분을 다시 구현할 사안이 아니라, **변경 영향 계약을 실행·검수·발행·질문에 일관되게 적용해야 한다는 증거**다.

개선: 원본 전체 revision은 감사용으로 보존한다. 재사용 여부는 소비 기능별 입력 의존성으로 결정한다. 기간 변경은 기간 판정, 회사 답변 변경은 matcher, 표현 계약 변경은 재변환·재검증으로 보낸다. 실제 자격 문구/예외/참조 첨부 변경은 해당 조건과 관련 coverage를 재검토한다.

주의: 모델 입력이 같거나 기존 근거 문장이 같다는 이유만으로 안전한 변경이라 판정하면 안 된다. 입력에 빠졌던 새 제외 조항도 탐지해야 한다. 변경 전후 지원대상·제외대상 구역과 참조 문서의 완전성 검사가 필요하다. 범위를 결정할 수 없으면 재검수로 보낸다.

### 5. 국소 보호 장치는 늘었지만, 처음부터 끝까지의 완료 계약이 약하다

9월 7일 보고서에 변환 중 의미 변경, 필수 text_only의 해소 경로 부재, 작성 준비와 매칭 공급의 결합, 소비자 계약 불일치의 늦은 발견이 이미 기록돼 있다. 이후 현재 코드에 matching/authoring 분리, HOLD 영향 분리, material revision, 사용자 질문 패치가 추가됐다. 이를 없는 기능처럼 재설계할 필요는 없다.

9월 19일에는 검수 이력에서 뽑은 47건 중 3건의 shadow 경고 때문에 정상 44건을 이어서 발행하려고 subset continuation 계약을 추가했다. 보류의 영향 범위가 작업 단위보다 컸던 실제 사례다. 이 사례 자체는 해결됐다.

남은 구조적 과제는 각 단계의 성공이 다음 단계의 소비 가능한 산출물로 연결되는지다. **‘분석 publishable’ 대신 ‘조건을 보여 주고, 필요한 답변을 저장하고, 재판정하고, 필요한 경우 다른 공고에도 재사용할 수 있음’을 제품 인수 단위로 삼아야 한다.**

운영 worker의 observe_only와 로컬 exact batch 정책은 의도된 실행 제한이다. 작업 계획과 재개 판단을 자동화하는 것, 유료 모델 실행과 서비스 쓰기를 자동 허가하는 것을 분리한다. 본 제안은 현행 승인 경계를 우회하지 않는다.

## 제안하는 최소 구조

새 범용 에이전트나 전체 규칙 언어 교체보다, 기존 모듈을 잇는 두 계약을 우선 만든다.

### 조건 해소 계약

각 조건에 다음을 유지한다. 기존 criterion·source span·semantic identity·profile 계약을 재사용하며 이름은 구현 시 확정한다.

| 필드 | 역할 |
| --- | --- |
| 근거와 coverage | 어느 문서·구역·조건을 읽었는지, 누락/충돌 여부 |
| 조건 의미 | 필수/제외/우대, 적용 대상·트랙, AND/OR·예외, 기준일 |
| 비교 입력 | 필요한 회사 사실, 타입, 사업장 범위, 유효기간 |
| 해소 방식 | 코드 비교 / 회사 사실 질문 / 공고별 확인 / 원문 검수 |
| 질문 연결 | 질문·선택지·답변 효과·미확인 선택지 |
| 재사용 범위 | company fact / per notice, 의미 버전과 출처 |
| 변경 의존성 | 무엇이 바뀌면 어떤 산출물을 재검증해야 하는지 |

대상 집합을 단순히 평탄화하지 않는다. ‘시흥 소재 예비창업자 또는 창업 7년 이내 기업’은 원문에 따른 OR/AND 범위를 보존해야 한다. ‘법인’과 ‘일반기업’처럼 서로 다른 분류축을 문자열 비교하는 것으로 해결하지 않는다. 현재 표현할 수 없는 복합 조건은 검증된 원문을 보존하고 검수 작업으로 남긴다.

질문 예시: ‘현재 시흥시에 등록된 사업장이 있나요?’

- 이 문구를 쓰려면 공고가 본사만 요구하는지, 지사/공장도 허용하는지, 기준일이 언제인지 먼저 확정돼야 한다.
- 답변은 ‘이 공고 통과’가 아니라 검증된 계약의 회사 사실로 저장한다.
- 다른 3개 공고가 같은 사실을 요구하면 같은 답변으로 재평가한다.
- ‘공고일 이전 본사 이전 완료’ 등 의미가 다르면 자동 공유하지 않는다.
- 답변 수정·철회·기간 만료 때 이를 소비한 공고만 다시 평가한다.

### 후속 작업 계약

현재 증거를 읽어 **다음 최소 작업**을 결정하는 공용 함수를 둔다. campaign/관리자/리포트가 같은 결과를 소비해야 한다.

| 상황 | 다음 작업 | 원문 전체 모델 재분석 |
| --- | --- | --- |
| 동일 유효 입력, 분석 있음, 검수 없음 | 해당 결과 독립 검수 | 불필요 |
| 검수 완료, 질문만 없음 | 질문 구성·검증 | 불필요 |
| 유효 결과 있으나 미반영 | release 준비/기존 승인 내 처리 | 불필요 |
| matcher/변환 계약만 변경 | 재변환과 영향 회귀검사 | 기본 불필요 |
| 기간/상태만 변경 | 모집 상태·기간 재평가 | 기본 불필요 |
| 회사 사실 답변 변경 | 관련 공고 matcher 재평가 | 불필요 |
| 실제 자격조건 변경 | 관련 조건·예외·coverage 분석/검수 | 영향 범위에 한정 |
| 원문/첨부 누락 | 수집·변환 복구 | 확보 전 실행하지 않음 |
| 원문 해석 반복 실패 | 명시적인 검수 작업 | 무한 재시도 금지 |

입력·관련 계약 버전·단계별로 완료 결과를 재사용한다. 재시도의 skipped가 이전 성공을 지우지 않는 것, 동일 입력의 같은 단계가 중복 실행되지 않는 것을 공통 불변식으로 검증한다. 현재 구현이 모두 이를 위반한다고 단정하는 것이 아니라 인수 조건으로 둔다.

원문 변경 시 기존 결과를 무조건 노출하거나 무조건 삭제하는 이분법도 피한다. 바뀐 eligibility의 영향을 모르면 지원 가능 확정은 내려놓되, 영향받지 않은 근거와 원문 탐색 가치는 보존한다.

## Jev 조사와 적용 판단

공식 문서 기준 Jev는 입력 state에 대해 Choice/Score/Noul 형태의 좁은 판단을 제공한다. 원문 분석·질문 문구를 자유롭게 생성하는 모델이나 처리 전체를 관리하는 에이전트가 아니다. 코드가 흐름을 제어하고 모델은 제한된 판단을 맡는 구조다. [소개](https://docs.typesafe.ai/introduction), [설계 지침](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)

현재 모델 문서에는 `jev-1.13.0`, 입력 100만 토큰당 $0.042, 출력 무료, 텍스트 입력만 지원한다고 명시돼 있다. 영어 성능이 가장 좋고 CJK는 별도 검증이 필요하다. 운영 검증은 이동하는 `jev-latest` 대신 버전을 고정해야 한다. [모델 문서](https://docs.typesafe.ai/models)

### 적합한 도입 위치

| 좁은 작업 | 도입 판단 |
| --- | --- |
| 원문 문단이 지원대상/제외/우대/제출서류 중 무엇인지 | 평가해 볼 가치가 큼. 기타/불명확 선택지 포함 |
| 추출 조건이 근거 문단의 의미를 보존했는지 | 검수 보조 후보. 원문 주변 예외와 정의도 제공 |
| 회사 사실 질문으로 해결 가능한지, 원문 검수가 필요한지 | 라우팅 후보. 최종 계약은 코드가 검증 |
| 이미 뽑은 후보 중 적합한 조건 유형/템플릿 선택 | 후보에 정답 없음 선택지를 포함해 평가 |
| 변경 문단의 의미 차이 분류 | 검수 우선순위 보조부터 시작. 무해 판정 단독 권한은 주지 않음 |
| 업력·금액·날짜·지역 코드 비교 | 결정적 코드로 처리 |
| HWP/PDF 원문 복원, 긴 복합 공고 전체 추출, 질문 문구 작성 | Jev 대체 대상 아님 |
| 기업이 실제 조건을 충족하는지 사실 생성 | 맡기지 않음. 공식 사실/사용자 답변이 필요 |
| provenance 검증, 서비스 발행 승인 | 모델 확률로 대체하지 않음 |

공식 한계 문서는 수치·날짜 계산, 복잡한 간접 추론, 불필요하게 긴 문맥, 적대적 입력, 자유 문장 생성의 한계를 명시한다. 별도 질문 사이 논리적 일관성도 코드로 보장해야 한다. 창업 공고의 부정·예외·기준일은 이 약점과 겹친다. [Jev 1.13 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

따라서 ‘원문 전체 → Jev → 지원 가능’ 대체는 권하지 않는다. ‘원문 확보 → 근거 있는 후보 추출 → 작은 의미 판단 → 코드 검증 → 질문/검수/재평가’ 안에서 기존 판단 모델과 교체 가능한 어댑터로 평가한다.

### 확률과 홍보 수치의 해석

Choice/Score의 confidence는 출력 확률분포에서 계산한 통계다. Noul에는 별도 confidence가 없다. confidence 0.95가 한국어 공고에서 정답률 95%를 보장한다는 뜻은 아니다. 임계값은 자체 정답셋과 업무 위험으로 결정해야 한다. [Confidence 문서](https://docs.typesafe.ai/confidence)

공식 소개의 ‘환각 0’은 스키마 일치 보장을 설명하는 맥락이며, 의미 판단 무오류를 증명하지 않는다. 공개 workflow 비교도 사람 정답 대신 외부 모델 확률을 참조하고, 제작사 팀이 구성한 업무라는 한계를 밝힌다. 속도·비용 배수는 한국어 지원사업 판단 정확도나 전체 파이프라인 개선율로 옮겨 쓰지 않는다. [공식 출시 글의 평가 설명](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

입력 5,000토큰을 사용하는 요청 1,000회는 공시 단가로 약 $0.21이다. 이는 단순 산술 예시이며 실제 요청 수·재시도·텍스트 추출·상위 모델·사람 검수 비용을 포함하지 않는다. 지금 프로젝트에서는 모델 단가보다 보류를 해소하는 운영 비용과 실제 공급 지연이 더 큰 판단 기준이다.

입력 학습 금지는 공식 정책에 명시돼 있지만 이를 기본 무보관으로 해석하면 안 된다. 초기 평가는 공개 공고와 합성 회사 정보로 구성한다. [개인정보 정책](https://typesafe.ai/legal/privacy-policy)

## 평가 설계: 같은 예외 루프를 반복하지 않는 기준

1. 이미 겪은 오류를 공고 ID가 아닌 오류 유형으로 묶는다. 필수/우대 혼동, 본사/지사, 시도/시군구, OR 누락, 부정/예외, 미만/이하, 기준일, 현재 제재/과거 위반, 원문 누락을 포함한다.
2. 첫 탐색은 예를 들어 200~300개의 짧은 판단 사례로 시작할 수 있다. 이는 설계 오류 탐색용이며 저오류율의 운영 안전성을 증명하는 충분한 표본이라고 주장하지 않는다.
3. 원문 근거와 사람이 검토한 정답을 둔다. 기존 모델 PASS를 정답으로 복사하지 않는다. 불명확한 원문은 불명확으로 정답 처리한다.
4. 기관/템플릿/유사 공고를 묶어 개발셋과 보류 평가셋을 나눈다. 임계값을 맞춘 뒤 새로 유입된 공고로 전향 평가한다. 실패한 시험을 수정에 썼으면 같은 시험을 독립 검증으로 재사용하지 않는다.
5. 규칙만 사용하는 기준선, 현행 모델, Jev를 동일 입력·출력 계약으로 비교한다. 동일 유형 질문도 prompt/모델 버전에 결속한다.
6. 전체 정확도보다 잘못된 자동 확정, 놓친 후보, 재검수 비율, 확률 보정, 지연, 최종 공고 한 건을 공급하는 데 드는 총비용을 비교한다. 자동화 비율을 올리기 위해 불명확 선택지를 없애지 않는다.
7. 처음에는 그림자 평가로 실행해 DB·사용자 판정을 바꾸지 않는다. 한국어에서 검증된 좁은 라우팅부터 적용하고, 미달이면 기존 경로를 유지한다. Jev 미도입이어도 새 구조는 작동해야 한다.

## 구현 우선순위와 완료 조건

### 첫 단계: 끝까지 이어지는 한 경로

- 기존 readiness·criterion·question·matcher를 잇는 조건 해소 계약과 후속 작업 판정부터 구현한다.
- 지표 수정은 그 계약의 관측 결과로 한다. 별도 대시보드만 고치는 것으로 끝내지 않는다.
- 신규 공고 한 건에 대해 수집→조건 검증→질문 노출→답변 저장→재판정까지 실행되는 인수 사례를 만든다.
- 같은 회사 사실을 요구하는 4공고에서 한 번 답하고 모두 재평가되는 경우, 비슷하지만 다른 의미의 질문에는 전파하지 않는 경우를 같이 검증한다.

### 둘째 단계: 변경과 실패에서 최소 단계 재개

- 원문 구역/첨부 coverage와 소비 기능의 의존성을 결속한다.
- 관측값 변경, 기간 변경, 조건 변경, 새 예외 추가, 질문 문구만 변경을 서로 다른 회귀 사례로 둔다.
- 검수·발행 실패를 원문 재분석 큐로 무조건 되돌리지 않는다. 원인·담당 단계·재시도 조건을 남긴다.
- 현행 승인 정책 안에서 계획과 재개를 자동화한다. 유료 실행/운영 활성화 정책 변경은 별도 결정이다.

### 셋째 단계: 모델 비교와 점진 적용

- 공통 좁은 판단 인터페이스에 현행 모델과 Jev를 연결해 같은 평가셋으로 비교한다.
- 처음부터 Jev 전용 원장·새 검수 레인을 추가하지 않는다. 동일한 증거/질문 계약을 사용한다.
- 기존 342건은 새 처리 규칙의 일회성 이관 검증에도 사용하되, 최종 인수는 미래 신규 공고로 한다.

전체 완료는 ‘이번 batch가 통과했다’가 아니다. **개별 공고 ID 예외나 운영 코드 수정 없이 신규 공고가 동일 경로를 통과하고, 해결할 수 없는 경우에도 정확한 다음 작업으로 종결되는 것**이다. 원문이 불명확한 모든 공고를 자동 통과시키는 목표는 세우지 않는다.

## 검증 및 한계

코드와 문서 교차 검토, TypeSafe 공식 자료 열람, 문서 diff/상대 링크 확인을 수행했다. 제품 코드는 바꾸지 않아 제품 테스트는 실행하지 않았다. Jev의 한국어 실제 품질·우리 데이터에서의 확률 보정·실제 지연은 미측정이다. 이번 검토는 Jev 도입 효과의 실증 결과가 아니다.

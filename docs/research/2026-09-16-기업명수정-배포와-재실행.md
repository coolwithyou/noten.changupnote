## 재실행 준비에서 확인한 제약

현행 launch runner는 primary 재사용/application-only 실행을 제공하지 않는다. 따라서 이번 재실행은 기존 결과를 불변 보존하고 새 primary+application 결과를 생성하는 범위다.

기존 `prepare-field-repair`를 exact20으로 준비하면 admission에서 실패했다. 20건 모두 서비스 DB 필드는 0개지만 `preview_ready|fields_ready` HWP/HWPX surface가 있는 대상은 9개뿐이었다. 기업명 누락을 확정한 경북 공고는 HWP surface와 archive가 3개씩 존재하지만 surface 상태가 모두 `pending`이므로 이 경로에서 제외된다. DB 상태를 인위적으로 변경하지 않았다.

`terminal-repair`는 실패·보류만 선택하므로 이번 publishable 대상 10건을 담지 못하며, 신규30 원 코호트의 범위 밖 실패1건까지 선택한다. `authoring-guide-rerun`은 application 분석을 끄는 primary-only 경로다. 두 경로를 이번 목적에 사용하지 않았다.

현재 원천 결속 재검증에서는 18건이 통과했다. KICET 추가 모집(`59e77d80-520a-4faf-83b5-900ad1aec3a4`)과 인천 대기질 사업(`626501c7-74b2-4942-976b-7045a6bdb2cf`)은 지원 가능 조건은 통과했지만 source revision이 달라 이번 비교 재실행에서 보류한다. 바뀐 원문을 과거 승인 입력과 동일하다고 간주하지 않는다.

## 후속 개선 방향

기업명 공고의 나머지 application 미확정 47개는 모두 `inputLikelihood=0.15`, heuristic, `llmDecision=null`이다. 현행 LLM triage 조건 `>0.25 && <0.75` 밖이어서 전체 모델 재실행만으로 이 후보가 검토되지 않는다. 기업명 복구는 동일 좌표의 독립 label→blank 구조를 증명해 추천 입력으로 바꾼 결과이며, 나머지 후보까지 해결했다는 뜻은 아니다.

원문 IR 대조에서 24개는 독립 입력 대상이 아닌 구조로 분류했지만, 이는 오프라인 검토 기록이고 제품의 자동 판정이나 coverage 해제를 수행한 결과가 아니다. 23개는 별도 검토 대상으로 남겼다. 기능 설명 예시 표의 독립 빈칸 12개, 도입여부·수료예정일·비고 8개, 날짜 placeholder 2개와 금액 상한/기본값 후보 1개다. 특히 `(예시)` 문구만으로 표 전체를 비입력으로 확정해서는 안 된다.

후속 구현 순서는 다음과 같다. 이번 실행 중에는 material 계약을 바꾸지 않았다.

1. label→target 좌표·병합 anchor·열 역할·실제 값을 결속하는 구조 증명을 도입한다. 제목·예시·placeholder 같은 단어만으로 비입력을 확정하지 않는다.
2. coverage 미확정이면서 구조 증명이 없는 후보는 점수가 낮아도 선별 검토에 전달한다. 전역 임계값을 느슨하게 바꾸기보다 미확정 후보를 명시적으로 검토할 경로를 만든다.
3. 기업명·예시 표 빈칸·날짜·금액·병합 셀의 회귀를 확보한 후 exact 신청서 재분석을 검증한다.
4. 동일 source/input/attachment와 검증된 primary receipt를 재사용하는 application-only 경로를 추가해 지원조건 분석의 반복 호출을 줄인다. primary 계약이나 원문이 달라지면 재사용하지 않는다.
5. 작성 준비가 통과한 신청서부터 로그인 상태의 기업 정보 입력→LLM 작성→HWP 다운로드 및 한컴 렌더링을 검증한다. 코드 배포, 필드 추천, 실제 제출 가능 문서 검증을 분리한다.

부산 서구 임차료 공고의 primary 실패는 source/input/attachment와 primary 모델·prompt·validator 계약이 동일한 이전 실행에서도 나타난 오류다. 종전에는 repair 1회 후 통과했고 이번에는 2회 후에도 `source_incomplete`와 업력/입지 기간의 `semantic_misattribution`이 남았다. 기업명 수정과 직접 연결되는 증거는 없으며, 기존 primary repair의 불안정성을 별도로 개선해야 한다.

# 루프와 그래프 엔지니어링 접근 (2026-08-10)

> 질문: "현시점에서 cunote 개발에 루프와 그래프 엔지니어링을 이용한다는 개념은 어떻게 접근할 수 있을까?"
>
> 결론: 새로 도입할 개념이 아니다. **분석 실험실에 이미 구현되어 작동이 증명된 커널 — "그래프가 상태의 정본, 루프는 stateless 실행자" — 를 프로젝트의 공식 아키텍처 패턴으로 명명·승격하고, 커널 자체의 닫히지 않은 엣지를 마감한 뒤, 다음 적용처를 Phase 8 지식 루프로 잡는 것**이 현시점의 올바른 접근이다.

## 1. 개념 정의: 두 축의 역할 분담

- **그래프 = 상태와 의존성의 정본 (선언적)**. "무엇이 어디까지 왔고, 무엇이 무엇을 막는가"를 typed 계약으로 표현한다. 노드는 게이트(검증 단계), 엣지는 순서(`sequence`)와 재작업(`feedback`)이다.
- **루프 = 그래프를 소비하는 stateless 실행자 (명령적)**. 그래프를 접어(fold) 다음 행동을 계산하고, 행동을 실행한 뒤 그래프를 재평가한다. 루프 자신은 상태를 갖지 않는다 — 상태는 전부 그래프(와 그 밑의 런 파일·DB)에 있다.

이 분리가 핵심 속성 세 가지를 만든다:

1. **재개 가능성**: 루프가 어디서 죽어도 그래프를 다시 읽으면 이어서 돈다 (에이전트의 `resumedQualityTargets`가 실증).
2. **감사 가능성**: 사이클마다 "무슨 그래프를 보고 무슨 결정을 했나"가 구조화 기록으로 남는다 (`SubscriptionAgentCycleRecord`).
3. **정책 내성**: 루프가 그래프의 서술 문구를 파싱하지 않고 node id/status만 읽으므로, 정책(문구·요약) 변경이 루프를 깨지 않는다.

LangGraph류 오케스트레이션 프레임워크가 파는 것이 정확히 이 세 속성인데, cunote는 상태 정본을 프레임워크 내부가 아니라 자기 파일·DB에 두는 방식으로 이미 더 감사 가능하게 확보했다.

## 2. 현재 구현 실물 지도

### 2-1. 그래프: `AnalysisQualityGraph`

- 계약: `apps/web/src/features/dev/analysis-lab/quality-contract.ts` — 공고 1건마다 9개 노드(`input_sealed` → `deep_contract` → `independent_review` → `deep_promotion` → `matching_canary`, `application_source` → `field_adjudication` → `field_materialization` → `workspace_canary`), 3개 레인(deep_analysis / application / product), hard gate 플래그, 노드별 evidence·nextAction.
- 엣지: `quality-graph.ts:425-433` — sequence 7개 + **feedback 2개**(`matching_canary → deep_contract`, `workspace_canary → field_adjudication`). 하류 카나리아 실패가 상류 재작업으로 돌아오는 재작업 엣지가 명시돼 있다.
- 시각화: `/dev/analysis-lab`의 `QualityGraphTab`.

### 2-2. 루프: 반복형 구독 분석 에이전트

- 본체: `apps/web/src/lib/server/analysis-lab/subscription-analysis-agent.ts` (2026-08-10, 3fe7cf6). 사이클 구조:
  1. `inspectWork` — 코호트·런 파일·그래프에서 작업량 산출 (미분석 / 품질 회복 / 신규 후보)
  2. 신규 대상 자동 선정 → 딥분석 배치 → 검수(fable) → 감사(sonnet) → 충돌 판정(opus)
  3. `classifySubscriptionAgentGraphs` (`subscription-analysis-agent-core.ts:72`) — 그래프를 접어 5분류 결정: `completed / eligibilityRepair / applicationRetry / deepRetry / blocked`
  4. 결정에 따라 제한 재분석 실행 → 그래프 재평가 → 최대 `maxCycles`(≤5)까지 반복
- 안전판: fail-closed CLI 재사용, `--execute` 없으면 dry-run, `ANTHROPIC_API_KEY` 제거로 API 폴백 차단, 비용 상한(`maxCostUsd`), 보고서 `wx` 플래그(덮어쓰기 금지).
- 산출: `spike-out/analysis-lab/agent-runs/<agentId>.json` — 사이클별 결정 기록 포함.

### 2-3. 설계만 존재하는 루프: 18장 지식 루프

마스터 설계 18장(질문-응답-전파)은 구조적으로 위 커널과 **동형**이다:

| 커널 요소 | 실험실 (구현됨) | 지식 루프 (설계만) |
|---|---|---|
| 그래프 노드 | 품질 게이트 9종 | lesson lifecycle: feedback → 후보 → 승격 게이트 → approved → 주입 → eval → retired |
| hard gate | independent_review 등 | 승격 게이트 (golden case 동반 필수, 같은 scope 충돌 검출 — 18.5) |
| feedback 엣지 | 카나리아 → 상류 재작업 | eval_runs 회귀 → lesson 재검토, repeat-error → 주입 실패 신호 |
| 루프 실행자 | 구독 에이전트 (사이클) | 주간 리듬 러너 (교정 수집 → 승격 → eval → 리포트 — 18.9) |
| 에스컬레이션 | **(없음 — §3-1)** | Tier 0 → Tier 1(SLA) → Tier 2 |

### 2-4. 잠재 상태의 도메인 그래프

기관–공고–양식템플릿–필드–lesson–golden case–질문은 이미 관계(FK)로 존재한다. 18.4의 핵심 주장 "리뷰어 1명의 교정이 공고 1건이 아니라 양식 1종을 고친다"가 곧 그래프 순회다 — lesson이 template 노드를 거쳐 그 템플릿을 공유하는 모든 공고로 전파된다. 이 규모에서 Postgres FK가 곧 그래프이며, 그래프 엔지니어링이란 저장소 선택이 아니라 ① 노드 정체성(같은 양식 = 같은 template — Gate 1 field map 작업), ② 엣지의 선언화(lesson scope 매칭을 쿼리 가능한 형태로 유지), ③ provenance 체인(evidenceRefs로 답 → lesson → feedback → 원 질문 역추적)이다.

## 3. 진단: 커널의 닫히지 않은 엣지

이미 잘하고 있는 것(typed 계약, prose 파싱 금지, fail-closed, dry-run 기본, 재개 가능성, API 폴백 차단)은 §2에 담았다. 아래는 개선 여지다.

### 3-1. blocked의 종착지가 없다 (에스컬레이션 엣지 부재)

`classifySubscriptionAgentGraphs`가 산출한 `blocked`는 보고서 JSON에 사유와 함께 남지만 **거기서 끝난다**. 18장 어휘로 말하면 실험실 루프에는 Tier 0(자동 재시도)만 있고 Tier 1(사람 큐 + SLA)로 가는 엣지가 없다. blocked 공고는 다음 에이전트 런이 다시 집어들거나, 사람이 보고서 파일을 열어봐야 발견된다.

### 3-2. 에이전트 런 간 기억이 없다 (수렴 실패 미탐지)

사이클 내 상한(`maxCycles`)은 있으나 **런 간** 상한이 없다. 같은 공고가 에이전트 런 N회 연속 `deepRetry`→`blocked`를 반복해도 탐지되지 않는다. 구독이라 명목 비용은 0이지만, 검수(fable-5)·판정(opus) 하류 비용과 윈도 소모는 실재하고, 무엇보다 "재시도로 닫히지 않는 케이스"(예: HANDOFF-2026-08-03의 ARPA-H 2연속 refusal)를 사람 큐로 넘길 신호가 계측되지 않는다.

### 3-3. 루프 건강 지표가 없다

마스터 설계 18.10은 지식 루프의 건강 지표(repeat-error rate 등)를 정의했지만, 실험실 루프에는 그 대응물이 없다: 사이클당 회복률(deepRetry → terminal 전환율), 노드별 재실패율(같은 노드가 사이클을 넘겨 다시 실패하는 비율), blocked 사유 분포. 자동 확정률(s1 59% → s2 68.4%)처럼 수작업 집계로만 존재한다.

### 3-4. 에이전트 보고서가 UI에 없다

`agent-runs/*.json`은 파일로만 남는다. 배치 운영 탭(2026-08-03, 에이전트보다 먼저 구현)은 깔때기 6단계 중심이라 "에이전트가 언제 돌아 무엇을 결정했고 무엇이 blocked인가"를 보려면 파일을 열어야 한다.

### 3-5. 정본 쓰기 게이트가 코드 밖에 있다

`deep_promotion` 노드는 그래프에 있지만, 실제 승격(`lab:promote --write`)을 막는 가드는 코드가 아니라 관습(메모리·핸드오프 문서)에 있다: **P1 publisher 가드 전 승격분은 수집 크론이 말소한다**. 그래프의 hard gate가 실행 계층에서 강제되지 않는 유일한 지점이다.

### 3-6. 지식 루프는 설계만, 도메인 그래프는 잠재 상태

§2-3, §2-4. 커널 재사용 기회가 가장 큰 두 곳이다.

## 4. 개선 계획 제안

원칙: 각 단계는 독립적으로 가치가 있고, 앞 단계가 뒤 단계의 전제가 아니다(순서는 권장 순). 규모는 전부 소~중형이며 기존 fail-closed 구조를 건드리지 않는다. "P1 publisher 가드"라는 기존 용어와의 혼동을 피해 단계는 A~E로 명명한다.

### 단계 A. 커널 규율의 명문화 (이 문서 + CLAUDE.md 한 줄)

이 문서를 정본으로 삼고, 패턴 5칙을 규율로 남긴다:

1. 상태의 정본은 그래프(typed 계약)다. 루프·에이전트의 대화 컨텍스트에 상태를 두지 않는다.
2. 루프는 그래프의 node id/status만 읽는다. 서술 문구 파싱 금지.
3. 루프가 정본(운영 DB·사용자 노출면)에 쓰는 엣지는 반드시 hard gate 뒤에 둔다. 자동은 제안까지, 쓰기는 게이트 통과 후.
4. 모든 사이클은 결정 근거(입력 그래프 요약 + 분류 결과)를 구조화 기록으로 남긴다.
5. 재작업(feedback) 엣지에는 상한과 에스컬레이션 종착지를 함께 정의한다. 상한 없는 재시도 루프 금지.

검증: 문서 리뷰만으로 종결. 구현 없음.

### 단계 B. 루프 마감 — 에스컬레이션 엣지와 blocked 원장 (§3-1, §3-2)

- `agent-runs/` 보고서를 스캔해 공고별 blocked 이력을 접는 **blocked 원장**(파생 뷰, 새 저장소 불필요)을 만든다: 공고 × (연속 blocked 런 수, 최초/최근 사유, 마지막 성공 노드).
- 임계(예: 2런 연속 동일 사유 blocked, 또는 refusal 계열 사유 1회)를 넘으면 **자동 재시도 대상에서 제외하고 사람 큐 항목으로 산출**한다. `inspectSubscriptionAgentWork`의 recovery 후보 선정에서 원장을 조회해 제외하는 것이 배선 지점.
- 사람 큐의 실물은 검수팀 ops 배분 체계(`docs/plans/2026-07-23-review-team-ops-dispatch.md`, 확정·미착수)와 접점이 있다 — ops 구현 전까지는 배치 운영 탭의 목록 + 핸드오프 문서 기재로 충분하다.

검증: 단위 테스트(원장 접기·제외 로직) + ARPA-H류 refusal 케이스가 2런 후 자동 재시도에서 빠지는 것 실측.

### 단계 C. 관측 — 에이전트 런 히스토리 탭과 건강 지표 3종 (§3-3, §3-4)

- 배치 운영 탭에 **에이전트 런 히스토리** 섹션 추가: 런 목록(agentId, 기간, status, 대상 수) + 런 상세(사이클별 5분류 결정, blocked 사유). 데이터는 `agent-runs/*.json` 파싱만으로 충분.
- 건강 지표 최소 3종을 보고서에서 파생 계산해 같은 화면에 노출:
  1. **사이클 회복률** — deepRetry/applicationRetry로 분류된 공고가 다음 사이클에 terminal로 전환된 비율 (재작업 엣지의 실효성)
  2. **노드별 재실패율** — 같은 노드가 사이클을 넘겨 다시 held/failed가 된 비율 (18.10 repeat-error의 실험실 대응물)
  3. **blocked 잔존량과 사유 분포** (단계 B 원장의 표면화)

검증: 기존 agent-runs 실물 파일로 렌더 확인. UI 작업은 shadcn 스킬 규율 준수.

### 단계 D. 정본 쓰기 게이트의 코드화 (§3-5)

P1 publisher 가드(운영 수집 크론이 승격분을 말소하지 않게 하는 가드)가 구현되기 전까지 `lab:promote --write`가 **코드 수준에서 거부**되게 한다 — 가드 구현 여부를 확인할 수 없으면 fail-closed. 가드 구현 자체는 기존 트랙(운영 딥분석·겹침 가드)의 소관이며, 이 단계의 산출물은 "그래프의 hard gate = 실행 계층의 강제"라는 불변식을 promote 경로에 확립하는 것이다.

검증: 가드 부재 상태에서 `--write --confirm-go`가 거부되는 테스트.

### 단계 E. 커널 재사용 설계 — 지식 루프(Phase 8) 선행 계약 (§3-6)

Phase 8 착수 시점에(지금 구현하자는 것이 아니다) lesson lifecycle을 `quality-contract.ts`와 동형의 typed 그래프 계약으로 먼저 정의한다:

- 노드: `feedback_recorded` → `lesson_proposed` → `promotion_gate`(hard: golden case 동반 + scope 충돌 검출) → `approved` → `injected` → `eval_passed`, 종점 `retired`
- feedback 엣지: `eval_passed → lesson_proposed`(회귀 시 재검토), repeat-error 신호 → 주입 진단
- 루프: 주간 리듬 러너(18.9)를 구독 에이전트와 같은 구조(inspect → 실행 → 그래프 접기 → 결정 기록)로.
- 에스컬레이션: Tier 1 인박스가 단계 B에서 만든 "사람 큐" 패턴의 정식 후속이 된다.

도메인 그래프 명시화(§2-4)는 별도 단계로 세우지 않는다 — Gate 1(template identity)과 Phase 8(lesson scope)이 각자의 트랙에서 그 작업 자체다. 여기서는 ①정체성 ②엣지 선언화 ③provenance 3원칙만 상속시킨다.

### 하지 않을 것

- **오케스트레이션 프레임워크(LangGraph 등) 도입** — 상태 정본이 프레임워크 내부로 이동해 재개·감사 가능성을 해친다. 현행 typed 계약 + CLI + 사이클 러너가 우위.
- **그래프 DB 도입** — 질의 패턴(scope 매칭, 템플릿 전파, provenance 역추적)이 전부 조인 2~3단 수준.
- **루프 자동 쓰기 권한 확대** — 18.5 "피드백의 프롬프트 직행 금지"와 promote 게이트가 같은 원칙. 단계 D가 이를 강화하는 방향이지 완화가 아니다.

## 5. 우선순위 요약

| 단계 | 내용 | 규모 | 의존 |
|---|---|---|---|
| A | 커널 규율 명문화 | 문서 | 없음 |
| B | blocked 원장 + 에스컬레이션 제외 | 소 | 없음 |
| C | 에이전트 런 히스토리 UI + 건강 지표 3종 | 소~중 | B와 병행 가능 |

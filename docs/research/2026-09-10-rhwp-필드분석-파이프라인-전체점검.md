# RHWP 필드 분석 파이프라인과 세션 작업 연결 점검

2026-09-10 KST. DB 관측 23:35 KST. 코드 기준 `838bace`와 기존 작업트리 변경.
상태: 읽기 전용 조사 완료. 사용자 공고의 작성 기능 복구는 아직 미완료.

## 결론

정식 신규 대량분석에는 필드 분석이 포함된다. 그러나 **분석 실행, 서비스 DB 반영,
RHWP 위치 연결, 회사 정보 적용**은 서로 다른 단계이며, 현재 재고가 이 단계를 모두
통과한 것은 아니다. 특히 문제 공고는 필드 분석을 제외한 과거 작성 가이드 재분석을
거쳤고, DB에도 필드가 없다. 최신 대량분석 결과 역시 아직 서비스에 적용되지 않았다.

다른 `Codex ready` 세션의 편집기/문서 AI 작업과 연결되지만, 그 세션은 문단 단위
제안·적용·저장·재열기·Undo 검증을 마치고 필드 미연결 문제를 명시적으로 남겼다.
**이번 필드 분석부터 DB 반영까지의 후속 작업은 현재 세션을 주 담당으로 유지하는 것이 좋다.**

## 코드 경로와 단절 지점

1. **신규 분석:** `launch-batch-artifacts.ts:188`의 정식 manifest는
   `withApplicationRoundtrip=true`를 강제한다. `analyze.ts:495`가 실제 roundtrip을
   실행한다. `authoring_guide_adoption`은 같은 파일 225행 이하에서 false를 명시한다.
   작성 가이드 재분석을 신청서 필드 보완으로 취급하면 안 된다.
2. **로컬 결과 → 서비스 필드:** `promotion-release-cli.ts:378`은 authoring ready와
   현재 evidence verified인 대상만 application bundle에 포함한다.
   `promote-cli.ts:401`은 승인된 write에서 criteria와 동일 transaction으로 필드를
   반영하고 precompute receipt를 기록한다. 로컬 분석 성공만으로 DB에 자동 반영하지 않는다.
3. **매칭 준비와 작성 준비:** `analysisFeatureReadiness.ts`는 두 상태를 분리한다.
   필드 분석이 보류여도 매칭 검수·승격이 가능한 설계다. 따라서 `publishable` 또는
   공고 노출을 “지원서 작성 가능”으로 표시하면 잘못된 약속이 된다.
4. **과거 게시 metadata:** 적용된 119공고의 최신 release plan에는 새
   `runFeatureReadiness.authoring` projection이 모두 없다.
   `promotionServing.ts:195`는 이를 작성 준비 미검증으로 처리한다. 기존 DB 필드가
   있어도 새 작성 가능 표시와 같지 않다. 과거 receipt를 수정하지 말고 현재 evidence를
   검증하는 후속 release가 필요하다. 이것만으로 기존 필드 자체가 고장났다고 판단하지 않는다.
5. **DB 필드 → RHWP:** `documentFieldLink.ts`가 surfaceId를 우선해 로드한다.
   `workspaceData.ts:622`는 현행 필드가 하나 이상이면 ladder A로 분류하며,
   클라이언트가 각 필드의 유일한 문서 위치를 다시 확인한다. DB 행의 존재는 실제
   HWP 열기·정확한 입력 위치·전체 필수항목 커버리지의 대체 증거가 아니다.
6. **회사 정보 자동 입력:** `seedProfileAnswers.ts:82`는 저장된 프로필을
   `suggested/profile` 답변으로 준비한다. `rhwp/editPlan.ts:135`는 `accepted|edited`만
   문서에 반영한다. `ApplicationProfileAutofillDialog.tsx`도 사용자가 열고 적용해야 한다.
   **현재 동작은 확인 후 적용이다. 사용자가 기대한 진입 즉시 기본 회사 정보 입력과
   차이가 있으며, 필드 분석 보완만으로 이 차이가 없어지지 않는다.**

## 후속 완료 기준과 조사 한계

- 기존 분석 결과가 있는 공고는 현재 원문/계약/검수 결속부터 확인해 재사용 가능 대상을
  분리한다. 이력이 없는 실제 신청서만 별도 보완 대상으로 확정한다.
- 문제 공고를 첫 인수 대상으로 삼아 필드별 회사 매핑, 빈 필드 AI 작성, 정확한 문서 위치,
  적용·저장·재열기·Undo를 실제 사용자 회사 흐름에서 검증한다.
- 기본 회사 정보의 진입 시 자동 적용을 구현한다면 값의 출처·기존 작성값 보존·되돌리기를
  함께 검증한다. 저장되지 않은 회사 정보를 생성해 넣지 않는다.
- 신규 모델 호출과 서비스 쓰기는 기존 승인 경계를 따른다. 이번 조사에서는 모델 호출,
  서비스 DB/R2 쓰기, 배포, 제품 코드 수정, 세션 handoff를 하지 않았다.
- 현재 브라우저의 대상 회사 권한이 없어 정확한 사용자 URL 인수는 확인하지 못했다.
  다른 세션의 다른 공고/QA 사용자 검증은 이 공고의 인수 증거로 대체하지 않았다.
- 조사 산출물은 JSON 파싱·집계 일치·링크·diff로 검증했다. 제품 코드 변경이 없는
  조사이므로 기존 테스트를 반복하지 않았다. 기능 복구 완료를 선언하지 않는다.

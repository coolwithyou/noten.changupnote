# v19 기업명 field coverage 누락 진단

## 결론

수동 점검에서 발견한 `기업명`은 실제 누락이다. 원문에는 `기업명` 라벨 오른쪽에 독립된 빈 값
셀이 있고 같은 행의 `대표자`도 동일한 라벨→빈 값 구조다. 그런데
`suppressValueCellDuplicates`가 앞 셀 `기본정보`의 KorDoc `originalValue="기업명"`을 근거로
`기업명`을 앞 라벨의 값 placeholder로 오인해 입력 후보에서 제거했다.

이 오인은 두 단계에서 조용히 통과한다.

1. 후보 추출 단계가 `기업명`의 `recommendedInput`을 `false`, `inputLikelihood`를 `0.15`로
   낮춘다. 구독 planner는 `(0.25, 0.75)` 후보만 모델 판정하므로 `기업명`은 LLM에도 전달되지 않는다.
2. coverage 단계의 `EXPLICIT_REJECTION_SIGNAL`은 `값 placeholder`라는 부분 문자열만 본다.
   따라서 진단 문구인 `앞 라벨 “기본정보”의 값 placeholder 가능성`도 확정 비입력 근거로
   취급되어 `unresolvedCandidates=0`으로 닫힌다.

즉 원인은 모델 판정이 아니라 모델 호출 전에 실행되는 결정적 후보 억제와 coverage 종결 규칙의
조합이다. 현행 v19 결과의 `partial` 또는 authoring `ready`는 모든 실제 입력 필드를 포함한다는
보장이 아니다.

## 정확한 재현 경로

원문 block 20, row 0은 다음과 같다. 좌표는 0-based다.

| col | 셀 텍스트 | 구조 |
| --- | --- | --- |
| 0 | `기본\n정보` | `1x1` |
| 1 | `기업명` | `1x1` |
| 2 | 빈 셀 | `1x1` |
| 3 | `대표자` | `1x1` |
| 4 | 빈 셀 | `1x1` |

파싱 Markdown도 `<tr><th>기본<br>정보</th><th>기업명</th><th></th><th>대표자</th><th></th></tr>`로
같다. `기업명`과 `대표자`는 각각 오른쪽 빈 셀을 갖는 대칭적인 입력 라벨이다.

후보 추출 직후의 의미는 다음과 같다.

- `기본정보` 후보: 위치 col 0, KorDoc `originalValue="기업명"`.
- `기업명` 후보: 위치 col 1, `originalValue=""`, `empty=true`, 메타데이터 라벨 신호. 점수 규칙상
  억제 전에는 score 5, `recommendedInput=true`, `inputLikelihood=0.95`다.
- `대표자` 후보: 위치 col 3, `originalValue=""`, `recommendedInput=true`,
  `inputLikelihood=0.95`로 최종 결과에도 남는다.

`apps/web/src/lib/server/application-analysis/core.ts:623-647`의 owner 탐색은 같은 행의 앞 후보 중
`normalize(owner.originalValue) === candidate.normalizedLabel`인 항목을 찾는다. 여기서는 col 0
`기본정보`가 owner가 된다. 기존 예외인
`isEmptyMetadataSubfieldOfRowSpanningGroup`(`core.ts:767-788`)은 owner cell의 `rowSpan > 1`을
필수로 요구한다. `기본정보`는 `rowSpan=1`이라 예외가 적용되지 않고 `기업명`이 억제된다.

그 결과 v19 artifact의 `기업명`은 다음 상태다.

- `recommendedInput=false`
- `inputLikelihood=0.15`
- `analysisSource=heuristic`, `llmConfidence=null`
- 신호: `업체·담당자·과제 메타데이터 라벨`,
  `앞 라벨 “기본\n정보”의 값 placeholder 가능성`

`field-planner.ts:1179-1181`의 triage 범위 밖이므로 LLM이 이 결정을 검토하지 않는다.
`field-coverage.ts:19, 228-259`는 `가능성` 신호 안의 `값 placeholder`를 확정 거절로 인정한다.
실제 artifact는 `rawEmptyCandidateCount=306`, `acceptedInputCount=239`,
`unresolvedCandidateCount=0`, `structuralWarningCount=15`, `status=partial`이다. 15개 경고 어디에도
`기업명`은 없다.

## 안전한 판정 수정 조건

단순히 `메타데이터 라벨이면 억제하지 않는다`거나 `오른쪽이 비었으면 입력으로 둔다`는 수정은
안전하지 않다. exact 원문 하나만 구조 스캔해도 `앞 라벨 ... placeholder 가능성`이 붙고 자체
오른쪽 빈 셀이 있는 후보가 31개였다. 여기에는 실제 필드 외에 기능 분류, 예시 표의 `추가`,
`기존`, 기능 설명 같은 고정 셀도 포함된다.

최소 수정은 기존 후보를 새로 만들거나 값을 추정하는 방식이 아니라, 아래 조건을 모두 만족하는
경우에만 `suppressValueCellDuplicates`의 억제를 건너뛰는 것이다.

1. 후보가 억제 전부터 `recommendedInput=true`, `empty=true`, `originalValue`가 빈 문자열인
   `kordoc-form` 후보다. RHWP implicit 복구 후보까지 이 예외로 넓히지 않는다.
2. 후보 위치의 실제 IR 셀 텍스트가 후보의 normalized label과 정확히 일치한다.
3. 후보 라벨 셀의 span 끝 바로 오른쪽에 실제 셀이 존재하고 그 셀이 비어 있다. 즉 후보가 자기
   소유의 독립 값 슬롯을 갖는다.
4. owner 관계가 단순 문자열 suffix가 아니라, `owner.originalValue === candidate.label`인 KorDoc
   연쇄 오인 경로다. suffix 기반 중복 제거는 별도 동작으로 유지한다.
5. 후보 라벨은 `기업명`, `회사명`, `법인명`, `대표자`, `성명`, `담당자`, `책임자`, 연락처,
   등록번호 등 짧은 canonical leaf metadata 라벨의 exact 집합에 해당한다. 현행
   `POSITIVE_INPUT_LABEL`은 `기간`, `금액`, `년도` 같은 부분 문자열까지 잡으므로 그대로 쓰면
   범위가 너무 넓다.
6. 같은 행에 최소 한 개 이상의 다른 canonical leaf label→빈 값 쌍이 있어 교대형
   label/value 레이아웃을 독립적으로 확인한다. 본 건은 `대표자`→col 4 빈 셀이 이 증거다.

이 조건은 `기업명`을 원래의 고신뢰 입력 후보로 보존하면서, `금: 백만원`, `해당 시`, 표 머리글,
예시 기능 구분값, 행 끝 placeholder를 자동 입력으로 되살리지 않는다. 더 넓은 서술형 하위 필드
복구는 이 수정에 섞지 말고 별도 fixture로 판단해야 한다.

coverage에는 별도 fail-safe가 필요하다.

- `값 placeholder 가능성`은 이름 그대로 미확정 진단이므로 `hasResolvedRejection`의 확정 신호가
  되어서는 안 된다.
- `EXPLICIT_REJECTION_SIGNAL`에서 일반 `값 placeholder` 부분 문자열을 제거하고, 구조적으로
  증명된 중복에만 별도 exact rejection signal 또는 typed reason을 기록해야 한다.
- 위치 결속을 통과한 LLM `not_input`, span-aware placeholder의 명시적 rejection constant,
  unsupported/fixed-table rejection처럼 이미 구조 계약이 있는 경우만 coverage를 종결한다.
- 애매한 heuristic 억제가 남으면 `review_required`로 드러나야 한다. 이 fail-safe 없이 추출
  조건만 고치면 다른 라벨에서 같은 종류의 조용한 누락이 반복될 수 있다.

## 현행 v19 batch 영향

조사 snapshot 시점에 로컬에 생성된 v19 `analysis.json`은 6개였다. 이들 artifact에서
`empty=true`, `recommendedInput=false`, `앞 라벨 ... placeholder 가능성`을 가진 후보는 187개,
그중 현행 metadata/content 의미 신호도 가진 후보는 49개였다.

이 수치는 확정 누락 수가 아니라 검토 상한이다. 예시 표, 평가표, 연도·단위, 고정 분류도 다수
포함되므로 일괄 복구하면 거짓 입력을 크게 늘린다. 현재 확인된 확정 누락은 exact 원문을 대조한
`기업명` 1건이다. 다만 같은 기제가 다른 v19 결과에도 존재하므로, v19 application authoring
결과를 사용자 입력 필드가 완전하다고 간주할 수는 없다.

영향 경계는 다음과 같다.

- 딥분석 본문과 matching projection의 publishable 판정 자체를 뒤집는 증거는 아니다.
- 신청서 authoring 필드 inventory, `acceptedInputCount`, document `partial/complete`, 상위
  authoring readiness에는 직접 영향을 준다.
- 이미 생성된 v19 artifact는 이후 코드 수정으로 소급 교정되지 않는다. 사용자 대면 authoring이나
  promotion 근거로 소비하기 전에 exact field coverage 재검증이 필요하다.
- running v19 launch의 manifest/contract를 중간 변경하면 안 된다. 수정은 별도 material contract
  revision과 오프라인 회귀를 거쳐야 하며, live 재분석은 새 exact 실행 범위가 승인된 뒤의 일이다.

## 후속 최소 회귀 테스트

구현 시 최소한 다음을 추가한다. 이 진단에서는 실행하거나 구현하지 않았다.

1. `core.test.ts` exact positive fixture
   - `[기본정보, 기업명, 빈 셀, 대표자, 빈 셀]`을 구성한다.
   - `기업명`과 `대표자`가 모두 `recommendedInput=true`이고 `기업명`에 앞 라벨 placeholder 신호가
     붙지 않는지 검증한다.
   - `기본정보` 자체는 입력으로 승격되지 않는지 함께 검증한다.
2. `core.test.ts` negative fixtures
   - 기존 `[신청금액, 금: 백만원]`, span-aware `해당 시`, 행 끝 placeholder는 계속 억제한다.
   - `(예시)` 기능 표의 `기존/추가/수정/미사용`과 단순 머리글 연쇄는 독립 빈 값 슬롯 또는
     canonical sibling 증거가 없으므로 복구하지 않는다.
   - canonical처럼 보이는 문자열이 있어도 자체 blank 슬롯이 없거나 동일 행의 두 번째
     label→blank 쌍이 없으면 자동 보존하지 않는다.
3. `field-coverage.test.ts` fail-safe
   - 빈 비추천 후보에 `앞 라벨 ... 값 placeholder 가능성`만 있으면 `review_required`와 unresolved
     issue가 남아야 한다.
   - 새 exact/typed structural rejection을 가진 proven duplicate만 coverage에서 resolved로 닫힌다.
4. 결합 회귀
   - exact block 20 fixture를 추출→coverage까지 통과시켜 `acceptedInputCount`에 `기업명`이 포함되고
     `anchorReadyInputCount`도 증가하는지 검증한다.
   - 모델 응답, confidence 임계, keyword-only 강제 수락에 기대지 않는다.

## 남은 한계

- 수동 점검은 comprehensive review가 아니며 49개 의미 신호 후보를 원문별로 모두 판정하지 않았다.
- 실제 HWP 편집·저장·재열기 UAT는 수행하지 않았다. 이 진단은 field inventory 누락까지만
  확정한다.
- running launch가 계속 artifact를 만들고 있어 snapshot 이후 v19 영향 후보 수는 늘어날 수 있다.

주 에이전트도 최종 필드 artifact·파싱 원문과 `core.ts:623`의 억제 분기, `field-coverage.ts:19`의 부분 문자열 정규식을 직접 대조했다. 실행 중 코드 수정은 하지 않았다.

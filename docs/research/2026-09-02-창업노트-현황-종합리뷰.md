## 0. 한 페이지 요약

**제품 목적**은 2026-07-02 마스터 설계가 규정한 대로 "사업자번호 하나로 지원 가능한 공공 지원사업을 찾고, 공고문과 양식을 해석해, 사업자의 실제 정보와 근거를 바탕으로 입력값·초안·해설·체크리스트를 제공하는 작성 가이드"다. 자동 제출 대행이 아니고, 근거 없는 자동작성을 금지하며, 휴먼 터치를 제품 구조 안에 둔다.

## 1. 제품 목적: 문서가 말하는 것

정본은 `docs/public-support-application-guide-master-architecture.md`(2026-07-02, 1,547줄)다. 이 문서 자체가 "지원사업 발견 서비스 → 공공 지원사업 작성 가이드"로의 전환 선언문이다.

- **의도(2장)**: 검색→해석→준비→작성→검토를 한 흐름으로. "우리는 사용자를 대신해 공공기관에 제출하는 자동 제출 대행사가 아니다."
- **설계 철학(3장)**: 결과물 우선 / 원본 편집보다 시각 가이드 우선 / 텍스트와 시각을 모두 본다 / 근거 없는 자동작성 금지 / 휴먼 터치를 제품 구조에 포함.
- **궁극 목표(4장)**: 사업자번호 입력 → 회사 파악 → 추천 → 적격 이유 설명 → 서류 분류 → 양식 preview → 입력칸 표시 → 자동채움 → 부족 항목 질문 → 검토 → export → 사용자가 직접 제출.
- **비범위(21장)**: HWP 원본 직접 수정본 제공, 포털 자동 제출, 인증정보 저장, CAPTCHA 우회, 확인 없는 서명, 근거 없는 수치, 전문가 검수 없는 법률·세무 판단.

**주목할 모순**: 3.2 "원본 편집보다 시각 가이드 우선"과 21장 첫 항목 "HWP 원본 직접 수정본 제공 안 함"은 현재 제품 본체(RHWP Studio에서 HWP/HWPX를 직접 편집·저장·다운로드)와 정면으로 어긋난다. Gate 0 통과와 @rhwp/core 브라우저 렌더 검증으로 전제가 바뀐 것은 정당한 피벗이지만, 마스터 문서는 07-04 이후 한 번도 갱신되지 않았고 `CLAUDE.md`는 여전히 "단일 설계 문서"로 지목한다.

## 4. 현재 구현 방식: 잘된 것과 구조적 문제

### 잘된 것 (유지할 것)

- **core 도메인 설계**: 포트 주입(`repositories/ports.ts` 31 인터페이스), 계약 파생 타입(`as const` → 타입), 모든 판정이 `RuleTraceEntry`로 남는 설명가능성, LLM 응답 불신 원칙(`extractor.ts` `normalizeCriteria`·`verifySpan`으로 근거 span 실재 검증, 계약 위반 row는 `text_only` 강등).
- **딥분석 큐 동시성**: advisory lock + `SKIP LOCKED` + generation CAS, unique identity 기반 멱등 enqueue, append-only receipt, 재시도 4분류, fail-closed 기본값(`DEEP_ANALYSIS_EXECUTE=1` 필수).
- **클라이언트 경계**: `@/lib/server` import 33파일 전부 `import type`, 스키마·fs·postgres 클라 유출 0.
- **본선 게이트 녹색**: 6개 tsconfig 0오류(strict + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`), `pnpm test` 75스크립트 70초 통과, lab 35종 통과.
- **문서 위생(4세대 이후)**: 강등 배너, "현재 정본" 앵커, 인증 사고 정정문, "reviewed 0건이면 정확도를 주장하지 않는다" 같은 정직성 규율.

### A. 가치 전달 단절 — 심각도 높음

- 6주 투자(E4~E6 490커밋, analysis-lab 75k + deep-analysis 36k 라인)의 산출이 사용자에게 도달한 경로가 없다. `lab:promote --write` 0회, 워커 `observe_only`, 실사용자 약 10명.
- 매칭 골든셋은 9쌍(`packages/core/scripts/verify-matching-eval-v3.ts:37` `total === 9`), 회사 프로필은 synthetic 33건, `labelStatus=reviewed` 데이터는 저장소에 없다. `golden/README.md`가 스스로 "50~100건 이상 도메인 라벨 골든셋을 별도로 확장해야 한다"고 적어 두었다. 현 상태에서 ruleset v8→v9 변경은 사실상 무검증 배포다.
- 딥분석 실험실은 이미 221건을 분석하고 사람·AI 검수를 받았다. 그 검수 결과에서 `(회사 archetype × 공고) → eligibility` 라벨을 뽑아 매칭 골든으로 승격하는 파이프라인이 없다. 두 트랙이 서로의 연료가 될 수 있는데 연결돼 있지 않다.

### B. 방어 코드 누적 루프 — 심각도 높음

- 08-16 결정("범용 방어 코드 확장 중단") 이후에도 08-25~09-02 41커밋 중 "차단·보강·봉인·바로잡는다" 계열이 대부분이다(예: `a316f52` 포털 메타데이터 오판정 차단, `ac8a59c` 검수 축 계약 위반 응답 차단, `abb46e6` 축 간 규모 오판정 차단, `5420d80` 미해결 축 오판정 차단).
- churn 최상위가 계약(`contracts/deep-analysis.ts` 51회, `dto.ts` 45회)과 감사 판정(`auditAdjudication.ts` 27회, `validator.test.ts` 21회)이다. 판정 규칙이 가장 불안정한 부위다.

## 5. 개선 방식

### 0단계 — 이번 주 (코드 몇 줄, 되돌리기 쉬움)

1. `CUNOTE_AUTH_REQUIRED` 기본값을 production에서 true로 뒤집고, mock·dev 로그인은 `NODE_ENV !== "production"`에서만 허용하도록 코드에서 거부한다. 익명 데모가 의도라면 marketing 라우트에만 명시적으로 허용한다.
2. `factory.ts`에서 `VERCEL_ENV=production`이고 어댑터가 drizzle이 아니면 부팅 실패. 4개 스토어(consent·refreshToken·preferences·notification)를 factory 경유로 통합.
3. `apps/conversion` `bootstrapFromEnv`에서 secret 비면 throw. `runJob` finally에서 `rm(workDir, {recursive:true})`. 잡 맵·캐시 맵에 TTL.
4. 깨진 테스트 3건 갱신. `node --test "**/*.test.ts"` glob 러너로 나열식 스크립트를 대체(기존 assert 코드는 `test()` 래핑만 필요). CI를 `pnpm test`와 동일 집합으로.
5. `completeDeepAnalysisJob`/`failDeepAnalysisJob`에 `WHERE id=? AND worker_id=? AND status='leased'` 조건 추가.

### 1단계 — 다음 4주: 가드 대신 루프 닫기

6. **검수된 승격 1회를 최우선 마일스톤으로.** 08-26 봉인 기준 투영 가능 46건을 P1 publisher 가드(승격분이 수집 크론에 말소되는 문제) 해결 → 독립 검수 → release gate → `lab:promote --write`까지 실제로 통과시킨다. 이 한 번이 6주 투자의 첫 회수다.
7. **방어 코드 모라토리엄.** 새 차단 규칙은 (a) 실사용자 또는 사람 검수에서 발견된 실패에만, (b) 골든 케이스 추가와 함께만 허용한다. AI 검수가 발견한 오판정은 가드가 아니라 골든셋에 먼저 쌓는다.
8. **매칭 골든 9 → 50+.** 딥분석 검수 결과(221건 target의 confirmations·audit)에서 `(archetype × grant) → eligibility` 라벨을 파생해 `golden/matching-v3/*.reviewed.jsonl`로 승격하는 스크립트를 만든다. 이것이 두 트랙을 잇는 연료다.
9. **실사용자 루프.** 클로즈드 베타 9건 active를 실사용자 10명에게 실제 노출하고, 답변 1회당 매칭 4중 계산(`applyCompanyProfileAnswer.ts:91-123`)을 1회로 줄인 뒤 관측한다. 마스터 설계 3.1 "결과물 우선"으로 무게중심을 되돌린다.

### 2단계 — 구조 (2~6주, 병렬 가능)

## 6. 방향성에 대한 판단

현재 방향(분석↔작성 분리, RHWP 직접 편집, 사용자 요청 시에만 LLM, 좌표는 LLM이 만들지 않음, exact manifest/grant/receipt)은 마스터 설계의 살아 있는 철학(근거 없는 자동작성 금지, 휴먼 터치 내장, 결과물 우선)과 정합하며 타당하다. 문제는 방향이 아니라 배분이다.

- 마스터 설계 3.1은 "인프라나 모델 자체가 제품 가치가 아니다"라고 했는데, 지난 6주의 실행은 인프라·가드·승인 계약에 편중됐다.
- 07-13 평가의 진단("측정 인프라는 과잉, 연료는 비어 있음")이 두 달 뒤에도 유효하다. 그 사이 인프라는 더 정교해졌고 연료(검수 라벨·실사용자 피드백)는 여전히 비어 있다.
- 사람 검수 병목을 AI 검수와 가드로 대체하는 전략은 순환성 가드가 잘 설계돼 있어 방법론적으로는 건전하지만, 종착이 "가드 무한 증식"이 되고 있다. 가드를 멈추는 유일한 외부 신호는 실사용자다.

따라서 다음 4주의 배분을 "새 차단 규칙 0건, 검수된 승격 1회, 실사용자 노출 1회"로 뒤집는 것이 가장 큰 개선이다. 그 뒤에 2단계 구조 정리를 하면 실험실 분리와 골든 확장이 실사용 데이터 위에서 이뤄진다.

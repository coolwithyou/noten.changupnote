## 안성: 기존 보류 해소 확인

`신 청 내 역` 후보는 `<td colspan="6">신청내역</td>`인 구획 제목이며 아래에 비용 입력 행들이 따로 있다.

기존 두 번의 재판정이 없어졌고 미해결 후보가 1→0이 됐다.

- 추천 입력 후보 ID 집합은 두 문서 각각 **6개·30개로 완전히 동일**하다. 새로 입력을 제거하지 않았다.
- 보류 해소로 실제 사용 가능으로 집계되는 필드는 6→36개, 준비된 신청 문서는 1→2개다.
  새로운 입력칸 30개를 생성했다는 뜻이 아니라 이전에 보류된 문서의 후보들이 사용 가능 상태가 된 것이다.
- 기존 구조 경고 4개는 내용까지 동일하다. 신청서 상태는 review_required→partial이며 complete는 아니다.

- 공통 서식 planner는 44.469→40.637초, 신청서 전체 wall은 53.454→49.859초로 줄었다.
  그러나 primary 응답이 길어져 target 전체는 74.435초로 늘었다.

## TECHFEST: 기존 지적과 새 필드 누락을 분리

새 primary 출력은 실제 제외업종 4개만 구조화 tags에 두고, 구체 업종이 특정되지 않은 법률 위임 조항은
별도 industry/text_only로 보존했다. 평가조건에는 순위를 바꾸는 사실을 두고 대표자 직접 참석·직원 대리 참석 절차는
신청 주의사항으로 옮겼다. 기존 2개 지적에 해당하는 출력 변경을 확인했으며 독립 검수 결과는 아래에 기록한다.

독립 검수의 새 지적은 prior_award 두 항목의 중복이다. 다만 원문은 창업진흥원 해외전시회 참가와
특정 사업에 선정된 후 K-스타트업 통합관 참가를 별도로 적고 있어, 두 집합의 동일성·완전 포함 관계를
원문만으로 확정할 수 없다. 이 지적은 **범위·기간·횟수를 보존한 통합 검토 대상**으로 해석한다.
한 항목을 단순 삭제하거나 서로 다른 참가 횟수를 합산하거나 답변을 공용화하지 않는다.
공식 검수 artifact는 그대로 두고 gpt-6-astra high의 원문 재검토 의견을 별도로 기록했다.

신청서 자동 결과는 complete·미해결 0이지만 추천 필드가 39→37개로 줄어 별도 원문 대조를 수행했다.

## 단양: 원문 누락은 그대로인데 ready로 바뀐 판정 주의

신청자격 등을 포함한 본문·붙임 1을 추가 확보하지 않은 동일 입력 재검증이다.
그런데 자동 matchingReadiness는 conditional→ready로 바뀌었다. 분석 서술은 여전히 공고 본문 미제공과
신청자격·제외대상·제출서류 확인 불가를 명시하지만 `other` 축이 input_missing 대신 inspected_no_condition으로 바뀌었다.
따라서 이 ready를 원문 누락 해소나 전체 자격 검토 완료의 증거로 인정하지 않는다.
평가표를 신청서가 아닌 것으로 처리했고 신청서 모델 호출은 계속 0회다.
기존과 달리 skip summary에 requestCount·usage를 명시적 0으로 기록하여 공식 관측의 계측 누락은 없어졌다.
시간은 51.691→58.195초로 늘었으며 현재 병목은 재판정이 아니라 최초 primary 응답이다.

## 남은 개선의 우선순위

1. TECHFEST와 같은 반복 label은 후보의 block/row/col에 결속된 문맥으로 판정해야 한다.
   전체 문서에서 찾은 첫 문자열 일치를 근거로 고신뢰 비입력 판정하는 문제를 먼저 해결한다.
2. 신청서 complete 외에 입력 후보 전후 차이와 같은 양식 간 대응 필드를 검수해야 한다.
   이번 누락은 confidence와 coverage 지표만으로는 탐지되지 않았다.
3. 전체 시간 단축은 primary의 생성 작업을 줄이는 방향을 검증해야 한다.
   신청서 호출 절감이나 scheduler 슬롯 확대만으로 이번 배치의 병목이 해결되지는 않는다.
   독립 검수에도 요청별 진행 관측과 제한된 동일 packet 재시도가 필요하다. 기본 20분 timeout 동안
   완료 여부만 기다리는 현재 관측 경로는 장기 지연의 원인과 실제 진행을 구분하기 어렵다.
4. 이번 실행의 코드·원문·조건을 고정한 기록을 기준으로 유지한다. 이번 요청에서는 결과 확인을 위해
   재분석했으며, 새 회귀를 고쳤다고 보이도록 원 artifact를 수정하거나 추가 실행을 반복하지 않았다.

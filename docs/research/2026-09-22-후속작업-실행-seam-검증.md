# 후속 작업 실행 seam 검증

작성일: 2026-09-22

## 전체 계획 위치

- 실행 묶음: R3 — 분류된 다음 작업을 실제로 끝내기
- 이번 범위: R3-0 exact 실행 admission과 처리 후 readiness 재평가
- 다음 범위: R3-1 검수된 질문 준비 adapter와 R3-2 source rebind/recruitment refresh adapter

## 구현 계약

`grantNextWork`는 지금까지 다음 작업 이름만 판정했고, campaign도 운영자 행동 문자열로 표시하는 데 그쳤다. 새 `grantNextWorkExecution` seam은 구체 adapter 앞에서 아래 순서를 강제한다.

1. 현재 source·analysis·question evidence와 변경 영향 영수증을 canonical hash로 봉인한다.
2. 실행 직전에 snapshot을 다시 읽고 예상 hash가 다르면 adapter를 호출하지 않는다.
3. `condition_analysis`처럼 모델 실행이 필요한 작업은 기존 별도 실행 권한 없이는 `blocked`로 끝낸다.
4. 명시적으로 등록된 exact action adapter만 한 번 호출한다.
5. 모델 불필요 작업 receipt의 `modelCalls`는 반드시 0이어야 한다.
6. 처리 뒤 같은 loader로 readiness를 다시 읽어 `completed`, `partial`, `stalled`, `regressed`를 구분한다.
7. 이미 `reuse_ready`이면 write 없이 `already_complete`로 멱등 종결한다.

변경 영향 영수증의 current raw hash와 readiness source raw hash가 다르면 snapshot 자체를 만들지 않는다. adapter receipt는 action, receipt SHA, 모델 호출 수, 외부 쓰기 수를 명시한다. 이 seam은 adapter의 DB transaction을 대신하지 않으므로 구체 writer는 여전히 원자성·CAS·rollback을 자체 보장해야 한다.

## 검증

- `pnpm --filter web typecheck`
- `pnpm exec tsx --tsconfig apps/web/tsconfig.json apps/web/src/lib/server/productReadiness/grantNextWorkExecution.test.ts`
- `pnpm test:grant-product-readiness`

검증 사례는 stale snapshot에서 adapter 0회, 모델 작업 차단, adapter 미등록 차단, 질문 준비 후 `reuse_ready` 이동, 모델 호출 오염 거부, 무진전·부분 진전·회귀 구분, 이미 준비된 공고의 write 0 멱등 종결을 포함한다.

## 남은 경계

- 실제 질문 draft/release adapter 등록과 격리 PostgreSQL 왕복
- `source_rebind`의 의미 불변 evidence와 successor serving 계약
- `recruitment_refresh`의 모집 상태 갱신과 자격 해석 재사용 계약
- 처리 이력의 영속 원장과 관리자 작업 표면
- 운영 migration, 모델 실행, 실제 서비스 쓰기

현재 결과는 처리 adapter가 따라야 할 실행 경계를 증명한다. 실제 공고의 readiness를 이동시켰다는 뜻은 아니다.

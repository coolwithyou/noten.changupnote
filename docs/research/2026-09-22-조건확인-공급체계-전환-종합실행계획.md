## 1. 목표와 완료의 의미

**새 공고를 조건별로 해석하고, 사용자에게 필요한 사실만 물어보고, 한 번 확인한 사실을 의미가 같은 공고에 재사용하며, 변경·실패 시 필요한 단계만 이어서 처리한다.**

완료 기준은 분석 성공 건수나 기존 342건 처리율이 아니다. 신규 공고가 공고 ID별 예외 코드 없이 같은 경로를 통과하고, 자동 해결 불가 사례는 근거·담당 단계·다음 작업을 갖고 남아야 한다.

최종 인수는 아래 네 가지를 모두 충족해야 한다.

1. 검수된 조건에 회사 사실만 부족하면 카드 안에서 답변하고 즉시 재판정할 수 있다.
2. 같은 사실을 쓰는 네 공고는 한 번 답하면 함께 재판정되고, 의미가 다른 공고에는 잘못 전파되지 않는다.
3. 검수·질문·발행만 필요한 결과를 원문 전체 재분석으로 되돌리지 않는다.
4. 설계·임계값 확정 이후 유입된 공고에서도 동일 경로를 검증한다. 미지원 조건은 정확한 검수 사유로 남긴다.

‘확인하면 지원 가능’ 문구는 다른 필수/제외 조건과 coverage가 확인된 경우에만 사용한다. 원문 누락·미검수 조건이 남으면 ‘이 조건을 확인하면 다시 판단할 수 있어요’로 표현한다. 자격조건 충족과 선정·지원금 지급을 구분한다.

## 2. 범위와 기존 자산 재사용

### 반드시 포함

- 조건 해석 상태와 회사 비교 상태 분리, 조건별 해소 방법.
- 조건에서 질문 수요 도출, 사용자 답변 저장·수정·철회·재평가.
- 회사 공통 사실과 공고별 확인의 구분, 의미·기준일에 따른 재사용.
- 분석/검수/질문/발행/현행성의 독립 관측과 다음 최소 작업 판정.
- 변경 영향에 따른 재검증, 중복 실행 방지, 기존 이력의 재사용.
- 기존 자산 이관과 신규 공고 전향 인수, 점진 노출과 rollback.

### 이번 전환의 필수 조건이 아닌 것

- Jev 채택, 전체 추출 모델 교체, 범용 에이전트/규칙 언어 신규 개발.
- 모든 불명확 공고의 자동 확정, 신청서 작성 자동화의 완성.
- 운영 유료 worker 자동 활성화. 현행 observe_only와 exact 실행 승인을 유지한다.

## 3. 핵심 계약

### 조건 해소 Module

Interface의 입력은 조건·근거 검수·회사 사실·현행 질문/답변이다. 출력은 판정, 미확인 이유, 해소 방법, 필요한 사실 또는 질문, 재사용 범위다. UI·집계·후속 작업이 이 Interface를 소비한다. 판정 로직을 호출부마다 복사하지 않는다.

- 원문 해석: 검증 / 자료 누락 / 의미 충돌 / 표현 미지원.
- 회사 비교: 충족 / 미충족 / 사실 필요 / 공고별 확인 필요 / 비교 보류.
- 해소 방법: 코드 비교 / 회사 사실 입력 / 공고별 확인 / 원문 검수 / 자료 복구.
- 의미: 필수·우대·제외, 대상·트랙, AND/OR·예외, 기준일·단위 보존.
- `text_only`는 표현 형식이며 사용자 질문 허용의 단독 근거가 아니다.
- coverage에는 읽은 구역뿐 아니라 미확보 참조 첨부·누락 가능성도 포함한다.

공통 사실은 사업장 범위·기준일·의미 버전·출처·확인 시각을 갖는다. ‘일반기업에 해당함’ 같은 공고 해석을 회사의 영구 사실로 무조건 저장하지 않는다. 사용자의 공고별 해석 답변을 공식 기업정보보다 우선시하지 않는다.

### 후속 작업 Module

Interface의 입력은 현재 evidence snapshot과 승인 범위다. 출력은 원인별 상태, 다음 최소 작업, 필요한 입력, 기존 결과 재사용 여부, 외부 실행/쓰기 필요 여부다. 판정은 부작용 없이 수행하고 실행은 기존 Adapter에 맡긴다.

작업 종류: 자료 복구 / 조건 추출 / 재변환 / 독립 검수 / 질문 준비 / 발행 준비 / 재매칭 / 재사용 / 담당자 검수 / 기간 종료 / 승인 대기.

- 분석 없음과 유효한 발행 증거 없음은 다른 상태다.
- 같은 관련 입력·계약·단계가 완료됐으면 재사용한다.
- 실패한 단계만 재시도하고 skipped가 이전 성공을 지우지 않는다.
- 결과가 불명확하면 명시적으로 보류한다. 성공할 때까지 무한 모델 재호출하지 않는다.
- 모델 실행 승인과 서비스 쓰기 승인은 판정 결과와 별도다. 승인 대기도 정상적으로 관측 가능한 상태다.

### 모델 배정과 비용 통제 — 2026-09-22 확정

표의 Sol은 `gpt-5.6-sol`, Terra는 `gpt-5.6-terra`, Astra는 `gpt-6-astra`다. 기본 진행·통합 담당은 **Sol / high**다. reasoning effort는 작업별 시작 설정이며 성능을 보장하는 등급이 아니다.

공식 비교 문서에서 Astra는 가장 어려운 작업, Sol은 복잡한 전문 작업, Terra는 지능과 비용의 균형에 해당한다. 위 배정은 이를 이번 저장소의 변경 위험에 적용한 설계 판단이며, 이 프로젝트에서 측정한 모델별 성능 순위는 아니다. [OpenAI 공식 모델 비교](https://developers.openai.com/api/docs/models/compare)

- **Astra 기본 투입은 T1과 T5의 제한된 계약 검토 두 지점**이다. T1에서는 원문 해석/회사 사실/질문 의미/AND·OR·예외를, T5에서는 coverage와 변경 무효화 범위를 검토한다. 전체 구현·로그 읽기·진행 관리는 Sol이 맡는다.
- T3에서 T1이 확정한 사실 재사용 계약을 구현하는 경우 Astra 재검토는 생략한다. 새 의미 범위나 공식 정보 우선순위가 생기면 해당 diff만 검토한다.
- T7도 자동으로 Astra에 전체 리뷰를 맡기지 않는다. 미해결 의미 차이, 틀린 적격 판정, 기존 계약을 바꾸는 발견이 있을 때만 제한 검토한다.
- Terra는 확정된 계약의 UI, 관리자/리포트 연결, 평가 Adapter, 읽기 전용 비교, 명시된 시나리오의 UAT를 담당한다. 인증·답변 효과·DB 쓰기·이관 결정의 책임은 Sol에 유지한다.
- Luna는 기본 배정에서 제외한다. 이 작업은 상태·의미 계약이 촘촘해 지나친 분할이 재검토 비용을 만들 수 있다. 필요할 때만 `gpt-5.6-luna / medium`으로 링크 검사·표 형식 정리 등 기계적 작업을 분리하며 정답 라벨·제품 판정은 맡기지 않는다.
- 모델을 파트마다 무조건 바꾸지 않는다. Sol이 이미 관련 문맥을 보유한 작은 UI/문서 수정은 직접 끝낸다. Terra로 분리할 때는 독립 산출물과 확정된 입력/출력이 있어야 한다.
- Astra 검토 입력은 관련 계약·반례·변경 diff·실패 증거로 제한한다. 동일 전체 저장소 탐색과 같은 SHA의 검증을 모델마다 반복하지 않는다.
- Terra 작업이 공유 계약 변경을 요구하면 Sol로 올린다. Sol이 재현 가능한 의미 충돌을 해결하지 못하거나 고위험 계약 선택이 필요하면 Astra로 올린다. 단순 테스트 실패를 곧바로 모델 승격 사유로 삼지 않는다.
- `xhigh` 이상은 기본값으로 사용하지 않는다. 재현된 어려운 문제가 남은 경우에만 이유와 범위를 기록하고 해당 작업에서 사용한다. 토큰 절감률이나 API 단가를 실제 Codex 구독 사용량과 동일하다고 주장하지 않는다.
- 이 배정은 **개발 에이전트 역할**이다. 공고 분석 운영 모델을 변경하거나 유료 모델 실행을 승인하는 설정이 아니다. 이번 문서 변경으로 세션 모델 전환이나 하위 에이전트 실행이 이뤄진 것은 아니다.

- 주 작업 폴더 `d134b49`와 최근 배포 작업 checkout `526283d`는 조사 당시 기준이다. 착수 시 현행 상태로 갱신한다.

- 숫자 537/342를 고정 대상 목록으로 쓰지 않는다. 현행 지원기간·중복·입력 기준으로 읽기 전용 snapshot을 다시 만든다.
- 기존 오류 사례를 유형별로 수집한다. 회사 개인정보는 합성값을 사용한다.
- 산출물: 소스 기준표, 현행 경로 지도, casebook, 측정 분모 정의. 별도 전수 원인조사를 반복하는 단계로 확대하지 않는다.

### T1–T3 — 사용자 여정부터 완결

- 첫 경로는 이미 표현 가능한 검수된 조건으로 시작한다. 새로운 복합식 언어를 선행 개발하지 않는다.
- 질문 수요는 조건 해소 결과에서 계산한다. 질문 생성 전에는 질문 준비 대기라는 작업이 존재해야 한다.
- 실제 v2 질문과 근거·답변 효과를 연결하고 기존 인증·회사 소유권·동시 수정 방어를 유지한다.
- 카드는 필요한 질문과 답변 행동을 먼저 보여 준다. 충족한 조건은 접어 두고 근거는 열람 가능하게 한다.
- 낙관적 표시가 서버의 확정 판정을 대신하지 않는다. 실패·중복 클릭·만료 질문은 답변 성공으로 표시하지 않는다.
- 같은 사실을 소비하는 공고의 갱신 결과를 사용자에게 보여 준다. 전체 공고 결과를 무차별 삭제하거나 사실을 부풀려 저장하지 않는다.
- 원문 검수와 회사 입력을 구분한다. 사용자가 해결할 수 없는 항목에는 반복적인 ‘회사 정보 확인’ 버튼을 내보내지 않는다.

### T4–T5 — 공급 경로와 변경 처리 연결

- evidence loader는 유효 결과만 반환해 탈락 이유를 잃지 않도록 바꾼다. 준비도와 campaign은 동일한 후속 작업 결과를 소비한다.
- 최소 재개 결정표: 분석 있음/검수 없음→검수, 검수 있음/질문 없음→질문, 발행 없음→발행 준비, 회사 답변 변경→재매칭.
- 원본 revision은 보존한다. 소비 기능의 의존성과 원문 coverage를 기준으로 재검증 범위를 계산한다.
- 기간·상태 변경은 eligibility 해석 재사용과 모집 여부 재판정을 분리한다. 자격조건을 바꾸는 날짜 문구는 단순 기간 변경으로 처리하지 않는다.
- 원문 구역 신설·제외 조건 추가·참조 첨부 누락을 탐지한다. 기존 source span 불변만으로 자동 재사용하지 않는다.
- 모델 수정 재시도는 유형별 횟수 상한과 종결 이유를 둔다. 구체 상한은 기존 실행 계약을 조사해 T1 결정표에 확정하며 무제한을 허용하지 않는다.
- 계획 자동화는 승인된 실행 범위만 이어간다. 재시도마다 사용자 승인을 새로 만드는 것도, 범위 밖 쓰기를 자동 수행하는 것도 금지한다.

### T6–T7 — 이관과 실제 전환

1. additive 계약과 호환 reader로 시작한다. 불명확한 legacy 결과는 ready로 추정하지 않는다.
2. 기존 immutable receipt는 그대로 두고 검증된 연결/파생 결과를 별도로 결속한다. 실제 DB 스키마는 기존 테이블로 표현 가능한지 먼저 판단한다.
3. 동일 snapshot에서 기존/신규 판정과 질문·노출 차이를 비교한다. 차이는 개선/회귀/의도 변경/미확정으로 기록한다.
4. 승인된 exact 대상으로 소량 이관하고 기존 답변·소유권·출처·idempotency를 검증한다. 의미 변경된 답변은 조용히 재해석하지 않는다.
5. 제한 노출 후 점진 확대한다. 코드 배포 성공과 DB 이관 성공, 실제 사용자 답변 성공을 각각 기록한다.
6. rollback은 새 판정 경로의 노출/작업을 중단하고 검증된 기존 경로로 전환한다. 새 사용자 답변은 삭제하지 않고 보존하며 구 reader가 오해하지 않게 한다.
7. 신규 유입 전향 평가를 통과한 뒤 중복 판정 경로를 제거한다. 롤백 가능 기간과 이관 완료 여부를 먼저 확인한다.

측정 지표는 전체/지원기간 유효/원문 확보/검수 완료 등 분모를 명시한다. 평균 분석 성공률 하나로 대체하지 않는다.

- **필수 불변식:** 위 인수 사례 전부 통과, 잘못된 사실 전파와 누락 조건에 의한 확정 0건, 불필요 재분석 사례에서 모델 착수 0회.
- **사용자 가치:** 질문 노출률, 질문 답변→재판정 성공률, 한 답변으로 해소된 공고 수, 확인 전후 이탈.
- **공급 효율:** 신규 유입→질문 가능한 노출까지의 p50/p95, 단계별 대기시간, 공고당 재분석 수, 사람 검수량, 공급 건당 총비용.
- **품질:** 잘못된 적격/부적격, 놓친 후보, 원문 검수 보류, coverage 누락, 판정 변경 이유.

전향 인수의 초기 최소 관찰 범위는 설계 고정 뒤 유입된 **50개 고유 공고, 최소 7일**이다. 두 수집원과 위 주요 오류 유형을 포함한다. 특정 유형이 없으면 추가 보류 사례셋으로 보충하고 미관찰 항목을 표시한다. 이는 안정성 관찰 기준이며 낮은 오류율을 통계적으로 보장하는 표본 크기는 아니다.

성능·질문 완료율 등의 개선 목표 수치는 T0 기준선을 본 뒤 T1에서 고정하고 평가 뒤 유리하게 바꾸지 않는다. 치명적 의미 오류가 나오면 해당 유형 자동 확정을 중단하고 회귀 사례를 추가한 후 새로운 미사용 표본으로 재검증한다. 일부 희귀 미지원 사례가 존재한다고 전체 전환을 무기한 중단하지는 않는다.

## 6. 검증 실행 원칙

- 조건/질문 변경: 관련 국소 테스트, `test:matching-unit`, `test:confirmation-natural-guards`, `test:confirmation-question-draft`에서 영향 범위를 선택한다.
- 준비도/후속 작업: `test:grant-product-readiness`, `lab:matching:projection:test`, 새 결정표 회귀검사.
- 공유 계약·데이터·인증 변경: 관련 suite + 프로젝트 집계 `test:product-journey`, DB 변경 시 `test:product-postgres`, 영향 패키지 typecheck.
- 원천/발행 계약: `verify:deep-analysis-contract`, `lab:release:test`, source corrections 관련 검증을 변경 범위에 맞게 수행한다.
- 실제 저장·갱신: PostgreSQL 통합과 `verify:match-state-refresh`, 실제 화면의 질문·오류·재진입 확인.
- 상위 gate가 같은 SHA의 하위 검증을 포함하면 영수증을 재사용한다. 무관한 전체 테스트를 매 단계 반복하지 않는다.
- 개발 서버는 시작하지 않는다. UI 검증 시 기존 서버를 확인하고 없으면 실행을 요청한다.
- 배포/외부 실행은 구체적인 검증 결과를 만든 뒤 기존 승인 범위로 진행한다. 승인 범위가 실제로 확대되는 최종 단계에서만 추가 승인을 요청한다.

## 7. Jev 선택 트랙

J1은 T7의 필수 선행 작업이 아니다. 공식 기능·제약은 조사 문서를 참조하고 실제 평가 직전에 버전·정책을 확인한다.

- 공개 원문·합성 회사 사실과 사람이 검토한 정답으로 시작한다.
- 문단 유형, 근거 의미 일치, 해소 주체 등 좁은 판단만 비교한다.
- 현재 방식/규칙 기준선/Jev를 같은 입력·출력 계약으로 평가한다.
- 기관·템플릿 단위로 개발/보류 평가셋을 분리하고, 확률 임계값과 모델 버전을 고정한다.
- 실제 API 실행은 대상·호출 상한·데이터 범위를 구체화한 뒤 승인된 범위에서만 수행한다.
- 자동 확정 오류, 보류율, 사람 검수 시간, 전체 비용을 비교한다. 저렴함만으로 채택하지 않는다.
- 통과 시 기존 Interface의 Adapter로 넣고, 별도 Jev 전용 검수 원장은 만들지 않는다. 장애·미달 시 기존 경로로 돌아갈 수 있어야 한다.

### R0 — 정본과 통합 기준 고정

### R1 — 사람 결정에서 기존 v2 초안까지 연결

Sol/high가 공용 review 계약과 기존 deterministic draft/manual/release 경로를 연결한다. 별도 질문 발행 엔진이나 가짜 LabRun·검수자 이력을 만들지 않는다. 기존 경로가 실제로 요구하는 provenance를 먼저 확인하고, 복원할 수 없는 경우 누락 근거와 다음 작업으로 종결한다.

- manifest·packet·decision set의 schema/hash, 질문 집합의 정확한 일치, 중복, reviewer, 극성·scope를 소비 경계에서 재검증한다. 파일 hash는 사람 신원 인증을 대신하지 않는다.
- 현재 원문 revision·criterion 의미·질문 상태가 달라진 항목은 격리한다. 과거 결정을 새 의미에 자동 적용하지 않는다.
- 승인 항목만 v2 초안으로 변환한다. 수리·폐기 결정은 다음 작업으로 출력하고, 이 단계에서는 기존 질문을 삭제하거나 서비스에 공개하지 않는다.
- 동일 입력 재실행은 같은 산출물을 재사용한다. 일부 항목 실패는 사유와 함께 격리하고 공유 manifest 손상은 묶음을 중단한다.
- 기존 공통 사실 의미와 연결되는 표준 키를 검증한다. `company_fact` 선택이나 문장 유사성만으로 공유 키를 발명하지 않는다.

UI 보완은 Terra/high 또는 문맥을 가진 Sol이 수행한다. 고정 `22건`을 manifest 수량으로 바꾸고, 중간 작업 저장·재개를 제공한다. 미완료 작업 파일과 최종 결정 파일은 상태를 명확히 구분한다. 승인에 필요한 극성·scope와 수리/폐기 메모까지 충족한 항목만 완료로 집계한다. import/export 중에는 오래된 묶음의 내보내기를 차단한다.

검증: 변조·누락·중복·다른 묶음·잘못된 극성·source drift·재실행·부분 실패, 기존 draft/release 회귀, product journey와 영향 패키지 typecheck. 통과 기준은 합성 사람 결정 fixture가 기존 초안 소비 경로까지 연결되는 것과 실제 packet import/UI 재개 인수다. 실제 사람의 결정을 AI가 대신 기록하지 않는다.

2026-09-22 구현 보정: 기존 promotion writer는 공고의 전체 criteria·질문 snapshot을 교체하므로 질문 한 건의 이관 adapter로 직접 재사용하지 않는다. ### R2 — 소량 이관과 사용자 왕복 완결

Sol/high가 격리 DB와 검증된 원문 표본으로 이관 리허설을 준비하고 Terra/high가 기존 서버에서 화면을 확인한다. 같은 의미 네 공고와 범위/기준일이 다른 공고, 기존 답변이 있는 경우를 포함한다. 현재 22개 packet의 저장 답변은 0건이므로 답변 보존은 별도 fixture로 검증한다.

필수 인수: 질문 기본 노출 → 예/아니오/모름 저장 → 재판정 → 관련 공고 갱신 → 답변 수정·철회 → 새로고침·재진입. 저장 성공/재판정 실패, 동시 수정, 비권한 사용자, stale 질문, 만료, 모바일·키보드도 포함한다. rollback 후 새 답변을 보존하고 구 reader가 오해하지 않는지 검증한다.

2026-09-22 R2-1 구현: 기존 전체 공고 promotion item을 재사용하지 않고 `analysis_lab_legacy_question_migration_items` 전용 원장을 추가했다. 준비 시 현재 source·criterion·legacy 질문·답변 0건을 봉인하고, 준비자와 다른 승인자의 exact plan 승인 뒤에만 공고별 advisory lock 안에서 legacy 질문 비활성화, v2 질문 생성, confirmed dedup component의 match state 무효화와 receipt 기록을 원자 적용한다. rollback은 현재 after receipt가 그대로이며 신규 질문 답변이 0건일 때만 legacy 질문을 복구하고 successor를 이력으로 비활성화한다. 신규 답변이 있으면 `post_migration_answers_present`로 중단해 삭제하지 않는다. 격리 PostgreSQL에서 재시도, baseline drift, RLS, 답변 보존, 제한 rollback을 검증했다. 이는 live DB migration 적용이나 실제 질문 이관 승인이 아니다.

2026-09-22 R2-2 seam 검증: R2-1 writer가 만든 migrated v2 질문을 실제 `listGrantConfirmations`·`submitGrantConfirmations`·`withdrawGrantConfirmation` 경로로 답하고 수정·철회했다. 동일 company-fact 의미를 가진 독립 공고 3건과 현재 공고 1건이 함께 재계산 대상으로 잡히고, 관련 공고의 투영 답변이 충족→미충족→미답변으로 이동하는 것을 격리 PostgreSQL에서 확인했다. 인라인 카드 브라우저 회귀는 관련 공고 4건 갱신 안내를, 전체 확인 시트 브라우저 회귀는 exact question/answer/company-fact revision에 결속된 철회를 확인했다. 두 브라우저 회귀는 로컬 mock fetch를 사용하므로 인증·DB·Next runtime을 함께 거친 UAT 증거는 아니다.

2026-09-22 R2-2c 인증 화면 인수: 이관 release item에 기존 promotion parent, 적용 직전 serving hash, 적용 뒤 전체 공고 serving hash를 기록하고, reader는 활성 이관 release·유일한 활성 parent·최신 successor frontier·현재 snapshot·질문/criterion/grant exact 결속이 모두 맞을 때만 migrated `company_fact` 질문을 matcher에 제공한다. 회사 사실로 답변된 뒤 matcher가 일반 profile 값으로 판정해도 이 exact 결속을 카드에 유지해 “확인 내용 수정” 진입이 사라지지 않게 했다. 폐기형 로컬 PostgreSQL과 immutable source snapshot의 Next production runtime에서 실제 password 로그인 후 카드 inline 긍정 답변, 관련 공고 4건 안내, 지원 가능 전환, 신청 준비 이동, 수정 진입 유지, 인증된 부정 변경·철회, 철회 뒤 질문 재노출을 확인했다. model call과 외부 쓰기는 0건이었다. 이 증거는 실제 서비스 DB schema 적용이나 승인된 공고 이관을 승인하지 않는다.

통과 기준: 실제 저장과 화면 결과가 일치하고 네 공고 전파/다른 의미 비전파가 증명됨. 개발 서버가 없으면 실행을 요청하되 adapter·DB·리허설 준비는 계속한다. 여기서 운영 반영이 필요하면 대상과 쓰기 상한을 구체화한 뒤 프로젝트 승인 경계를 따른다.

### R3 — 분류된 다음 작업을 실제로 끝내기

Sol/high가 `grantNextWork`와 readiness가 내보내는 작업을 기존 처리 adapter에 연결한다. Terra/high는 운영자 목록을 기존 관리자 구성요소로 연결한다. 새 거대 관제 화면보다 원인·근거·다음 행동·처리 결과가 보이는 최소 표면을 우선한다.

1. 질문 준비 5건과 발행 준비 가능 사례의 처리 경로를 먼저 연결한다. 수량은 현재 snapshot에서 갱신한다.
2. 296건 조건/결속 검수는 유형별 대표 사례로 기존 근거 재사용·조건 수리·추가 근거 필요를 나누고, 각 유형의 처리기를 검증한 뒤 확대한다. 모든 행에 수동 예외 코드를 만들지 않는다.
3. `source_rebind`는 의미 불변 증거가 있을 때만 새 결속을 만들고, `recruitment_refresh`는 모집 상태를 갱신한다. `coverage_review`는 새 조항·첨부를 확인한 뒤 유지/부분 수리/추가 분석을 결정한다.
4. 194건 분석 후보는 유효 분석 자산 재사용 가능성을 실행 전에 확인하고 기존 승인된 모델 경로로만 보낸다. 후속 작업 분류가 모델 실행 권한을 만들지는 않는다.

모든 처리기는 현재 입력 확인, 중복 처리 방지, 완료/보류/실패 사유, 제한된 재시도와 이전 성공 보존을 갖는다. 처리 후 공통 readiness를 다시 평가해 다음 상태를 기록한다. 질문 17개 구조 수리와 3개 프로필 판정 후보도 같은 유형별 경로로 처리한다.

통과 기준: 대표 사례가 검수 대기에서 실제 다음 단계로 이동하며 분석 불필요 사례의 모델 착수는 0회다. DB 변경은 격리 PostgreSQL·원천/발행 회귀·집계 gate로 검증한다. 운영 migration 적용과 과거 이벤트 backfill은 구분하며 과거 payload를 추정 생성하지 않는다.

### R4 — 신규 유입도 같은 경로로 연결

Sol/high가 수집→변경 영향→조건 해소→질문 수요→초안/검수→발행 준비→매칭의 연결을 완결한다. 기존 공고용 우회 분기를 신규 공급의 정본으로 만들지 않는다. 표준 사실 키의 안정성, 미지원 조건의 정확한 보류, 첨부 누락, 관측 메타데이터 변경, 부분 실패를 신규 fixture와 미사용 표본으로 검증한다.

작업별 시작·종료·대기 사유·재시도·재사용·모델 실행 수를 기존 원장/관측에 남긴다. 신규 유입부터 질문 가능 노출까지 p50/p95, 사람 검수량, 불필요 재분석, 사용자 답변 성공률을 계산할 수 있어야 한다. 공통 사실 공유를 많이 만드는 것만으로 성공을 평가하지 않는다.

통과 기준: 신규 공고 ID별 패치 없이 같은 처리 경로로 결과 또는 정확한 보류 사유를 얻는다. 기존 관측 지표와 새 지표의 분모를 고정한 뒤 운영 표본을 시작한다.

### R5 — 통합·제한 운영 적용

R0 통합 지도에 따라 코드와 migration 순서를 검증하고 필요한 회귀 gate를 통과한 정확한 commit으로 적용 후보를 만든다. 역할별 배포 인증과 observe_only 계약을 지킨다. 코드 배포, DB schema 적용, exact 질문 반영, 매칭 갱신의 결과를 각각 기록한다.

최초 제한 대상은 현재 유효하며 사람 검수와 release 근거가 모두 있는 소량 집합이다. 배포 URL/alias 확인에 더해 로그인한 실제 사용자 질문 왕복을 확인한다. 예상 밖 적격 확정·잘못된 사실 전파·답변 손실이 발생하면 해당 경로 확대를 중단하고 준비된 rollback을 실행할 수 있어야 한다.

통과 기준: 제한 운영 스모크와 rollback 리허설 증거가 함께 존재함. 배포·서비스 쓰기·모델 호출은 문서 작성이나 구현 완료만으로 승인된 것으로 간주하지 않는다. 승인된 exact 범위 안의 재시도는 반복 승인을 만들지 않는다.

### R6 — 전향 관찰과 확대

설계·임계값 고정 뒤 유입된 고유 공고 50개 이상과 최소 7일을 모두 충족한다. 두 수집원, 미지원/보류 이유, 지연, 검수 부담, 실제 답변 성공과 잘못된 판정을 보고한다. 표본이 부족한 날을 완료 처리하지 않는다. 평가 중 계약을 바꾸면 변경 시점과 영향 표본을 분리하고 미사용 표본으로 재검증한다.

필수 불변식을 모두 통과하고 사전에 고정한 품질·공급 목표를 충족하면 점진 확대한다. 미관찰 유형은 한계를 기록하고 해당 유형의 자동 확정을 보류한다. legacy 경로 제거는 이관 범위와 rollback 기간을 확인한 뒤 수행한다. Jev 비교는 이 전환의 완료를 지연시키지 않는 선택 트랙으로 유지한다.

### 다음 실행과 종료 보고

다음 구현은 **R3의 분류된 다음 작업 처리 연결**이다. 질문 준비·발행 준비·source rebind·모집기간 갱신 가운데 모델 실행 없이 끝낼 수 있는 대표 사례부터 실제 처리 adapter와 readiness 재평가를 연결한다. 실제 서비스 DB의 스키마 적용과 승인된 exact 샘플 이관은 R5의 배포·제한 이관 경계로 남긴다. 각 묶음 종료 보고에는 원래 T 작업, 변경 commit, 검증 증거, 사용자에게 새로 가능한 행동, 미실행 운영 단계, 다음 묶음을 기록한다. 기존 동일 소스의 검증 영수증은 재사용한다.

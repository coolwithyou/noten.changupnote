## 주 작업 폴더와 통합 경계

주 작업 폴더는 공통 기준 commit 위에 매칭 이벤트·사용자 화면·DB schema·repository·OpenAPI·migration journal 변경이 미커밋 상태다. 다음 영역은 격리 브랜치의 앞선 구현과 의미가 겹치므로 전체 브랜치 merge나 무차별 cherry-pick을 금지하고 파일별로 재조정한다.

- 매칭 화면과 이벤트: `EligibilityMatchAccordion`, `GrantOverviewView`, `Programs`, 두 match event route, `matchEvents`
- 저장 계약: `db/schema.ts`, `repositories/drizzle.ts`, `repositories/runtime.ts`, repository integration test
- migration: `0086_match_journey_events.sql`, `0087_grant_source_change_impact.sql`, `meta/_journal.json`
- 공용 계약: `dto.ts`, `openapi.ts`, generated OpenAPI, repository ports
- 실행 명령: 루트 `package.json`

R1 신규 adapter 본체와 테스트 파일은 주 작업 폴더에 동명 변경이 없다. 통합할 때는 신규 파일을 먼저 옮기고, `package.json` script 한 줄과 정본 계획 문서는 현재 주 작업 폴더 내용을 보존한 채 hunk 단위로 합친다. schema·migration journal은 R2 실제 쓰기 설계 전까지 건드리지 않는다.

## 정본 산출물과 소비 순서

1. read-only repeatable-read snapshot으로 `legacy-question-migration-review-manifest-v1`과 packet을 생성한다.
2. 관리자가 exact manifest 전체를 판정해 `legacy-question-migration-review-decision-set-v1`을 만든다.
3. 소비 시점에 같은 read-only loader를 다시 실행해 최신 manifest·packet을 만든다.
4. R1 adapter가 과거 manifest·packet·decision set과 최신 manifest·packet을 모두 검증한다.
5. 의미가 같은 승인만 v2 migration draft로 만들고, drift·수리·폐기·공통 키 누락은 각각 다음 작업으로 격리한다.

이 산출물들은 모델 호출, 서비스 DB 쓰기, migration, release, promotion, live 질문 공개 권한을 만들지 않는다. 이후 release adapter가 현재 질문 상태와 쓰기 계획을 다시 결속해야 한다.

## 지표 분모

- 레거시 검수 분모: exact review manifest의 `packetCount`; 다른 공고 readiness 수량과 합산하지 않는다.
- R1 변환 결과: `draftCount + nextWorkCount = decisionCount`를 유지한다.
- 최신성 격리: `refresh_review / decisionCount`.
- 공통 사실 준비: 발행 가능한 `company_fact` draft와 `register_company_fact_key`를 따로 센다.
- 사용자 왕복과 신규 공급 지표는 R2·R4에서 수집하며, offline draft 수량을 지원 가능 공고 수량으로 보고하지 않는다.

## R1 종료 전 남은 경계

- migration draft를 기존 release/promotion 입력으로 바꾸는 adapter는 아직 없다.
- `company_fact`는 기존 packet에 검증 가능한 표준 key가 있을 때만 초안으로 만들며, scope 선택만으로 key를 생성하지 않는다.
- 실제 사람 decision set, DB 쓰기, 기존 질문 수정·철회, 배포는 수행하지 않았다.
- 주 작업 폴더 통합은 현재 미커밋 변경 소유자가 확정된 뒤 파일별로 수행한다.

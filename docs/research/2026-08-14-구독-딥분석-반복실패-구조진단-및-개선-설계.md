## 0. 이 문서의 역할

이 문서는 조사 결과를 보존하는 보고서이면서 이후 구현의 계약이다. 구현은 이 문서가 정한
Interface, 불변식, 단계별 exit gate를 통과하는 범위에서만 진행한다. 새 기능이 유용해 보여도
현재 실패 원인을 직접 제거하지 않거나 exit gate에 필요하지 않으면 이번 트랙에 넣지 않는다.

특히 다음 세 문장을 정본으로 둔다.

1. 구독 실행에서 명목 USD는 관측값이지 실행 권한이나 중단 기준이 아니다.
2. `held`는 품질을 안전하게 종결한 상태이지 오류나 자동 재시도 대상이 아니다.
3. 프로세스 종료, 잡 lifecycle, 공고 품질, 통계 게이트, 승격 자격을 하나의 성공/실패 축으로 접지 않는다.

## 1. 현재 판정

### 1-1. 실행 판정

추가 10건/30건 배치, 자동 review repair, 대량 검수·감사, 승격·배포는 계속 중단한다.
구조 수정과 모델 호출 없는 회귀 검증을 먼저 완료하고, 새로운 비중복 단건 canary는 이 문서의
Gate R을 통과한 뒤에만 별도 승인 대상으로 올린다.

### 1-2. 사용자 결정: 구독 USD 상한 폐기

`claude-cli` 구독 실행은 요청별 API 과금 경로가 아니므로 `--max-cost-usd`로 신규 작업을 중단하지
않는다. 기존 `costUsd`는 다음 용도로만 보존한다.

- API 환산 사용량 관측
- 모델·prompt·문서 복잡도 비교
- 비정상 fan-out 진단
- API 운영 경로의 실제 비용 guard 산정 자료

구독 실행 안전장치는 비용 대신 이미 존재하는 다음 자원을 기준으로 한다.

- 전역 Claude CLI 프로세스 4슬롯
- 요청별 timeout
- Max window exhaustion 감지
- 명시적 코호트 크기와 공고 ID
- 사용자 pause와 runtime lease

현재 Max window 감지는 batch/review/audit에는 있으나 confirmations에는 동일하게 배선돼 있지 않다.
P1에서 confirmations도 window marker를 만나면 신규 착수를 중단하고 별도 exit로 종결하도록 맞춘다.
이는 새 quota가 아니라 이미 정의된 구독 소진 신호의 의미 일치 수정이다.

이번 구현에서는 새 범용 wall-time scheduler, 호출량 quota, 별도 daemon을 추가하지 않는다. 먼저
잘못된 USD 중단을 제거하고 상태·실험 계약을 바로잡는다. 이미 확인한 905후보 fan-out은 P4의
도메인 candidate/request admission으로 제한하고, 모든 lane에 적용하는 generic quota는 별도 증거와
명확한 SLA가 생길 때만 설계한다.

## 2. 관측된 실패

### 2-1. 확대 10건

고정 코호트 `cohort.deep-v17-cp2b-expand10-20260814.json`의 결과는 다음과 같다.

| 항목 | 결과 |
|---|---:|
| publishable / held | 7 / 3 |
| repair 사용 런 / 시도 | 6/10 / 7회 |
| pilot 포함 누적 repair | 6/15 |
| first-pass issue | 22건, 실제 교정 대상 10건 |
| 배치 wall | 64.54분 |
| deep / Kordoc 명목 USD | 14.4990 / 31.6714 |
| 총 명목 USD | 46.1704 |
| Kordoc 상태 | complete 4 / partial 4 / not_applicable 2 |

명목 USD는 더 이상 구독 실행의 실패 판정에 쓰지 않는다. 다만 Kordoc이 관측 부하의 68.6%를
차지했고 후보 수·요청 수가 꼬리 지연과 강하게 연결된 사실은 lane 분리와 preflight 필요성의
근거로 계속 사용한다.

### 2-2. 직접 반복을 만드는 상태 충돌

현재 실행 경로는 하나의 held 결과를 다음처럼 서로 다르게 해석한다.

```text
runValidatedLabPrimary
  -> outcome = held
runLabAnalysis
  -> primaryValidationOutcome = held
  -> error = primary_validation_held
runLabBatch
  -> target-error / errorRuns += 1
batch CLI
  -> target가 있으면 exit 0
subscription agent
  -> successful-only index에는 held 없음
  -> retryErrors=true partition에서는 다시 pending
```

따라서 같은 실행이 품질 계층에서는 안전 종결, 저장 계층에서는 error, 프로세스 계층에서는 성공,
에이전트 계층에서는 성공 런 누락과 재시도로 해석된다. 이 모순이 반복 실패의 P0 원인이다.

### 2-3. 테스트가 놓친 이유

- quality graph 테스트는 held를 직접 만든 fixture로 검증한다.
- batch 테스트는 non-null `error`를 모두 `target-error`로 보는 현재 계약만 검증한다.
- agent 테스트는 `error: null`인 합성 런과 미리 만든 graph를 주입한다.
- 실제 `runValidatedLabPrimary -> LabRun -> batch -> agent` 경로를 통과하는 held fixture가 없다.

따라서 기존 테스트가 모두 GREEN이어도 seam 사이 상태 의미는 깨질 수 있다.

## 3. 근본 원인

### 3-1. 실험을 소유하는 깊은 Module 부재

현재 Module 경계는 코호트 파일, 단건 LabRun, batch runner, quality graph, CLI, readiness 문서에
분산돼 있다. 호출자는 다음 지식을 직접 운반한다.

- 어떤 코호트가 어느 실험의 연속 표본인지
- 어떤 lane을 실행해야 하는지
- held와 error 중 무엇을 재시도해야 하는지
- 어떤 exact run과 graph를 판정에 묶어야 하는지
- pilot 이후 다음 표본으로 진행할 통계적 권한이 있는지
- promotion에 어떤 end-to-end 근거가 필요한지

이 Interface는 얕다. 호출자가 Implementation의 순서와 불변식을 알아야 하므로 국소 수정이 다른
호출자에서 다시 깨진다.

### 3-2. 계획 단위와 실제 작업 단위 불일치

제어면은 공고 1건을 작업 단위로 보지만 실제 실행은 동적으로 팽창한다.

```text
공고
  +-- deep primary
  |    +-- deterministic normalization
  |    `-- 0..2 model repair
  `-- 문서 0..N
       +-- parse/classify
       +-- 후보 chunk 0..N
       `-- adjudication 0..2 rounds
```

공고가 끝난 뒤에야 비용·요청 수·부분 실패를 알 수 있고, 중간 성공 문서나 pass를 독립적으로
재사용하기 어렵다. 범용 DAG 엔진을 도입하지는 않지만, 최소 Experiment Module 내부에서는 lane과
stage receipt를 구분해야 한다.

### 3-3. 추출 계약과 matcher 표현 계층 혼합

현재 평면 criterion에는 actor, track, phase scope가 없다. validator는 source span과 note 정규식으로
scope 손실을 탐지하고 extractor에게 `text_only` 또는 전체 repair를 요구한다. 확대 10건의 실제
교정 issue 10개 중 최소 4개는 prompt가 아닌 deterministic/validator 문제이며, 추가 3개는 matcher
표현 한계가 강하게 개입했다. `repair 6/10`을 곧바로 모델 repair율로 사용하면 안 된다.

이번 구현에서는 DB/matcher schema를 즉시 바꾸지 않는다. 먼저 repair 계측과 ownership을 분리하고,
scoped evidence IR은 shadow projection으로만 도입 여부를 판단한다.

### 3-4. 코호트 층과 통계 gate의 불완전성

현재 층은 source x 공고별 최대 markdown bytes다. 총 입력량, 문서 수, 실제 문서 형식, 후보 수,
예상 request 수, actor/track 복잡도를 반영하지 않는다. pilot 0/5는 운영 canary 통과일 수 있으나
모집단 repair율 GO는 아니다.

pilot과 확대를 별개 수동 명령으로 만들지 않고 하나의 사전 동결된 sequence에서 누적 판정해야 한다.

## 4. 설계 대안과 선택

### A. 기존 runner 국소 보강

held 필드, exit code, 비용 옵션만 수정한다. 빠르지만 코호트·run lineage·통계 진행 권한을 여전히
호출자가 조립한다. P0 응급 수정에는 필요하지만 최종 구조로는 부족하다.

### B. 범용 workflow/DAG 엔진

동적 fan-out, retry, checkpoint에는 유연하다. 그러나 node DSL, plugin registry, 분산 실행까지
Interface가 팽창하고 현재 도메인의 불변식이 다시 caller 설정으로 빠져나갈 위험이 크다.

### C. Gate-first `AnalysisExperiment` Module

외부 Interface는 작게 유지하고, 도메인에 고정된 stage graph와 receipt는 Implementation 내부에 둔다.
이번 트랙의 선택안이다.

## 5. 최종 목표 Interface

호출자와 테스트가 사용하는 외부 seam은 세 동작이다.

```ts
interface AnalysisExperiment {
  prepare(spec: ExperimentSpec): Promise<ExperimentPlan>;

  execute(input: {
    planId: string;
    expectedPlanSha256: string;
    authority: ExecutionAuthority;
    signal: AbortSignal;
  }): Promise<ExperimentReceipt>;

  inspect(experimentId: string): Promise<ExperimentSnapshot>;
}
```

일반 운용 명령은 다음 하나를 목표로 한다.

```bash
pnpm lab:experiment -- --series=deep-v18
```

caller가 직접 지정하지 않는 값:

- retry/reanalyze flag 조합
- pilot/expand wave 크기
- latest-success 스캔 규칙
- repair와 review 순서
- lane별 성공 판정
- 다음 wave 권한

이 Interface는 최종 목표다. 이번 P3에서는 live `execute`, runtime authority, cancellation, `inspect`
read model을 구현하지 않는다. Gate R 이전에는 모델 호출 없는 `createPlan/replay` seam만 연다.

### 5-1. `ExperimentSpec`

```ts
type ExperimentSpec = {
  seriesId: string;
  objective: "deep-primary-repair-rate";
  cohort: {
    seriesManifestSha256: string;
    orderedGrantIds: string[];
    maxSampleSize: number;
    strataVersion: string;
  };
  policy: {
    promptVersion: string;
    validatorVersion: string;
    gatePolicyVersion: string;
    model: string;
    transport: "claude-cli";
  };
};
```

구독 spec에는 USD ceiling을 넣지 않는다. 명목 USD는 receipt usage에만 기록한다.

최종 Interface는 향후 `application-field`, `end-to-end` objective를 추가할 수 있지만 이번 P3에는
`deep-primary-repair-rate`만 구현한다. 기존 15건 replay는 pilot5와 expand10 두 source snapshot을
순서대로 묶은 하나의 legacy series manifest를 만들고 그 manifest SHA를 plan에 결속한다.

### 5-2. 독립 상태 축

```ts
type ExperimentLifecycle =
  | "planned"
  | "running"
  | "finished"
  | "aborted"
  | "infrastructure_failed";

type NoticeOutcome = "publishable" | "held" | "failed";

type LaneOutcome = "passed" | "partial" | "held" | "failed" | "not_applicable";

type GateVerdict = "CONTINUE" | "GO" | "NO_GO" | "INCONCLUSIVE" | "INVALID";

type PromotionEligibility = "eligible" | "ineligible" | "not_evaluated";
```

`success`, `ok`, `error` 하나로 이 축들을 접지 않는다.

### 5-3. receipt 결속

Experiment receipt는 최소한 다음을 exact 값으로 보존한다.

- series/attempt/wave와 parent receipt SHA
- cohort SHA와 전체 고정 순서
- grant ID, input SHA, attachment manifest SHA
- git SHA, package runtime SHA
- prompt/validator/model/transport
- exact run ID와 run artifact SHA
- deep/application lane outcome
- deterministic repair와 model repair call 수
- issue transition과 hold 이유
- 요청 수, input/output token, wall time, 명목 USD telemetry
- gate policy와 누적 판정

기존 15건에는 validator/git/package/attachment manifest와 deterministic/model repair 구분 provenance가
모두 존재하지 않는다. fixture에 값을 추측해 채우지 않고 `legacy_partial` 또는 `unknown`으로 보존한다.
미래 live receipt의 필수 필드와 legacy shadow replay의 가용 필드를 같은 완전성으로 주장하지 않는다.
또한 quality graph의 `evaluatedAt`은 호출 시각에 따라 바뀌므로 전체 graph JSON hash를 결속하지 않고,
`policyVersion + runId + 결정적 lane/node projection`만 판정 근거로 사용한다.

pilot5와 expand10은 처음부터 Nmax=30의 한 sequence로 선동결된 표본이 아니며 합계 strata도 완전하지
않다. 따라서 기존 artifact replay는 `mode=legacy_shadow`, `provenanceStatus=legacy_partial`로 표시한다.
이는 과거 관측이 0/5에서 계속 관찰했어야 하고 누적 6/15에서 중단했어야 한다는 NO-GO 재현에는
쓸 수 있지만 formal GO를 발급할 수 없다. legacy shadow의 GO 경계 도달은 `INVALID`로 막는다.
완전한 provenance와 strata 조건의 positive GO는 별도 synthetic manifest로 evaluator만 테스트한다.

## 6. 실행 Implementation

범용 graph Interface를 공개하지 않는다. Module 내부의 고정 순서는 다음과 같다.

1. 코호트와 입력 provenance 봉인
2. 모델 호출 없는 입력·첨부 preflight
3. objective에 따른 lane 선택
4. runtime authority와 전역 4슬롯 획득
5. deep primary 또는 Kordoc stage 실행
6. validator issue ownership 분류
7. deterministic normalization
8. 실제 extractor defect에만 model repair
9. stage/notice receipt 원자 저장
10. 누적 sequential gate 판정

실제 대체 구현이 있는 seam에만 Adapter를 둔다.

| Seam | Adapter |
|---|---|
| Model execution | Claude CLI / deterministic fake |
| Receipt store | local immutable filesystem / in-memory test |
| Runtime authority | 현재 local lease / in-memory test |

validator, graph compiler, outcome reducer, gate evaluator는 in-process Implementation으로 두며 불필요한
port를 만들지 않는다.

## 7. 통계 gate 제안

repair율 목표를 반복 관측에도 사용할 수 있도록 다음 값을 초기 정책 후보로 둔다.

- `p_good = 0.10`
- `p_bad = 0.20`
- `alpha = 0.05`
- `beta = 0.20`
- `Nmin = 15`
- `Nmax = 30`

이 후보 정책에서의 기대 판정:

| 누적 결과 | 판정 |
|---|---|
| 0/5 | CONTINUE |
| 0/15 | GO |
| 6/15 | NO_GO |

전체 sequence 예비 열거에서 `p=0.10`일 때 GO 52.82% / NO_GO 1.25% / INCONCLUSIVE 45.93%,
`p=0.20`일 때 GO 9.92% / NO_GO 27.45% / INCONCLUSIVE 62.62%였다. 오류율은 후보 한계 안이지만
Nmax 30에서 미결정 비율이 높다. 따라서 이를 범용 SPRT framework나 확정 운영 정책으로 만들지
않고, 상수가 고정된 `repair-sprt-v1` 순수 함수와 전체 sequence 열거 테스트로 먼저 검증한다.

hard gate가 하나라도
깨지면 통계값보다 먼저 `INVALID` 또는 `NO_GO`다.

- exact run/cohort/provenance 불일치
- confirmatory run에 예상 밖 review repair 혼입
- 필수 strata 미관측
- repair 후 신규 issue
- Kordoc field-level gold 없이 end-to-end GO 요청

## 8. 구현 단계와 커밋 경계

### P0. 상태 의미 복구

목표:

- held를 저장·batch·agent에서 품질 terminal로 보존
- held를 error count와 자동 retry에서 제외
- 구 artifact의 `primary_validation_held` sentinel 호환
- promotion/review 소비자는 publishable만 허용하는 기존 fail-closed 성질 보존

P0에서 held의 legacy `error` sentinel을 즉시 삭제하지 않는다. 그렇게 하면 `run.error === null`을
publishable 조건으로 사용하던 검수·감사·승격 소비자가 fail-open될 수 있다. 먼저 중앙 분류 함수로
의미를 한 곳에 모은다.

```ts
type LabRunOutcome = "publishable" | "held" | "failed";

classifyLabRunOutcome(run): LabRunOutcome
isPublishableLabRun(run): boolean
```

legacy truth table:

| 명시 outcome | error | 분류 |
|---|---|---|
| `publishable` | `null` | publishable |
| `held` | `null` | held, 신규 형식 |
| `held` | `primary_validation_held: ...` | held |
| 없음 | `primary_validation_held: ...` | held |
| 없음 | `null` | legacy publishable |
| `held` | 기타 error | failed, inconsistent |
| `publishable` | non-null | failed, inconsistent |
| 없음 | 기타 non-null | failed |
| `null`·알 수 없음 | 어떤 값 | failed, malformed |
| `publishable`·`held` | error 필드 누락 | failed, malformed |

batch는 `target-held` 이벤트와 `summary.held`를 별도로 기록한다. held는 표본 실행 완주에는 포함하지만
품질 GO 분자에는 포함하지 않는다. readiness는 이를 실행 BLOCKED로 오해하거나 GO로 통과시키지 않고,
품질 `ITERATE` 또는 experiment gate의 해당 scope 판정으로 보존한다. agent는 terminal held를 repair
대상으로 만들지 않고 명시적 held/blocking 결과로 보고한다.

검수·감사·확정 질문·dispatch·review selector·promotion candidate/release·관리 UI는 모두 최종적으로
중앙 outcome을 사용해야 한다. 단, ApplicationRoundtripRun과 문서의 `error`는 LabRun과 다른 계약이므로
`rg` 결과를 무차별 치환하지 않는다.

P0는 fail-open 창을 피하기 위해 세 수직 슬라이스로 나눈다.

1. **P0-A consumer hardening**: truth table, review/audit/confirmations/dispatch selector,
   `planGrantPromotion`과 source artifact 재검증을 `isPublishableLabRun`으로 방어한다. writer는 유지한다.
2. **P0-B writer와 batch 상태**: consumer가 GREEN인 뒤 신규 held를 `error:null`로 저장하고,
   `target-held`, `summary.held`, held telemetry, legacy sentinel scan을 도입한다.
3. **P0-C agent와 readiness**: terminal index를 publishable/held로 분리하고, primary held에는 review·repair를
   실행하지 않는다. 4 publishable + 1 held 표본은 batch/sample complete지만 deep quality 실패와
   최종 `ITERATE`로 판정한다.

필수 테스트:

- 실제 모양의 held LabRun이 `target-held`로 종결
- `summary.held=1`, `errorRuns=0`
- `retryErrors=true`여도 heldCurrent는 pending이 아님
- agent가 held를 “성공 런 없음”으로 throw하거나 재분석하지 않음
- provider error는 계속 retry/error 대상

예정 커밋: `딥분석 보류 상태를 오류와 재시도에서 분리하다`

### P1. 구독 USD를 telemetry로 전환

목표:

- `claude-cli` 실행은 nominal USD cap으로 중단하지 않음
- API transport는 기존 완료 비용 기반 soft stop을 보존
- batch/review/audit/adjudication/confirmation이 같은 transport 정책 사용
- subscription agent가 batch뿐 아니라 review/audit/adjudication에 전달하던 USD progression 옵션 제거
- confirmations가 Max window exhaustion을 일반 target 실패로 재시도하지 않고 신규 착수를 중단
- 과거 CLI 인자는 즉시 깨뜨리지 않되 구독에서는 1회 deprecation warning을 내고 실행 정책과
  새 snapshot에는 넣지 않음

공통 정책은 다음 작은 union으로 고정한다.

```ts
type NominalCostPolicy =
  | { kind: "api-settled-usd-stop"; maxUsd: number }
  | { kind: "subscription-telemetry-only" };
```

`api-settled-usd-stop`도 동시 실행이 완료된 뒤 누적값을 확인하므로 hard cap이 아니다. P1은 이
기존 API semantics를 보존할 뿐 reservation ledger를 추가하거나 hard cap으로 이름을 바꾸지 않는다.
`ai-adjudication`은 현재 구독 전용이므로 telemetry-only만 적용한다.

필수 테스트:

- claude-cli에서 임의의 높은 nominal USD에도 전 target 실행
- api에서 기존 cost-cap 동작 유지
- plan/summary에는 nominal USD telemetry가 계속 남음
- 구독 agent가 USD를 progression capability로 전달하지 않음

예정 커밋: `구독 분석 비용을 실행 상한에서 관측값으로 전환하다`

### P2. lane 명시화

목표:

- CLI가 Kordoc을 암묵적으로 강제하지 않음
- deep-repair 실험은 deep-only
- end-to-end 실험만 application lane 필수
- application retry가 deep primary를 다시 실행하지 않도록 후속 seam 준비

필수 테스트:

- flag/spec 없는 deep 실행에 Kordoc override 없음
- end-to-end policy에는 Kordoc 포함
- deep/application 결과가 독립 outcome으로 남음

예정 커밋: `딥분석 실험의 실행 레인을 명시하다`

### P3. 최소 Experiment kernel

목표:

- immutable plan/receipt 타입
- exact run/cohort binding
- 순수 sequential gate evaluator
- 기존 pilot5와 expand10을 모델 호출 없이 shadow replay

이번 단계의 외부 seam은 두 순수 동작뿐이다.

```ts
createDeepRepairExperimentPlan(manifest): DeepRepairExperimentPlan
replayDeepRepairExperiment(plan, observations): DeepRepairExperimentReceipt
```

실제 batch executor를 교체하지 않으며 `execute/inspect`, runtime authority, cancellation Adapter를
만들지 않는다. 새 kernel을 기존 artifact 위에 먼저 배치하고 판정의 정본을 옮긴 뒤 Gate R 이후에만
live 실행 Adapter를 검토한다. 기존 `bulk-pilot5` artifact는 v17 pilot5와 다른 ID이므로 성공 fixture로
재사용하지 않고 cohort mismatch가 `INVALID`가 되는 음성 fixture로만 사용할 수 있다. pilot5의 batch
lifecycle artifact가 없으므로 `finished` 상태를 창작하지 않는다.

필수 테스트:

- 동일 spec과 cohort는 동일 plan SHA
- 한 필드 drift는 INVALID
- 0/5 CONTINUE, 0/15 GO, 6/15 NO_GO
- run ID가 graph와 다르면 INVALID
- lifecycle finished라도 quality NO_GO 가능

여기서 0/15 GO는 완전한 synthetic manifest에 대한 evaluator 계약이다. 기존 pilot/expand legacy
artifact는 0/5 CONTINUE와 누적 6/15 historical NO_GO만 재현하며 GO 근거로 사용하지 않는다.

예정 커밋: `딥분석 실험 계획과 순차 게이트를 도입하다`

### P4. Kordoc preflight와 bounded stage

P0~P3 뒤 별도 gate에서 진행한다.

- 실제 파일 형식 probe
- 정책/지침/목록/참고문서 분류 보강
- 총 candidate/request 수 기록
- ambiguous 후보만 LLM 판정하는 triage 검증
- overflow는 silent truncation이 아니라 review_required

905후보 정책문서, 642후보 실제 신청서, 비용을 쓴 뒤 not_applicable이 된 공고를 fixture로 사용한다.

### P5. scoped evidence IR shadow

P0~P4의 issue ownership 계측 뒤 필요성이 재확인될 때만 진행한다. DB schema와 matcher를 바로
마이그레이션하지 않고 actor/track/phase scope를 가진 evidence IR을 현재 criterion으로 shadow
projection한다. 투영 불가능한 사실은 명시적으로 held/text-only로 남긴다.

## 9. Gate R: 새 모델 실행 재개 조건

다음 조건을 모두 만족해야 새로운 비중복 단건 canary를 제안할 수 있다.

- [ ] P0 상태 회귀 테스트 GREEN
- [ ] 구독 USD cap 미적용/API cap 보존 테스트 GREEN
- [ ] held/error/publishable 소비자 전수 리뷰 완료
- [ ] pilot5 shadow 판정 CONTINUE
- [ ] 누적 15건 shadow 판정 NO_GO
- [ ] exact run/graph/provenance drift 음성 테스트 GREEN
- [ ] 관련 package typecheck와 기존 analysis-lab 테스트 GREEN
- [ ] 구독 분석 runtime pause 유지 확인
- [ ] 운영 worker `observe_only` 유지
- [ ] 사용자에게 canary 범위·모델·코호트·중단 조건을 제시하고 승인 획득

Gate R 통과 전에는 `lab:agent --execute`, 새 batch, 자동 repair, promotion을 실행하지 않는다.

## 10. 과구현·오구현 방지선

이번 트랙에서 하지 않는다.

- 범용 DAG/workflow engine 또는 DSL
- graph DB와 전면 event-sourcing
- 별도 scheduler daemon
- 모든 helper의 port/interface화
- 구독 nominal USD hard cap의 다른 이름 재도입
- actor/track DB schema 즉시 전면 변경
- patch response schema 선도입
- 새로운 모델·검수 lane 추가
- confirmatory 실험 중 자동 review repair
- 자동 promotion
- UI 선구현
- 기존 확대 10건 즉시 재실행

판단 기준은 간단하다. 현재의 반복 원인을 제거하거나 Gate R을 검증하지 않는 코드는 이번 구현에
포함하지 않는다.

## 1. 문제 정의

lab 딥분석 + Kordoc(지원 양식 선분석)의 건당 처리 시간이 배치 기준 **평균 57분(최대 78.5분)**으로, 정례 배치·검수 파이프라인의 리드타임을 지배했다. 전 구간이 Max 구독 CLI(`claude -p`) 경유라 API 실지출은 0이지만, 전역 4슬롯과 사용량 창(window)이 유한 자원이다.

### 반증된 가설 (채택하지 않은 것과 그 이유)

- **sonnet-5 교체 단독**: A/B에서 총시간 **+71% 역효과**. TPS는 높지만 출력이 41% 더 장황하고 낮은 confidence로 재판정 라운드를 추가 유발.
- **순수 effort 하향(low/medium)**: 속도 −30~40%지만 실제 입력 필드를 거절 conf 0.75~0.80으로 **조용히 놓침**(canary 264후보 중 low 4건·medium 3건 누락, 재판정에도 안 넘어감). 사용자에게 "빠른 작성에서 필드가 소리 없이 빠지는" 회귀라 기각.
- **프로세스 스폰 최적화**: 호출당 고정 오버헤드 3.3~5.0초로 지연의 5% 미만 — 레버 아님.

### 발견 ① — 125015가 CP2 배치에 미편입

HANDOFF는 "`--reanalyze-outdated`로 125015(0aa42679…)도 자동 편입"이라 서술했으나, 이는 **자격 획득까지만 맞고 선정은 아니다**. 배치 선정이 코호트 순서 보존 + `pending.slice(0, limit)`(batch.ts:245)인데, 0aa42679는 기간 스킵 제외 후 40건 중 **32번째**라 limit=10 바깥이다. 실제 착수 10건은 재구성한 순서와 전부 일치했다. CP2 종료 직후 별도 세션이 `--grant-ids=0aa42679-…`로 125015를 착수했지만, 01:03 KST 확인 시 프로세스가 종료됐고 새 런 산출물은 없다. 이 실행은 중단된 시도로 기록하고, CP2 실패 원인을 재현·수정하기 전에 재시도하지 않는다.

## 8. 리뷰 결론과 후속 결정안

- **R1. 0.85 임계는 버전된 상수로 유지** — 3공고 264후보·누락 4건은 env 설정면을 늘리기엔 작다. 후속 실험에서 임계를 조절할 필요가 생기면 명시적 실행 옵션·provenance·reuse 계약을 함께 버전한다. **현재 코드 변경 없음.**
- **R2. 장식 플래그와 effort 누락은 코드 후속 과제** — `--with-application-roundtrip`을 제거하거나 실제 동작과 일치시키고, lab 배치 진입점에서 `medium`을 명시하지 않으면 실행 전 fail-fast하는 방식을 권장한다. core·API·운영 기본 `null`은 보존한다. **제안일 뿐 미구현.**
- **R3. CP2는 운영 게이트로도 실패** — 7/10 repair라 통계력 논의 전에 기준을 크게 초과했다. 다음 검증에서 `<20%`를 모집단 주장으로 쓰려면 순차 표본 규칙을 사전 고정한다. 단측 95% 상한이 20% 미만이 되려면 0건 repair일 때 최소 14건, 1건일 때 최소 22건이 필요하다.
- **R4. limit 선정은 명시적 층화 전략으로 분리** — 현재-version ok 스킵으로 반복 실행이 항상 같은 앞부분만 선택하는 것은 아니지만, 개별 limit 배치는 순서 편향이 있다. `buildBalancedShortlist`를 직접 재사용하지 말고, 실행 타깃용 strategy·seed·algorithm version·grant ID를 산출물에 기록하는 방식을 제안한다. **미구현.**
- **R5. 새 코호트는 버전을 분리** — 현재 자동 선정기는 기존 미처리 대상이 있으면 새 선정을 거부한다. 기존 60건을 덮어쓰지 말고 v15 검증용 신규 코호트를 별도 스냅샷으로 만드는 절차가 필요하다. **미구현.**
- **R6. Kordoc 전용 canary 도입** — 124870 메뉴형과 확약서형을 포함한 field-level 정답 표본으로 재현율·거짓 거절을 비교한다. 기존 출력과의 diff는 정답이 아니므로 사람 확정 표본이 필요하다. **미구현.**
- **R7. launchd·상시 러너는 보류** — 현 단계에서는 `caffeinate` + lease + 체크포인트 재개를 표준 절차로 유지한다. 정례 주기와 운용 소유자가 확정된 뒤에 상시 러너를 재검토한다.
- **R8. P1 승격 보호는 이미 완료** — `c79e2c0`에서 publisher 가드와 수동 CLI 락·재판별을 구현했고 `verify:promotion-protection`이 test 체인에 배선돼 있다. P1 부재를 이유로 한 `lab:promote --write` 전면 금지는 해제됐지만, release·write·confirm·품질 게이트는 그대로 유지한다.

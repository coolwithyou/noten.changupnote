## 1. 문제 정의

lab 딥분석 + Kordoc(지원 양식 선분석)의 건당 처리 시간이 배치 기준 **평균 57분(최대 78.5분)**으로, 정례 배치·검수 파이프라인의 리드타임을 지배했다. 전 구간이 Max 구독 CLI(`claude -p`) 경유라 API 실지출은 0이지만, 전역 4슬롯과 사용량 창(window)이 유한 자원이다.

## 2. 병목 분해 — 검증된 사실 (08-11)

세 인수의 곱으로 분해되고, 각각 독립적으로 줄일 수 있음을 실측으로 확정했다 (계획 §2).

| 인수 | 실측 | 근거 |
|---|---|---|
| 호출당 지연 | 2.15분/호출 — 95%+가 **출력 토큰 생성 시간** (스폰+인증은 5초) | 40후보 opus 호출 91초 중 86초가 8.0k tok 생성. bs20→bs40 마이닝: 묶음 2배 = 요청당 출력 2배 = 시간 2배 |

### 반증된 가설 (채택하지 않은 것과 그 이유)

- **sonnet-5 교체 단독**: A/B에서 총시간 **+71% 역효과**. TPS는 높지만 출력이 41% 더 장황하고 낮은 confidence로 재판정 라운드를 추가 유발.
- **순수 effort 하향(low/medium)**: 속도 −30~40%지만 실제 입력 필드를 거절 conf 0.75~0.80으로 **조용히 놓침**(canary 264후보 중 low 4건·medium 3건 누락, 재판정에도 안 넘어감). 사용자에게 "빠른 작성에서 필드가 소리 없이 빠지는" 회귀라 기각.
- **프로세스 스폰 최적화**: 호출당 고정 오버헤드 3.3~5.0초로 지연의 5% 미만 — 레버 아님.

## 3. 채택된 변경

### T0 — 운용값 (코드 무변경)

배치 인플라이트 10→**4**(전역 슬롯과 일치), `ANALYSIS_LAB_TIMEOUT_MS=900000` 유지. 처리량은 불변(슬롯 상한)이지만 건당 완료가 ~3배 빨라져 검수 레인 리드타임이 준다.

### T1 — Kordoc 2단 effort (커밋 `9c80d18`)

- round 0 = `effort medium` + **거절 수락 임계 0.85** / 재판정 라운드 = 기본 effort + 임계 0.75(현행).
- 설계 논거: 순수 하향의 누락이 전부 거절 conf [0.75, 0.85) 경계 구간에 몰림 → 그 구간만 uncertain으로 떨어뜨려 기본 effort 재판정에서 회수.
- 실파이프라인 재canary 3공고: **입력 필드 손실 0건**, 판정 요청당 −35%, 재판정 부하 +9%(추정 +10~15% 안쪽).
- env `APPLICATION_ROUNDTRIP_EFFORT`로만 활성(코드 기본 null = 현행 보존). summary·run에 effort provenance 기록, 재사용(reuse) 계약 비교에 effort 포함.

### T4 — repair 상수화 해소 (커밋 `01f40ea` 계측 + `85c210d` 프롬프트 v14)

- 계측: `LabRun.primaryPasses`에 패스별 소요 시간·validator issue 코드를 additive 기록.
- 첫 수확(08-11 검증 배치): repair 주범 = **`unresolved_axis`(성공 9런 전원)**. 원인은 프롬프트가 ambiguous/input_missing을 가르치면서 validator는 무조건 실패시키는 **계약 충돌** — 종결 규율이 repair 지시문에만 있어 첫 패스가 헤징하고 전 런이 교정 패스(22축 풀 재생성)를 지불.
- 해소: repair의 축 종결 규율을 첫 패스 시스템 프롬프트(axis 섹션)로 승격, **프롬프트 v13→v14**. validator 계약 불변.
- canary(08-12): 178559 **무repair**(v11 이후 최초, 첫 패스 issue 0) · 125126 repair 1 유지. 표본 2로는 방향 확인까지 — 규모 판정이 이번 **CP2**.

### T4 CP2-b — 보류/교정 분리와 진단 보존 (08-13 정적 구현)

- `ef3a984`: 첫 패스 issue 정확한 총량과 path·axis·criterion snapshot을 bounded additive 계약으로 보존한다.
- `af65bf2`: `accept/repair/hold`를 공유 판정으로 분리하고 실제 `ambiguous`·`input_missing`은 전체 LLM 재생성 없이 held로 종결한다. held는 비-null sentinel이라 기존 검수·감사·승격 성공 소비처에 섞이지 않는다.
- `9e33f6a`: 운영 processor도 같은 판정을 쓰며 held run/job은 기존 `blocked` terminal 경로를 사용한다. 같은 축 validated criterion + `inspected_no_condition`만 결정론적으로 동기화하고 두 hold 상태와 반대 방향은 건드리지 않는다.
- `3c16cf3`: 프롬프트 v15/v21에서 실제 충돌·입력 누락을 정직한 hold로 보존하고 canonical 표현 불안만 `text_only`로 닫는다.
- `29f0491`: 최종 리뷰에서 발견한 테스트 공백을 보강해 held/input-blocked가 attempt 여유와 무관하게 terminal `blocked`가 되는 상태 결정을 순수 테스트로 고정한다.
- 이 단계는 fake transport·contract·quality/runtime 회귀만 수행했다. 실제 구독 모델 repair율과 의미 품질은 아직 재실측하지 않았다.
- 구현 후 Claude 적대적 상태 전이 리뷰는 **APPROVE, 미해결 P0/P1 0**이었다. 전체 diff Sonnet 리뷰는 로컬 CLI 경합으로 무응답이어서 중단했고, 핵심 `validator → processor → worker policy` seam을 축소 리뷰해 fail-closed 전이를 확인했다.

#### 125015 v15 live canary (08-13)

`0aa42679-26df-43bb-9c1a-edc3518fba9d`를 exact ID·concurrency 1로 재실행했다. 새 run `run-2026-08-12T213913.089Z-aa6354`는 첫 패스 issue를 `unresolved_axis:$.axis_assessments.size` 1건으로 정확히 보존하고 `held`로 종결했다. model repair는 0회였고 신규 issue도 없었다. structured 지원대상은 중소기업이지만 사업요약과 신청서식은 중소·중견기업을 명시하므로 실제 범위 충돌이며, size criterion을 임의로 만들지 않은 보류가 정확하다. Kordoc는 936후보 입력을 `complete`·adjudication `resolved`·잔여 unresolved 0으로 종결했다.

이 결과는 v13의 repair 2회 후 동일 size unresolved 실패를 **전체 재생성 없이 의미 보존 hold**로 바꾼 실제 repair 개선이다. held는 publishable 성공률 분자에 넣지 않는다. 단건 게이트는 GO이며, 다음은 층화·버전 코호트에서 publishable/held/repair/new-issue를 분리 측정한다.

`947d932`에서 기존 `cohort.json`을 덮어쓰지 않는 `cohort.<label>.json` 불변 스냅샷과 `--cohort-snapshot` 배치 소비 경로를 구현했다. 라벨 경로 조작을 차단하고 같은 라벨 덮어쓰기를 `EEXIST`로 막았으며, 기존 정본 60건을 신규 후보에서 제외한다. seed `20260813`, label `deep-v17-cp2b-pilot5`로 동결한 5건은 `bizinfo/medium`, `bizinfo/thick`, `kstartup/medium`, `kstartup/thick`, `kstartup/thin` 각 1건이고 통합공고·rich-criteria 쿼터도 1/1이다. 정본 `cohort.json` SHA-256은 전후 `2e6300b2…05c3b6a`로 같았다.

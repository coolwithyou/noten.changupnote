# 매칭 단독 실패13건 — 원천 결속 변경 진단

## 결론

이번13건은 모델 분석 실패가 아니라 착수 전 source revision 검사에서 차단됐다.
현재 재구성한 Lab 입력 텍스트와 첨부 provenance는 준비 당시와13/13 동일하다.
그중12건은 rawHash 하나의 변경으로 준비 당시 source revision과의 차이가 설명된다.
seq0은 rawHash 외 추가 source projection 변경이 있으므로 동일 원인으로 뭉뚱그리지 않는다.
이는 실행 결속 범위가 모델 소비 입력보다 넓다는 증거이지, 모든 변경이 무해한 메타데이터라는 증거는 아니다.

## 구조적 원인과 해석 한계

`deep-analysis/sourceRevision.ts`는 공고 source fields, rawHash, 첨부 projection을 함께 봉인한다.
`ingestion/grantRawHash.ts`는 전체 raw payload를 해시하며 관측 필드를 별도로 제거하지 않는다.
반면 `analysis-lab/input.ts`의 inputSha256은 선택·렌더된 모델 입력 텍스트의 해시다.
따라서 모델 입력이 그대로여도 전체 raw payload 변화가 source revision을 바꾸고 launch를 차단할 수 있다.
현재 guard는 선언된 계약대로 동작했으며, 이번 차단은 모델 성능이나 지원서 분석 실패로 집계할 문제가 아니다.

과거 inventory와 collectionEvents에는 과거 raw payload 전체가 없어 변경된 raw 필드까지는 증명하지 못했다.
특정 조회수·수집 시각 필드 탓이라고 단정하지 않는다. 특히 KStartup detail heal에는 fetched_at만 바뀌면
raw를 갱신하지 않는 기존 보호가 있으므로 그것만 원인으로 지목하면 안 된다.
입력 해시 동일은 실제 소비 텍스트 동일을 뜻하며, 입력에서 누락된 중요한 원천 조건이 없다는 보장은 아니다.
현재 관측을 실행 당시 전체 DB snapshot과 동일하다고 주장하지도 않는다.

## 권고하는 최소 후속 구현

1. 수집 provenance와 트랙별 material execution binding을 구분한다. 기존 raw revision은 감사용으로 보존한다.
2. matching-only의 입력·첨부·신청 상태/기간·핵심 자격조건 결속을 명시한다. 모델 텍스트 동일만으로 원천 검사를 생략하지 않는다.
3. 관측값만 변경된 사례와 실제 자격조건/첨부/상태가 바뀐 사례를 대조하는 국소 회귀 검증을 둔다.
4. 과거 receipt/manifest를 수정하지 않는다. seq0의 불명확한 추가 변경은 보류하며 성공6건을 재실행하지 않는다.

새 큐·자동 재분석 엔진·광범위한 예외 목록은 이번 문제 해결에 필요하지 않다.
구현한다면 먼저 이 경계를 작게 수정하고, 그 이후 필요한 실패 대상에 한해 현행 결속과 승인 범위를 확인한다.
이번 진단은 코드 수정이나 새 live 실행 승인이 아니다. 옛 manifest의 단순 retry로 변경된 결속을 우회하지 않는다.

## 수행·미수행

DB SELECT/R2 GET, 로컬 진단 산출물 및 문서 기록만 수행했다. 모델 호출·DB/R2 쓰기·lease 변경·재봉인·재실행·승격·배포는0이다.
실제 source builder 재현과 시작/종료 결속 비교를 검증 증거로 사용했다.
제품 코드를 바꾸지 않아 전체 테스트/typecheck를 반복하지 않았다. 과거 raw 필드 delta와 seq0 추가 변경 원인은 미확정으로 남는다.

## 후속 코드 수정 — 사용자 진행 요청 이후

진단 이후 사용자 요청으로 구현(sol-xhigh)을 진행했다. 신규 matching-only 준비물에만
`analysis-matching-material-source-binding-v1`을 봉인한다. 기존 공고 필드·첨부 projection에서 rawHash만
제외한 material revision을 사용하고, 원래 sourceRevision과 sourceRawSha256은 provenance로 보존한다.
입력 텍스트·첨부 provenance 변경은 기존 모델 착수 전 admission이 계속 거부한다.
현재 모집 상태·신청기간 검사도 유지한다. 과거 inventory에는 새 의미를 소급하지 않으며,
application-only/통합 실행은 새 binding이 있더라도 기존 sourceRevision으로 검사한다.

이는 raw 변경이 메타데이터뿐임을 증명하는 기능이 아니라, 매칭 실행의 유효성 기준을 명시적으로 좁힌 것이다.
진단에서 원인이 미확정인 seq0을 옛 승인으로 통과시키거나 실패13건을 자동 재실행하지 않았다.
새 큐·DB 스키마·추가 검수 단계·운영 쓰기는 없다. 과거 manifest/receipt 및 성공6건은 그대로 보존했다.

검증(Node v24.20.0, pnpm10.30.1): `pnpm lab:launch:test` PASS(current inventory29개 포함 관련 집계),
`pnpm --dir apps/web typecheck` PASS, `git diff --check` PASS.
공유 계약 변경에 필요한 launch gate와 웹 타입 검사만 실행했으며 전체 저장소 suite·live 모델 평가는 미실행이다.
따라서 실제 실패 대상의 재실행 성공·품질·서비스 공급을 아직 주장하지 않는다. 코드 변경은6파일이며 커밋·push·배포하지 않았다.

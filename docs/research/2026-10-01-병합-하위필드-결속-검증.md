# 병합 하위 필드 coverage와 실제 native 쓰기 검증

2026-10-01 authoring-first 체크아웃에서 모델 호출·운영 데이터 쓰기 없이 확인했다.

## 문제와 수정

`detectUnsupportedNativeInputGaps`는 고정 분류·집계 라벨 뒤의 logical grid 빈 칸을 모두 독립 입력으로 셌다. 또한 명시적 `table_cell` target만 인정해 이미 accepted인 Kordoc/RHWP 라벨의 오른쪽 native 값 셀을 누락했다.

일반 수정은 유효한 rowSpan/colSpan 원점과 빈 covered dummy를 구분한다. accepted 하위 필드가 현재 원문 라벨 좌표, 원문 라벨 전체, 동명 occurrence, 빈 원래 값, 정확한 오른쪽 셀을 모두 만족할 때만 기존 RHWP 입력 계약으로 인정한다. 새 필드를 만들거나 분류 라벨을 입력으로 승격하지 않는다. malformed covered 영역, 라벨·좌표·값·occurrence 불일치, 실제 추가 미결속 값 셀은 계속 경고한다. 고정 집계의 독립 다열 입력 경고도 유지한다.

## 실제 원문

- launch receipt: `c634172a8731ece151dc44544974ad4590bb0d8eab110749359d01fe4be40f19`
- 원문 SHA256: `ceb2c53a1a4ff825e3661deecd5a7533d23a4d55f2e82126a240b6de3f06e150`
- application run: `roundtrip-2026-10-01T041138.341Z-800a5b`
- 신청서 block 3, row 15: `목표 고객` col 0 span 2×2 / `고객군` col 2 span 1×2 / 빈 값 col 4 span 1×2
- 경고의 col 3과 col 5는 covered dummy였다. col 4는 기존 accepted `고객군` 필드의 값 셀이었다.

R2에서 원문을 GET으로 읽고 위 SHA를 확인했다. Kordoc parse, 기존 `loadDocumentAgentCore`와 `resolveStudioFieldBindings`로 실제 원문을 열었다. 고객군은 `unique`, section 0 / parentPara 4 / controlIndex 0 / cellIndex 34 / paragraph 0에 결속됐다. native `insertTextInCell`로 합성 문안을 입력하고 `exportHwpx`, 새 `HwpDocument` 및 Kordoc parse로 재열기했다.

재열기에서도 같은 unique binding과 입력 문자열이 유지됐다. 무편집 export 기준과 비교하면 전체 표의 변경은 block 3 / row 15 / col 4 한 셀뿐이며, label과 covered dummy를 포함한 나머지 셀·span은 동일했다. 원본→무편집 export에는 별도 block 1 / row 10 / col 7의 일반 공백이 U+2007로 직렬화되는 변화가 있다. 이 기존 serializer 변화를 입력 변경과 구분해서 JSON에 모두 기록했다. 원본과 결과가 byte-for-byte 같다는 주장은 하지 않는다.

## 범위와 계약

불변 `analysis.json`과 receipt는 수정하지 않았다. 저장된 89개 후보 중 신청서 accepted 66개를 복제한 로컬 coverage 검증은 accepted/anchorReady 66, unresolved 0을 유지하면서 structuralWarning 1→0, complete를 반환한다. 이 계산은 새 모델 분석·release admission을 대신하지 않는다. 공고문 등 다른 문서의 역할 판정도 바꾸지 않는다.

`APPLICATION_ROUNDTRIP_VERSION`은 v22로 유지한다. 필드·target·쓰기 의미와 후보 집합을 바꾸지 않고, 이미 정의된 병합 RHWP 계약을 coverage에서 정확히 집계하는 구현 수정이다. 현재 package runtime SHA는 contracts/core dist를 대상으로 하므로 이 서버 구현 수정만으로 package hash가 바뀐다고 보지 않는다. 새 실행은 이 수정이 포함된 clean commit과 source provenance를 봉인한 새 manifest로 준비한다. 기존 receipt를 최신 분석 결과로 덮어쓰거나 승격할 수 없다.

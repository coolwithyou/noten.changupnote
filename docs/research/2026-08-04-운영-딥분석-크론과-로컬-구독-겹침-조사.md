# 운영 딥분석 크론 현황과 로컬 구독 트랙 겹침 조사

## 1. 결론 요약

1. **운영의 유료 LLM 딥분석은 지금 자동으로 돌지 않는다.** 메인 워커(Cloud Run Job, 5분 주기)는 `DEEP_ANALYSIS_WORKER_MODE=observe_only` + `DEEP_ANALYSIS_CLAIM_SCOPE=unconfigured` 2단 fail-closed로 하트비트만 남기고 종료한다(실측: 최근 7일 하트비트 1,570건 전부 idle/observe_only, 최근 24h 분석 런 0건, 마지막 분석 2026-07-31 리빌드 15건).
2. **주변 자동화는 살아 있다**: ① input-preparation 워커(10분 주기 — 입력 봉인 + 잡 enqueue, **pending 1,013건 누적 중**) ② serving monitor(30분 — 관측 receipt만) ③ Vercel 수집 크론(kstartup/bizinfo 하루 2회 — 수집·기본추출·publish).
3. **승격(criteria 반영)은 전 경로 사람 게이트다**: deep release → 분리 승인(`lab:release --approve`) → `lab:promote --write --confirm` 3단 수동. 운영 워커는 grant_criteria를 아예 건드리지 않는다(processor에 참조 0건). servingState 자동 변경 경로도 없음(staged 실측 0).
4. **로컬 구독 트랙과 운영 딥분석은 현재 구조적으로 겹치지 않는다**: 로컬 lab은 DB에 런을 안 쓰고(spike-out 파일), 운영 워커 사슬은 `ANALYSIS_LAB_TRANSPORT`를 아예 안 읽는다(격리 rg로 커밋마다 증명). DB 쓰기 접점은 오직 `lab:promote --write` 순간뿐.
5. **⚠️ 진짜 충돌은 "로컬 vs 운영 분석"이 아니라 "승격 결과 vs 수집 크론"이다.** `normalizedGrantPublisher.ts:233`이 재발행 시 해당 공고 criteria를 무조건 전삭제→파서 결과로 재삽입한다(stableKey·승격 원장 무인지). 승격된 criteria는 revision 지문에 포함되므로 승격 자체가 `changed` 재분류를 유발할 개연성이 높아, **승격분은 다음 수집 재발행 창(하루 2회)에서 말소되는 구조**다. 말소 시 자가신고 질문은 FK SET NULL로 "active인데 서빙에서 사라지는 유령"이 되고, 승격 원장은 applied로 남아 DB와 모순되며, 이후 롤백은 rollback_drift로 거부된다. lab 승격분은 상시 서빙 모니터의 감시 필터(`deepAnalysisRunId IS NOT NULL`) 밖이라 자동 탐지도 안 된다.

## 2. 운영 딥분석 발동 조건 (전수)

- **스케줄**: Vercel cron에 딥분석 없음(9개 전부 수집·크레딧). 실체는 GCP Cloud Run Job 3종 + Cloud Scheduler(main 5분 / input-prep 10분 / serving-monitor 30분), 프로젝트 changupnote-com.
- **활성화 게이트(전부 통과해야 LLM 호출)**: `DEEP_ANALYSIS_EXECUTE=1`(이미지에 하드코딩) + `DEEP_ANALYSIS_WORKER_MODE=active`(현재 observe_only — Cloud Run env) + `DEEP_ANALYSIS_CLAIM_SCOPE=bounded|all`(현재 unconfigured, bounded는 cohort sha256 화이트리스트 최대 100건). 모델 실험 튜플은 별도 확인 문자열 강제. `.env`류에 DEEP_ANALYSIS_* 키가 없어 로컬 오발동도 fail-closed.
- **대상 선정(켜졌을 때)**: KST 기준 활성 공고 566건(실측) 중 source 관측 워터마크(`GREATEST(updated_at, raw, 첨부, surface)` > 같은 policy version의 마지막 관측)가 갱신된 것만, 마감 임박 우선, 인보케이션당 상한. 비용은 일일/공고당 캡 + 모델 단가 fail-closed.
- **켜는 순간의 부하**: pending 1,013건이 claim 대상이 된다(707/31 리빌드 잔여 580 + input-prep 유입 433). 활성화 전 큐 정리 필요.

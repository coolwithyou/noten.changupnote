# 대량 분석 효율과 매칭 정합성 리뷰

기준: `8559563`의 코드, 2026-09-07 06:01~06:12 KST 서비스 DB 읽기,
기존 `deep-v34`와 후속 보정의 불변 로컬 산출물. 모델 호출·lease 변경·승격·배포 없음.
코드와 DB를 연결해 검사한 결과이며, 배포된 웹의 SHA 및 로그인한 실제 사용자 화면까지 검증한 것은 아니다.

## 결론

**분석 결과를 매칭에 전달하는 경로는 연결되어 있으나, 의미 보존과 사용자 확인 경로까지 정확히 맞지는 않는다.**
신규 100건을 더 분석하기 전에 변환기의 조건 종류 보존, 필수 서술형 조건의 확인 방법,
매칭 준비도와 신청서 준비도의 분리를 개선하는 편이 효과가 크다.

현재 제품 방향은 “사업자 정보를 완성 → 조건별 판단을 확인 → 공고를 선택 → 작성”이다.
따라서 목표 지표는 분석 완료 건수보다 **잘못된 확정 판정 없이 사용자 입력으로 해소되는 조건의 비율**과
**검수 결과가 유효기간 안에 매칭 후보로 공급되는 비율**이어야 한다.

## 우선순위별 발견 사항

### P1. 변환기가 우대·필수 조건을 배제 조건으로 바꾼다

`packages/core/src/bizinfo/llm-criteria.ts:266`의 예약 축 강등은
`premises`, `export_performance` 등을 `other/text_only`로 바꾸면서 `kind: "exclusion"`을 고정한다.
표현을 서술형으로 낮추는 것과 필수·우대·배제라는 의미를 바꾸는 것은 다른 일이다.

원차수 publishable 80건의 조건을 **현행 변환기로만 오프라인 재투영**한 결과:

- 입력 573개 → 출력 555개. 종류 변경 35개: required→exclusion 28개, preferred→exclusion 7개.
- 실제 “화재에 취약한 건물 우선 지원” 조건은 `premises/preferred`에서 `other/exclusion`으로 바뀐다.
- 이 단일 조건을 격리해 matcher를 실행하면 원래 `eligible`이던 결과가 `conditional`로 변한다.
  우대 확인의 불확실성이 필수 자격 판정을 막는 불확실성으로 이동하기 때문이다.
- 강등은 `needs_review=true`로 남지만, 그것만으로 잘못 변경된 kind를 복구하지는 않는다.
  `guardAnalysisLaunchPromotionPlan`도 conversion error/drop은 차단하지만 kind 변경을 검사하지 않는다.

이 80건은 독립 검수 PASS/서비스 승격을 가장한 집합이 아니다. 위 7개가 운영에 이미 반영됐다는 주장도 아니다.
현행 변환 인터페이스의 의미 변경을 실제 분석 산출물로 재현한 것이다.
기존 테스트는 예약 축 강등을 확인하지만 우대·필수의 종류 보존을 충분히 검증하지 않는다.

**개선:** 강등 시 kind·근거·원래 축을 보존하고, 종류 변경은 명시적인 원문 기반 교정으로만 허용한다.
추출→변환→matcher까지 연결한 회귀 사례에 필수/우대/배제 각각을 포함한다.
과거 승격 자료는 별도 영향 조사 없이 일괄 재작성하지 않는다.

### P1. 필수 서술형 조건은 사용자가 정보를 채워도 해소할 경로가 없다

`packages/core/src/matching/match.ts:215`는 `text_only`를 회사 정보 평가보다 먼저 `unknown`으로 반환한다.
`:334`의 확인 답변 적용과 `analysis-lab/promote.ts:460`의 질문 발행은 exclusion만 대상으로 한다.
DB의 유효 확인 질문 97개도 모두 exclusion 조건에 연결되어 있었다.

서비스 90건 중 76건에 필수 서술형 조건이 있다. 예를 들어 “고양시 소재, 지사·연구소 포함”은
현재 본사 지역 코드만으로 판단할 수 없어 서술형으로 보존하는 것이 맞다.
그러나 사업자 프로필을 아무리 완성해도 해당 조건을 확인했다는 답변을 연결할 수 없으면 여정이 멈춘다.
required 조건에 `disqualified=false` 확인 답변을 넣어도 무시되어 conditional이 유지되는 것을 재현했다.

**개선:** 공통 회사 사실과 공고별 확인을 구분한다. 반복되는 시군구·지사/공장·기준일 조건은
정형 계약을 확장하고, 정형화하기 어려운 필수 조건에는 근거를 보여 주는 공고별 확인 질문을 제공한다.
답변 의미는 `충족/미충족/확인불가`처럼 조건 종류와 분리하고, 사용자 확인이라는 출처를 유지한다.
공식 원천의 확정 불일치나 정정 검토 상태를 자가신고로 덮어쓰면 안 된다.
모든 서술형을 자동 통과시키거나, 모든 복합식을 한 번에 새 규칙 언어로 바꾸는 접근은 권하지 않는다.

### P1. 신청서 준비 실패가 매칭 공급까지 막는다

`analysis-lab/launch-batch-production.ts:113`은 primary가 publishable이어도
신청서 필드 분석이 held이면 target 전체를 held로 바꾼다.
`analysis-launch-promotion.ts:133`은 publishable target만 release 후보로 받는다.

deep-v34의 held 13건 모두 `primaryValidationOutcome=publishable`이었고,
`field_analysis_held` 때문에 전체 보류되었다. 원문 불확실성을 억지로 통과시키자는 의미가 아니다.
매칭 조건 검수와 신청서 편집 준비는 서로 다른 제품 역량이다.

**개선:** terminal receipt에 matching readiness와 authoring readiness를 독립적으로 기록하고,
검수된 조건은 매칭 후보로 공급하되 작성 화면에는 준비 상태를 별도 표시한다.
기존 영수증을 수정하지 말고 호환 reader/새 계약으로 분리하며, 독립 검수·출처·승격 승인은 유지한다.
신청서 분석은 재사용 가능한 원본 SHA 기준 자산으로 운영한다.

### P1. primary 통과가 현행 매칭 계약 통과를 보장하지 않는다

동일 80건의 오프라인 변환에서 1건은 전체 18개 조건이 변환 실패했다.
`PBLN_000000000126143`, `run-2026-09-05T010404.161Z-6649e1`이다.
예약 축을 other/exclusion으로 합치는 과정에서 같은 source span의 중복 계약 오류가 발생했다.
release의 conversion error/drop 차단은 이를 막으므로 잘못된 결과가 무조건 발행되는 것은 아니다.
문제는 primary 성공 뒤에야 소비자 계약 불일치를 발견한다는 점이다.

독립 검수 역시 필요하다. 원 deep-v34의 publishable 80건 중 두 검수 aggregate에서
각각 22/36건, 20/44건이 결함 영향을 받았다. 이 수치는 후속 보정 전 원차수 결과다.
후속 20건 보정 grant도 실행은 20건 publishable로 끝났지만, 6/11/3건에 대한 재검수에서
각각 4/5/1건이 다시 결함 영향을 받았다. 따라서 실행 성공률을 정확도로 보고하면 안 된다.

**개선:** 주된 검증 seam을 “실제 매칭용 변환 결과”로 잡는다.
kind·연산자·단위·경계값·예외/OR 경로·근거·질문 연결을 변환 전후 비교하고,
실제 matcher에 서로 반대인 회사 사례를 넣어 판단 차이를 검사한다.
독립 검수에서 나온 “3년 미만 vs 36개월 이하”, “시군구 vs 시도”, “현재 제재 vs 과거 위반”을
회귀 정답셋으로 축적한다. 지금의 방어적 unknown은 유지하되 그 이유와 사용자 해소 방법까지 검증한다.

### P2. 같은 승격 manifest를 공고마다 가져오고 검증한다

`repositories/drizzle.ts:248`은 applied item마다 전체 release manifest를 조인해 가져온다.
`promotionServing.ts`는 각 item에서 manifest를 파싱·검증하고,
`promotionReleaseContract.ts:626`은 plan/manifest 전체 해시를 다시 계산한다.
이후 reviewed metadata hydration에서도 유사한 조회가 반복된다.

현재 120개 applied item / 9개 release에서 첫 조회의 반복 manifest JSON은 **40,573,725 bytes**다.
release별 한 번만 읽으면 **1,893,100 bytes**다. 첫 조회의 이 부분만 약 95.3% 줄일 여지가 있다.
90건 전체 조회의 로컬→DB 실측은 두 번 각각 5,978ms, 6,095ms였다.
이는 전체 조회 시간이며 네트워크·다른 쿼리·검증 비용을 분리한 프로파일이나 운영 p95가 아니다.
2분 프로세스 캐시가 있지만 cold miss 비용과 다른 프로세스의 중복은 남는다.

**개선:** release별 manifest 조회/해시 검증을 1회 수행하고 item별 plan/run 결속만 비교한다.
요청 내부에서 검증 결과를 재사용한 뒤, 필요한 경우 manifest SHA 기반 bounded cache를 둔다.
release 상태·rollback·현재 item 결속의 재확인을 생략해서는 안 된다.
현재 증거는 인덱스 부족보다 중복 전송/중복 검증을 먼저 개선해야 함을 가리킨다.

### P2. 병목 지표가 실행 건수에 머물면 대량 분석을 잘못 최적화한다

deep-v34 원차수의 두 실행 영수증 소요 합은 215.66분이다. 그 사이 중단 시간과 후속 검수/보정은 제외했다.
고유 100건 기준 약 27.8건/시간, primary/field 결합 publishable 80건 기준 약 22.3건/시간이지만,
이는 검수 PASS나 서비스 반영 처리량이 아니다.

해시를 대조한 최신 non-skipped run 99개에서 중앙값 227.8초, p95 537.6초,
primary repair를 거친 run 24개, 모델 교정 30회·결정적 교정 4회였다.
primary pass 시간 합은 412.58분, run wall time 합은 421.84분이었다.
primary와 신청서 분석은 이미 병렬이고 CLI는 공고별 공정 큐를 쓰므로,
이 두 합의 차이를 “신청서 전체 비용”으로 읽으면 안 된다. 큐 대기와 중첩된 실행이 포함된다.
최신 20건 보정 grant에서는 네 실행 중 두 번이 lease/DB 관련 systemic failure로 중단됐다.
근본 네트워크 원인이나 안전한 동시성 상향 폭까지 이번 관측으로 확정할 수는 없다.

한편 마지막 실제 승격은 2026-09-02 00:11 KST이고, deep-v31은 승인 뒤 적용 전이다.
공급량 개선에는 신규 모델 호출뿐 아니라 기존 검수/승격 대기 자산의 현행 유효성 확인이 중요하다.

**개선:** 다음 지표를 같은 grant/source revision/receipt 기준으로 연결한다.

- 모델 성공 → 변환 무손실 → 독립 검수 PASS → 승격 → 실제 노출.
- unique 공고당 총 모델 호출·교정 호출·queue wait·실행 시간·보정 후 재결함률.
- lease 중단 사유와 낭비된 작업, 신청서 분석 재사용률, 마감 전 공급률.

신규 시리즈 선정은 현재 25건뿐이므로, 100건을 유지하려면 재고 확보가 선행된다.
과거 대상을 임의 재편입하거나 승인 범위를 자동 축소하지 않는다.

## 권장 실행 순서

1. **변환 의미 보존부터 수정:** required/preferred/exclusion 보존 + 원문 사례 회귀 테스트.
2. **필수 조건 확인 루프 연결:** 공통 회사 정보와 공고별 확인을 분리하고 matcher까지 왕복 검증.
3. **매칭/작성 준비도 분리:** 기존 검수·provenance를 유지한 독립 소비 계약.
4. **승격 조회 중복 제거:** 변경 전후 전송량·cold latency·rollback 반영을 비교.
5. **기존 자산의 공급 회복:** 승인된 47건과 후속 검수 PASS 자산의 현행 입력/첨부/기간을 읽기 전용 재대조.
   실제 서비스 쓰기는 해당 exact 범위의 승인과 gate에 따라 진행한다.
6. **그 다음 신규 대량 분석:** 재고/동시성 선택은 별도 확정하고, 처리량과 제품 공급량을 함께 관측.

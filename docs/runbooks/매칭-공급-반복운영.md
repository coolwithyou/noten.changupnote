# 매칭 공급 반복 운영

작성: 2026-09-24 KST. 적용 범위: K-Startup·BizInfo의 현재 지원 가능 공고. 실행 이력과 현재 남은 검증은 [통합 개선 계획](../plans/2026-09-24-매칭공급-근본원인-재평가-통합개선계획.md)을 따른다.

## 운영 경계

- 실행자는 깨끗한 단일 checkout과 그 checkout의 `spike-out` 불변 산출물을 계속 사용한다. 다른 checkout의 manifest·grant·receipt를 이름만 맞춰 섞지 않는다. 이 문서 작성 시 실행자는 Codex 통합 세션이며, 상시 운영 담당자와 자동 실행 시각은 아직 지정되지 않았다.
- 각 수집원 수집이 끝난 뒤 하루 한 번 KST 운영 창에서 두 수집원을 같은 `since`·`until`로 조회하는 주기를 제안한다. 실제 스케줄러가 설정된 상태는 아니다. 수집 시각·담당자·시작/종료·다음 작업 수·최장 대기 건을 주기별 기록에 남긴다.
- 웹 요청에서 모델을 실행하지 않는다. 로컬 분석은 Claude CLI 구독, 독립 검수는 Codex 구독, 운영 worker는 `observe_only`를 유지한다. 신규 exact manifest의 모델 실행, release 승인, 서비스 승격은 각 단계의 현행 권한과 원장 역할 분리를 따른다.
- 분석의 `publishable`은 매칭 분석 결과이며 신청서 분석 완료를 뜻하지 않는다. `matching_only`에는 신청서 실행을 포함하지 않는다. 회사별 적격 여부는 저장된 회사 사실과 criterion을 비교해 판정한다.

## 수집 직후 발견과 선택

```bash
git status --short
pnpm verify:db-migrations
pnpm report:grant-supply -- --source=kstartup --since=<UTC-시작> --until=<UTC-끝>
pnpm report:grant-supply -- --source=bizinfo --since=<UTC-시작> --until=<UTC-끝>
pnpm report:grant-supply -- --grant-id=<선택한-UUID>
```

보고서는 DB `REPEATABLE READ READ ONLY`이다. 기간 조회가 많으면 결과의 `nextCursor`를 확인하고 같은 기간에 `--after-source-id=<값>`을 붙여 다음 페이지를 읽는다. `inactive`는 공급 수에서 제외하고, `condition_review`·`source_change_review`·`question_preparation`은 각각 관리자 검토·원천 재확인·질문 준비 작업으로 남긴다. `reuse_ready`는 현재 불변 분석·검수 결속을 재확인한 뒤 발행 대상으로 선정한다. `condition_analysis`는 현재 공개·접수·대표·원문/첨부 결속과 전체 과거 이력 제외를 확인한 exact 공고만 선정한다. 오류나 drift가 있는 대상을 다른 공고로 임의 대체하지 않는다.

## 신규 매칭 분석과 독립 검수

```bash
pnpm lab:launch:prepare-current -- --grant-ids=<exact-UUID-CSV> --analysis-mode=matching_only --concurrency=2
pnpm lab:launch:grant -- --manifest=<출력-manifest-SHA256> --approved-by=<승인자>
ANALYSIS_LAB_TRANSPORT=claude-cli pnpm lab:launch -- --grant=<출력-grant-SHA256>
pnpm lab:independent-review -- --launch-receipt=<terminal-receipt-SHA256>
pnpm lab:independent-review:codex -- --manifest=<출력-manifest-경로>
pnpm lab:independent-review -- --aggregate-manifest=<같은-manifest-경로>
```

준비 단계는 모델·서비스 쓰기 없이 exact input/attachment/source와 실행 계약을 봉인한다. `lab:launch:grant` 전에 대상·SHA·모드·동시성·구독 인증·DB runtime paused/lease 상태를 확인한다. 실행 실패는 terminal receipt에서 대상별 `held`·`failed`와 공유 실행 중단을 구분한다. 같은 grant의 오류만 `lab:launch -- --grant=<SHA256> --retry-errors`로 재시도하며, 근거 인용 불일치·`repair_limit`·drift는 원문 조사 없이 재호출하지 않는다. 독립 검수 aggregate의 `heldTargets=0`만으로 품질 통과를 선언하지 않고, 각 대상의 실제 consensus defect와 release inspect를 확인한다.

독립 검수 결함을 고쳐야 할 때는 `pnpm lab:independent-review:repair:prepare -- --aggregate=<aggregate.json> --original-sequences=<n,...> --concurrency=1`로 원본 대상만 봉인한다. 출력 manifest가 `matching_only`이고 신청서 실행이 없으며 원본 source/input/attachment가 그대로인지 확인한 뒤 현행 launch grant와 실행 경로를 따른다. 근거가 없는 인용은 이전 결과에서 상속하지 않는다.

## 발행과 서비스 확인

`pnpm lab:release -- --inspect --launch-receipts=<terminal-receipt-SHA256-CSV> --grantIds=<exact-UUID-CSV>`로 발행 가능 대상만 확인한다. 같은 launch의 검수 manifest가 여럿이면 `--review-manifest=<exact-SHA256>`을 지정한다. 그 다음 [딥 공고 분석 운영 승격 Runbook](deep-analysis-promotion.md)의 `prepare → aggregate GO → shadow PASS → dry-run PASS → 다른 actor approve → canary write/verify → full write/verify`를 그대로 수행한다. 불변 `dry-run.json`이 이미 PASS로 존재하면 재실행으로 덮지 않고 기존 SHA와 결속을 검증한다. 승격 후 `active/applied` 원장과 실제 serving reader의 검증 근거, 회사 후보 목록 포함을 확인한다. `condition_review`가 남아도 발행 실패로 바꾸거나 `reuse_ready`로 강제하지 않는다.

공개 경로 200, 비인증 API 401, 인증 회사 후보 카드·답변 저장·수정·철회는 서로 다른 검증이다. 실제 계정이 없는 주기에는 인증 사용자 인수를 미실행으로 기록한다. Popbill 유료 조회를 smoke로 실행하지 않는다. 공개 재조회 공통 lease가 남은 경우 SDK 요청 종료, 캐시와 과금 기록을 확인한 뒤 정확한 행만 운영자가 수동 복구한다.

## 주기 기록과 종료 판정

| 항목 | 매 주기 기록 |
| --- | --- |
| 범위 | KST 실행 시각, UTC `since`·`until`, 수집원별 수집 완료 시각, 실행자, checkout SHA |
| 발견 | 신규·중복·inactive·reuse/review/analysis/held 수, 가장 오래 기다린 작업과 이유 |
| 실행 | exact manifest/grant/receipt/review/release SHA, 모델 요청 수, 대상별 성공·보류·실패 |
| 발행 | canary/full verify 결과, 실제 serving 건수, 비대상 변경 여부 |
| 시간 | 발견·입력 준비·모델 primary/repair·검수·발행 각 wall 시간과 end-to-end 지연 |
| 복구 | 새 프로세스에서 같은 불변 산출물과 DB 상태를 다시 읽은 결과, 오류·재시도·잔존 lease |

두 수집원에서 **각각 두 번 이상의 실제 공급 주기**와 프로세스 재시작 후 이어받기를 확인해야 반복 운영을 완료로 표시한다. 그 뒤 신규 50건·최소 7일 관찰에서 공급 지연 p95, 실제 발행 수, 오판·관리자 보류, backlog 최장 대기 시간을 집계해 확대 여부를 결정한다. 아직 이 반복·관찰·인증 사용자 인수는 완료 증거가 없다.

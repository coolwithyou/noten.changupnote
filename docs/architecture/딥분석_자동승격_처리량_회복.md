# 딥분석 자동승격 처리량 회복 설계

작성일: 2026-07-29
상태: R1 readiness 분리 구현 중
기준 계획: `docs/plans/2026-07-24-deep-analysis-production-rollout.md`

## 목적

창업노트의 핵심 사용자 흐름은 사업자등록번호로 만든 회사 프로필과, 공고 본문·첨부
HWP를 읽은 딥분석 criterion을 matcher에서 대조하는 것이다. 현재 랜딩은 승격된
딥분석 공고만 사용하도록 강제됐지만, 신규 공고가 자동승격까지 도달하는 처리량은
사실상 0이다.

이 문서는 반복 실패를 개별 prompt 결함으로만 보지 않고 다음 질문을 분리한다.

1. 공고와 첨부를 충분히 읽고 22축을 분석했는가?
2. 독립 AI 검수가 match-impacting 오류를 찾았는가?
3. 분석 결과를 현재 matcher가 의미 손실 없이 표현할 수 있는가?
4. 자동승격할 수 있는가?
5. 자동승격할 수 없다면 반복 실패가 아니라 사람 검수라는 정상 종착점으로
   이동했는가?

## 진단 결론

개선은 실제지만, 현재 최종 처리량을 막는 지배적 원인은 구조적이다.

`CQ2`부터 `AQ8`까지 계획 문서로 재구성 가능한 구간에는 exact 2건 실행이 8회,
실행 슬롯이 16건, 고유 공고가 6건 있다. primary validator는 약 13/16까지
통과했지만 fresh 실행에서 명시적 `concur`까지 간 슬롯은 2/16이고 신규
자동승격은 0/16이다.

반복한 공고쌍에서는 계약 오류와 알려진 누락이 줄었다.

- audit `raw_contract_invalid` 76건을 계약 단순화 뒤 0건으로 줄였다.
- AQ3는 primary와 audit validation을 각각 2/2 통과했다.
- AQ5는 primary와 matcher 소비를 2/2 통과했다.
- AQ6는 검증된 IP 누락을 다음 primary에 넣어 accepted blocker를 1→0으로
  교정했다.

그러나 새 공고쌍으로 바꾸면 primary 0/2 또는 1/2로 다시 떨어졌고, 통과한 AQ8
Bizinfo도 `전남 6개월 영위 또는 영광군 이전 확약`이라는 대안 조건을 현재
matcher가 무손실 표현하지 못해 promotion에서 차단됐다.

따라서 같은 구조에서 2건 유료 재실행과 공고별 prompt 보정을 반복하는 것은
중단한다. 다음 유료 실행은 이 문서의 R1~R3 구조 체크포인트를 오프라인 artifact로
검증한 뒤에만 연다.

## 구조적 원인

### 1. 전체 공고가 하나의 직렬 성공 조건이다

현재 자동승격은 다음 조건 중 하나만 어긋나도 공고 전체를 차단한다.

- primary response contract
- 정확히 22개 axis
- 모든 criterion의 canonical value
- 모든 exact evidence span
- 독립 audit 전체 합의
- adjudication과 deterministic finding 검증
- promotion adapter의 무손실 변환
- 모든 resolution `confirmed_correct`

조건 수가 많은 공고에서 두 모델의 전체 출력이 동시에 완벽해야 하므로 criterion
단위 품질이 높아져도 공고 단위 통과율은 낮다. 안전장치는 정상이나, 하나의
`PASS/FAIL`만으로 운영하면 어느 단계가 개선됐고 어디서 사람 판단이 필요한지
구분할 수 없다.

### 2. 22축 분석 계약과 matcher 표현 계약이 다르다

`premises`, `export_performance`는 22축 taxonomy에는 있지만 회사 프로필과
evaluator에서는 예약축이다. 발행 adapter는 이를 `other/text_only +
needs_review`로 강등하며 promotion은 강등 한 건만 있어도 전체를 차단한다.

또한 `A 또는 B`, 예외, 미래 이전 확약, 선정 후 의무처럼 단일 criterion 배열로
무손실 표현하기 어려운 관계가 있다. 이 경우 LLM의 문서 이해가 맞아도 matcher
결과가 false ineligible이 될 수 있다.

### 3. 독립 audit의 책임이 너무 넓다

primary가 전체 22축 typed set을 만들고, audit도 사실상 별도의 전체 조건 집합을
다시 생성한다. 두 번째 모델의 span, enum, typed value 하나가 어긋나도 전체
합의가 깨진다.

독립성은 유지하되 audit의 책임은 다음 match-impacting 검증으로 좁힌다.

- required·exclusion 조건의 누락
- 예외 조항 누락
- AND/OR 관계와 적용 시점 손실
- matcher eligibility를 뒤집는 잘못된 criterion

평가표 preferred 행의 전수 재추출이나 조건이 없는 축 상태 생성은 primary 및
결정론 서버 계약이 담당한다.

### 4. 반복쌍 교정이 새 공고로 일반화되지 않는다

같은 두 공고에서는 보존 artifact를 이용해 2/2에 도달했지만, 새 공고쌍에서는 다른
typed shape, span, 축 관계 또는 matcher 표현 문제가 나타났다. 이는 개별 fixture
회귀가 필요 없다는 뜻이 아니라, fixture 회귀만으로 production 일반화를 증명할 수
없다는 뜻이다.

## 목표 상태

딥분석 공고 한 건은 아래 상태를 독립적으로 가진다.

| 상태 | 의미 | 차단 시 종착점 |
| --- | --- | --- |
| `analysis_complete` | sealed 입력에서 primary 계약·22축·근거 검증 완료 | 재처리 또는 입력 예외 |
| `audit_complete` | 독립 audit가 match-impacting set에 합의 | 사람 검수 |
| `matcher_representable` | 현재 matcher에 의미 손실 없이 투영 가능 | 사람 검수 |
| `auto_promotable` | 위 세 상태와 promotion 불변조건 통과 | 자동승격 |
| `human_review_required` | 분석 실패가 아니라 자동화 한계가 명시된 정상 route | Ops 사람 검수 |

`human_review_required`는 `auto_promotable`의 반대 terminal route다. 사람 검수로
보내더라도 source/input/run/audit SHA와 최초 blocker를 보존해야 하며, generic
`failed`로 되돌리지 않는다.

## R1 — promotion readiness seam

하나의 순수 인터페이스가 분석 완료 이후 상태를 판정한다.

```ts
assessDeepAnalysisPromotionReadiness({
  auditVerdict,
  requiredExclusionConflictCount,
  plan,
})
```

반환값은 다음을 포함한다.

- `analysisComplete`
- `auditComplete`
- `matcherRepresentable`
- `autoPromotable`
- `humanReviewRequired`
- `terminalRoute`
- stage, code, count, detail이 있는 blocker 목록

기존 `buildDeepAnalysisPromotionPlan`은 성공 시 readiness를 함께 반환하고, 자동승격
불가 시 `DeepAnalysisPromotionReadinessError`에 동일한 readiness를 보존한다.
promotion의 fail-closed 동작은 바꾸지 않는다.

R1 blocker code:

- `audit_not_concur`
- `required_exclusion_conflict`
- `conversion_error`
- `empty_criteria`
- `conversion_dropped`
- `conversion_downgraded`
- `question_anchor_lost`
- `resolution_unconfirmed`

## R2 — audit 책임 축소

R1을 통해 실패 위치가 계량된 뒤 audit 인터페이스를 match-impacting 검증으로
줄인다.

1. primary criterion별 claim과 sealed evidence ref를 입력한다.
2. audit은 각 claim의 `supported / contradicted`와 누락된 required·exclusion·예외
   후보만 반환한다.
3. exact span은 모델이 작성하지 않고 sealed evidence ref를 서버가 복원한다.
4. 조건 없는 22축 상태와 preferred 전수 목록을 audit 출력 계약에서 제거한다.
5. adjudication은 실제 blocking 후보가 있을 때만 호출한다.

두 모델의 독립성은 유지하지만 두 모델이 같은 대형 typed document를 완성해야 하는
곱셈 실패 구조는 제거한다.

## R3 — matcher 표현 가능성 사전판정

promotion 직전이 아니라 audit 전에 다음을 결정론적으로 분류한다.

- `direct`: 현재 criterion으로 자동판정 가능
- `conditional_only`: criterion은 보존하지만 자동 eligible/ineligible 근거로 사용
  금지
- `unsupported_relation`: OR·예외·적용시점 관계를 현재 matcher가 표현하지 못함

`unsupported_relation`이 hard eligibility와 결합되면 해당 공고를
`human_review_required`로 보낸다. criterion 삭제, legacy fallback 또는 false
ineligible 발행으로 우회하지 않는다.

compound relation을 matcher에 새로 구현할지는 보존된 고유 공고 6건에서 반복
빈도를 계량한 뒤 별도 결정한다. 한 공고만을 위한 schema 확장은 하지 않는다.

## R4 — 새 공고 exact 2건 검증

R1~R3을 보존 artifact로 통과한 뒤에만 서로 다른 새 활성 공고 2건을 한 번 실행한다.

성공 조건:

1. sealed input 2/2
2. `analysis_complete` 2/2
3. `audit_complete` 2/2
4. matcher 표현 상태 2/2 판정 완료
5. 각 공고가 `auto_promotable` 또는 근거가 봉인된 `human_review_required` 중 하나의
   terminal route에 도달
6. 표현 가능한 공고는 release·랜딩까지 실제 검증

이 단계에서도 두 건 모두 사람 검수로만 끝나면 자동 coverage 회복은 실패로
판정한다. terminal routing 성공과 자동승격 처리량을 별도 지표로 보고 과장하지
않는다.

## 비목표와 안전 불변조건

- validator나 promotion gate를 통과율 목적으로 완화하지 않는다.
- audit disagreement를 자동 `concur`로 바꾸지 않는다.
- 표현할 수 없는 hard condition을 삭제하지 않는다.
- legacy parser criterion을 랜딩 matcher fallback으로 다시 열지 않는다.
- R1~R3 전에는 추가 유료 exact 2건을 실행하지 않는다.
- 개발 서버, Cloud Run, Scheduler, Vercel과 production model policy를 이 구조
  체크포인트에서 변경하지 않는다.

## 현재 제한과 다음 작업

- R1은 상태를 구조화하지만 아직 DB 원장이나 Ops 화면에 terminal route를 저장하지
  않는다.
- R2 audit 인터페이스 축소와 R3 matcher 표현 가능성 분류는 아직 구현하지 않았다.
- AQ8의 지역 OR 조건을 자동 해결하지 않았으며 기존처럼 사람 판단 대상으로 남는다.
- 다음 체크포인트는 R1 독립 리뷰 후, 보존 artifact만 사용해 audit이 실제로 필요한
  match-impacting 후보 수를 계량하는 R2 설계다.

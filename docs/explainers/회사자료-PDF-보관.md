# 회사 자료 PDF 보관과 검증 범위

2026-09-30 작성. authoring-first 작업 브랜치 구현이며 운영 적용은 미실행이다.

## 사용자 흐름

작성 화면의 ‘회사 자료·사업 설명’에서 PDF와 기준일을 입력한다. 추출 성공 시 원본과 텍스트를
새 자료로 보관한다. 자동으로 생성 근거에 선택하지 않는다. ‘내용 보기’에서 표·숫자·읽기 순서를
확인하고 자료를 선택한 뒤 사업 설명과 함께 저장한다. PDF 원본은 해당 회사와 문서 범위 권한을
검사한 다운로드 API에서만 복호화한다. 자료 사용 중단 후에는 원본 다운로드와 새 생성 근거에서
제외하며, 이미 작성한 문서 내용은 유지한다.

현재 한도는 파일 4MiB, 30쪽, 추출 텍스트 30,000자다. Vercel Function의
[4.5MB 요청·응답 제한](https://vercel.com/docs/functions/limitations)에 multipart 여유를 둔다.
텍스트가 없는 페이지가 하나라도 있으면 부분 결과를 완성 자료처럼 저장하지 않는다. 스캔·암호·
손상 파일은 직접 텍스트 붙여넣기로 안내하며 OCR을 자동 실행하지 않는다.

## 저장·실행 계약

- 원본은 AES-256-GCM으로 암호화한 뒤 기존 R2 객체 저장소에 `application/octet-stream`으로
  저장한다. public URL이나 presigned URL은 사용자에게 반환하지 않는다. 회사명·원본 파일명을
  객체 key에 넣지 않는다. 평문을 공용 첨부 자산으로 등록하지 않는다.
- `CUNOTE_WRITING_SOURCE_KEY_BASE64`는 별도 32바이트 키의 base64다. 서버 비밀 설정으로만
  공급한다. 미설정 또는 잘못된 키이면 업로드/복호화가 거절된다. R2 인증 환경도 필요하다.
  이 개발에서는 운영 키 생성·등록·R2 쓰기를 수행하지 않았다.
- 회사·신청 scope와 요청 ID·원본 SHA를 암호문의 인증 문맥에 결속한다. 원본 SHA·파일명·쪽 수·
  key ID·객체 key는 자료의 불변 메타데이터다. 공개 DTO는 파일명·쪽 수·SHA만 포함한다.
- 텍스트 추출은 별도 Node 프로세스의 PDF.js를 사용한다. 서비스 비밀/NODE_OPTIONS를 상속하지
  않고 JS 평가·폰트 렌더링을 비활성화한다. 프로세스당 동시 2개, 실행 20초, V8 heap 128MiB,
  출력 200KB 제한이다. V8 heap 상한은 프로세스 전체 RSS 보장이 아니다.
- 원본 내려받기는 객체 조회 전후 권한·철회를 검사하고, 인증 태그·원본 SHA·길이를 확인한다.
  `private, no-store`, attachment disposition을 적용한다.
- 암호화 키를 교체하기 전에 기존 key ID의 원본 복호화·이관을 준비해야 한다. 현재는 다중 key
  ring·자동 재암호화·키 복구를 구현하지 않았다. 기존 키를 없애면 해당 원본은 열 수 없다.
- 파일 업로드와 DB 쓰기는 원자적이지 않다. DB 저장 실패 시 암호화 객체만 남을 수 있다.
  같은 요청/파일의 재시도는 같은 객체 key를 사용하지만 미참조 객체의 자동 회수는 아직 없다.
  현재 자료 철회도 물리 삭제가 아니다. 정식 보관/삭제 정책 적용 전의 파일럿 범위다.

## 검증

`pnpm test:writing-context`에 합성 PDF의 실제 자식 프로세스 파싱, 크기·쪽 수·빈 페이지·
잘못된 PDF·동시 실행 상한, 암호문 변조·다른 회사 문맥·잘못된 키 검증을 포함한다.
`pnpm test:product-postgres`는 실제 격리 DB와 메모리 객체 저장소로 PDF 생성→추출→암호화→
원본 재열기, 신청 범위/회사 공통 재사용, 불변 메타데이터, 재시도, 조회 도중 철회를 검사한다.

빌드 trace에 PDF.js 본체와 worker가 포함되는지도 확인한다. 실제 R2·Vercel 런타임 subprocess·
회사소개서 품질·로그인 브라우저는 별도 인수이며 위 합성 검증으로 대체하지 않는다.

## 1. 2026-08-02 transport 전환에서 만들어진 것 (역사적 범위)

당시 구현은 딥분석의 모델 호출 transport를 **Anthropic API 토큰(달러)**과 **Claude Max 구독**
(이미 결제 중인 정액제) 사이에서 선택할 수 있게 만든 것이다. 아래 내용은 transport 배선과 그 채택 당시의
A/B 검증을 설명하며, 현재 end-to-end 품질 승인이나 live 실행 권한을 뜻하지 않는다.

```
                          ┌─ (기본) Anthropic API ──── 토큰 과금 · 운영 worker는 항상 이쪽
공고 → 딥분석 파이프라인 ─┤
                          └─ (스위치 ON) claude CLI ── Max 구독 목표 · 인증 격리 필수 · 로컬 전용
```

당시 transport 채택 범위의 핵심 사실 세 가지:

1. **A/B 비교에서 분석 로직은 같았다.** 같은 프롬프트, 22축 스키마와 원문 인용 검증을 두 transport에 적용했고, 비교 변수는 모델 호출 경로였다.
2. **transport 채택 근거만 검증됐다.** 당시 원문 대조 판정 59건에서 구독 레인이 추출 30:3, 감사 19:1로 우세했고, 환각 0건·원문 인용 검증률 100%였다. 이 결과는 최신 repair/Kordoc 및 전체 실험 시스템의 품질 `GO`로 재사용할 수 없다.
3. **운영과 로컬 lab의 경로를 분리했다.** 구독 스위치는 로컬 실험실에 한정하고 운영 worker는 API 경로를 유지하도록 설계했다. 현재 실제 모델 실행은 transport와 무관하게 Gate R admission이 차단한다.

레인별 경로 (transport 배선 기록·현재 실행 차단):

| 레인 | 하는 일 | 경로 |
|---|---|---|
| 추출 (`lab:smoke`/`lab:batch`) | 공고 → 22축 조건 분해 | **구독 (opus-5)** |
| 블라인드 감사 (`lab:ai-audit`) | 검수 결과 재검증 → 일치 시 자동 확정 | **구독 (sonnet-5)** |

모든 명령은 리포 루트(`~/noten.works/cunote`)에서 실행합니다. 스위치는 env 3개가 전부입니다:

| env | 값 | 의미 |
|---|---|---|
| `ANALYSIS_LAB_TRANSPORT` | `claude-cli` | 구독 경로 ON (미설정 = 기존 API) |

### 3-0. 정식 런칭 batch — 현재 정본

런칭 경로는 후보 inventory·준비·승인·실행을 분리한다. 신규 series inventory와 launch 준비는
모델을 호출하지 않는다. 현재 target input/attachment SHA와 실행 material contract는 launch
manifest에 다시 봉인되므로, 이전 plan의 source drift는 target telemetry로 흡수된다.

```bash
pnpm lab:experiment:prepare -- --series=deep-v32
pnpm lab:launch:prepare -- \
  --series=deep-v32 --sequences=0-49 --concurrency=2
```

출력의 `manifestSha256`, target 수, `changedSinceInventory`를 사용자에게 제시한다. exact manifest
범위를 한 번 승인받은 뒤에만 grant를 기록한다.

```bash
pnpm lab:launch:grant -- \
  --manifest=<manifest-sha256> --approved-by=<actor>
```

그 grant로 cohort 전체를 실행한다. concurrency와 model은 manifest에 고정되므로
실행 명령에서 변경할 수 없다.

```bash
pnpm lab:launch -- --grant=<grant-sha256>
```

- 실행 시작 전 Max 인증을 공통 preflight로 한 번 확인하고, DB runtime snapshot 한 번과 cohort
  전체 exact-generation lease 하나를 사용한다. 변경 없는 실행마다 gcloud를 재인증하지 않는다.
- target의 `held`, non-publishable, input/attachment drift, source unavailable,
  개별 timeout·응답 실패는 그 target만 격리하고 다음 target을 계속한다.
- manifest/grant 손상, 공통 Max 인증 실패, DB lease 충돌·상실, 프로세스 abort, Max window 소진만
  잔여 target의 신규 착수를 중단한다.
- precision·structured ratio·명목 API 환산 비용은 cohort telemetry다. 더 많은 target을 시작하기
  위한 별도 admission이나 10+10 checkpoint가 아니다.
- 동일 grant의 실패 target만 다시 시도할 때는 material binding이 같으면 새 사용자 승인을 묻지 않고
  `pnpm lab:launch -- --grant=<grant-sha256> --retry-errors`를 사용한다. 성공·held target은 재실행하지 않는다.
- 결과는 target별 LabRun hash를 포함한 content-addressed
  `analysis-launch-receipt-v1`으로 종결된다. 이 receipt는 분석 증거이며 서비스 DB write, release approve,
  `lab:promote --write`, 배포, 운영 worker 활성화 권한은 아니다.

작성 가이드 전환에서 과거 publishable 런의 현행 input/attachment가 달라진 공고는 신규 formal
series에 다시 편입하지 않는다. 오늘 기준 `authoring-guide-adoption-manifest-v1`에서
`rerun_required`이면서 current source가 sealed인 공고만 다음 명령으로 별도 launch manifest에 봉인한다.

```bash
pnpm lab:authoring-guide:rerun:prepare -- \
  --adoption-manifest=<adoption-manifest-sha256> --concurrency=2
```

이 준비는 모델을 호출하지 않는다. 생성된 manifest는 adoption SHA와 현재 input/attachment SHA,
`existingRunPolicy=rerun_exact_targets`, 구독 모델·prompt·validator·package runtime을 결속한다.
source가 미봉인된 공고는 포함하지 않고 Kordoc도 함께 실행하지 않는다. 출력된 exact manifest를
사용자가 승인한 뒤에만 기존 `lab:launch:grant`와 `lab:launch`를 사용한다. 서비스 DB 승격은 여전히
별도 `lab:promote --write` 승인 범위다.

아래 단건 experiment·legacy batch 절은 역사 artifact 해석과 장애 복구 참고용이다. 신규 런칭 batch에
target별 authority, 직전 receipt `CONTINUE`, approval TTL을 전이하지 않는다.

### 3-1. 맛보기 1건 (스모크)

현재 `lab:smoke`도 실제 모델 실행이므로 허용하지 않는다. 단건이라는 사실만으로 exact cohort,
provenance와 사용자 canary 승인을 증명하지 못하며, 실행하면 `gate_r_not_satisfied`로 중단된다.
신규 코호트 `refresh`, 저장 대상 소실에 따른 대체 선정, `lab:cohort:freeze`도 새 표본을 만드는

### 3-2. 반복형 분석 에이전트와 단건 experiment Adapter

legacy agent는 신규 공고 선정부터 딥분석·Kordoc·독립 검수·감사·원인별 보정까지를 묶는다.
현재 허용되는 기본 동작은 **계획 확인만**이며 모델을 호출하지 않는다.

```bash
ANALYSIS_LAB_TRANSPORT=claude-cli ANALYSIS_LAB_MODEL=claude-opus-5 \
  pnpm lab:agent -- --count=30
```

출력된 `기존 품질 보정 / 미분석 실행 / 신규 안전 후보` 수는 관측용이다. Gate R 전에는
`--execute`를 붙이지 않는다. CLI와 관리자 화면 모두 실제 실행을 `gate_r_not_satisfied`로 차단한다.

구현된 receipt-bound 단건 Adapter도 legacy agent의 “비면 자동 선정→실행” 흐름을 복원하지 않는다.
실행 순서는 다음 계약으로 제한한다.

1. 모델 호출 전에 exact Nmax·순서·층·입력·runtime provenance를 불변 plan으로 봉인
2. 사용자가 exact proposal과 canary를 승인한 뒤 trusted coordinator가 content-addressed approval을 기록
3. approval SHA로 현행 worker 증거와 paused runtime을 검증해 exact-next 단건 authority를 발급
4. plan의 정확한 다음 공고와 명시된 lane만 실행하며 실행 중 신규 공고를 자동 편입하지 않음
5. exact run/artifact/lifecycle/quality receipt를 수집해 순차 gate를 평가
6. `CONTINUE`일 때도 다음 target은 새 사용자 approval과 authority가 있어야 진행하고,
   `GO`/`NO_GO`/`INCONCLUSIVE`/`INVALID`는 모두 즉시 종결

실제 표면은 아래처럼 분리돼 있다. 현재는 사용자 approval artifact가 없으므로 두 번째·세 번째
명령을 실행하지 않는다.

```bash
pnpm lab:experiment:prepare -- --series=deep-v20
pnpm lab:experiment:issue -- --approval=<approval-sha256>
pnpm lab:experiment -- --authority=<authority-sha256>
```

`prepare`는 DB/R2를 읽어 proposal을 불변 저장하지만 모델·gcloud·lease를 호출하지 않는다.
`issue`는 사용자의 명시적 승인 뒤에만 사용하며 전용 gcloud configuration의 현행 worker 증거와
DB runtime pause를 읽고 immutable authority를 발급한다. 사용자 대신 승인하는 CLI는 없고,
proposal·approval·authority 중 어느 하나만으로 다음 target이나 promotion이 자동 진행되지 않는다.

`deep-v20`의 `strata-v2`는 과거 비중복 표본이 현행 `kstartup/thick` 7건을 모두 사용한
실제 재고 소진을 반영한다. 신규 모집단에 남은 5층은 필수, `kstartup/thick`은 새 재고가 있으면
계획에 들어올 수 있는 선택 층이다. 이 변경은 과거 `strata-v1` 결과를 재해석하지 않고,
없는 신규 후보를 억지로 재실행하지 않기 위한 진행 계약이다.

`deep-v23`의 `strata-v3`는 전체 과거 이력을 제외한 2026-08-18 신규 모집단에서
`bizinfo/thick`과 `kstartup/thick` 비중복 재고가 모두 소진된 상태를 반영한다. 첫 15건은
`bizinfo/medium`, `bizinfo/thin`, `kstartup/medium`, `kstartup/thin` 4층을 필수로 포함한다.
thick 두 층은 새 비중복 재고가 생길 때만 optional로 선택하며, v1·v2 artifact의 필수 층 의미는
그대로 보존한다.

`deep-v32`의 `strata-v4`는 deep-v31 50건 실행 후 `bizinfo/thin` 비중복 재고도
소진된 2026-09-03 현황을 반영한다. 첫 15건은 `bizinfo/medium`, `kstartup/medium`,
`kstartup/thin` 3층을 필수로 포함하고, 나머지 층은 새 비중복 공고가 유입되면 optional로
선택한다. v1·v2·v3 artifact의 필수 층과 deep-v31의 50건 계약은 재해석하지 않는다.

Kordoc은 딥분석과 분리해 `preflight → exact 단건 승인 → canary`로 실행한다. 2026-08-15 proposal
`a604b9b8...`의 sequence 7/source `73b82ccf...` 한 건을 승인받아 `claude-cli/claude-opus-5`로 실행했고,
44개 구조 필드 중 추천 입력 27개·미해결 0·구조 경고 0으로 complete 종결했다. receipt는
`2503e071...`이며 API fallback은 없었다. 이 성공은 나머지 4건의 자동 권한이 아니므로 후속은

### 3-3. 비정상 종료 복구

단건 실행 프로세스가 종료됐으면 먼저 모델을 다시 호출하지 말고 다음 읽기 전용 명령으로 durable 상태를
확인한다.

```bash
pnpm lab:experiment:recover -- --inspect=<authority-sha256>
```

- claim이 없으면 모델 미착수다. 별도 recovery approval로 만료 lease만 해제한 뒤 새 canary approval을 발급한다.
- claim은 있고 terminal이 없으면 착수 여부 불명이다. recovery는 series를 중단하며 같은 slot을 재실행하지 않는다.
- 유효 terminal이 있으면 결과 bytes와 통계 판정을 보존하고 runtime lease만 해제한다.

실제 변경 명령 `--approval=<recovery-approval-sha256>`은 위 관측, 로컬 프로세스 종료, exact runtime
snapshot을 사용자가 별도로 승인한 뒤에만 쓴다. 자동 retry, artifact 삭제, successor series 생성은 없다.

`passed`, 안전한 `partial`, 빠른 작성 대상 문서가 없는 `not_applicable`은 종결이다. `held`도 품질상
안전하게 종결된 상태이므로 오류나 자동 repair 대상으로 되돌리지 않는다. provider 실패 같은 `failed`의
재시도는 원래 confirmatory run과 분리된 새 experiment receipt에서만 허용한다.

deep primary의 `publishable`은 Kordoc 완료와 같은 말이 아니다. `matchingReadiness=ready`는 22축 분석이
완결된 후보, `conditional`은 확인된 조건으로 매칭하되 unresolved 축을 사업자 질문으로 보완하는 후보다.
확인 축이 1개 이하이거나 unresolved 축과 criterion이 모순되면 `held/deferred`로 후보 발행을 보류한다.
Kordoc 완료는 `withApplicationRoundtrip`을 명시한 별도 실행과 application artifact가 있을 때만 판정한다.

과거에는 같은 명령을 반복해 미완료 공고를 재개했지만 현재는 이 반복이 구조적 실패를 증폭한 경로로
판정됐다. legacy agent를 반복 실행하지 않으며, 재개는 사전 봉인한 실험 계획과 exact receipt에 결속된
단건 Adapter가 남은 Gate R 증거와 target별 사용자 승인을 모두 통과한 뒤에만 한다.

- 실행 보고서: `spike-out/analysis-lab/agent-runs/agent-*.json`
- 현재 formal `lab:launch` 실행 범위: 50건, 동시성 2
- 아래 legacy agent 기록의 기본 실행 범위: 30건, 교정 3사이클, 동시성 2
- API 폴백: 없음. 자식 단계의 `ANTHROPIC_API_KEY`를 비워 구독 CLI 실패가 API 과금으로 바뀌지 않게 합니다.
- 자동 승격: 없음. exact release prepare/gate/approve는 promotion admission이 별도로 소유하고,
  실제 `lab:promote --write`만 명시적인 실승격 승인 뒤 수행한다.

Gate R 전에는 `--max-cycles`나 `--concurrency`를 조정해 실행하지 않는다. 향후 승인된 Adapter에서도 실제
Claude CLI 프로세스의 전역 기본 상한 4개를 유지한다. 과거 `--max-cost-usd`를 넘기면 1회 경고만 내고
구독 실행 정책에서는 무시한다.

**공고 인플라이트는 전역 CLI 상한과 같게(기본 4) 두는 것을 권장합니다(2026-08-11 실측).** 총 처리량 상한은 전역 CLI 슬롯이므로 인플라이트를 10으로 늘려도 배치 전체 시간은 같고, 건당 완료 시간만 큐 대기로 ~3배 부풀어집니다(10건 배치 실측: 건당 평균 57분, 슬롯 4개 내내 포화, 호출당 실행 2.15분 vs 요청 wall 최대 ~14분). 인플라이트 4는 같은 처리량으로 개별 공고를 훨씬 일찍 닫아 검수·감사 레인이 앞당겨집니다. 근거: `docs/plans/2026-08-11-deep-analysis-throughput-plan.md` §2-1·T0.

### 3-2-1. 하위 대량 배치 (문제 격리용)

Gate R 전에는 대상 수, lane 선택, 예상 fan-out만 `--dry-run`으로 확인한다. 모델 호출이 있는 직접
batch는 문제 격리 목적이어도 허용하지 않는다.

```bash
ANALYSIS_LAB_TIMEOUT_MS=900000 ANALYSIS_LAB_TRANSPORT=claude-cli ANALYSIS_LAB_MODEL=claude-opus-5 \
  APPLICATION_ROUNDTRIP_EFFORT=medium \
  pnpm lab:batch -- --dry-run --reanalyze-outdated --with-application-roundtrip \
  --roundtrip-model=claude-opus-5 --limit=30 --concurrency=4
```

- 2026-08-09 현행 5건 파일럿에서 딥분석과 Kordoc를 합친 명목 예상치가 30건 `$53.26`으로 계산됐다. 이 값은 API 환산량과 fan-out 회귀를 비교하는 telemetry이며 구독 실행을 멈추지 않는다.
- Kordoc은 구독 경로에서 후보 40개를 한 요청으로 보내고 공고 당 2개 묶음을 동시 처리합니다. 응답에서 누락되거나 저신뢰인 후보는 미해결로 남겨 작은 묶음으로 최대 2회 재판정하므로 처리량을 늘려도 누락을 성공으로 숨기지 않습니다.
- 2026-08-11 고정 30건 실제 산출물에서 기존 Kordoc 247회 호출은 새 40개 묶음 계약으로 보수적으로 151회(`-38.9%`)로 줄어든다. 425개 후보를 처리한 영천 공고는 25회에서 약 15회로 줄어드는 계산이다.
- 2026-08-11 영천 공고 실측에서 신규 전체 분석은 33분 03초 대비 17~21분, 같은 독립검수 blocker를 반영한 repair-loop는 의미 회귀 자동 교정 1회를 포함해 10분 21초(`-68.7%`)였다. 상세 근거는 `docs/research/2026-08-11-단건-절대-처리-속도-canary.md`다.
- 과거 live batch는 이미 publishable인 공고를 건너뛰었지만, 현재 명령은 dry-run 관측만 수행한다.
- `--retry-errors`는 과거 live batch 옵션이며 Gate R 전에는 사용하지 않는다.
- `--with-application-roundtrip`은 Kordoc lane을 계획에 포함한다. 현재 dry-run에서는 선택 범위만 확인하고 실제 후보 판정은 시작하지 않는다.
- 향후 독립 검수 blocker나 `deep_contract`만 고치는 재분석은 새 Kordoc을 돌리지 않는다. 기존 Kordoc run id가 있으면 원본 SHA 세트·Kordoc/엔진 버전·모델·transport·미처리 여부를 검증한 불변 산출물만 재결속하고, 없으면 deep-only로 계획한다. 재사용 계약이 하나라도 다르면 primary 모델 시작 전에 fail-closed 한다.
- 전역 CLI 상한을 높이는 것은 동시 작업 수를 늘리는 것과 다릅니다. 기본 `4`를 유지하고, 세션 한도·메모리·실제 처리량 근거가 있을 때만 `ANALYSIS_LAB_CLAUDE_CLI_MAX_CONCURRENCY`를 조정합니다.
- 재판정 뒤에도 모호한 필드는 억지로 확정하지 않습니다. 확정된 안전 필드만 `부분 완료`로 빠른 작성에 반영하고, 남은 필드는 문서 직접 편집으로 열어둡니다.
- 과거 실행 artifact와 상태는 브라우저 연결과 무관하게 보존된다. 현재 새 분석 요청은 `gate_r_not_satisfied`가 lease/busy 판정보다 먼저 적용될 수 있다.
- `--grant-ids=<uuid,uuid,...>`는 향후 exact cohort Adapter가 참조할 legacy 선택 옵션일 뿐 현재 live 권한이 아니다.

### 3-2-2. 5건에서 30건으로 넓히는 준비 게이트

이 절은 과거 bulk-readiness 계약을 해석하기 위한 기록이다. 처음부터 30건을 성공으로 간주하지
않았다는 원칙은 유지하지만, 이 판정은 현재 live 실행 권한이 아니다. 현재 정본은 고정 30건 계획과
순차 gate를 가진 `deep-repair-experiment` shadow replay다.

1. 배치가 오류·구독 창 소진 없이 정상 종결하고 명목 USD는 telemetry로 보존
2. 요청한 5건이 모두 시작·성공하고 중복이나 미착수 없음
3. 딥분석과 Kordoc 모두 `claude-cli/claude-opus-5` provenance
4. 딥분석 22축과 독립 AI 검수·감사 통과
5. Kordoc가 `complete/partial/not_applicable`로 안전 종결하고 필수 입력 미해결 0건

5건 실행 직후 판정:

```bash
pnpm lab:bulk-readiness -- --stage=pilot5 --write
```

후속 재분석으로 현재 `batch-job.json`이 바뀐 뒤에도 원래 5건 배치를 다시 판정하려면 보존한 불변 스냅샷을 명시합니다.

```bash
pnpm lab:bulk-readiness -- --stage=pilot5 --batch-job=<보존한-batch-job.json> --write
```

- `GO`: 과거 readiness 조건을 만족했다는 뜻뿐이다. 30건 live 실행으로 이어가지 않고 dry-run 관측만 한다.
- `ITERATE`: 과거 의미는 문제 공고만 좁혀 검토한다는 뜻이다. 현재는 자동 재검수·재판정을 시작하지 않는다.
- `BLOCKED`: API 혼입, Kordoc 병렬 미사용, 배치 오류처럼 실행 계약이 깨진 상태입니다. 대량 실행을 시작하지 않습니다.
- `WAIT`: 배치 실행 중입니다. 실행이 끝난 뒤 같은 명령을 다시 사용합니다.

과거 30건 실행의 판정 JSON은 `spike-out/analysis-lab/bulk-readiness/<batch-job-id>/` 아래 불변 증거로
남는다. 신규 30건 실행은 금지되며, 이 게이트는 제품 승격이나 현재의 대량 생산 준비를 승인하지 않는다.

### 3-3. 품질 그래프 피드백 루프

다음은 과거 5건·30건 배치에서 사용한 흐름이다. Gate R 전에는 어느 단계도 live로 재실행하지 않는다.

1. Opus 5가 22축 딥분석과 Kordoc 빠른 작성 선분석을 공고당 병렬 실행
2. Fable 5가 추출 조건·빈 축 누락을 검수
3. Sonnet 5가 Fable 판정을 원문 기준으로 독립 감사
4. 두 모델이 충돌한 항목만 Opus 5가 3차 판정
5. `eligibility` 누락이 확정된 공고만 `lab:repair-held`로 재분석하고 최근 5개 런의 고유 교정을 누적

`ranking` 누락은 신청 가능성을 바꾸지 않으므로 전체 배치를 막지 않고, 해당 점수 신호를 미반영한 `partial`로 남긴다. Kordoc도 확정 필드를 사용할 수 있고 필수 미해결이 0건이면 `partial`을 안전 종결로 인정한다. 이 경계가 대량 분석을 막는 과도한 완벽주의와 신청자격 오판을 동시에 피한다.

### 3-4. 블라인드 감사 (검수 후 자동 확정)

블라인드 감사도 실제 모델 호출이므로 현재는 중지한다. 향후 승인된 실행에서는 결과 파일의
`aiAuditTransport: "claude-cli"`로 provenance를 추적하지만, 과거 감사 명령 자체는 재개 권한이 아니다.

### 3-5. API로 되돌리기

transport 설정을 빼면 API 정책으로 해석되지만 Gate R 차단은 transport와 무관하다. 따라서 env를
제거해 API로 우회할 수 없으며, 코드 롤백 없이도 모든 analysis-lab live 모델 경로가 중지된다.

## 4. 모니터링 — 무엇을 보면 되나

### 4-0. ops 구독 분석 에이전트

로컬 ops 개발 서버에서 `/subscription-agent`를 열면 반복형 에이전트를 한 화면에서 관리할 수 있습니다.

- 5·10·30건 단위로 모델 호출 없는 계획 확인
- 기존 품질 보정, 선정된 미분석, 신규 안전 후보 수 확인
- 신규 선정 → 22축·Kordoc → Fable → Sonnet → Opus → 원인별 보정 단계 표시
- 현재 배치 성공·실패·명목 비용·소요 시간과 실시간 로그 확인
- 최근 불변 에이전트 보고서의 품질 종결·Kordoc 재시도·22축 재시도·blocker 확인
- Gate R 전에는 실제 실행 버튼 비활성화와 서버 pre-spawn 차단
- Gate R 이후에도 운영 API 자동화 또는 다른 로컬 lease가 켜진 상태에서는 새 실행 차단
- 기록된 PID가 실제 구독 분석 에이전트일 때만 안전 중단

현재 이 페이지는 로컬에서도 계획 확인만 허용하고 실제 실행은 비활성화한다. 과거 실행 증거는
`batch-job.json`, 전용 로그, `agent-runs/*.json`을 결합해 읽기 전용으로 복원한다.

### 4-1. 과거 실행 증거: 배치 로그

기존 터미널 로그를 해석할 때 볼 것 세 가지:

- `(n/전체) 완료: [층] 공고제목 · 63s · $0.32` — 정상 진행. 달러 표시는 **명목 비용**입니다(§4-3).
- `(n/전체) error 런 저장: ...` — 과거 배치의 provider/계약 실패 기록이다. 자동 재시도로 정상화된다고 가정하지 않는다.
- `윈도 소진 감지 — 신규 착수 중단` — Max 구독의 5시간 사용량 창이 바닥난 것. 배치가 스스로 멈춥니다(§5-1).

### 4-2. 실행 후: 결과 확인

- **런 파일**: `spike-out/analysis-lab/<공고>/run-*.json` — `transport`와 중앙 outcome을 함께 확인한다. `error: null`만으로 publishable을 판정하지 않는다.
- **품질 게이트**: `pnpm lab:aggregate` — 정밀도 등 품질 지표를 판정합니다. `cost_per_notice` 비용 판정은 API 산출물에만 적용하고, 구독의 명목 USD는 별도 telemetry로 표시하며 게이트 수에서 제외합니다.
- **과거 5→30 준비 판정**: `lab:bulk-readiness` artifact는 해당 배치의 상태를 해석하는 자료일 뿐 현재 실행 권한이 아니다.
- **검수 화면**: dev 서버의 analysis-lab 페이지에서 런을 열어 22축 결과를 사람 눈으로 확인하는 것도 기존 그대로입니다.

### 4-3. 구독 사용량 (진짜 지갑 모니터링)

- 런 파일·로그의 `costUsd`는 원칙적으로 **"API로 돌렸다면 얼마였을까"의 명목치**다. 단,
  2026-08-15 인증 격리 수정 전 `claude-cli` artifact는 실제 자격증명을 증명하지 못하므로 이 값을
  API 과금 위험 추정치로 보고 Console Billing을 정본으로 삼는다. 수정 후 실행도 최초 canary에서
  Console API 요청 0을 확인하기 전에는 실지출 0으로 선언하지 않는다. 비용은 품질·승격 게이트로
  사용하지 않되, 인증 회귀는 즉시 실행 중단 사유다.
- 실제로 소진되는 것은 **Max 구독의 사용량 창**(5시간 롤링 + 주간 상한)입니다. 확인 방법:
  - `/claude-dashboard:check-usage` (Claude Code 안에서) 또는 셸의 `check-ai` 별칭 — Claude/Codex 사용량 한눈에
  - claude.ai → Settings → Usage
- 과거 실측치: v12 3건 재분석은 동시성 2에서 15분 55초, 명목 `$4.5092`였다. 양식 후보 약 97개·3문서인 포항 공고는 11분 23초가 걸렸다. 이는 fan-out과 wall telemetry 비교 자료이며 신규 실행 지시가 아니다.

## 5. 운용 수칙 (채택 조건 — 지켜야 하는 것)

1. **Gate R은 live 모델 실행에만 적용합니다.** lease, transport env, 과거 GO로 모델 실행을
   우회하지 않으며, 반대로 이 target별 승인 규칙을 release prepare/gate/approve에 전이하지 않습니다.
2. **구독 경로는 로컬 dev 전용입니다.** 운영 서버·배포 환경에 `ANALYSIS_LAB_TRANSPORT`를 설정하지 않습니다(약관 경계이자 설계 경계).
3. **사람 표본 감사를 유지합니다.** 구독 감사는 자동 확정률이 높아지는 방향이라, 자동 확정된 항목의 표본 검토(기존 검수팀 절차)를 계속 돌립니다.
4. **검수 가이드 사례집이 안전판입니다.** A/B에서 발견된 추출 결함 패턴 2종(축 값 오배치, 배제 조건 연산자 반전)이 사례집에 등재돼 있어 검수 단계에서 걸러집니다 — 검수 시 exclusion 조건의 부등호 방향은 꼭 원문과 대조하세요.

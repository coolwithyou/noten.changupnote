# 검수된 공고별 확인 질문 v2 발행

기준일: 2026-09-08. [분석·매칭 순차 개선 계획](../plans/2026-09-07-분석-매칭-정합성-순차개선.md)
2단계의 수동 최초 발행과 같은 run의 질문 개정·철회 경로다. 운영에 적용했다는 기록이 아니며,
[감사 로그](../plans/2026-09-07-분석-매칭-개선-감사로그.md)의 검증·잔여 범위를 함께 확인한다.

## 적용 대상

사람이 원문을 검수한 `correct` 조건 중, 공고별로 사용자가 직접 확인할 수 있는 조건만 다룬다.
첫 구현은 근거가 확인된 `other / text_only`, `per_notice`, 단일선택 질문에 한정한다.
required·preferred·exclusion의 종류를 바꾸지 않는다.

- 일반 회사 사실은 기존 회사정보 입력 경로에서 보완한다.
- 원문 근거 누락·조건 해석 충돌·명시 강등으로 보류한 조건은 원문/관리자 검수에 남긴다.
- 공식 원천의 확정 실패와 원천 정정 검토 상태는 사용자 답변으로 뒤집지 않는다.
- 모델의 자동 질문 생성은 기존 legacy exclusion 계약을 유지한다. 새 관리자 질문 편집 GUI는 없다.

## 수동 파일 준비

기존 immutable run과 해당 run의 실제 사람 검수 `.review.json`이 있어야 한다.
원문과 적용 범위를 확인한 질문 작성자가 아래 형식의 JSON을 준비한다.
이 예시는 합성 형식 설명이며 실제 공고의 검수 결과나 승인으로 사용할 수 없다.

```json
{
  "questionAuthorEmail": "question-author@example.invalid",
  "items": [
    {
      "criterionIndex": 0,
      "resolutionScope": "per_notice",
      "prompt": "이 공고의 해당 요건을 충족하나요?",
      "options": [
        { "value": "yes", "label": "충족해요", "evaluation": "satisfied" },
        { "value": "no", "label": "충족하지 않아요", "evaluation": "unsatisfied" },
        { "value": "unknown", "label": "확인할 수 없어요", "evaluation": "unknown" }
      ]
    }
  ]
}
```

`criterionIndex`는 원본 run의 0부터 시작하는 조건 위치다. 변환 후 배열 위치를 넣지 않는다.
선택지는 정확히 세 개이며 서로 다른 value와 세 evaluation을 모두 가져야 한다.
서버는 질문 문구나 yes/no 문자열에서 평가 의미를 추측하지 않는다.

| 평가 | required | exclusion | preferred |
| --- | --- | --- | --- |
| satisfied | 필수 조건 충족 | 결격에 해당하지 않음 | 우대 조건 충족 |
| unsatisfied | 필수 조건 미충족 | 결격에 해당함 | 우대 조건 미충족 |
| unknown | 미확인 유지 | 미확인 유지 | 미확인 유지 |

preferred의 미충족·미확인만으로 기본 자격을 탈락/조건부로 바꾸지 않는다.
조건 검수자는 기존 review에서 `criterionReviewerEmail`로, 질문 작성자는 입력한
`questionAuthorEmail`로 구분해 보관한다. 사람 이메일 형식과 기존 AI 라벨러 거부 검사를 적용한다.
이 검사는 실제 계정 인증이나 사람이 검수했다는 외부 증명의 대체 수단은 아니다.

## 로컬 artifact 생성과 발행 경계

저장소 루트에서 실제 식별자와 파일 경로를 넣는다.

```sh
pnpm lab:confirmations:manual -- --grantId=<공고-UUID> --runId=<기존-run-ID> --input=<수동-JSON-경로>
```

이 명령은 모델·DB·네트워크를 호출하지 않는다. 원본 run 옆에
`<runId>.confirmation-evaluations.json`을 신규 생성하고, 원본 run은 수정하지 않는다.
선택한 run의 source revision·input·run 결속과 조건 검수, 선택지 의미를 검증한다.
현재 DB 원천과의 대조는 후속 release/발행 및 제품 조회·저장 경로에서 수행한다.
파일이 이미 존재하면 덮어쓰지 않고 `EEXIST`로 거부한다. 손상된 기존 파일은 부재로 간주하지 않는다.

### 같은 run의 질문 개정·추가·철회

최초 파일은 revision 1이다. 원본 run이나 최초 파일을 복제·수정·삭제하지 않고
`<runId>.confirmation-evaluations.r2.json`, `r3.json`처럼 별도 불변 개정본을 만든다.
각 개정본은 바로 이전 revision의 실제 파일 SHA, 원본 run 내용, 변경 내용과 철회 목록을 결속한다.
개정 번호는 1~1,000의 연속된 정수다. 저장 전 부모 이력 전체를 검증하고 동일 번호 동시 저장은
하나만 성공한다. 성공한 파일은 덮어쓰지 않는다.

개정 입력의 `items`는 **변경한 항목만이 아니라 전체 활성 질문 목록**이다. 남길 질문을 모두
포함하고, 부모에 있었지만 뺀 index는 `withdrawnCriterionIndexes`에 정확히 적는다.
아래는 부모에 index 0만 있을 때 문구를 수정하는 합성 예시다.

```json
{
  "questionAuthorEmail": "question-author@example.invalid",
  "intent": "replace",
  "withdrawnCriterionIndexes": [],
  "items": [
    {
      "criterionIndex": 0,
      "resolutionScope": "per_notice",
      "prompt": "이 공고의 해당 요건을 신청일 기준으로 충족하나요?",
      "options": [
        { "value": "yes", "label": "충족해요", "evaluation": "satisfied" },
        { "value": "no", "label": "충족하지 않아요", "evaluation": "unsatisfied" },
        { "value": "unknown", "label": "확인할 수 없어요", "evaluation": "unknown" }
      ]
    }
  ]
}
```

문구·선택지·적용 기준은 검수된 원문이 실제로 뒷받침해야 한다. 위 예시의 신청일 문구를 다른
공고에 그대로 적용하지 않는다. 질문 추가도 같은 full snapshot 방식이며 새 index는 사람 검수
correct 조건이어야 한다. 부모와 동일한 목록으로 새 개정본을 만드는 무변경 요청은 거부한다.

```sh
pnpm lab:confirmations:manual -- --grantId=<공고-UUID> --runId=<기존-run-ID> --input=<개정-JSON-경로> --parent-revision=<부모-번호> --parent-sha256=<부모-파일-SHA256>
```

CLI 성공 출력의 `selector`에는 grantId/runId/revision/실제 파일 SHA가 들어 있다. 부모 번호와
SHA 둘 다 필요하며 최신 파일을 자동 선택하지 않는다. 개정 입력에 부모가 없으면 거부한다.

부모의 활성 질문이 index 0, 1일 때 전량 철회 입력은 다음과 같다.

```json
{
  "questionAuthorEmail": "question-author@example.invalid",
  "intent": "withdraw_all",
  "withdrawnCriterionIndexes": [0, 1],
  "items": []
}
```

빈 목록은 `withdraw_all`과 부모 전체 철회가 함께 확인될 때만 허용한다. 이미 빈 부모를 다시
전량 철회하는 요청은 거부한다. 이후 질문을 다시 추가하려면 빈 부모를 지정한 `replace` 개정본을
명시적으로 만든다. 수동 질문 철회는 공고 조건 자체나 별도의 기존 legacy 질문을 삭제하지 않는다.

### release의 exact 개정본 선택

선택 JSON은 다음 형식이다. 아래 식별자와 SHA는 설명용이며 실제 승인 근거로 쓰지 않는다.

```json
{
  "schema": "lab-manual-confirmation-evaluation-selection-set-v1",
  "selections": [
    {
      "grantId": "11111111-1111-4111-8111-111111111111",
      "runId": "run-2026-09-08T000000.000Z-acde24",
      "revision": 2,
      "artifactSha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  ]
}
```

기존 exact release의 준비 권한 안에서 `lab:release` 준비/조사 명령에
`--manual-confirmation-selections=<선택-JSON-경로>`를 전달한다. 신규 준비는 해당 run의 질문
파일이 존재하면 선택을 요구한다. 중복·대상 밖·다른 run·잘못된 hash 선택은 거부한다.
발행 계획과 source artifact는 같은 개정 번호/SHA/활성 수/철회 의도를 가져야 하며,
전량 철회도 질문 0개라는 사실과 별도로 철회 artifact를 결속한다.

역사 release의 SHA-only 질문 근거는 최초 파일만 검증한다. 질문 근거가 없던 역사 release는
새 질문 파일이 생겨도 자동 채택하지 않는다. 특정 revision을 선택한 release도 상위 파일의 등장에
영향받지 않는다. 질문 개정은 material promotion plan 변경이므로 기존 질문 계획과 동일하다고
간주하지 않으며, 실제 release 처리·운영 승격은 기존 exact 승인 범위를 따른다.

후속 release 준비에서 원본 run/receipt 검증을 먼저 수행한 뒤 질문용 파생 입력에 sidecar를 적용한다.
sidecar의 해시와 질문 계획은 release 근거에 포함되며, 파일 생성만으로 서비스에 노출되지 않는다.
실제 DB 발행은 기존 exact release·승격 보호 경로를 따른다.
이 안내는 live 모델 실행, 새 cohort, 운영 DB 쓰기나 배포 승인을 부여하지 않는다.

## 저장·호환·되돌리기

- migration `0081_confirmation_evaluation_v2.sql`은 기존 질문/답변 원장에 컬럼을 추가한다.
  적용 전 검증·배포 순서는 별도로 관리하며, 신규 앱을 미적용 DB에 연결하지 않는다.
- v2 질문의 legacy criterion anchor는 비워 구 boolean reader가 새 답변을 오독하지 않게 한다.
  구 앱에서는 새 답변을 무시해 미해소로 남기는 안전한 축소 동작이며 기능 동등성은 아니다.
- 현재 회사의 owner/editor만 저장한다. 트랜잭션에서 회사 권한, 원천, 질문 결속과 answer revision을
  재확인하며 오래된 제출은 거부한다. 확인불가는 명시적인 답변으로 저장한다.
- 같은 원천·같은 질문 의미의 재발행은 ID/답변을 보존한다. 원천 또는 질문 의미가 달라지면
  새 질문 버전으로 재확인하며, 무효화된 질문의 답변 이력은 삭제하지 않는다.
- 원천 비교는 최신 분석 job의 시각이 아니라 현재 DB의 공고 필드·raw hash·첨부 결속을 사용한다.
  조회와 저장, 매칭 reader가 같은 계산을 사용한다.
- publication rollback은 기존 질문/조건 결속을 복원하고 새 답변 이력을 보존한다.
  실제 운영 rollback 실행 권한과 이 로컬 검증 결과는 별개다.

## 남은 범위

동일 run의 개정·철회 코드와 독립 검사는 추가됐으며, 최종 검증 상태는 감사 로그를 정본으로 본다.
원본 run 복제·모델 재실행·기존 sidecar 삭제를 우회 경로로 사용하지 않는다.
자동 질문 생성·관리자 편집 GUI는 후속 작업이다. 행동 분류/UI 연결은 이전 단위에서 검증했지만,
검수된 핵심 other/text_only 조건이 질문 annotation 전에 제외되는 준비도 한계는 별도로 남는다.
실제 OAuth/로그인·재접속·회사 전환 화면 인수도 격리 계정·환경 연결 후 별도로 수행해야 한다.

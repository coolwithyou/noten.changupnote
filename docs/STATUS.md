# 창업노트 현재 방향과 순차 개선

기준일: 2026-09-06. 사용자가 이번 세션에서 확정한 제품 방향을 기록한다.

## 제품 방향

창업노트는 사용자가 매칭에 필요한 사업자 정보를 완성하고, 그 정보와 공고의 검증된 조건을
대조해 지원 여부를 판단하며, 실제 지원서 작성을 진행하는 정밀한 소프트웨어다.
사업자번호 조회는 기본정보 입력을 돕는 시작점이다. 조회만으로 모든 조건을 확인했다거나
지원 여부·작성·제출이 자동으로 완료된다고 약속하지 않는다.

- 자동조회값, 사용자 입력, 미확인, 명시적 해당 없음, 출처 충돌을 구분한다.
- 입력 완료와 공고 적격은 다르다. 사용자가 정보를 모두 입력해도 부적격일 수 있다.
- 공고 분석이 부족한 문제를 사용자의 정보 미완성으로 표시하지 않는다.
- 이미 입력한 사실과 공고별 확인 답변은 저장·재접속·재계산 후에도 유지한다.
- 기준일·회사정보·공고조건·확인 답변이 같으면 같은 판정과 이유를 반환한다.
- RHWP 편집, 근거 기반 제안, 사용자 선택 후 적용·저장·Undo 방향을 유지한다.
- 신청서 검토·서명·증빙 확인·최종 제출은 사용자가 수행한다.

제품 진입의 필수정보 범위는 입력 UX 단계에서 명시한다. 22축 전체의 확정을 새로운
진입 차단 조건으로 자동 해석하지 않으며, unknown을 임의의 부정 답변으로 바꾸지 않는다.

## 개선 순서와 완료 기준

| 단계 | 범위 | 완료 증거 | 상태 |
|---|---|---|---|
| 1 | 회사 접근 권한, 기준일, 확인 답변 보존 | 권한 회귀, 매칭 경로 대조, 답변 저장 회귀, 집계 gate | 구현·자동 검증 통과, 운영 미반영 |
| 2 | 사업자 정보 완성 흐름 | 필수정보·미확인 사유·수정·재개 흐름과 실제 화면 검증 | 대기 |
| 3 | 정밀 매칭 결과와 신청서 연결 | 이유 확인 → 추가정보 → 작성 → 저장 → 재개방 → 다운로드 | 대기 |
| 4 | 독립 사례집과 검증 발견 체계 | 실제 오류 유형의 독립 기대값, 오프라인/통합/live 검증 구분 | 대기 |
| 5 | 분석 공급과 기능별 준비도 관측 | 유효 공고의 승격·노출 지연과 작성 기능 준비도를 설명 | 대기 |
| 6 | 실험실과 제품 모듈 분리 | 제품이 실험·승격 내부 절차를 알지 않는 조회·실행 interface | 대기 |

단계별로 구현·자동 검증·브라우저 검증·운영 반영을 따로 기록한다. 분석 확대나 범용
재설계 때문에 사용자 정보 완성부터 실제 문서 결과물까지의 검증을 뒤로 미루지 않는다.

## 단계 1 작업 기록

- 출발 소스: `59c1eda` 및 기존 사용자 미커밋 match-results 4개 파일·next-env.d.ts.
- 기존 미커밋 파일은 이번 단계에서 편집하거나 커밋에 포함하지 않는다.
- 운영 환경에서는 인증 해제·mock·개발 로그인/OAuth/사업자 검증 플래그로 인증을 우회하지 못한다.
  익명 데모는 고정 회사의 읽기만 허용하고, 명시적 로컬 mock만 그 회사의 쓰기를 허용한다.
- 만료된 회사 선택 쿠키는 읽기에서만 소속 회사로 복구한다. 쓰기 요청이나 viewer의 권한
  오류는 다른 회사의 owner 권한으로 대체하지 않는다.
- 대시보드·초기 매칭·티저·상태 갱신·프로필 변경 영향 계산 및 기준일을 받는 시뮬레이션에
  동일한 `asOf`를 전달한다. 과거 수혜기간에 대한 2026년/2030년 회귀로 경로를 대조했다.
- 프로필 답변 저장 전 공고별 확인 답변을 한 번 읽어 변경 전후 판정·응답 카드·상태 갱신에
  함께 사용한다. 확인 답변 조회 실패 시 프로필 저장도 하지 않는다.
- 신규 회귀를 `test:profile-answer-consistency`로 묶어 기본 테스트와 Matching CI에 연결했다.
  Matching CI에는 회사 접근·앱 인증 검증도 포함했다.

## 다음 단계: 사업자 정보 완성

잠정 진입 흐름은 공통 필수정보 완성 → 매칭 → 공고별 추가조건 확인이다. 사업자 정보
전체를 먼저 입력받도록 하는 별도 사용자 결정이 오면 그 결정에 맞춘다.

1. 기존 profile field/question/evidence 계약에서 공통 필수 항목과 공고별 추가 항목을
   구분한다. 새로운 22축 전수 입력 gate를 만들지 않는다.
2. 미입력·모름·해당 없음·조회 충돌을 구분하고, 자동조회값도 사용자가 확인·정정할 수
   있게 한다. 공고 원문 검수 부족은 사용자 입력 완료율에 섞지 않는다.
3. 완료율은 입력 상태로 계산하고 적격률과 분리한다. 저장 후 재접속·수정·재계산에서도
   상태와 판정 근거가 유지되는지 검증한다.
4. 현재 별도 작업 중인 match-results 변경과 소유 범위를 먼저 대조하고 기존 화면을
   연결한다. 브라우저 검증은 사용자가 실행한 개발 서버에서 수행한다.

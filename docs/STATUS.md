## 제품 방향

창업노트는 사용자가 매칭에 필요한 사업자 정보를 완성하고, 그 정보와 공고의 검증된 조건을
대조해 지원 여부를 판단하며, 실제 지원서 작성을 진행하는 정밀한 소프트웨어다.
사업자번호 조회는 기본정보 입력을 돕는 시작점이다. 조회만으로 모든 조건을 확인했다거나
지원 여부·작성·제출이 자동으로 완료된다고 약속하지 않는다.

- 자동조회값, 사용자 입력, 미확인, 명시적 해당 없음, 출처 충돌을 구분한다.
- 입력 완료와 공고 적격은 다르다. 사용자가 정보를 모두 입력해도 부적격일 수 있다.
- 공고 분석이 부족한 문제를 사용자의 정보 미완성으로 표시하지 않는다.
- 이미 입력한 사실과 공고별 확인 답변은 저장·재접속·재계산 후에도 유지한다.
- 기준일·회사정보·공고조건·확인 답변이 같으면 같은 판정과 이유를 반환한다.
- RHWP 편집, 근거 기반 제안, 사용자 선택 후 적용·저장·Undo 방향을 유지한다.
- 신청서 검토·서명·증빙 확인·최종 제출은 사용자가 수행한다.

제품 진입의 필수정보 범위는 입력 UX 단계에서 명시한다. 22축 전체의 확정을 새로운
진입 차단 조건으로 자동 해석하지 않으며, unknown을 임의의 부정 답변으로 바꾸지 않는다.

## 단계 1 작업 기록

- 출발 소스: `59c1eda` 및 기존 사용자 미커밋 match-results 4개 파일·next-env.d.ts.
- 기존 미커밋 파일은 이번 단계에서 편집하거나 커밋에 포함하지 않는다.
- 운영 환경에서는 인증 해제·mock·개발 로그인/OAuth/사업자 검증 플래그로 인증을 우회하지 못한다.
  익명 데모는 고정 회사의 읽기만 허용하고, 명시적 로컬 mock만 그 회사의 쓰기를 허용한다.
- 만료된 회사 선택 쿠키는 읽기에서만 소속 회사로 복구한다. 쓰기 요청이나 viewer의 권한
  오류는 다른 회사의 owner 권한으로 대체하지 않는다.
- 대시보드·초기 매칭·티저·상태 갱신·프로필 변경 영향 계산 및 기준일을 받는 시뮬레이션에
  동일한 `asOf`를 전달한다. 과거 수혜기간에 대한 2026년/2030년 회귀로 경로를 대조했다.

## 단계 2 후속 기록: 저장된 회사 프로필로 재진입

설정의 사업자 정보 수정 링크는 `/matches#profile`인데, 기존 화면은 `biz`가 없으면 빈 화면을
표시했다. 로그인 여부와 무관하게 익명 티저만 조회하므로 저장된 답변을 재사용하지 못했다.

- `/matches?biz=…`는 익명 조회로 유지한다. 로그인만으로 사업자번호 조회에 비공개 정보를
  합치지 않는다. `/matches`는 현재 선택 회사, `/matches?companyId=…`는 명시한 소유 회사를
  `GET /api/web/company-matching` → `owned_read`로 읽는다. 성공 후 URL에 회사 ID를 고정한다.
- 이 조회는 실제 세션(또는 명시적인 로컬 mock 세션)을 요구하며, 세션이 없으면 401이다.
  명시한 회사가 비어 있거나 접근 불가능하면 다른 회사나 데모로 대체하지 않는다.
  응답은 `private, no-store`이며 조회가 프로필·회사 공용 매칭 상태를 쓰지 않는다.
- 저장된 회사의 답변은 기존 `/api/web/profile/field`로 단건 저장한다. 서버가 반환한 동일
  기준일의 매칭·질문·프로필을 함께 반영한다. 익명 임시 답변이나 새 회사 생성으로 후퇴하지 않는다.
  정보 시트는 임시 보관/계정 저장 상태를 구분하며 실패 시 입력폼을 유지한다.
- 프로필 쓰기 및 공고 확인 답변의 GET/PUT에 회사 ID를 명시적으로 결속한다. 다른 탭에서
  선택 쿠키가 바뀌어도 화면의 답변을 그 쿠키 회사에 저장하지 않는다. 기존 호출자의 쿠키 방식은
  호환 유지한다. 쿠키 기반 상세/대시보드로 이동할 때는 해당 회사를 먼저 선택한다.
- 저장 직후와 재조회 비교에서 직접 답변의 `observation.scope` 누락을 발견했다. DB row codec은
  사용자 범위를 보충하지만 runtime 저장소에는 그대로 남아 `owned_read`가 답변을 제외했다.
  저장 명령부터 `user`/`portable_user_answer`를 명시해 저장 어댑터에 따른 차이를 없앴다.
- 저장 회사 매칭에는 공고별 criterion confirmations를 전달한다. 별도 프로필 답변·재접속 후에도
  확인 답변을 잃지 않으며, 확인 저장 후 건수와 다음 질문도 재계산한다. ‘모름’은 유효한 질문
  억제 상태에서 복원하며 입력 완료나 ‘해당 없음’으로 바꾸지 않는다.
- codebase-design/React 스킬에 따라 소유 프로필 snapshot과 클라이언트 통신 경계를 분리했다.
  shadcn 스킬에 따라 기존 화면 컴포넌트를 유지하고 동작·상태 안내만 연결했다.

  것은 아니며 이미 로그인한 상태의 즉시 생성·다른 탭·서버 측 재시도는 별도 검토 대상이다.
- 기존 사용자 변경은 보존했다. 커밋·push·배포·운영 DB 쓰기·모델 실행은 하지 않았다.

## 후속 구현 기록: 회사 문맥·저장 안정성·제품 여정 (2026-09-06)

위의 ‘다음 순서’였던 회사명 표시, 저장 재시도·경합 방지, 랜딩 문구를 구현했다.
전체 계획의 운영 인수까지 완료했다는 뜻은 아니다. 사례와 남은 인수 기준은
[제품 여정 인수 검증](plans/2026-09-06-제품여정-인수검증.md)에 분리했다.

- 회사명과 소유 회사 문맥을 표시하고, 매칭 → 공고 상세 → 작성 → 문서 선택 → 공고 복귀에
  `companyId`를 전달한다. 작성 API 호출에는 같은 출처의 `/api/web/`에만 회사 헤더를 싣고,
  서버는 이를 소속/역할로 검증한다. 외부 저장소 요청에는 헤더를 보내지 않는다.
  명시한 회사와 헤더가 다르거나 값이 잘못되면 선택 쿠키로 후퇴하지 않는다.
- 작성 화면 진입은 초안 ensure·시드 쓰기를 포함하므로 쓰기 권한을 요구한다. 로더에서도
  viewer를 조회/생성 전에 거부한다. 관리자·가상 기업의 비영속 미리보기는 별도 경로를 유지한다.
- 새 회사 저장은 사용자 + 저장 의도 UUID + 정규화 요청 내용으로 서버 생성 ID를 결속한다.
  기존 회사 PK의 충돌 처리와 회사/소속/프로필의 한 트랜잭션으로 같은 요청의 중복 생성을 막는다.
  재시도는 현재 owner 소속을 확인하고 기존 프로필을 덮어쓰지 않는다. 스키마 변경은 없다.
  브라우저는 24시간의 요청 해시/의도 영수증을 보관하며 원문 답변을 그 영수증에 남기지 않는다.
  legacy 헤더 없는 호출, 보관 기간 밖 또는 별도 브라우저에서 시작한 새 의도의 전역 중복
  사업자 제거 기능은 아니다. runtime 어댑터는 여전히 고정 데모 회사이며 DB 유일성 증거가 아니다.
- 소유 프로필 응답에 원시 사실·구간·출처 기반 버전을 반환한다. 오래된 화면의 저장은 409로
  거부하며 편집값은 유지한다. 조회기가 보충하는 추적 ID와 사실값 없는 구간의 파생 observation은
  버전에서 정규화하고, 구간 원문은 보존한다. 반올림 전 수치 변경도 감지한다.
  저장소에서는 회사 행 잠금 뒤 기존 프로필을 비교한 후 전체 교체한다. 매칭·외부 조회는 잠금 밖이다.
- 랜딩에서 조회만으로 수혜/자동 완료를 약속하던 문구와 검증되지 않은 30초·80% 표현을 제거했다.
  기본정보 보완 → 근거 확인 → 제안 선택/직접 검토·제출로 안내한다. 작성 화면도 편집 가능,
  제안 활성화, 계정 저장/미리보기, 최종 제출을 구분한다.
- `test:product-journey`를 기본 `pnpm test`와 Matching CI에 연결했다. 정밀 매칭의 직접 작성한
  기대값, 회사 문맥, 저장 재시도·경합, 작성 준비도, 제품 import seam을 함께 검사한다.
- `report:product-readiness --source=runtime|--source=database`는 기존 저장소 정책을 재사용하는
  읽기 전용 관측이다. 원천 부족과 사용자 정보 부족, 작성 신호와 실제 파일 왕복 성공을 합치지 않는다.
- 작성 근거의 release/snapshot 검증을 `analysis-serving/verifiedDeepSources` 어댑터로 옮겼다.
  분석 버전/상한/identity 함수는 `applicationAnalysisContract`를 정본으로 공유하며 역사 export는
  유지했다. 계약 버전과 identity 알고리즘은 바꾸지 않았다. 기존 실행/승격 코드 전부를 분리한 것은 아니다.

## 이전 후속 목록 — 바로 아래의 전체 완료 요청 기록으로 갱신

1. 테스트 계정/DB 범위를 확정해 회사 저장 → 로그아웃 → 재로그인 → 회사 전환을 검증한다.
   현재 오프라인·합성 응답 검증을 실제 영구 저장의 완료 증거로 취급하지 않는다.
2. 실제 Postgres에서 동일 저장 의도 동시 생성, 서로 다른 탭의 버전 충돌, 세션/소속 변경을
   검증한다. 실제 HWP/HWPX 편집 → 저장 → 재개 → 다운로드 내용 일치도 같은 격리 범위에서 확인한다.
3. 정정 문의 이후 검수 → 원천 갱신 → 재매칭을 설계한다. 서버 보호를 없애 직접 덮어쓰는
   방식으로 해결하지 않는다. 문의 링크만으로 정정 처리 완료를 선언하지 않는다.
4. 승격 시각과 최초 사용자 노출 시각의 결속 관측을 추가한다. 현재 보고서는 해당 지연을
   `unavailable`로 반환하며 성공/실패 또는 0초로 추정하지 않는다.
5. 남은 application 분석·materialization·repository의 실험실 직접 의존을 계속 줄인다.
   현재의 작은 interface 추출을 전체 모듈 분리 완료로 취급하지 않는다.

## 전체 완료 요청 후속: 실제 DB/파일 왕복과 모듈 분리

운영 접속 문자열 대신 새 Unix socket 전용 PostgreSQL cluster에 마이그레이션 80개를 처음부터
적용했다. TCP는 열지 않고 종료 시 서버를 정지한다. `pnpm test:product-postgres`로 재현하며
Matching CI에도 추가했다. 테스트 데이터/로그만 `/tmp/cunote-product-pg-*`에 남긴다.

- 실제 일반 권한 RLS에서 `user_company → team_invitations → user_company` 정책 재귀와
  viewer의 자기 역할 owner 승격을 재현했다. `0078`은 초대 판정을 현재 사용자만 확인하는
  SECURITY DEFINER로 분리하고 자기 역할 변경/owner 변경을 막는 팀 관리 계약을 DB에 적용한다.
- 동일 의도 생성 6개는 회사/소속 각 1건, 같은 버전 수정 2개는 저장 1건·충돌 1건이었다.
  재시도가 최신 답변을 덮지 않고, 타인/뷰어 쓰기/소속 제거 후 재시도가 차단됨을 확인했다.
- 실제 RHWP WASM으로 생성한 HWP/HWPX 합성 양식에서 후보 적용 → DB 저장 → exact revision
  재조회 → 바이트 재개방 → Undo → 재저장을 수행했다. SHA·부모 revision·값·오래된 head 충돌·
  다른 회사 접근을 검증했다. 객체 저장소는 메모리 어댑터이며 실제 OAuth/브라우저 다운로드/
  R2/기관 양식 인수는 아니다. 저장 함수의 viewer 차단도 객체 업로드 전에 보강했다.
- `application-analysis`는 문서 파싱·필드 계획·위치 검증, `analysis-serving`은 순수 승격 증거·
  snapshot·작성 근거를 소유한다. 로컬 파일 읽기와 R2 준비는 실험실의
  `application-precompute-prepare`로 옮겼다. 기존 import 호환, v9/후보 180/receipt 해시는 유지했다.
  이동 함수 179개의 본문 동일성과 공용 graph의 실험실 runtime 의존 0을 검사했다.
  로컬 preview와 역사 artifact 타입은 보존하며 live 실행 재개는 하지 않았다.

## 승격 결속 카드 노출 관측

- 최신 유효 승격 criterion snapshot과 실제 결과가 같을 때만 사용자/회사/승격 item/발급 시각에
  결속된 서명 토큰을 발급한다. GET과 프로필 답변 후 재매칭 모두 연결했다.
- 카드의 뷰포트 진입 50%·500ms 후 신호를 보낸다. 화면 밖·숨긴 탭·접힌 목록의 선계산은
  노출로 기록하지 않는다. 페이지당 observer 하나로 동적 카드도 등록한다.
- `0079`는 승격 item당 최초 서버 수신 한 행만 보관한다. 사용자/회사/입력값을 저장하지 않는다.
  서명·15분 만료·회사/사용자를 확인하고, 중복 수신과 DB UPDATE/DELETE는 최초 시각을 바꾸지 않는다.
  기록 실패는 사용자 여정을 차단하지 않는다.
- 활성화는 migration 후 `CUNOTE_PRODUCT_EXPOSURE_ENABLED=true`와 32자 이상의 기존
  `NEXTAUTH_SECRET` 또는 `AUTH_SECRET`이 필요하다. 서버 DB 쓰기 권한도 확인해야 한다.
  현재 환경 설정은 변경하지 않아 미활성이다. 일반 SQL 접근은 RLS로 닫혀 있다.
- DB 보고서의 지연은 계측 도입 이후 인증된 카드의 최초 **수신**이며 네트워크 지연을 포함한다.
  과거 최초 노출·모든 사용자 노출·가려짐 없는 가시성·실제 열람을 증명하지 않는다.
  미활성/fixture는 `unavailable`, 미관측 지연은 null이다.
